# 00 · 프로젝트 큰 틀 (확정본)

> **이 문서의 지위 — 돌아오는 기준점.**
> 논의가 길어지거나 문맥이 틀어지면 여기로 돌아온다. 새 대화를 열 때 물려주는 세 문서 중 첫 번째다(이 문서 + `00_불변식_카드` + `00_용어_대장`).
> §1~§4가 **확정된 틀**이고, §5가 남은 미결, §6이 작업 순서다. §7은 어떻게 여기 왔는지의 이력(참조용, 읽지 않아도 됨).
> 여기서 확정된 것은 챕터로 상세화되고, 챕터가 안정되면 명세로 분해된다. 현재 정본 관계: **이 문서 > 챕터(서술완료분) > 명세(골격 챕터의 소유 절)**.

## 1. 프로젝트 — 한 문장과 3축

**사내 제조 문서를 넣으면 자동으로 지식 그래프까지 만들어지고, 자연어로 물으면 근거와 함께 답하며, 정보층을 계속 추가해도 코드가 늘지 않는 시스템.**

| 축 | 내용 | 챕터 |
|---|---|---|
| 축1 · 쓰기 | 문서 → 그래프 (정형/비정형 상이) | CH2(계약·등록) · CH3(인입) |
| 축2 · 층 | 새 정보층의 생성과 기존 층과의 연결 | CH4 |
| 축3 · 읽기 | RAG 질의 | CH5 |

## 2. 두 모드 — 이 시스템의 1급 프레임

```
문서 도착 → doc_type/층 등록 여부 조회 (결정적, LLM 아님)
   ├─ 등록됨   → [운영 모드] 파싱 → (추출) → 구축 → 그래프     ※ 사람 개입 없음
   └─ 미등록   → [구축 모드] 처리 방식을 먼저 만든다 → 검수 → 등록 → 이후 운영 모드
```

**구축 모드의 산출물**

| 산출물 | 소유 | 내용 | 생성 |
|---|---|---|---|
| 어댑터 코드 | 파서(사내) | 정형: 어느 행/열을 어떻게 읽는가 · 비정형: **청크 분할 규칙** + 이미지 요약 훅 | LLM 생성 → 사람 검수 |
| 매칭 스키마 | 에이전트 | 필드 → role + edges 번역표. **동시에 메타데이터 스키마(필드 선언)를 겸한다** (§4-Q5) | LLM 생성 → 사람 검수 |
| config | 에이전트 | 층 신설 시만 — 카테고리·정의문·**관계 목록**·골격 | LLM 초안 → 사람 확정 |

**검수의 수준 (오해 방지 — v2.1 명확화)**
- **검수는 구축 모드(등록, 양식당 1회)에만 있다. 운영 모드에는 검수가 없다** — 등록이 끝난 타입의 문서는 사람 없이 흐른다. 이 문장은 flow의 관문이 아니라 등록 때 1회 내는 통행료다.
- 사람이 보는 것은 코드가 아니라 **결과 뷰**다: 표본 문서를 어댑터로 파싱한 결과(계층은 트리 렌더), 필드→role 배정표, (층이면) 카테고리 정의문·관계 목록. 시스템이 이 뷰를 자동으로 만들어 제시한다.
- **통과 = 승인 1회(클릭 수준, 분 단위 작업).** 문제 없으면 그대로 승인하고 끝. 문제 있으면 그 자리에서 수정 지시(재생성) 후 재확인.
- "무수정 = 자동 통과"로는 하지 않는다. 등록 산출물은 이후 그 타입의 **모든** 문서에 곱해지는 지렛대라서, 명시적 승인 기록 1건이 "운영은 무개입"의 근거가 된다. 무게는 클릭 수준으로, 기록은 명시적으로.

## 3. LLM 역할 — 전역 지도 [확정]

**원리 두 개.** 사람=구조의 확정 / 코드=커밋·게이트·순서 / LLM=식별과 초안 제안. 그리고 **설계는 과감하게(1회+검수), 운영은 보수적으로(무검수+안전망).**

| 단계 | 설계·등록 시점 (구축 모드) | 운영 시점 (운영 모드) |
|---|---|---|
| 파서 | **어댑터 코드 생성** (정형: head ~10줄 관찰 / 비정형: 문서 구조 관찰 후 분할 규칙 생성) | 생성된 규칙의 결정적 실행 + 이미지 요약 + 좌표 태깅(닫힌 목록 선택) + **구조 지도 패스(구조 가변 prose 한정 — §4-Q2 개정)** |
| 등록 | **매칭 스키마 + (층이면) config 초안** — 확정은 사람 | — (조회만) |
| 추출 | 프롬프트·정의문은 사람이 확정 | **내용 파악** — 개체 후보(닫힌 카테고리) + 관계 후보(닫힌 관계 목록) + 부착 이름 |
| 구축 | — | **개체 판정**(같은 개념인가)만. 게이트·엣지 생성·커밋·순서는 전부 코드 |
| 구조 개정 | — | 골격 빈틈 **감지·제안** — 반영은 사람 파일 경유 |
| 질의 | 프롬프트는 사람 | 답변 생성 1지점 — 그래프를 직접 읽지 않음 |

**발명 금지 3종 (시점 무관)**: ①관계 타입 ②카테고리 ③골격. 운영 중에는 선택만, 설계 시점에는 초안 제안까지이며 확정은 사람.

**관계에 대한 최종 입장**
- 운영 중 새 관계 생성은 **하지 않는다**. 조건부 신규 출력("정말 필요하면") 같은 예외도 두지 않는다 — 조건 판정이 신뢰되지 않는다.
- 대신 **관계 목록을 구축 모드에서 충실히 만드는 데 힘을 싣는다.** 층 config를 만들 때 LLM이 문서를 충분히 검토해 필요한 관계를 다 뽑고, 사람이 확정한다.
- 운영 중 게이트에서 거부가 잦다면 그것은 "새 관계가 필요하다"가 아니라 **"관계 목록이 부실하다"는 신호**이며, 대응은 운영 중 생성이 아니라 **config 개정(구축 모드 재진입)**이다.
- 게이트는 유지한다: 모든 관계 후보는 `(출발 카테고리, 관계, 도착 카테고리)` 패턴 대조를 통과해야 커밋된다. 방향 반대는 자동으로 뒤집지 않고 큐. 거부는 사유와 함께 기록(커버리지 신호).

**LLM이 아닌 것 (착각 주의)**: 모드 판별, 게이트 대조, 정형의 관계 생성, mirrors, 재인입 회수, 2-pass 순서 — 전부 코드의 결정적 연산이다.

## 4. 이번에 확정된 세부 (Q1~Q5)

### Q1. 추출은 독립 단계다 [확정]

파싱과 구축 사이에 **독립된 추출 단계**를 둔다. 파서 안도 아니고 구축 파이프라인 안도 아니다.

```
[파싱] → 계약 JSON(청크) → [추출] → 후보 JSON → [구축] → 그래프
          ↑ 파서 소관              ↑ 체크포인트        ↑ 에이전트 소관
```

근거: ①추출은 비싸고 구축은 싸다 — 재빌드 때 추출을 다시 돌리지 않으려면 산출물이 독립 체크포인트여야 한다 ②파서는 형태만 다룬다는 원칙이 지켜진다 ③**플랫폼 관점에서 자연스럽다** — 화면에서 "파싱 완료 → 추출 중 → 구축 대기"가 각각 상태를 갖는 단계로 보인다.

### Q2. 청크 분할 — 규칙은 구축 모드에서 만들고, 운영 중에는 실행만 한다 [확정 · v2.8 개정: 구조 가변 prose는 예외]

정확한 구조는 어댑터 생성과 완전히 같다:

```
[구축 모드] LLM이 문서 구조를 관찰 → 분할 규칙을 코드로 생성 → 사람이 검수 → 고정
[운영 모드] 고정된 규칙이 결정적으로 분할 (매 문서마다 LLM이 판단하지 않는다)
```

즉 "문단이나 끊어야 할 위치에서 끊는다"는 판단은 LLM이 하되, **문서마다 1회(등록 때)** 하고 그 결과를 코드로 굳힌다. 운영 중 매 문서마다 LLM에게 물으면 같은 양식인데 결과가 흔들린다.

**범위** — 청크 분할은 **비정형 경로에만** 있다. 정형(표준양식 엑셀)은 행=record가 처리 단위라 분할 문제 자체가 없다(content 필드가 필드별 청크가 될 뿐). "줄글·목차형 엑셀"은 비정형으로 취급한다.

**판정 방식 — 신호를 코드로 열거하는 것이 아니라, LLM이 표본을 보고 판단한다.** 아래 신호 목록은 우리가 규칙으로 하드코딩하는 것이 아니라 **구축 모드에서 LLM에게 주는 관찰 체크리스트**다.

| 타입 | 분할 단위 | LLM이 관찰할 신호 |
|---|---|---|
| PPT | 슬라이드 1장 | (구조가 명시적 — 관찰 거의 불요) |
| Word | 절/섹션 | 스타일 헤딩 레벨 |
| PDF | 제목·절 경계 | 제목 서식·여백 패턴 |
| **Excel(줄글·목차형)** | **계층 블록** | 들여쓰기 값 · 열 위치 · 번호 패턴(`1.`/`1.1`/`가.`/`①`) · 서식(굵게·배경색·크기) · 셀 병합 · 빈 셀 패턴 |

- **표본 크기**: 기본 head 10~30줄. 목차형은 같은 패턴이 반복되므로 **계층 패턴이 2~3회 반복해 나타날 때까지** 확장한다.
- **판단이 안 서면** LLM이 추측으로 규칙을 만들지 않고 **"판정 불가"로 검수 화면에 올린다.** 사람이 그 자리에서 기준을 정해준다.
- 그래도 운영 중 어긋나는 경우가 남으므로, 세 겹으로 받는다.

1. **검수를 눈으로 보게 만든다.** 어댑터 검수 시 파싱 결과를 계층 트리(텍스트 들여쓰기)로 렌더해서 보여준다.
2. **운영 중 실패는 큐로.** 규칙에 안 맞는 행은 계층 미확정으로 표시하고 큐에 넣는다. 조용히 틀린 계층으로 넣지 않는다.
3. **폴백이 있다 — 문서의 계층을 완벽히 복원할 필요가 없다.** 그래프의 계층은 **골격(Tier1)이 이미 갖고 있다.** 계층 판정이 어려우면 평면으로 읽고 좌표만 태깅해도 그래프는 성립한다. **문서 계층 ≠ 그래프 계층.**

> **[개정 — 2026-08-18, 사용자 발의 · 판정문: `안건/D31_판정문안_section지위.md` 제2부]**
>
> 위 "규칙 고정" 구조가 성립하는 것은 **구조가 안정적인 계열**(table 전체 · 분할 자명 prose[PPT 등])이다. **구조 가변 prose** — 같은 doc_type 안에서 판본·작성자별로 구조(heading pattern·목차)가 다르게 관찰되는 계열(목차형·보고형 엑셀, RFQ류) — 는 분할 규칙을 등록 상수로 고정하지 않고, **운영 인입마다 구조 지도 패스**를 거친다:
>
> ```
> reader 원시 추출
>   → 구조 지도 패스 (LLM · 공용 코어 소유 — 어댑터 아님, 이미지 요약과 동형 배선)
>       입력: 원시 추출물 + 등록 시점 관찰 기록(프라이어 — 강제 아님)
>       출력: 구조 지도 = 데이터 {행/단락 → 헤딩 여부·레벨·제목}
>   → 지도 타당성 검사 (결정적 코드) — 실패 시 평면 폴백(위 3겹의 ③) + 기존 큐(hierarchy_unresolved·parse_failure, 신설 없음)
>   → 결정적 분할기 (지도 적용 → 청크·section 산출. 공용 코어, doc_type 무관)
> ```
>
> - **어댑터는 매 문서 다시 만들어지지 않는다.** 어댑터는 여전히 doc_type당 1개·등록 1회이며, **"문서의 형태(heading 구조)를 LLM이 파악하는 기능"을 어댑터가 선언하고 힌트(등록 시점 관찰 기록)를 제공**한다. 실제 LLM 호출은 공용 코어가 소유한다(C12 이미지 요약과 동형 — 어댑터 순수 함수 C11 유지). 매 문서 새로 나오는 것은 어댑터(코드)가 아니라 **지도(데이터)**뿐이다.
> - **LLM이 청크를 직접 나누지 않는다는 원칙은 불변이다** — 지도(데이터)를 내고, 나누는 것은 결정적 코드다. 지도는 파스 산출물과 함께 보존된다(같은 지도 → 같은 분할 → 같은 chunk_id, "왜 이렇게 잘렸나"의 기록).
> - **내용 파악은 여전히 추출 단계(파싱 뒤)다** — 지도 패스가 읽는 것은 형태(어디가 헤딩인가)이지 의미가 아니다. 파싱과 추출의 분리(Q1 체크포인트)는 불변이다.
> - **근거 문장 "같은 양식인데 결과가 흔들린다"는 table에 한해 참이다.** 비정형은 같은 doc_type이어도 양식이 고정되지 않는 것이 기본값이다 — 실측: 사용자 발의(RFQ 판본별 heading pattern 상이) · 파서_명세 ⑴-C″("비정형은 구조 신호의 변별력이 없어 지정 필수" — 명세 스스로 prose 구조가 doc_type의 지문이 될 수 없다고 인정) · 실행검증 표본 2부(TOC01/02의 목차 상이).
> - 비용의 급은 바뀌지 않는다 — prose 인입은 이미 문서마다 LLM을 쓴다(추출 n3 · 이미지 요약).
> - **불변 목록**: 검수 1회(등록 시 층 선언·표본 검수 — M9) · 운영 무인(사람 개입 0 — 늘어나는 것은 LLM 호출 1종) · 어댑터 순수성(C11 — 구조 패스는 코어 소유) · 위 안전망 3겹 · table과 분할 자명 계열의 규칙 고정.

### Q3. 비정형 메타데이터 — 양식은 전 층 하나, 층별로 다른 것은 어휘 [확정]

- **양식(구조)은 전 층 하나다.** 봉투 + 조각 공통 + 청크 payload(text·section·meta) — 층이 늘어도 형태는 같다.
- **층별로 다른 것은 추출 LLM에게 주입되는 어휘다** — 카테고리 목록·정의문·관계 목록. 이것들은 층 config가 소유한다.
- "여기서 나온 정보가 어떤 것을 의미하는지를 항목으로 정리해놔야 한다"가 바로 **카테고리 정의문**이고, 그것이 층 config에 있다.

정리하면: **한 양식 + 층별 어휘 주입.** 새 층이 생겨도 파서와 계약은 바뀌지 않고 config만 는다.

### Q4. 층간 연결 — A안(연결 노드) 확정 + 허브 폭증 대응 [확정]

**A안 채택**: 공정 골격은 공정층에 1벌만 두고, 다른 층의 노드가 cross 엣지로 가리킨다. (B안=각 층에 골격 복제는 "같은 개념=한 노드"를 깨고 골격 개정이 N배가 되므로 채택하지 않는다.)

**① 이미 있는 방어**
- cross 브리지는 **1홉·비재귀** — 허브를 지나 다른 층으로 번지지 않는다
- 수집 상한 8 + 2-tier(직접 > 확장) — 확장분은 뒤로 밀리고 잘린다
- 브리지는 config로 켜고 끈다 — 층별로 조절 가능

**② 대량 인스턴스 층은 허브에 직접 매달지 않는다 [규칙]**
불량이력층 같은 사건 스트림은 사건 하나하나가 공정에 붙으면 안 된다. 두 방법 중 하나로 한 단계 경유시킨다.
- 사건 → **집계/기간 노드**("2026-07 노칭 불량 이력") → 공정
- 또는 사건 → **Failure**(품질층, 이미 공정에 연결됨) → 공정 (2홉)

즉 **허브에 직접 붙는 것은 유형(type) 수준의 노드만이고, 개체(instance) 수준은 유형을 경유한다.**

**③ 넓은 질의는 층별로 나눠 답한다**
"노칭 관련 전부"는 사실 답이 정해지지 않은 질문이다. 층별로 무엇이 있는지 요약해 제시하고 사용자가 좁히게 한다. **허브 노드 차수를 계기판에 추가**해 폭증을 조기에 본다.

### Q5. 메타데이터 스키마의 물리 형태 — 매칭 스키마가 겸한다 [확정]

**답: 어댑터에만 두면 안 되지만, 세 번째 파일도 만들지 않는다. 매칭 스키마가 그 역할을 겸한다.**

어댑터에만 두면 안 되는 이유 셋:
1. **어댑터는 사내(파서)에 있고 매칭 스키마는 외부(에이전트)에 있다.** 둘은 코드로 만나지 않고 JSON으로만 만난다 — 필드 목록이 어댑터 코드 안에만 있으면 에이전트 쪽에서 그것을 알 수 없다.
2. **검증할 근거가 없어진다.** 파서 출력이 계약을 지켰는지 보려면 "무엇이 나와야 하는가"의 선언이 필요하다.
3. 어댑터는 자주 손보고 계약은 안정적이어야 하는데, 한 파일에 있으면 튜닝할 때마다 계약을 건드리게 된다.

세 번째 파일도 안 만드는 이유: **같은 필드 목록이 두 파일에 살면 반드시 어긋난다.**

```
어댑터 코드 (파서)        : 어떻게 뽑는가          — 자주 손봄
매칭 스키마 (공유 계약)    : 무엇이 나와야 하고     — 안정적
                            그것이 무슨 role인가
        └─ 둘은 "필드명"으로 만난다 (얇은 약속)
```

등록 세션에서 둘이 함께 생성되므로 초기 정합은 보장되고, 이후 어댑터를 고칠 때 매칭 스키마의 `fields`와 대조 검증한다.

### 해석 확인 2건 [확정]

1. **관계 출력** — 닫힌 목록에서 선택·출력하는 것으로 확정. 조건부 신규 생성은 두지 않음(§3).
2. **meta data schema의 뜻** — "문서 타입별 출력 JSON의 양식. 파싱을 통해 문서 내용을 넘기기 위한 메타데이터의 형식." 그리고 그 메타데이터를 role과 이어주는 것이 matching schema. 확정.

### A1. 벡터 검색 대비 — 되돌릴 수 없는 것만 지금 고정

**원칙**: 리트리버 설계·융합 방식·임베딩 모델·랭킹은 지금 정하지 않는다(P7). **그래프 구축 시점에 결정되어 버려서 나중에 바꾸려면 전량 재적재가 필요한 것만** 고정한다.

**되돌릴 수 없는 것 = 지금 고정 (4건)**

| # | 규칙 | 안 지키면 나중에 |
|---|---|---|
| A1-1 | **청크 id는 재적재·순서·병렬에 무관하게 동일해야 한다** (→ A4의 결정적 id) | 재적재마다 벡터 인덱스 전체 무효 |
| A1-2 | **전 청크를 보존한다.** 링킹 0건 청크도 버리지 않는다: 인덱싱할 원본이 없으면 하이브리드를 켤 수 없다 | 인덱싱 대상 자체가 존재하지 않음 |
| A1-3 | **원문을 그대로 보존한다.** 정규화·요약본은 별도 필드로 두고 원문을 덮지 않는다 | 다른 임베딩 모델이 원문을 볼 수 없음 |
| A1-4 | **어댑터 버전을 기록한다.** 분할 규칙이 바뀌어도 기존 문서를 다시 파싱하지 않으므로, 어느 규칙으로 잘린 청크인지 추적할 수 있어야 한다 (계약상 위치는 A7-3) | 옛 경계와 새 경계를 구분할 수 없음 |

**지금 정하지 않는 것 (미결)**: 무엇을 임베딩할 것인가(청크 / 노드 canonical+정의문 / 경로 직렬화), 임베딩 모델, 리트리버 구성, 융합 방식, 랭킹. — **현재 저장 구조가 이 셋을 모두 지원하므로 지금 고를 필요가 없다.**

**분할 규칙 변경 시의 처리 (재파싱 없음 — 확정)**
> 어댑터의 분할 규칙을 개정하면 **그 이후 인입되는 문서에만 새 규칙이 적용된다. 기존 문서를 다시 파싱하지 않는다.** 같은 doc_type 안에서 문서마다 청크 경계가 달라지지만 문제가 되지 않는다 — **청크는 서로 독립적인 검색 단위이고, 일관성이 필요한 것은 그래프 구조이지 청크 크기가 아니다.**
> 특정 문서가 잘못 파싱된 것이 확인되면 **그 문서만 doc_id 단위로 재인입**한다. 이때 옛 청크와 그로부터 생긴 노드·엣지의 처리는 재인입의 기존 메커니즘이 담당한다.

**삽입 문안 (§5.6.6 확장)**
> 임베딩 인덱스는 진실(그래프 JSON + 청크)에서 언제든 재생성 가능한 파생물이다(P5). 따라서 임베딩 모델·리트리버·융합 방식은 되돌릴 수 있는 결정이며 측정 후 정한다(P7). 다만 **인덱스의 기본키가 되는 청크 id의 안정성**(§8-R3), **전 청크 보존**, **원문 무손실 보존**은 구축 시점에 결정되어 사후 복구가 불가능하므로 지금 고정한다. 분할 규칙 변경은 이후 문서에만 적용하며 기존 문서를 재파싱하지 않는다.

### A2. 인스턴스 변경 — 4연산과 폐기 규칙 (L5 공백 채움)

**진단**: 생성 시점의 동일성 판정 규칙은 있다. 없는 것은 **사후 연산** — 이미 만들어진 노드를 합치고·나누고·개명하고·폐기하는 규칙이다. 변경 등급표 L1~L4는 스키마 축만 다루므로 **직교 축(I축)**을 신설한다.

**삽입 문안 (§9 확장 + §6.3 직교 축 신설)**

> **인스턴스 변경 등급 (I축 — 스키마 축 L1~L4와 직교)**
>
> | 등급 | 연산 | 규칙 | 자동화 |
> |---|---|---|---|
> | **I1** | **개명(rename)** | canonical을 바꾼다. **id는 불변**(P4). **옛 canonical은 자동으로 alias로 강등한다**. 스코프 카테고리는 부모 개명 시 자식 canonical이 **연쇄 변경**되며, 실행 전 파급 미리보기 대상이다. 골격·config 대상이면 파일도 함께 고친다(§9.1) | 도구 실행, 파급 자동 |
> | **I2** | **병합(merge)** | 두 노드가 같은 의미로 판명될 때. **id 생존자 = 작은 id**(먼저 생성된 것). **선택 기준이 단 하나인 이유는 정확성이 아니라 결정성이다** — 어느 쪽을 죽여도 툼스톤이 리다이렉트하므로 참조는 살아나고 내용은 전부 합쳐지므로, 필요한 것은 "처리 순서·병렬과 무관하게 항상 같은 답이 나오는 기준"이다. 사람이 생존 id를 지정할 수 있다(override). 결과 노드의 status는 둘 중 높은 쪽. **canonical 선택은 id 선택과 분리한다**.<br>**정보 손실은 없다**: 흡수 노드의 **provenance가 전부 생존자로 이관**된다. 엣지는 생존자로 이설(중복은 provenance 합집합), attribute는 context 그룹별로 합치되 같은 그룹에 다른 값이면 `spec_conflict` 큐.<br>**흡수된 id에는 `{status: merged_into, target, at}` 툼스톤만 남긴다** — 용도는 **옛 id로 들어온 참조를 새 id로 안내하는 것** 하나다. 질의는 `merged_into`를 **전이적으로** 따라간다 | 도구 실행, 사람 지시 |
> | **I3** | **분리(split)** | 한 노드가 실은 둘일 때. **자동 불가** — 어느 alias·provenance·엣지가 어느 쪽인지 사람이 지정해야 한다. **판정 3분기의 "불확실 → 신규 생성"이 분리를 예방하는 장치다** | 사람 지정 필수 |
> | **I4** | **폐기(obsolete)** | **삭제하지 않는다.** `status: obsolete` + `replaced_by: <id> \| null` + 사유 + 시점을 기록한다. 질의는 obsolete 노드를 기본 제외하되 `replaced_by`가 있으면 **전이적으로** 따라간다 | 사람 판정 |
>
> **재인입은 노드를 제거하지 않는다 — 제거는 별도 기능(I4)이다.** 재인입은 그 문서 몫의 provenance를 회수하고, 근거가 0이 된 노드를 `evidence_lost`로 **표시만** 한다. **시스템이 자동으로 기존 문서를 다시 읽는 경로는 없다.**
>
> **evidence_lost와 obsolete의 구분**: `evidence_lost`는 근거 0의 **자동 감지·검토 대기**, `obsolete`는 사람의 **종결 판정**. **근거가 사라졌다는 것이 곧 지식이 틀렸다는 뜻은 아니므로 자동 폐기하지 않는다.**
>
> **병합 시 canonical 선택 (I2 부속)**: 후보 = 두 노드의 canonical + 모든 alias 전부. 각 후보에 **출현 빈도**와 **출처 등급**을 함께 표시하고, **LLM이 1개 추천 → 사람이 확정**. 빈도를 자동 규칙으로 쓰지 않는 이유는 복사·붙여넣기로 **오타가 반복 등장**할 수 있어서다. 선택되지 않은 표기는 전부 alias로 남으므로 **정보 손실이 없다.**
>
> **체인 순환 방어 (I2·I4 공통)**: **쓰기 시점** — 도구가 연산 실행 전에 대상이 이미 체인상에 있는지 검사하고 순환이면 **거부**한다. **읽기 시점** — 추적에 방문 집합과 최대 깊이 제한을 두고, 한계 초과 시 **결함으로 로그**한다.
>
> **모든 I축 연산은 실행 전 파급 미리보기를 제시하고, 실행 후 연산 로그를 남긴다**(행위자·시점·대상·사유).

**미결**: 병합 생존자 선택의 3순위 필요성 / 분리 지정의 UI 형태 / obsolete 노드의 질의 노출 정책.

### A3. 동종 카테고리 쌍의 방향 — 일반 규칙

> 관계에는 **방향**이 있고, 방향은 어딘가에서 와야 한다. 이종 카테고리 쌍은 카테고리 조합 자체가 방향을 함의하므로 `category_pair_map`이 방향을 준다. **동종 카테고리 쌍은 두 방향이 같은 키로 붕괴하므로 매핑이 방향을 줄 수 없다.**
>
> 따라서 **방향성 있는 동종 쌍 관계는 방향 출처가 명시된 경로에서만 커밋된다.**
>
> | 경로 | 방향 출처 | 동종 쌍 커밋 |
> |---|---|---|
> | ① seed | 사람이 방향 포함해 심음 | 가능 |
> | ② edges 선언(정형) | 필드 구분이 방향을 줌 | **가능** |
> | ③ 추출 후보(비정형) | 출처는 있으나 **게이트가 검증할 수 없음** | **커밋 안 함 — 큐 보존** |
> | ④ 자동 규칙 | 코드가 결정 | 대칭 관계만 해당 |
>
> **대칭 관계는 예외다.** `mirrors`처럼 방향이 무의미한 동종 쌍 관계는 이 제약을 받지 않는다. 관계 목록 선언 시 각 관계의 대칭 여부를 표시한다.
>
> **③의 처리 — 버리지 않는다**: `direction_unverifiable` 큐에 후보 그대로 보존한다. 자동 커밋하지 않는 이유는 **인과 그래프에서 방향 반전이 "틀린 사실을 확신 있게 기록하는 것"**이기 때문이다.
>
> **재인입 시 처리 — 회수 후 재생성**: 근거 문서가 개정되면 그 문서에서 나온 미확인 후보는 **회수하고, 재추출되면 새로 등록**한다. **이 처리는 문서에서 유래한 모든 후보성 큐 항목의 일반 규칙이다**(사람의 판단이 기록된 항목은 보존한다).
>
> **조건부 개방**: 골든셋으로 정확도가 측정되고 허용 수준이면 자동 커밋으로 승격할 수 있다(P7).

**품질층 적용 (§15.4 처리)**
> §15.4의 `[사내 항목]`을 위 일반 규칙의 참조로 교체한다. **§15.8·§13의 해당 확인 항목은 삭제한다** — 우리 자료구조의 성질이므로 사내 확인 항목이 아니다.
> **귀결**: PFMEA(정형)가 만드는 Failure→Failure `causes` 연쇄는 살아 있다(경로 ②). 산문 경로에서만 큐로 간다.

**Failure 병합(고장모드+고장원인)은 유지한다 — 쪼개지 않는다**
> 쪼개면 같은 현상이 문서의 행 위치에 따라 두 노드가 되어 `causes` 연쇄가 끊긴다(P4 위반). **원인이냐 모드냐는 노드의 속성이 아니라 엣지에서의 위치다.**

### A4. 근거 축의 결정적 id

**축 분리**: id 규칙을 두 축으로 나눈다.

| 축 | 대상 | id 방식 | 근거 |
|---|---|---|---|
| **근거 축** | 문서·청크·레코드 | **내용에서 계산(해시)** | 개명되지 않고 동의어가 없다. 정체성이 곧 내용이다. 계산하면 재적재·순서·병렬·재시작에 무관하게 같은 그래프가 나온다(멱등) |
| **의미 축** | Unit·Property·Process·Failure 등 | **발급 유지 — 발급 방식은 ULID (A8-4로 개정, 구 전역 시퀀스 N####)** | 개명이 일어나고 alias로 정체성이 사후에 넓어진다. 해시로 하면 개명이 곧 id 변경이 되어 엣지가 끊어진다(P4 위반) — **"발급한다"는 원칙은 불변이고, A8-4가 바꾼 것은 발급의 방식뿐이다** |

**삽입 문안 (§8-R3 확장)**

> **근거 축 id 산식**
> ```
> doc_id    = 파서 봉투가 부여하는 문서 식별자 (해시 아님)
>             ※ 재인입 단위이므로 개정판이 같은 doc_id를 가져야 한다.
>               개정 구분은 revision 필드가 담당한다.
> chunk_id  = f"{doc_id}:{sha256(norm(text) + '\x00' + section + '\x00' + str(occ))[:12]}"
> record_id = f"{doc_id}:{sha256(norm(join(field_values,'\x1f')) + '\x00' + str(occ))[:12]}"
>
>   occ = 그 문서 안에서 동일한 (section, norm(text)) 조합이 몇 번째로 나왔는지 (0부터).
> ```
> - `norm()`은 **연속 공백 정리와 앞뒤 공백 제거까지만** 한다. **원문은 정규화하지 않고 그대로 저장한다**(A1-3) — 정규화는 해시 계산에만 쓴다.
> - 구분자(`\x00`, `\x1f`)를 반드시 넣는다.
> - **출현 순번(occ)이 충돌 접미를 대체한다.** 접미 방식(`#2`)은 "어느 것이 두 번째인가"를 **처리 순서**가 정하므로, 순서가 바뀌거나 병렬 처리되면 id가 서로 뒤바뀐다. occ는 **같은 텍스트의 반복 횟수만 세므로 처리 순서와 무관**하다.
> - **문서 내 위치(seq)는 해시 입력에 넣지 않는다.** 앞에 한 문단만 추가되어도 뒤의 모든 id가 바뀌기 때문이다.
> - **해시 절단 12자**는 한 문서 안의 유일성 확보용이다. 계산된 id가 이미 존재하면 **조용히 덮어쓰지 않고 결함으로 로그**한다.
> - **doc_id는 파서 계약이다**(§12) — 파서가 같은 문서에 항상 같은 doc_id를 부여해야 재인입이 성립한다.
> - **계산 주체는 에이전트다** — A7-1 참조.

**효과**: 같은 문서를 다시 넣으면 청크·레코드 노드가 같은 id로 재계산되어 중복이 발생하지 않는다. 이것이 재인입 멱등성 검증의 근거 축 절반이고, 나머지 절반(의미 축)은 사전 보존이 담당한다.

**미결**: 문서 노드를 그래프에 실체화할지 여부(현재는 provenance 문자열로만 참조).

### A5. 자동 생성의 방향 — 하향만 [명문화]

> **자동 생성된 노드는 기존 노드의 하위 또는 동급으로만 붙는다. 기존 노드의 상위에 새 노드가 자동으로 삽입되는 일은 없다.** 계층 상단의 변경은 골격 개정이며 사람이 파일(seed·config)로 수행한다(§9.1).
> 예: 문서에 "노칭은 전극가공 대공정에 속한다"고 되어 있는데 골격에 `전극가공`이 없으면, 그것을 노칭의 상위로 자동 생성하지 않고 `orphan_anchor` 큐 → 구조 개정 제안(`structural_proposal`)으로 넘긴다.

**부착이 나중에 바뀌는 경우 — 세 층으로 이미 처리된다**

| 변화 | 처리 | 자동화 |
|---|---|---|
| 새 개체가 기존 골격 아래 붙는다 | 일상 경로 | 자동 |
| **부착 대상이 바뀐다** | 재부착 3분류 — 같은 출처 정밀화는 자동 갈아끼움, **다른 문서끼리 충돌하면 `attach_conflict` 큐**, 사람 정정은 툼스톤 | 조건부 |
| **계층 구조 자체가 바뀐다** | `structural_proposal` → 사람이 파일로 반영 | 제안만 |

**그래프가 조용히 재편되는 경로는 없다.**

### A6. 중복 문서 차단 — 인입 진입 검증

**문제**: 같은 내용의 파일이 **다른 이름으로** 올라오면 doc_id가 다르므로 청크 id도 달라지고, **같은 내용의 청크가 두 벌 생긴다.** 의미 노드는 판정이 매칭시켜 하나로 유지되므로 그래프 구조는 오염되지 않지만, 검색 결과에 같은 내용이 중복으로 뜬다.

| 경우 | 처리 | 결과 |
|---|---|---|
| **같은 doc_id로 다시 인입** | 재인입 (정상 경로) | 중복 없음 |
| **다른 doc_id로 같은 내용 인입** | **아래 진입 검증이 막는다** | 사람 확인 전까지 인입 보류 |

**삽입 문안 (인입 진입점 — 계산 주체는 A7-2)**
> 인입 시 문서 전체 내용의 해시(`doc_hash`)를 계산해 기존 문서와 대조한다. **같은 `doc_hash`가 다른 `doc_id`로 이미 존재하면 인입을 보류하고 사람에게 확인을 요청한다** — 이때 두 문서의 파일명·크기·인입 시점·기존 doc_id를 함께 제시한다.
> **파일명·파일 크기를 판정 기준으로 쓰지 않는다** — 이 둘은 사람이 판단할 때 참고하도록 화면에 표시만 한다. 판정은 내용 해시로 한다.
> `doc_hash`는 청크 해시를 계산하는 과정에서 함께 얻을 수 있으므로 추가 비용이 없다.

**미결**: 부분 중복(개정판인데 doc_id를 새로 부여한 경우)의 탐지. 청크 해시 겹침 비율로 가능하나 임계값 근거가 없어 지금 정하지 않는다.

### A7. 근거 축 계산의 소유와 파서 계약 귀결 [세션 1 확정 — 2026-07-27]

A1·A4·A6은 "무엇을 계산하는가"까지만 정했고 **"누가 계산하는가"를 남겨두었다.** CH2 검토에서 이것이 현행 파서 계약(§12: `chunk_id`를 파서가 부여)과 정면 충돌함이 드러나 확정한다.

**A7-1. 근거 축 id의 계산 주체는 에이전트다.**
> 파서가 내는 것은 `doc_id`(A4)와 `source_locator`(그 조각이 원본 문서 어디서 왔는지의 위치 표기 — 예 `"Sheet1!R12"`, `"슬라이드 5"`. role=meta, 형식은 파서 자유이며 요구는 "문서 안에서 유일할 것" 하나)뿐이다. **정본 `chunk_id`·`record_id`는 에이전트가 인입 시점에 A4 산식으로 계산한다.**
>
> 근거 셋: ①멱등성의 근거를 사내 파서 구현에 위임하지 않는다 — 파서 버전마다 산식이 갈리면 "두 번 넣으면 그래프가 같다"가 깨진다 ②산식은 재인입·저장 규칙에 종속되므로 소유가 에이전트여야 한다(P1의 정신: 계약은 데이터, 산식은 로직) ③파서 계약이 산식 개정의 영향을 받지 않는다.
>
> **파서 계약 귀결 — 필드 개명**: 현행 조각 공통의 `chunk_id`를 **`source_locator`로 개명**한다. 같은 이름을 두 뜻(파서 로컬 위치 / 에이전트 계산 정체성)으로 쓰면 정의서 §3.4의 `{record chunk_id}-{필드명}` 규칙부터 모호해지기 때문이다. 그 규칙도 `{record_id}-{필드명}`으로 정정한다. 파서가 아직 구현 전(국면 2-3)이므로 개명 비용은 0이다.

**A7-2. `doc_hash`의 계산 주체도 에이전트다.**
> A6의 진입 검증은 에이전트의 인입 진입점에서 수행한다. 청크 해시(A7-1)를 계산하는 과정의 부산물이므로 추가 비용이 없고, 파서가 다른 문서의 존재를 알 필요가 없다.

**A7-3. 어댑터 버전은 봉투에 1회 둔다.**
> A1-4는 "청크에 어댑터 버전을 기록한다"고 했으나 그것은 **저장 관점**이다. **계약 관점의 위치는 봉투의 `adapter_version` 1회**이며, 청크 저장 시 에이전트가 봉투 값을 복사해 붙인다 — 한 문서는 한 어댑터로 파싱되므로 조각마다 반복할 이유가 없다. 어댑터는 doc_type별로 따로 개정되므로 `parser_version`으로 대체할 수 없다.
> 함께 확정: 봉투에 **`payload_kind`**(`table` | `prose` — 닫힌 2값)를 둔다. payload가 `records[]`인지 `chunks[]`인지 가르는 결정적 스위치다.

**A7-4. 공정좌표 2형제는 둘 다 anchor이고, 부착하는 것은 `process_ref` 하나다.**
> `process_group`(대공정)과 `process_ref`(세부공정)는 **둘 다 사람이 고정한 골격 노드를 가리키므로 role은 anchor다**(구현문서 §2.4 blocks의 정의와 일치). `process_no`는 anchor가 아니라 meta다 — 사내 번호 체계가 비표준·가변이라 조회 키로 쓸 수 없다.
>
> **부착의 기본 대상은 `process_ref` 하나로 고정한다.** 규칙 B의 폴백 대상(`@process_ref`)과 규칙 A의 좌표 조회는 세부공정을 쓴다. **`process_group`은 해소만 하고 부착하지 않으며**, 용도는 `process_ref`의 골격 조상이 맞는지 대조하는 검증이다 — 어긋나면 조용히 한쪽을 택하지 않고 **`coord_mismatch` 큐**로 표면화한다.
>
> **좌표 태깅 프롬프트는 세부공정 닫힌 목록만 준다**(§5.4-3). `process_group`은 선택된 세부공정의 **골격 트리 부모에서 파생**한다 — 대공정을 따로 고르게 하면 두 좌표가 어긋날 수 있다. 세부공정이 `null`이면 `process_group`도 `null`이다. *(※ M2 개정: 닫힌 목록은 골격 전 노드로, 파생은 tier:main 조상으로 — A11-6·7이 이 문단을 대체한다.)*
>
> **귀결 — anchor role의 정의 정정**: anchor가 둘이 되면서 "anchor는 이 행의 정보를 그 노드에 붙들어 맨다"(정의서 §3.1)가 거짓이 된다. **anchor의 동작은 "해소"이지 "부착"이 아니다** — 골격 노드를 찾아내는 것까지가 role의 일이고, 해소된 노드를 무엇에 쓰는지는 스키마가 정한다(`edges`의 `@좌표필드` 참조 / 규칙 B의 폴백 대상 / 다른 anchor의 검증 기준). 정의서 §3.1과 용어 대장의 anchor 문안을 이에 맞춰 정정한다.

**인입 검증의 최종 순서 (A6 + A7)**
```
① 진입 검증   doc_hash 계산 → 기존과 대조 → 같은 해시·다른 doc_id면 보류 + 사람 확인
② 근거 축 id   chunk_id / record_id 계산 (A4 산식). source_locator는 해시 입력이 아니라 출처 장부로
③ 필드 검증   unknown_field / optional 검사(미선언이면 missing_field)
```

### A8. 저장 계층과 id 발급 — 경계 확정 [쟁점 A 판정(사용자) — 2026-08-06]

> 배경: 저장 계층 검토(논의안건서_적재전결정3건 쟁점 A)에서, 전면 인입 규모(노드 50만+)에서 단일 JSON 전체 재기록이 인입 도중에 실용 한계를 지나고, 전역 시퀀스 id가 병렬화를 구조적으로 막는다는 것이 확인되었다. **판정: 저장 방식은 지금 바꾸지 않고, 되돌릴 수 없게 되는 것(경계 부재·id 축적)만 지금 막는다.**

**A8-1. P1 해석 [D안 채택]**
> P1·P5의 "파일"은 단일 JSON을 의미하지 않는다. 샤드 집합도 SQLite 파일도 파일이며, 요구는 **DB 서버 없이 원천이 복원 가능할 것**이다. 저장 계층의 전환은 이 해석 안에서 기술 판단으로 결정한다 — 원칙 논쟁의 대상이 아니다.

**A8-2. GraphStore 경계 [A안 채택]**
> 그래프 저장 접근(로드·저장·노드/엣지 갱신)은 **GraphStore 인터페이스(core/graph.py) 경유로만** 한다. **graph.py 밖의 코드가 graph.json을 직접 열지 않는다** — run.py·viz.py·cli·테스트 포함(현존 직접 접근 지점은 증분 0 단위 A0가 계수·교체). 저장 방식은 현행 유지 — 층별 단일 JSON, 직렬화는 orjson(표준 json 폴백 — 에이전트 코어 "외부 패키지 0" 원칙은 폴백으로 보존). 전환 방향(B-1 샤딩 JSONL / B-2 SQLite)은 **지금 채택하지 않고** 알람선 도달 시 별도 판정한다.

**A8-3. 알람선과 관측 [A안 채택]**
> 계기판에 지표 2종을 추가한다(계기판 7·8번 — CH5 5.5): **graph 저장 크기(층별 최대 파일)** · **build 소요 시간**. **알람선 = 200MB 또는 30초** — 도달 시 B안(저장 전환) 판정을 개시한다. 알람선 수치는 일반 파싱 성능 기준의 가결정이며 실측(A0의 장비 RAM 확인 포함) 후 조정할 수 있다.

**A8-4. 의미 축 id 발급 = ULID [C안 채택 · 발효 조건부]**
> 의미 축 id의 발급 방식을 전역 시퀀스(N#### + id_seq.json)에서 **ULID**로 바꾼다. 근거: ①중앙 카운터 없이 유일 — 직렬 실행 계약(F14)의 근본 원인 중 id 축을 제거한다 ②시간순 정렬 가능 — 시퀀스의 실용 장점(생성 순서) 보존 ③내용과 무관 — 개명해도 불변(해시 id 기각 근거 유지). 발효 시 id_seq.json은 폐지한다.
> **발효 조건: 증분 0 단위 A0의 N#### 하드코딩 계수 확인 후** — mock·테스트·큐에 시퀀스 id가 박혀 있는 규모가 파급을 정하므로, 계수 결과로 "함수 하나"임을 확인하고 발효한다.
> **id에 의미(공정·순서·유형)를 담지 않는다** — 소속·순서는 그래프(part_of·precedes)가, 사람이 읽을 이름은 canonical이 담당한다. 의미를 담은 id는 의미가 바뀔 때 id 변경 압력을 만들어 P4를 위협한다(process_no의 meta 강등·의미 축 해시 기각과 같은 계보의 세 번째 결론).

### A9. 적재 경계 — T0~T3과 그래프 입주 [쟁점 B 판정(사용자) — 2026-08-07]

> 배경: "전면 자산화" 목표는 "설비 데이터도 넣자"는 요구를 반드시 부른다. 기준 없이 답하면 요구가 개별적으로 들어와 설계가 잠식된다(적재 전 결정 3건 중 쟁점 B). 시계열을 넣는 순간 규모가 6~7자릿수 커진다(설비 1,000대 × 태그 50 × 1초 = 연 1.5조 포인트).

**A9-1. 4계층 정의 [채택]**

| 계층 | 무엇 | 저장소 | 그래프와의 관계 | 기수 |
|---|---|---|---|---|

**A9-3. 현 구축 범위 = T0~T2 [규정]**
> T3은 이 문서에서 **계층으로 정의만** 하고, 연동(참조 구조·조회 경로)은 그래프 구축 완료 후의 별도 작업이다(R11). 이 규정의 효과: "설비 데이터 넣자"는 요구에 대한 답이 거절이 아니라 로드맵이 된다 — "그것은 T3 연동 단계의 일이다."

**A9-4. 경계 판정 [전건 확정]**
> - **그래프 진입 경로는 문서 경유뿐이다.** 8D·불량조사 보고서로 들어온 불량 사건은 T1 개체 + T2 근거가 된다. 같은 불량이라도 품질 DB의 개별 레코드 직수신은 T3이다 — "기억할 가치"의 판정은 문서화라는 사람의 행위가 이미 수행했다.
> - **스펙·관리 한계는 T1이다** — 문서에서 나오고 잘 변하지 않는다. 그 스펙에 대응하는 실측값은 T3이다.
> - **로트·셀·Event Frame(런·사이클)·개별 불량 레코드는 전부 T3이다** — 원안의 "로트까지 T1" 절충과 "Event Frame T1 예외"는 채택하지 않는다(예외 0). 귀결: 문서에 적힌 로트 번호는 추출 대상 개체가 아니라 attribute/meta 값이다. 로트 기반 추적 멀티홉은 T3 연동 후의 일이다.
> - **T3의 T1 승격 절차는 만들지 않는다** — 생산 raw가 지식이 되어야 한다면 그것은 승격이 아니라 신규 층 도입(R1 절차)의 문제다.

**A9-5. 그래프 입주 3테스트 — 층 설계 시점의 입주 기준 [수정 채택 — R1 게이트로 편입]**
> ①동일성(이름이 있어 다른 문서가 같은 것을 가리킬 수 있는가) ②연결(다른 정보로 가는 경유지가 되는가 — 못 되면 노드가 아니라 속성) ③기수(개수가 문서 수 비례인가 시간 비례인가 — **시간 비례면 무한이고, 무한은 넣지 않는다**).

**A10-2. `classification` 필드 [채택 — 자리만]**

### A11. 골격의 두 축 — 분해는 구조, 순서는 지식 [M2 판정(사용자) — 2026-08-10]

> 배경: precedes가 구조인지 지식인지 미정인 채 "seed 나열 순서 자동 파생"으로 운영되어, ①극성 형제를 나열하는 순간 거짓 순서(세대 종속 순서를 공장 무관 진실처럼)가 생기고 ②전극 공정의 극성별 병렬 체인과 공정 내 부분 분화(일부 스텝만 극성이 갈림)를 표현할 수 없었다. 제조 정보모델 표준(ISA-95/88·BOP)이 분해 계층과 라우팅을 별도 모델로 가르는 것과 같은 분리를 명문화한다. R9(electrode_type)는 이 분리 위에서 종결된다. **판정 기록 전문·통용성 검토·seed 형식 경위: `안건/M2_판정문안_초안.md`.**

**A11-1. part_of = 구조 [채택]**
> 공정의 분해 계층이며 **공장·제품·세대 무관으로 참인 것만** 담는다. 이것이 주소 체계(좌표 태깅·anchor의 대상)이고 골격의 본질이다. 깊이는 가변이며 기본 3단(main>sub>detail)을 상정하되 고정하지 않는다 — 구 "2단으로 시작" 서술은 이 문안으로 대체.

**A11-2. precedes = 지식(대표 흐름) [채택]**
> 순서는 구조가 아니라 **"대표 흐름"이라는 한 벌의 지식**이다(용도: Q2·Q3 질의). 선언 기준: **회사 표준·현행 기준의 대표 순서 한 벌** — 공장·세대별 미세 상이는 "대표"라는 지위가 명시적으로 흡수한다(그래서 구조가 아니라 지식이다). **선언 방식: seed 자식 배열의 순서가 곧 선언이다**(별도 FLOW 블록 없음, 단일 원천). 구 "나열 자동 파생"과의 차이는 **비참여 옵트아웃의 존재**다: `::` 인스턴스는 자동 비참여, `{"@unordered": <항목>}` 래퍼는 개별 무주장, `"@noflow"`(배열 첫 요소)는 그 부모 아래 전체 무주장 — 따라서 **극성 인스턴스 간 순서와 병렬 스텝의 거짓 순서는 구조적으로 생기지 않는다.** 비참여 항목 사이는 "순서를 주장하지 않음"이다(병렬 단정도 순차 단정도 아님). 문서에서 순서를 추출하지 않는다는 기존 금지(명세 §5.3)는 유지된다 — 출처는 seed 하나뿐.

**A11-3. 부정형 [명문화]**
> **공장별·세대별 실제 라우팅은 골격에 넣지 않는다.** (예: 구세대 설비의 "양극 스텝 전부 후 음극 진행" 순서, 극성 스텝 간 인터리브 방식.) 그것은 공장 무관 골격(T0)의 자격이 없는 지식이다. 표현·저장(신규 층 / context 붙은 순서 엣지 / T3 참조 중 택일)은 R13으로 이연한다. 안전 근거: 골격 노드 id 불변(P4)이 미래 라우팅의 참조 안정성을 보장하고, precedes의 지식 강등이 공존을 보장하며, 라우팅 문서의 원문은 전 청크 보존(N5)으로 이미 소급 가능하다 — 재적재를 강제하는 항목 0.

**A11-4. 극성 표현 3패턴 [채택 — 명세 §5.2 케이스 ①/② 폐지 · 단극성 문법 확정]**
> 분화의 실제 단위는 공정이 아니라 **스텝**이다 — 한 공정(예: 탭용접) 안에서 일부 스텝만 극성이 갈리고 공유 스텝(이송·검사·마킹 등)은 극성 무관으로 흐른다. 공유 스텝을 극성 가지 안에 복제·격리하는 구조는 금지한다. 표현은 3패턴이며 **어느 패턴을 쓸지는 사람이 공정·스텝마다 정한다**(골격=Tier1):
>
> | 패턴 | 조건 | 표현 |
> |---|---|---|
> | **① 극성 무관** | 극성별로 다른 것이 없다 | 노드 하나 (polarity: none) |
> | **② 주소만 극성** | 스텝·지식은 공통 개념인데 **극성 라인이 실재하고 문서·관행이 극성 공정명을 쓴다** | 개념 노드 + **자식 없는 극성 인스턴스** (예: 노칭 — 전극~노칭은 극성 라인 완전 분리) |
> | **③ 스텝 분화** | **그 스텝이 극성별로 따로 관리된다** | 스텝 개념 노드 + 극성 인스턴스 자식 (`@split`) |
>
> **단극성 특이 공정 = `"@cathode"` 또는 `"@anode"`** — @split의 단극성형이며 **개념 노드 + 인스턴스 1개**를 만든다. 개념을 생략하지 않는 근거: 반대 극성이 나중에 실재로 판명되면 `@anode` → `@split` 한 글자 수정으로 끝난다 — 기존 노드 무개명·alias 무이동. 인스턴스 canonical의 극성 접두도 쌍 유무와 무관하게 균일 유지(같은 근거). **Tier1의 단극성 인스턴스는 mirror_asymmetry 큐에 올리지 않는다**(사람 보증 = 짝 없음이 의도).
> 설비만 다른 경우는 어느 패턴도 아니다 — Unit(잎사귀)에서 가른다(기존 극성 결합 메커니즘 유지). **극성 인스턴스 간에는 precedes가 생기지 않는다**(자동 비참여) — 그것이 곧 병렬의 표현이며, 명시적 병렬 주장 장치는 별도로 두지 않는다. "cathode 구간에 속한 스텝"은 노드 소속이 아니라 **파생 집합**(공통 조상 + polarity=cathode)이다 — 트리는 단일 부모이므로 스텝 개념이 부모를 갖는다(공통 alias의 모호성 방지가 우선).

**A11-5. 순서 파생 규칙 [채택 — 질의 traverse 확장, 결정적 코드]**
> 노드 X의 "다음"을 물으면: ①X 자신에게 precedes 선언이 있으면 그것이 답 ②없으면 부모 P로 올라가 P의 후속 Q를 찾는다 ③Q에 X와 같은 polarity의 인스턴스가 있으면 그 인스턴스, 없으면 Q 자체 ④조상까지 선언이 없으면 "순서 정보 없음"으로 답한다(추측 금지). 귀결: 극성 인스턴스의 순서는 선언 없이 파생되고(pre용접::cathode → pre vision::cathode), **공유 스텝 합류가 자동이다**(laser용접::cathode 다음 → bead press). 파생 답은 어느 해상도에서 나온 답인지 표기한다(fact_template — G4 상세).

**A11-6. 좌표 태깅 닫힌 목록 = 골격 전 노드 [채택 — D5 구조 소멸]**
> 파서에 공급하는 닫힌 목록은 **골격 전 노드**(개념+인스턴스)다. 문서가 상위·개념 해상도로 말하면("탭용접", "pre 용접") 개념 노드를 고른다 — 오류가 아니라 **저해상도 부착**(규칙 B의 철학). **극성 모호 규칙(카드 D5)은 전 레벨에서 구조적으로 소멸한다**: 극성 무관 표면형의 alias는 개념 노드만 소유하고, 극성 수식 표기는 인스턴스의 alias(auto)다. "쓰기는 좁게(문서가 말한 해상도), 읽기는 넓게(part_of 하향 포함)"는 유지. **짧은 이름 자동 alias는 골격 안에서 유일할 때만 사전에 등재한다** — 두 노드 이상에 걸리는 짧은 이름(예: "비전검사")은 등재하지 않고 접두 키로만 조회한다. 등재하면 소비처가 조용히 하나를 고르게 된다 — 조용한 임의 선택 금지 계보(레포 D-51).

**A11-7. tier와 process_group 파생 [채택 — main/sub/detail]**
> `tier`는 **main(대공정) / sub(공정) / detail(세부공정)**이며 사람이 적지 않는다 — **loader가 seed 중첩 깊이에서 파생한다**(1단=main, 2단=sub, 3단 이하=detail). **극성 인스턴스는 깊이 계수에서 제외하고 자기 개념의 tier를 상속한다.** **process_group = 조상 사슬에서 tier:main인 첫 노드**로 파생한다 — 구 "골격 트리 부모" 규칙(A7-4·C3)은 깊이 가변에서 거짓이 되므로 대체. process_ref = 태깅된 노드 자체. coord_mismatch 대조는 동일하게 동작한다.

**A11-8. R9 종결 — electrode_type은 구조 필드, polarity는 파생 필드 [채택 · D-1 확정 승격]**
> `electrode_type`은 **role 배정 대상이 아닌 구조 필드**다 — fields·블록에 넣지 않고, 검수 뷰 6지선다에 올리지 않으며, 소비자는 entity 해소 코드 하나다. 원천 다수(정의서 §5.1 attribute·구현문서 §2.4 role:attribute)는 **문법적 불가능을 근거로 기각**한다: 극성 결합 대상이 한 행의 Unit·Property 둘인데 attach_to_field는 하나만 지정한다.
> **해소 코드는 극성 결합 판정 시 노드(Unit·Property)에 `polarity` 파생 필드를 기록한다.** 닫힌 4값: `cathode` / `anode` / `none`(both·무표기) / `unbound`(극성 표기 있었으나 게이팅 ①②③ 미충족 — 걸침 필드의 [사내 확인] 후 재검토 시 복원 경로). Tier1 seed에서는 극성 마커에서 loader가 파생한다 — **polarity·tier는 seed·시스템 전용 어휘이며 LLM·스키마·attribute 핸들러가 쓸 수 없다.**
> **원칙: 코드는 canonical 문자열을 파싱해서 판정하지 않는다.** 판정 근거는 필드다(process_no 강등·id 무의미화와 같은 계보의 세 번째 결론). canonical의 `::cathode`는 저장 정보가 아니라 층 내 유일한 이름을 만들기 위한 표기다. mirrors·순서 파생·극성 필터는 전부 polarity 필드 위에서 돈다.
> 분화 축 일반화(identity_axis를 config로)는 이연한다. 트리거: 극성 외 두 번째 분화 축이 실물에서 관찰될 때(Rule of Three). ※`electrode_type`은 B1(core 무층어휘)의 현행 유일 예외로 명시한다 — 통용성 검토는 M2 판정 기록 §11.

**A11-9. 부착 정합 — 골격 polarity와 극성 결합의 상호작용 [채택 · ⓪은 v2.10 신설]**
> ⓪**하강 부착 [신설 — 판정필요-6 판정(사용자), 2026-08-19]**: 부착 대상 좌표가 **개념 노드**인데 record의 electrode_type이 확정(cathode/anode)이면, **그 개념의 동일 극성 인스턴스가 존재할 때 그리로 하강해 부착**한다(`탭용접`+cathode → `탭용접::cathode`). 하강 후에는 ①이 그대로 적용된다 — 극성이 주소에 실렸으므로 표면형 결합 생략. **인스턴스가 없으면 하강하지 않고 현행 F1 결합이다**(임의 인스턴스 생성 금지 — 골격은 Tier1). 근거: F1(개념 좌표 경로)과 ① 생략(인스턴스 좌표 경로)이 같은 실물에 다른 canonical을 만드는 규칙 접점 결함(G6.5 D1 수리가 실측 — `탭용접::cathode 용접 가압력` ↔ `탭용접::cathode::용접 가압력`). A11-5 순서 파생의 "동일 polarity 인스턴스 하강, 없으면 개념"과 동형 — 새 발명이 아니라 기존 규칙의 부착 측 적용이다.
> ①**이중 결합 방지**: 부착 대상 골격 노드의 polarity가 none이 아니면 **표면형 극성 결합을 생략한다** — 극성이 이미 주소(스코프 접두)에 있으므로 표면형에 다시 붙이면 이중 표기다(F11 이중 접두 방어의 확장). 생성되는 Property·Unit의 polarity 필드는 기록한다(부착 노드에서 상속). **[개정 — M2 후속(2026-08-10)]** 이 생략은 **부착 주소(스코프 접두)가 canonical에 들어가는 카테고리(현행 Property)에 한한다.** 스코프가 없는 카테고리(Unit)는 극성이 주소에 실리지 않으므로 표면형 표기가 이중이 아니다 — **기존 F1 극성 결합을 유지한다.** 검출: 허브 C12 실측 — 생략을 Unit에 적용하면 polarity 필드만 다르고 이름이 같은 노드 2개가 공존한다(P4 취지 위반, 레포 BLOCKERS 판정필요-5 ②).
> ②**polarity 대조**: record의 electrode_type과 부착 골격 노드의 polarity가 둘 다 확정인데 서로 다르면 조용히 한쪽을 택하지 않고 **coord_mismatch 큐**로 표면화한다.
> ③부착 사슬 전체는 기존 메커니즘으로 성립한다: 좌표 태깅(닫힌 목록에서 LLM 선택) → anchor 해소(사전 → 판정 → orphan_anchor) → Property canonical 스코프(부착 노드 접두 — 극성별 자동 분리) → attribute 저장.

## 6. 플랫폼 연결점 — 지금 박고, 구현은 나중에 [방침 확정]

**계약만 지금 박는다. 부하는 작고, 나중에 하면 비싸다.**

| | 지금 박을 것 (계약 — 부하 작음) | 나중에 할 것 (구현 — 부하 큼) |
|---|---|---|
| 내용 | 단계별 진입점과 파일 계약 · 각 단계의 상태 표현 · 큐 조회/처리 인터페이스 형태 · 구축 모드의 단계 분리와 검수 지점 | 화면 설계 · 워크스페이스 IA · 편집 UI · 권한 |
| 이유 | 나중에 바꾸면 파이프라인 구조를 건드려야 함 | 계약만 지켜지면 언제든 바꿔 붙일 수 있음 |

이미 명세에 "플랫폼화 인지 계약 2개"(모든 단계는 CLI 진입점 + 파일 입출력 / 파이프라인은 수정 재료를 빠짐없이 기록)가 있고, 여기에 세 가지를 더한다.

1. **단계 경계가 곧 화면 단위다** — 파싱 / 추출 / 구축이 각각 독립 실행·상태 조회 가능해야 한다.
2. **구축 모드는 사람이 개입하는 워크플로우다** — 생성 → 검수 → 확정의 3단계가 코드 레벨에서 분리되어 있어야 화면이 붙는다.
3. **큐는 처리 대상 목록이자 화면이다** — kind별 조회·처리·재시도가 API 형태로 노출 가능해야 한다.

**각 챕터에 "플랫폼 훅" 한 줄씩만 표시**하는 방식으로 반영한다.
