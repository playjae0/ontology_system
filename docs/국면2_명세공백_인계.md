# 국면 2 인계 — 명세 공백 목록 (P6 V4 역질문이 검출)

> **지위**: 이 목록은 정제 결함이 아니다 — V4(역질문) 90건 중 원천(챕터 13종+증분0)에도 답이 없는 것으로 판정된 공백이다. 정제본은 원천이 가진 것을 전부 승계했고, 여기 항목들은 **원천 자체가 정하지 않은 것**이다. 국면 2(사내 이식) 설계 시 안건으로 올린다. 원천 대조 근거는 로컬 검증 자산 V4V2_2라운드_결과.json에 전문 보존.
> **분류**: [안건] = 구현마다 답이 갈려 명문화가 필요 · [재량] = 구현 재량으로 두어도 해석 동일성이 깨지지 않음

## [안건] 판정 임계 0.85의 적용 대상
원천(CH3A 3.3 규약 1·2, 카드 E1~E3, 증분0 G3 'match_threshold 0.85')도 '매칭(≥0.85)'과 3단 경로·단일 임계만 말하고, 임계가 걸리는 양(임베딩 vs LLM 점수)·결합 규칙·top-k·uncertain 산출 방식은 없다. 실제 명세 공백(안건감 — 멱등·재매칭 직결). 참고: 배경 구명세(구현용문서 §3 matcher·§8 mock '→ match 0.95', config match_threshold)는 임계가 matcher(판정 단계) 점수에 걸리는 구현 관행을 시사하나 규범 문장은 아니다. R6은 질의 측 벡터검색 이연이라 이 갭을 덮지 않는다.

## [안건] 동의어 사전 조회의 키 정규화
조회 키 정규화 규범은 원천에도 없다 — norm()은 원천에서도 해시 계산 전용(카드 N4·CH6 저장 규약·틀 A4). 사전 미스는 후보검색+LLM 판정으로 넘어가므로 갈리는 것은 무LLM 단계의 히트율 — 구현 재량에 가깝되 H8 멱등 재현성 관점에선 명문화 안건감. 한편 'canonical 사전 등재' 소질문은 정제본 부록 '동의어 사전' 행('canonical과 alias를 모아')이 이미 답한다(원천 용어 대장 동일 행·구명세 dictionary.py 'canonical과 alias 모두 등재'와 정합 — E5의 '유일한 경로'는 alias 누적에 한정된 문장).

## [안건] 매칭 시 노드 provenance 누적 여부
원천도 매칭 분기에 'alias 자동 누적'만 규정(CH3A 3.3 규약 1, CH2 2.4③, 구명세 ingest.py 'entity 3분기: 매칭(alias 누적)')하고 노드 자체 provenance가 매칭으로 자라는지는 어디에도 없다. evidence_lost 판정의 분모(회수 ①의 '근거 0')가 구현마다 갈리는 실제 명세 공백 — 재인입 의미론 직결이라 안건감.

## [안건] 큐 항목 스키마와 수명
원천에는 조각만 있다: duplicate_doc_hold 동봉 필드(증분0 §3 G1·§7 D-4 — 파일명·크기·인입 시점·기존 doc_id, '보류 문서는 그래프·청크에 아무것도 쓰지 않는다')와 해소 문장(CH2 2.8① — '다른 문서다'→진행 / '중복이다'→취소), orphan_attach dedup 키(구명세: (노드id, 정규화 표면형)). 항목 공통 필드·상태 전이(open→처리/기각)·'사람의 판단이 기록된 항목' 표시 방법은 원천에도 없다 — 재인입 보존/회수 판정이 이 스키마에 걸리므로 스키마 규격은 안건감, 나머지는 구현 재량.

## [안건] '문서 유래 후보성 큐'의 kind 전수
원천도 일반 규칙 문장뿐이다(틀 §4B-A3 '이 처리는 문서에서 유래한 모든 후보성 큐 항목의 일반 규칙이다', CH3A 3.4 규약 6 동일) — '후보성'의 정의와 20종 kind 대응표는 원천에도 없다. 특히 spec_conflict·attach_conflict(두 문서 관여)의 회수 vs 재평가 배속이 갈리는 실제 명세 공백 — 안건감.

## [안건] spec_conflict 시 신규 값의 저장 위치
원천(CH3B 3.6 규약 5 'deep-equal로 다르면 spec_conflict 큐(덮어쓰지 않음)', CH2 2.5 attribute 계약)도 착지 위치를 정하지 않는다. 배경 구명세 ingest.py('[{context,value,provenance}] 리스트에 추가... 충돌은 같은 context 그룹 내 deep-equal만')는 노드에 병렬 저장 후 큐 표시를 시사하나 규범 문장이 아니다 — 저장 위치 승계 명문화와 사람 판정 전 질의 노출 규칙이 안건감.

## [안건] attach_conflict의 발생 조건
원천도 CH3A 3.4 규약 7(b) '문서끼리 충돌 = attach_conflict 큐, 판단 전에는 먼저 확보된 부착 유지'뿐. 판정 술어의 최선 문면은 배경 구명세 §15.7(b) '교차 출처 충돌(다른 문서가 같은 개체에 다른 부착 주장) = 두 엣지를 만들지 않고 큐'이나, 어떤 관계·카테고리 조합이 배타적인지(occurs_in 다중 정상, Property 스코프 분기와 충돌의 경계)는 어디에도 없다 — 실제 명세 공백, 안건감.

## [안건] '2홉 도달성 검증' 미정의
원천 CH3A 3.4 규약 7(a)도 정의 없이 사용한다 — 정제 손실이 아니라 국면 1 원천에서 이미 끊긴 참조. 정의는 배경 구명세에만 있다: 명세 §15.7 검증① — "공정의 관리인자는?" 질의가 공정→(part_of 하향)→설비→(has_property)→인자 경로로 도달하는지의 구현 테스트(통과 시 (a) 자동 갈아끼움 보류 해제, 미통과면 보류 유지; v1.17 프론티어 전파 정의가 성립 근거). 경로 성립 근거 자체는 CH5 5.1 규약 5(정제본1 K12로 승계)에 있으므로, '검증'의 절차·통과 기준·보류 해제 연동 문면의 승계가 안건감.

## [안건] 재부착 정밀화와 스코프 canonical
원천에도 사후 재부착×canonical 상호작용 규칙은 없다 — P4 접점의 실제 명세 공백(안건감). 유일한 인접 선례는 틀 v2.10 A11-9 ⓪ '하강 부착'(D-75): 극성 축에서 '같은 실물이 좌표 해상도에 따라 두 canonical로 갈리는 P4 위반'을 부착 시점 하강으로 봉쇄했다 — 좌표 정밀화 축에도 같은 유형의 봉쇄(부착 시점 또는 I1 개명 연동)가 필요하다는 방향 시사만 있다.

## [안건] relation 후보의 끝점 미해소 처리
원천도 attach에 대해서만 해소 범위를 규정한다(CH3A 3.11 규약 6 — 문서 버퍼+사전). relations의 src/dst 해소 규칙, 같은 체크포인트 entities에 없는 표면형의 카테고리 획득, 미해소 끝점 후보의 착지(큐 vs 폐기)는 원천에도 없다 — G5(조용한 소실 금지)와의 정합상 실제 명세 공백, 안건감. orphan_chunk_link는 content 청크 속 언급 미해소용(CH3B 3.7 표)이라 이 자리가 아니다.

## [안건] attach 폴백 엣지의 경로 분류와 매핑 부재 쌍
경로 지위는 원천 CH3A 3.4 규약 3 'attach_to는 ③의 폴백이다'가 답이고 정제본4에도 승계돼 있다(③ 소속 — 동종 쌍 비커밋 규약 6의 사정권). 그러나 해소된 카테고리쌍이 매핑에 없을 때의 처리(거부+기록? orphan_attach 유지?)와 동종 쌍 attach의 방향 부여는 원천에도 없다 — 기본 패턴표가 Unit→Process·Property→Unit·Process 2행뿐이라 실측 시 반드시 만나는 실제 공백, 안건감.

## [안건] record_id 산식의 입력 세부
원천도 D-14(증분0 §3 G0: 'join 대상 field_values = 매칭 스키마 fields에 선언된 필드의 값들을 스키마 선언 순서로 — 순서가 산식의 일부')까지다 — 정제본 N11과 동일 수준. use_blocks 전개 필드의 포함·순서, optional 부재 표현, 구조체·숫자의 직렬화는 원천에도 없다. record의 occ 키는 카드 N3이 '(section, 내용) 조합'으로 일반화해 뒀으나 record에 section이 없어 여전히 미해결 — 멱등성 판정(클린 2회 동일) 직결의 실제 공백, 안건감.

## [안건] doc_hash 산식
원천도 성질 서술뿐이다 — CH2 2.8① '문서 전체 내용의 해시... 청크 해시를 계산하는 과정에서 함께 얻으므로 추가 비용 없음', CH6 저장 규약 3 동일. 입력 정의(봉투 가변 필드 parsed_at 포함 여부, 조각 연결 순서·구분자)는 어디에도 없다. 산식에 따라 N8 중복 차단 판정이 달라지므로 실제 명세 공백 — 안건감.

## [안건] revision 비교와 동일 문서 재도착
동일 doc_id 재도착 = 재인입 정상 경로(no-op 아님)는 원천 CH2 2.8①이 답하며 정제본2 2.7①에 이미 승계돼 있다('같은 doc_id 재도착은 중복이 아니라 재인입(정상 경로)이다'). 남는 핵심 — revision의 형식·순서 비교·역행(구판) 감지·동일 doc_hash 재제출의 단축 — 은 원천에도 없다(doc_registry.json은 doc_id→doc_hash·revision 기록만, 증분0 G1). 구판 재제출이 최신을 덮는 문제라 안건감.

## [안건] 재인입 회수된 청크의 물리 처분
원천도 '회수'의 물리 의미(삭제 vs 무효화 보관)를 정하지 않는다(CH3B 3.8 회수 ① — 목록만). 배경 구명세 store.py의 ChunkStore(remove_doc)는 물리 제거 관행을 시사하나 규범이 아니다. '전 청크 보존'(N5 — 하이브리드 검색 전제)의 대상이 현행 revision 한정인지 역대 전부인지도 원천에 없다 — 과거 답변의 근거 참조 절단 문제와 얽히는 실제 공백, 안건감.

## [안건] obsolete 노드와 판정·사전·부활 차단
원천도 I4에 목적('①옛 문서·답변이 참조 ②재인입 부활 차단')과 질의 측 제외·전이 추적만 있고, 쓰기 측 — 판정 후보 검색·사전 조회에 obsolete가 포함되는지, 매칭되면 무엇을 하는지 — 는 무규정이다. merged_into는 사전 lookup 리다이렉트가 규정돼 있으나(증분0 §4.2 I-1 시나리오) obsolete는 대응 규정이 없다. '부활 차단'이 무엇으로 달성되는지의 메커니즘 명세가 필요한 실제 공백 — 안건감.

## [안건] status 전이와 confirmed 승격 경로
원천도 어휘 정의뿐이다(용어 대장 'confirmed(사람이 보증·승격)', D4 anchor 자격) — 승격이 어떤 도구·행위로 일어나는지(I축 4연산에 없음), evidence_lost가 재인입으로 근거를 회복하면 자동 복귀하는지 모두 무규정. 상태 전이표(누가·언제·어떤 도구) 부재는 실제 명세 공백 — anchor 자격(seed·confirmed)이 승격 경로에 걸려 있어 안건감.

## [재량] anchor 해소의 판정 분기
원천도 CH2 2.4①(사전 조회→미스 시 후보검색+판정→미해소면 orphan_anchor, Tier1 한정: auto 후보는 후보 id 동봉 큐)까지다 — entity 3분기를 anchor에 접는 명문(uncertain의 착지), 임계 0.85·LLM 적용의 명시는 원천에도 없다. 다만 '판정'은 3.3 파이프라인 재사용이고 anchor는 신규 생성 금지+Tier1 한정이므로 'seed/confirmed 매칭만 해소, 나머지 전부 orphan_anchor'가 유일하게 정합하는 해석 — 구현 재량에 가까우나 한 문장 명문화로 닫히는 공백.

## [안건] 공정좌표 null일 때의 부착 폴백
실제 명세 공백이되 의도된 이연 — CH2 2.8 규약 1이 "빈 셀 부착(부착 대상 부재)"를 핸들러 폴백 훅의 사내 갭 관찰 대상(P7)으로 명시해 채움을 미룸. null 좌표×규칙 B 교차의 착지(노드만 생성? orphan_attach?)는 원천 어디에도 없음 — 국면 2 안건감

## [안건] 빌드 원자성과 크래시 복구
실제 명세 공백 — 원천도 '비원자적이므로 직렬'(H5·§16.1)까지만. H5 주석("저장이 파일 전체 재기록인 동안 직렬 계약 유지")이 말미 일괄 저장을 함의할 뿐, 회수-재삽입 중단 시 상태·트랜잭션 경계·저장 시점 계약은 없음. R10(저장 전환) 판정과 같은 자리에서 다룰 안건감

## [안건] orphan 재시도 배치의 주기와 호출 주체
실제 공백 — 원천도 '주기 재시도'(3.7 규약 5·3.4 규약 5)뿐. 부분 경로 둘: P-3(큐 kind별 재시도 API 노출 — 플랫폼/사람 트리거 함의)·H2 ③(재인입 시 그 문서발 큐 재평가). 주기 정의·진입점·소유는 미규정 — 플랫폼 트랙/국면 2 안건감

## [재량] Pass 1 내부 처리 순서
구현 재량에 가까움 — CH2 2.8 루프 예시가 스키마 선언 순 순회를 보이고 D-14(record_id join=fields 선언 순)가 선언 순의 규범 선례. 스코프 canonical·하강 부착(A11-9 ⓪)은 부착 좌표 해소를 입력으로 요구해 anchor 선행이 기능적으로 강제됨. 다만 규범 문면은 원천에도 없어 멱등성 관점 문면화는 가치 있음(경미 공백)

## [재량] electrode_type의 계약 값 어휘

## [안건] missing_field 큐 후 레코드 잔여 처리

원천도 CH4 4.7 절차 6단계에 '표본 인입 스모크 + 스모크 질의'라는 항목명만 있고 합격 기준·부작용 처리는 없다. 구현 관행의 단서는 증분0에 있다 — S1 시나리오는 등록 완료(registry 등재) 후 표본 TOC01을 별도 단계로 운영 인입하고(자동 인입 아님), S10은 등록 완주 후 registry 비활성화를 '잔재 정리는 재량'으로 둔다 — 즉 현행은 구현 재량으로 처리 중이다. 일반 규칙(스모크 산출물의 실그래프 잔존 여부·합격 기준)은 실제 공백이며, R1 실효성 실험(국면 2 진입 게이트)에서 확정할 안건감.

## [안건] process_ref 미해소 레코드의 잔여 처리
폴백 대상(좌표) 자체가 미해소인 케이스의 명문 규칙은 원천에도 없다. 다만 기존 규칙 조합으로 방향은 도출된다 — anchor는 해소만 하고 노드를 만들지 않으며(D3), entity 생성은 anchor 해소와 독립이고(승인 게이트 없음·자동 커밋 G1), 부착 실패는 orphan 계열 큐+주기 재시도(3.7 규약 5: 그래프가 자라면 해소될 수 있어 재시도)가 받는 구조라 '노드는 생성되고 부착만 큐에 남는' 쪽이 설계 결이다(record 보류는 문서 단위 실패 C14의 사유가 아님). 그래도 'record 보류 vs 부착 없는 생성'의 명문은 공백 — 구현 재량 + 소형 안건감(어느 큐에 착지하는지 명명 필요).

## [재량] prose doc_type 등록 검수 뷰의 배정표
구현 재량. 원천도 검수 뷰 구획 ②를 table 전제('필드→role 매핑, 6지선다')로만 서술하고 prose 렌더 규칙은 없다(파서_명세 §7·M11). D-31 확정(prose fields={}, payload 고정 키 4종은 구조 필드라 6지선다 대상 아님)의 자연 귀결로 prose 배정표는 빌 수밖에 없으며, 무엇으로 채우나(공란 vs layer·use_blocks 확인 표시)는 렌더러 재량이다 — 검수 뷰 데이터 스키마 실물(킷 자산 검수뷰_데이터스키마.json)과 렌더러(P2 산출물)가 레포에 실재해 구현이 사실상 정본. 명세 공백으로 승격할 무게는 낮다.

## [안건] 그래프 입주 3테스트 ①동일성 탈락의 처리
원천 CH4 4.7 규약 1의 판정표 자체가 ①동일성 탈락 칸을 '—'로 비워 두었다(틀 A9-5도 ①의 탈락처 미기재) — 정제 손실이 아니라 원천 그대로의 공백이다. '탈락은 반려가 아니라 강등(제자리 찾기)'이라는 총칙상 이름 없는 후보는 ②와 같은 attribute 강등이 자연 귀결로 보이나 명문이 없다. R1 절차의 실효성 실험(국면 2 진입 게이트 — 품질층 재등록)에서 판정표를 실사용할 때 확정할 안건감.

## [안건] 식별자 명명 규칙
원천에도 doc_type 이름·층 이름의 허용 문자·표기 규칙이 없다(파서_명세 §6은 중복 거부만, layers/ 폴더명↔config layer 값 일치 요구도 미명문). 현재는 구현 재량 — 레포 실물(cp·pfmea·toc_report·process·quality 등 소문자 스네이크)이 사실상의 규범이고, 이름이 파일명·조회 키·record_id 접두와 결합되므로 재량이 실사고를 낸 기록도 없다. 사내 이식(국면 2 — doc_type 실물 목록·사내 한글 명칭 유입 시점)에 명문화할 소형 안건감.

## [안건] PPT 임계 등 파서 측 설정값의 소유 파일
원천도 '임계(config 값 — 초기 제안 600자 또는 텍스트 shape 5개, 측정 후 조정 P7)'(파서_명세 §5 규약 5)·'PPT 임계는 config 값'(증분0 P1 조절점)까지만 있고 소유 파일 지정이 없다 — 층 config는 층 어휘용이라 부적합하다는 질문자 지적은 원천에서도 미해소다. 관리 자산 원칙(CH6 6.1: 어댑터 판단 상수는 ADAPTER.expects)을 적용하면 코어 기본 어댑터의 expects가 자연 후보이나 명문 없음 — 구현 재량(레포 실물이 정본)이되, 파서 측 설정 파일의 존재·위치는 국면 2 반입 문서화 때 명문화할 소형 안건감.
