# B61 구현 요청문 — 상태 거부는 원인과 다음 줄을 낸다 (규칙 + 남은 두 자리)

> **수신**: 구현 세션 · **발신**: 허브 (2026-09-11) · **출처**: B59·B60이 등록 단계(§4)의 막다른 길을 닫았다. **같은 모양이 다른 단계에 남아 있는지**를 구조로 짚었다 — 사람이 상태를 이유로 거부당하는 자리는 가이드 단계마다 하나씩이고, §2 골격·§5 인입 둘이 남았다. 그리고 **자리마다 고치면 다음 자리에서 또 난다** — 규칙을 세우고 어서션으로 잠근다.
> **한 줄**: 상태 거부(`SystemExit`)는 **원인 + 완성된 다음 명령**을 함께 낸다. 사용법 오류는 대상이 아니다 — 그건 사용법이 답이다.
> **LLM 0.**

## 전제 대조표

| # | Claim | Command | Expect |
|---|---|---|---|
| 1 | `SystemExit` 자리가 `cli/`·`run.py`에 56곳 | `grep -c 'SystemExit(' cli/*.py run.py \| awk -F: '{s+=$2} END{print s}'` | ~56 |
| 2 | 골격 확정 거부가 「seed를 고쳐 다시 실행한다」 | `grep -n '확정하지 않았다' cli/skeleton.py` | 1 hit — 어느 줄·어느 규칙인지 불명 |

| 4 | 인입 중 문서 단위 실패가 어디서 화면에 나오나 | `grep -n 'parse_failure' cli/ingest.py core/pipeline.py parser/pipeline.py` | 착지는 큐 — **화면 출력 자리를 보고** |

## ① 규칙 — 상태 거부 문면의 계약

**상태 거부**: 사람이 명령을 옳게 쳤는데 시스템 상태(파일·등록부·판정·seed 내용)를 이유로 진행하지 않는 것. **사용법 거부**(인자 누락·형식 오류·알 수 없는 명령)는 대상이 아니다.

상태 거부는 셋을 낸다:
1. **원인** — 무엇이 어긋났나, 가능하면 **어디서**(파일·줄·필드)
2. **다음 줄** — 사람이 **그대로 칠 수 있는** 명령 한 줄 이상. 「고쳐라」·「통과시켜라」 같은 동사만으로 끝내지 않는다
3. **지금 잰 것** — 저장값이 아니라 그 자리에서 판정한 것(B60 ① 원칙)

**어서션 — 상태 거부 문면에 `python run.py` 또는 `python -m cli.`가 들어 있다.** 56곳을 훑어 상태 거부만 골라(사용법 거부는 제외) 그 집합을 코드에 목록으로 두고, 목록의 문면 전부가 계약을 지키는지를 회귀가 센다. **새 `SystemExit`이 생기면 목록에 넣거나 「사용법」으로 표시해야 통과한다** — 표시 없는 새 거부는 빨갛다. 이것이 다음 자리를 잡는 장치다.

**완료판정 ①**: ⓐ 상태 거부 목록(파일·줄·분류) ⓑ 어서션 — 목록 전건이 계약을 지킨다 ⓒ 어서션 — 목록 밖 `SystemExit`은 전부 사용법 표시가 있다 ⓓ 변이 시험 — 표시 없는 `SystemExit`을 하나 넣으면 붉어진다.

## ② §2 골격 확정 — 어느 줄이 어느 규칙을 어겼나

`skeleton confirm`이 「확정하지 않았다 — seed를 고쳐 다시 실행한다」로 막는다. **내용은 사람 몫이고 코드는 문법만 본다**(순환·canonical 중복·극성 마커 오타·읽기 실패) — 막는 건 맞다. **어느 줄이 어느 규칙인지를 안 말하는 것이 틀렸다.**

거부 블록:
```
■ 골격 확정 거부 — process
  [FAIL] K02  canonical 중복 — '노칭' (12행 · 27행)
  [FAIL] K05  극성 마커 문법 — 19행 '탭용접::cathod' (cathode?)
  ▶ 다음 줄:
     (seed의 위 줄을 고친 뒤)  python run.py skeleton confirm process --by <이름>
```
- 태그(`K##`)는 B59 `G##`과 같은 방식 — 정본 한 자리, 읽어서 전달.
- 위반 전건을 낸다 — 첫 하나에서 멈추지 않는다.
- `skeleton status <층>` — 확정 없이 판정만.

**완료판정 ②**: ⓐ 위반 둘을 심은 seed로 블록(화면) ⓑ 어서션 — 위반 전건이 줄 번호와 함께 나온다 ⓒ 어서션 — `status`·`confirm`이 같은 판정 함수.

## ③ §5 인입 — 문서 단위 실패가 화면에 이유와 행을 낸다

C14: 계약 위반 행·어댑터 예외·validator 위반이 하나라도 있으면 **그 문서는 통째로 인입하지 않는다** + `parse_failure` 큐. 큐에는 가는데 **화면에 어느 행·왜**가 뜨는지가 불명이다. 사람은 `ingest-file` 치고 화면을 본다 — 큐를 먼저 열지 않는다.

`ingest-file`·`ingest-dir` 실패 화면:
```
■ 인입 실패 — 관리계획서_라인3.xlsx (doc_id 관리계획서_라인3)
  [FAIL] P12  계약 위반 행 — 27행 process_ref가 리스트 ['노칭','스태킹']
  [FAIL] P31  validator — 봉투 payload_kind 없음
  큐: parse_failure 1건 (같은 내용)
  ▶ 다음 줄:
     (문서의 27행을 고친 뒤)  python run.py ingest-file <같은 파일>
     양식이 바뀐 거면:        python -m cli.register generate <doc_type> --revise
```
- 이유는 이미 큐 payload에 있다 — **그것을 화면에도 찍는다.** 두 자리가 아니라 같은 재료.
- `ingest-dir`은 문서마다 독립(B46)이라 끝에 실패 목록을 모아 보인다 — 이미 그렇다면 그 목록의 항목이 위 꼴인지만.

**§5 하나 더 — `scan` 지문 불일치의 다음 줄을 명령으로**: 「양식 표류면 어댑터 개정, 새 양식이면 신규 doc_type 등록」 → `python -m cli.register generate <doc_type> --revise` / `python -m cli.register generate <새이름> <층> <문서>`.

**완료판정 ③**: ⓐ 계약 위반 행을 심은 문서로 `ingest-file` → 위 블록(화면) ⓑ 어서션 — 화면의 FAIL 줄과 큐 payload가 같은 재료 ⓒ `scan` 불일치 문면에 `--revise` 명령이 있다.

## ④ 화면의 등록 명령 형태를 하나로 — `python -m cli.register`
실측에서 나온 것: 가이드는 `python -m cli.register …`인데 화면 일부가 `python run.py register …`를 찍는다. 같은 함수를 부르지만, 사내에서 태그를 **읽어서** 옮기는 사람에게 두 형태는 두 명령으로 보인다.
- 고칠 자리: `grep -n 'run.py register' cli/register.py cli/platform.py` — 전부 `python -m cli.register`로. (`cli/register.py`의 873~890 부근은 이미 이 형태다 — 그 형태로 맞춘다.)
- `run.py`의 `register` 서브커맨드 자체는 **그대로 둔다** — 지우는 게 아니라 화면 문면만 통일.

**완료판정 ④**: `git grep 'run.py register' -- cli/`가 0줄. 어서션 없음 — 문면이다.
