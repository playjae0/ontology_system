# B74 구현 요청문 — 사전이 실제로 히트하게(키 불일치) · 판정 대장(생성 경로 기록) · 평가 뷰어(엣지 라벨·출처·집계) · 행별 `show report` · `ops alias` · 칸 3.4 · 3.1 · 3.5 · 0.3

> **수신**: 구현 세션 · **발신**: 허브 (2026-09-16 · 사용자 확정 2026-09-16) · **B73 뒤(#55)** · **출처**: 사용자 — 「그래프가 구성되는데 평가를 해야 하는데 뷰어가 너무 간단하다 · 엣지값이 안 보인다 · 몇 개가 로직 처리·몇 개가 LLM 처리인지 · 동의어 사전이 정말 작동하나 · notching의 cutter와 separator의 cutter 구분」.
> **진단 ① (허브 실측 열셋째 — 이 회차의 머리)**: **동의어 사전은 스코프 카테고리(관리항목·설비 — CP의 대부분)에서 한 번도 히트하지 않는다.** `build.py::_register`는 **원 표기**(`노칭 프레스`)를 키로 등재하고, `resolve_entity`는 **스코프 canonical**(`노칭::노칭 프레스`)로 `resolve → candidates → dictionary.lookup`을 부른다. 키가 다르니 `exact` 후보가 0이다. 허브 실측(mock · CP01 재인입): 예고는 `표기 31종 · 사전 히트 31종`이라 하고 실제는 `판정 — 호출 60 · 사전 0` — **예고와 판정이 다른 키로 사전을 본다**(예고 `pipeline.py:901`은 원 표기로 조회). mock은 `_similarity`의 포함 규칙이 1.0을 내서 노드 +0으로 가려진다. **사내 실호출에서는 다르다**: 값마다 LLM 호출이고, 그 판정이 auto 노드에 0.95로 MATCH를 내면 B73 ③ `_guard_auto`가 `uncertain`으로 내려 **같은 canonical의 노드가 하나 더 생긴다**(`add_node`는 canonical 중복을 막지 않는다 — 허브가 판정기를 0.95 MATCH로 대체해 재현: `{'type': 'uncertain', 'matched_id': None}`). B73 ③은 「표기가 같으면 사전 히트로 1.0」을 전제했는데 그 전제가 스코프 카테고리에서 비어 있었다. B73이 호출 하나의 크기를 줄였고, 이것이 호출의 **수**와 중복 노드를 만든다 — 평가 뷰를 만들기 전에 이것부터 고쳐야 뷰가 중복을 보여 주지 않는다.
> **진단 ②**: 노드·엣지에 **어떻게 생겼는지**(골격 / 사전 / 스코프 후보→판정 / 임베딩 후보→판정 / 신규 / 폴백)가 기록되지 않는다 — 판정 경로는 `matcher.STATS`(문서 단위 합계)와 로그에만 흐르고 사라진다. 「몇 개가 로직, 몇 개가 LLM」을 사후에 셀 수 없고, 행 하나가 어디에 붙었는지 사람이 문서를 옆에 놓고 대조할 표가 없다.
> **진단 ③**: 뷰어 데이터(`export.py::graph_data`)는 엣지에 `rel`을 싣지만 html이 **라벨을 그리지 않고**(`fillText`는 노드 이름 1곳) 엣지 `provenance`·`status`는 싣지도 않는다(graph.json에는 있다). 노드 툴팁은 축 값·연결 수·출처 4건. 집계는 노드·엣지·걸침 수뿐.

## ① 사전 키 = 조회 키 — 스코프 canonical로 등재·조회하고 예고도 같은 함수를 쓴다 (칸 3.4)

- **등재**(`build.py::_register`): 원 표기(질의 링킹의 `surfaces()` 스캔이 쓴다 — 유지)에 **더해** 그 노드의 **스코프 canonical**을 같은 provenance로 등재한다. 스코프 없는 카테고리는 둘이 같으므로 1건.
- **조회**(`matcher.candidates` ①): 넘어온 surface(스코프 canonical)로 조회 — 지금과 같다. 안전망 하나 추가: `exact` 후보도 **`parent`가 다르면 넣지 않는다**(스코프 카테고리 한정 — 원 표기 키로 조회되는 경로(retry `_pick_*` · 병합 후보)가 다른 부모의 동명을 exact로 올리지 못하게).
- **예고**(`pipeline.py` 판정예고): 사전 히트 수를 **판정이 쓰는 것과 같은 키·같은 필터**로 센다 — 함수 하나를 둘이 부른다(예고가 판정의 예고가 되게 — B22 원칙).
- 사용자 질문의 답을 여기서 확정한다: 「notching의 cutter / separator의 cutter」는 **키가 `노칭::cutter` · `세퍼레이터::cutter`로 갈리고, 후보 조립도 부모로 가른다.** 원 표기 키 `cutter`는 질의 링킹용이며 거기서는 질문의 좌표·카테고리가 가른다(문서 5).

**완료판정 ①**: 어서션(성질) — 같은 문서 2회째 인입에서 스코프 카테고리의 entity 해소가 **전부 exact 경로**(판정 함수 미도달 — mock에서는 `STATS["판정"] == 0`, 실호출 어서션은 `_judge_live` 미도달로 잰다) · 같은 표기·다른 부모는 exact에 들지 않는다 · 예고의 사전 히트 수 == 판정의 사전 경로 수 · 질의 링킹의 원 표기 스캔 불변(회귀 P 계열 초록) · 중복 canonical 노드가 생기지 않는다(같은 층·같은 canonical·live가 2개면 FAIL — **이 어서션은 회귀 전체에 상시로 건다**).

## ② 판정 대장 — 문서마다, 값마다, 어떻게 해소했는지 (칸 3.1 · 3.5)

정본이 아니라 **장부**다(§5.4 표에 행 추가 · 재인입이 덮는다). 자리 `data/ingest_log/<doc_id>.json`(구현 세션이 다른 자리를 고르면 D-로 남긴다 — 조건: 문서 7 §7.8의 산출 자리 표에 오른 곳). 행 하나 = entity 값 하나(anchor·attribute·content 부착 결과도 같은 표에 — 종류 열로 가른다):

```
{ locator, field, role, surface, canonical, layer,
  path:   "skeleton" | "dictionary" | "scope+judge" | "embedding+judge" | "overlap+judge" | "none",
  verdict: "match" | "new" | "uncertain" | "anchor" | "lowres" | "orphan" | "attached" | "pending" | "gate_reject",
  node_id, candidates_n, confidence, llm: {calls, in_tokens, out_tokens}, queue_kind }
```
`path`·`verdict`는 **닫힌 값**이고 코드가 아는 사실만 적는다(LLM 산출 아님 — C38의 결). 대장을 만드는 자리는 `pipeline`의 행 루프 하나(`_row_roles`/`resolve_entity`의 반환에 경로를 실어 올린다 — `matcher.match`의 반환 dict에 `path` 키 하나 추가, 계약 4.3-6의 세 키는 그대로).

**완료판정 ②**: 어서션(성질) — 대장 행 수 == 그 문서의 entity 값 수 + anchor 행 수 + 부착 시도 수 · `path`·`verdict`가 닫힌 집합 밖이면 FAIL · 재인입 뒤 이전 대장이 남지 않는다 · mock 회귀에서 대장의 `llm.calls` 합 == `llm.usage_total()["calls"]`.

## ③ 뷰어 — 엣지 라벨·출처, 노드 상태·경로, 집계 패널, 문서 필터 (칸 3.5)

**완료판정 ③**: 어서션(성질) — `graph_data` 엣지에 `status`·`prov` 있음 · 노드에 `made_by` 있고 값이 ②의 닫힌 집합 ∪ {seed, unknown} · html의 DATA에 `rel`·`made_by`가 실린다(문면·수는 세지 않는다) · 문서 필터로 거른 노드 집합 == `show doc <id>`의 노드 집합.

## ④ `run.py show report <doc_id>` — 행별 결과표 (칸 3.1)

②의 대장을 사람 순서로: 행(locator)마다 `필드 · 표기 → canonical(node_id 앞 6) · 경로 · 판정 · 큐`. 머리에 집계(값 N · 사전 d · 스코프→판정 s · 임베딩→판정 e · 신규 n · 불확실 u · 보류 p · LLM 호출 k · 토큰 t), `--json`. `show doc <id>`의 끝에 「행별은 `show report <id>`」 한 줄(새 최상위 진입점을 늘리지 않는다 — 문서 7 §7.1 「같은 기능을 다른 이름으로」의 결). 목적: 사람이 문서를 옆에 놓고 **정합성을 행 단위로 눈 검수**한다 — 평가의 단위.

**완료판정 ④**: 화면 · 어서션(성질) — 집계의 각 수 == 대장에서 센 수 · `--json`의 행 수 == 대장 행 수 · 없는 doc_id는 상태 거부.

## ⑤ `ops alias <층> <node_id|canonical> <표기> --actor` — 사람이 표기를 잇는다 (칸 0.3 · 3.4)

지금 사전에 표기를 넣는 사람의 길은 골격 alias(seed `ALIASES`)뿐이고 entity의 alias는 판정 결과로만 쌓인다. 연산: ①의 등재 함수로 원 표기 + 스코프 canonical을 provenance `op:alias:<actor>`로 등재 · 노드 `aliases`에 추가 · ops_log 5요소. **거부**: 툼스톤·타층 id · 그 표기가 같은 층·같은 카테고리·같은 부모의 **다른 live 노드**에 이미 붙어 있으면 거부하고 그 노드를 보인다(합칠 것이면 `ops merge`다 — alias로 우회 병합을 막는다). 미리보기 없음(파급 1건 — 문서 4 §4.7-4 예외).

**완료판정 ⑤**: 어서션(성질) — 등재 뒤 같은 부모 아래 그 표기가 exact로 해소 · 충돌 거부 · 툼스톤 거부 · ops_log 5요소 · `--actor` 없으면 거부.
