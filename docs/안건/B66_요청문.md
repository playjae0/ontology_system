# B66 구현 요청문 — 헤더 지문은 포맷을 보지 않는다 (CSV 스캔) · 미선택 문면 네 갈래 · 확정 화면의 「다음」 · **CSV 전 구간 등가 어서션** · 칸 0.2 · 3.1 · 1.7

> **수신**: 구현 세션 · **발신**: 허브 (2026-09-15) · **출처**: 사내 실측 여섯째 — CSV 어댑터를 확정한 뒤 `run.py ingest-file <문서.csv> --dry-run`이 「미선택 · 지문 일치 0건 · 대조할 정형 어댑터가 없다」. 어댑터의 `expects.header_labels`는 차 있었다. **원인은 어댑터가 아니라 스캔이다** — `cli/scan.py::FINGERPRINTABLE = ("xlsx",)`가 CSV를 지문 대상에서 빼서 어댑터를 하나도 대조하지 않았고, `cli/ingest.py::select`는 스캔이 돌려준 `not_fingerprintable` 표시를 읽지 않고 빈 결과를 「어댑터가 없다」로 번역했다.
> **같은 병의 셋째 자리다.** B62 ①-a가 `parser/preflight.py::header_labels`의 `format != "xlsx"`를 없앴고 `cli/scan.py::_header_actual`의 복제본을 preflight 호출로 바꿨는데, 같은 파일 30줄 아래의 **포맷 튜플은 B62 대조표에 없었다**(허브 누락). 명세는 이미 답을 갖고 있다 — 문서 6 §6.4 지문 추출 규약 「**포맷을 보지 않는다** — `sheets` 구조가 있으면 읽는다(csv도 같은 규약)」 · 문서 1 C37 「xlsx·csv를 `table`로 읽는다」. 코드가 명세를 어긴 것이고, 어긴 것을 회귀가 못 잡은 이유는 **CSV 표본으로 스캔을 돌리는 어서션이 하나도 없어서**다.
> **허브 실측(이 zip의 기준 origin, USE_MOCK=1)**: CSV 표본(`tests/fixtures/raw/CSV05_wide.csv`)으로 `generate` → 관문 38/0 PASS → `confirm` → `ingest-file --doc-type` → **성공 record 4**. 같은 문서를 `--doc-type` 없이 → 사내와 같은 「대조할 정형 어댑터가 없다」. `FINGERPRINTABLE`에 csv를 넣고 다시 → 후보 1건(7/7). **CSV 경로에서 막힌 자리는 이 한 줄이 전부다** — reader·preflight·관문·확정·인입은 CSV로 돈다.

## ① `FINGERPRINTABLE` 폐지 — 지문 대상은 `sheets` 구조다 (칸 0.2)

포맷 이름 튜플을 없앤다. 스캔이 거르는 기준은 **reader가 `sheets`를 냈는가**(= `reader.GRID_EXT` — xlsx·xlsm·csv·tsv)이고, prose 포맷(pptx·pdf)만 「지문 대상 아님」이다. `render`의 「지문 대상이 아니다」 분기는 남되 조건이 바뀐다.

- 포맷 이름을 코드에 다시 쓰지 않는다 — B62 ①-a·`_header_actual`·이번 셋이 전부 같은 실수였다. 남는 포맷 분기가 0이 되는 것이 이 항목의 성질이다(대조표 2).
- 06 손잡이 대장에 0.2 행이 없었다 — 대장에 없는 손잡이였기 때문에 아무도 안 봤다. 마감 뒤 허브가 0.2 행을 적는다(「지문 대상 = `GRID_EXT` — 포맷 상수 없음」).

**완료판정 ①**: ⓐ CSV 표본 `run.py scan tests/fixtures/raw/CSV05_wide.csv --adapters <csv 어댑터>` → `◎ 후보 … 일치 7/7` ⓑ 어서션(성질) — **같은 헤더의 표본 두 포맷(xlsx · csv)에서 같은 어댑터가 같은 후보 판정**을 받는다(포맷이 판정에 안 들어가는 성질 — tsv는 사내에 없어 표본을 만들지 않는다, 사용자 결정) ⓒ 어서션(성질) — `ingest-file <csv> --dry-run`(doc-type 없이)이 등록된 CSV 어댑터를 **스캔으로** 고른다(`basis.by == "scan"`) ⓓ `grep -rn --include=*.py 'get("format")' cli/ core/ parser/ kit/` 동작 줄 0.

## ② 미선택 문면 네 갈래 — 「없다」는 어댑터가 0건일 때만 (칸 3.1)

`select`의 status `none`이 한 문면(「지문 일치 0건 — 대조할 정형 어댑터가 없다」)으로 서로 다른 넷을 덮는다. B61 계약(원인 + 다음 줄 + 지금 잰 것)으로 가른다:

| Case | Screen (원인 · 다음 줄) |
|---|---|
| 지문 대상 아닌 포맷(prose) | `비정형(<확장자>) — 헤더 지문이 없다 · 다음: --doc-type <dt>` (지금 pptx 분기와 합친다 — ①로 이 갈래는 pptx·pdf만 남는다) |
| 어댑터 소재지 비었다 | `대조할 어댑터 0건 — 등록부 비었다 · 다음: register generate` |
| 자격 없는 어댑터만 있다 | `자격 있는 어댑터 0건 — <dt>: <사유> …` (사유 = `match_detail`의 `note` — prose 어댑터 · expects 없음) `· 다음: --doc-type <dt> 또는 register --revise` |
| 자격은 있는데 일치 0건 | `지문 일치 0건 — <dt>(누락 n·잉여 m) … · 상세: run.py scan <문서>` — 지금 문면 그대로 |

- `scan()`의 반환에 이미 재료가 다 있다(`not_fingerprintable` · `details[].eligible/note`). **새 계산 0** — 읽지 않던 키를 읽는다.
- `[미선택]` 요약 행(일괄 결과 표)에도 같은 갈래 이름이 간다.

**완료판정 ②**: 어서션(성질) — 네 경우가 **서로 다른 문면**이고, 「없다」 문면은 소재지가 비었을 때만 난다(어댑터가 하나라도 있으면 그 이름이 문면에 있다).

## ③ 확정 화면의 「다음」 = 가이드의 인입 흐름 (칸 1.7)

`cmd_confirm`의 「다음」이 `parse run` · `build` · `(한 번에: ingest-file)` 세 줄인데, 가이드 §4·§5가 사람에게 시키는 흐름은 `ingest-file --dry-run` → `ingest-file`이다(사내에서 「가이드에 없는 명령」으로 읽혔다). 두 줄로 바꾼다:

```
   다음 — 인입 (등록이 그래프를 만들지는 않는다):
     python run.py ingest-file <문서> --doc-type <dt> --dry-run   ← 선택·형태 판정만 본다
     python run.py ingest-file <문서> --doc-type <dt>
```

`parse run`·`build`는 가이드 §5 부품 표에 남는 명령이니 지우지 않는다 — 확정 화면에서만 뺀다. `--doc-type`을 붙인 채로 안내한다: ①이 되면 스캔으로도 고르지만, **방금 확정한 doc_type을 사람이 알고 있는 자리**라 지정이 맞다(P7 — 유일 일치여도 자동 라우팅하지 않는다는 원칙과 같은 결).

**완료판정 ③**: 화면 diff. 어서션 없음(문면).

## ④ 선택 근거 줄에 어댑터 실물 경로 (칸 3.1)

`--dry-run`의 `선택 근거: 사람 지정 --doc-type csvlive` 줄에 **어느 파일이 골라졌는지**(`adapters/csvlive.py` · 또는 내장 소재지 `tests/fixtures/adapters/cp.py`)를 붙인다. 사내에서 「mock 소재지가 뭐냐」가 나온 이유가 이것이다 — 어댑터는 등록부(`data/doc_types.json` → `adapters/<dt>.py`)를 먼저 보고, 없으면 내장 doc_type(cp·pfmea·ipqc — 스키마만 싣고 어댑터는 `tests/fixtures/adapters/`)을 본다. 사람이 등록한 것은 늘 등록부에서 오지만, **화면이 그것을 말하지 않으면 사람은 모른다.**

**완료판정 ④**: 화면 diff — `선택 근거: … ← adapters/csvlive.py`. 어서션 없음.

## ⑤ CSV 전 구간 등가 어서션 — 같은 표는 포맷이 달라도 같은 지식이 된다 (칸 2.1 · 2.9 · 3.2 · 4.x)

지금까지 CSV가 실행으로 확인된 구간은 reader(`test_p1`) · 등록(`test_p3` B62·B64) · 인입 parse(허브 실측 record 4)까지다. **build가 노드를 세우는 것과 질의가 답하는 것을 CSV 출처로 돌려본 적이 없다** — 회귀에 CSV 출처 질의 0건이고, xlsx와 내용이 같은 CSV 표본이 없다(`CP01.xlsx` 33×10 vs `CSV01.csv` 4×4). 파서 뒤는 포맷을 모르니 다를 수 없다는 것은 논리이고, 이 프로젝트는 실행으로 판정한다.

- 표본 쌍: `CP01.xlsx`의 시트를 **같은 내용의 `CP01.csv`**로 저장해 `tests/fixtures/raw/`에 둔다(셀 값 동일 · 헤더 행 동일). 어댑터는 `cp` 하나 — `expects.sheet` 생략(CSV는 생략 · 문서 6 §6.4).
- 어서션(성질) 셋 — 클린 상태에서 두 문서를 각각 등록 없이 `ingest-file --doc-type cp`로 인입해:
  - ⓐ `parsed/<doc_id>.json`이 `format` · `source_locator`의 시트 이름 · `doc_id`를 제외하고 **동일**(records · chunks · status).
  - ⓑ 그래프의 **노드 수 · 엣지 수 · 카테고리별 수가 동일**(골격 확정 상태에서 — 노드 0끼리 같은 것은 판정이 아니다. 어서션 전제에 「노드 > 0」을 넣는다).
  - ⓒ 스모크 질의 12문항(`tests/fixtures/queries.json` — 골든셋 B54와는 별개 자산) 중 cp 출처를 지나는 질의의 **답·근거 id 집합이 동일**.
- 이것이 「CSV는 다른 문서처럼 돈다」의 잠금이다. 이후 누가 포맷 분기를 다시 넣으면(이번이 셋째였다) 여기서 붉어진다.

**완료판정 ⑤**: ⓐⓑⓒ 초록 · **변이** — `reader.read_csv`가 헤더 한 셀을 바꾸도록 심으면 ⓐ가 붉어진다(어서션이 실제로 두 판을 비교한다는 증거) · 노드 수 > 0을 보고에 붙인다.

## 넣지 않는 것
- tsv 표본·어서션 — 사내에 없다(사용자 결정 2026-09-15). `GRID_EXT`의 `.tsv`는 그대로 둔다(reader는 이미 읽는다).
- 유일 일치의 자동 라우팅(P7) — 스캔은 고르고 사람이 지정한다는 원칙은 그대로.
- 내장 doc_type 소재지 폐지 — 별도 판단(mock 트랙이 쓴다).
- 명세 개정 — 문서 6 §6.4·C37이 이미 말한다.

## 순서
**① → ② → ③ → ④ → ⑤.** ①이 없으면 ②의 첫 갈래가 CSV를 삼킨다. ⑤는 ①과 무관하게 돌 수 있으나(`--doc-type` 경로) 마지막에 두는 것은 표본 쌍을 ①ⓑ가 같이 쓰기 때문이다 — 표본은 ⑤에서 만들고 ①ⓑ가 재사용한다. 회차당 4항목을 넘는 것은 ⑤가 새 기능이 아니라 ①ⓑ의 범위를 전 구간으로 넓힌 같은 성질의 어서션이기 때문이다(B65와 같은 예외).
