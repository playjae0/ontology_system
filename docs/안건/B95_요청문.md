# B95 구현 요청문 — 골격 카테고리의 어긋난 집은 노드가 없으면 자동으로 고친다 · 새 카테고리 경고에 이름 규칙 한 줄 · canonical_scope 판정 기준 가이드 · 칸 0.1

> **수신**: 구현 세션 · **발신**: 허브 (2026-10-01 · 사용자 확정 2026-10-01) · **B94 뒤** · 작은 회차.
> **출처 — 사내 첫 적용(2026-10-01 · 사용자 보고)**: 골격을 설비층(equip)으로 옮긴 뒤 `bootstrap`이 「'Process'의 home은 process인데 골격은 equip에 있다 — home을 equip으로 고친다」(ⓖ)로 멈췄다 — 공통 config가 골격이 공정층 폴더에 있던 때 만들어져 집이 옛 값이다. 사용자 원칙(2026-10-01): **공통 config는 사람이 관리하지 않는다 — 결정적으로 따라 나오는 것은 자동**. 또 `canonical_scope`를 무엇으로 채워야 하는지 근거가 안 보인다는 지적 — 층 config는 문서를 보고 만들므로 그 판단 재료가 없다. 허브 답(사용자 수용): 판정 기준은 질문 하나 「**공정을 모르면 뜻이 없는가**」(부품·파라미터 = 넣음 · 공정 자체·불량 유형·영향 = 넣지 않음) · 바탕을 깔 때 한 번 정하고 새 카테고리가 생길 때만 다시 묻는다.
> **허브 실측(2026-10-01 · origin `1ebba33`)**: ①ⓖ는 채운 집이 골격 층과 다르면 노드 유무와 무관하게 멈춘다(`catalog_sync.plan` — `sk_home`) — B92 제거 규칙 「노드 0이면 자동 · 있으면 멈춤」과 결이 다르다. 골격 노드는 늘 골격 층 그래프에 심기므로 어긋난 집 그래프에 그 카테고리 노드가 있는 경우는 드물다(인입이 골격 밖 노드를 만들던 B94 전의 흔적뿐). ②새 카테고리 경고(B94)는 기존 카탈로그만 보이고 이름 규칙(`canonical_scope.bind_categories`) 상태를 말하지 않는다 — 넣어야 할 카테고리를 빠뜨리면(부품) 공정마다 다른 실물이 한 노드로 합쳐지고, 넣지 말아야 할 것을 넣으면(불량 유형) 같은 유형이 공정마다 갈린다 · 노드가 생긴 뒤 바꾸면 재빌드다. ③가이드에 `bind_categories`의 판정 기준이 없다(「어느 카테고리에 좌표 스코프를 붙이나」만 있다).
> **원칙**: 자동 교정은 **어긋난 집 그래프에 그 카테고리 노드가 0일 때만** · 노드가 있으면 지금처럼 멈춘다 · 이름 규칙은 **표시만**(자동 추정 0 · 종료 코드 불변) · 코드에 층 어휘 0 · mock 동작 불변(네 벌 diff 0).
> **명세와의 관계 — 허브 확정 편차**: 문서 3 §3.1의 「ⓖ 채워진 집이 골격 층과 다르다(자동으로 고치지 않는다)」는 이 요청문이 근거다 — 허브가 마감 보고를 받아 [개정] B95로 고친다.

## ① 골격 카테고리의 어긋난 집 — 노드 0이면 자동 교정 (칸 0.1)

- 맞추기(`plan`)에서 골격 카테고리의 채운 집이 골격 층과 다를 때: **채운 집 그래프에 그 카테고리 노드가 0이면** 집을 골격 층으로 고친다 — 화면 한 줄(`공통 config 'Process' home process → equip (골격이 equip에 있다 · process 그래프에 Process 노드 0)`) · 로그 · `common_version` +1. **노드가 있으면 지금의 ⓖ로 멈춘다**(문면에 노드 수를 붙인다 — 「재빌드(`init --fresh` → `bootstrap` → 재인입) 또는 골격을 되돌린다」).
- 처음(파일 없음)은 영향 없음(빈칸 채움 그대로) · `--dry-run`은 계획만 · B92 집 변경 검사와 문면이 겹치지 않게(D-174 ③ 유지).

## ② 새 카테고리 경고에 이름 규칙 한 줄 (칸 0.1)

- B94 경고 블록 끝에 그 카테고리의 이름 규칙 상태를 한 줄: `이름 규칙: '<카테고리>'는 공정 스코프 적용(bind_categories 안) | 미적용 — 공정을 모르면 뜻이 없는 것(공정마다 다른 실물·값)이면 공통 config canonical_scope.bind_categories에 넣는다 · 노드가 생기기 전에 정한다`.
- 표시일 뿐(종료 코드 불변 · 자동 추정 0) · `--dry-run`도 같은 줄.

## ③ 가이드 (같은 커밋)

- **config작성**: `canonical_scope` 자리(186행 근처 · §0-a 표의 `canonical_scope` 행)에 **판정 기준** — 질문 하나 「공정을 모르면 뜻이 없는가」 · 넣으면 생기는 두 효과(이름에 공정 접두 — 공정이 다르면 다른 노드 · 좌표 미해소면 노드를 만들지 않는다) · 예(일반어 — 구성 부품·공정 파라미터 = 넣음 · 공정 자체·불량 유형·불량 영향 = 넣지 않음 — 넣으면 같은 유형이 공정마다 갈린다) · **노드가 생기기 전에 정한다**(바꾸면 재빌드) · 접두는 찾기 위한 키이고 뜻은 관계(`part_of`)가 담는다 · 문서 원래 표기는 별칭으로 남는다.
- **골격작성 §3-a 요청문 틀** 출력 3: 겸 한 줄에 더해 **`canonical_scope.bind_categories` 제안 한 줄**(위 기준으로) · 「층 config에는 `canonical_scope`를 넣지 않는다」.
- `걸어가기` §1-a: ① 화면(자동 교정) · `canonical_scope`는 층 config에서 지우고 공통 config의 `bind_categories`를 기준으로 확인.
- 구조도 `06_손잡이_대장`(0.1 공통 config 행) · `00_칸_대장` · `10_코드_지도`(생성).

**완료판정**: 테스트 세트(창작) — ⓐ 골격 카테고리의 채운 집이 골격 층과 다르고 그 집 그래프에 노드 0 → 자동 교정 · 판 +1 · 로그 · 종료 코드 0 ⓑ 그 집 그래프에 그 카테고리 노드가 있으면 → 멈춤(노드 수 문면) · 그래프 쓰기 0 ⓒ `--dry-run`은 ⓐ 계획을 보이고 쓰기 0 ⓓ 새 카테고리 경고에 이름 규칙 줄(적용·미적용 두 갈래) · 종료 코드 불변 ⓔ mock 네 벌 diff 0.
