> **수신**: 구현 세션 · **발신**: 허브 (2026-10-01 · 사용자 확정 2026-10-01) · **B93 뒤** · 작은 회차.

## ① 공통 config에 쓰는 층 — `used_by` (칸 0.1)

```json
"Failure": {"home": "defect", "used_by": ["defect", "issue"]}
```

- 카테고리마다 `used_by` = 그 카테고리를 `categories`에 선언한 층 전부(이름순). **`bootstrap`이 맞추기(`plan`)에서 층 config로부터 적는다** — 처음 · 추가 · 이미 있는 항목 모두.
- 바뀌면(층이 선언을 더하거나 뺌) 원자 쓰기 · `common_version` +1 · 로그 한 줄(`used_by 'Failure' + issue`). `--dry-run`은 계획만.
- 사람이 손으로 고쳐도 다음 `bootstrap`이 층 config 값으로 되돌리고 로그에 남긴다(「used_by는 층 config에서 온다」).
- **판정은 `used_by`를 읽지 않는다** — 집·제거·겹침·ⓒ검사는 지금처럼 `declared_by`(층 config)에서.
- 레포 mock seed `layers/common.json`에도 `used_by`를 넣는다(mock 맞추기 변경 0 유지 — 자산 해시 갱신).

## ② 새 카테고리 경고 (칸 0.1)

- `bootstrap`(·`--dry-run`)이 **카탈로그에 없던 카테고리를 더할 때**(자동 추가 · 빈칸 추가 · 골격 카테고리 모두) 그 줄 아래에 **기존 카탈로그**를 보인다 — 카테고리마다 `home` · `used_by` · 선언한 층들의 정의문 앞부분.
- 문면 머리(예): `[bootstrap] 새 카테고리 'DefectHistory'(issue) — 같은 뜻의 기존 카테고리가 있으면 그 이름을 쓴다(같은 이름이어야 노드 하나로 모인다):` + 기존 목록.
- **표시일 뿐**(종료 코드 불변 · 막지 않는다) · 로그에도 남긴다. 유사도·LLM 판정은 하지 않는다.

## ③ 골격 카테고리 개체는 조회 전용 (칸 3.3)

- 개체 해소에서 카테고리가 **골격 카테고리**(`catalog_sync.skeleton_layers`의 키 — tree·flat)면: 사전·후보·판정으로 **기존 노드에 매칭되면 지금 그대로** · **신규·불확실 갈래는 노드를 만들지 않는다** → 닫힌 20종 중 맞는 kind로 큐(예: `orphan_attach` — 「골격 대상 미해소」 · 고른 kind와 이유는 가결정) · 판정 대장에 남는다 · 골격 `ALIASES`가 생기면 다음 인입(또는 재시도 배치)이 붙인다.
- 산문 · table의 개체 경로 모두(좌표 `process_ref`·`process_group`은 이미 조회 전용 — 그대로).
- 겸으로 매칭되는 다른 카테고리(예: `Unit`으로 뽑혀 겸 골격 노드에 매칭)는 영향 없음 · 골격이 아닌 카테고리의 신규는 지금 그대로.

## ④ 가이드 (같은 커밋)

- **골격작성 §4 초안 프롬프트 규율 3**: 「골격에는 공정만 — 설비·인자·결함은 넣지 않는다」 → 「골격에는 공정만 넣는다 — 하위 공정(unit 단위)은 공정이다(이름에 unit·설비가 붙어도 넣는다) · 그 아래 구성 기계·부품·인자·결함은 넣지 않는다」.
- **골격작성 §3-a 5번**: 「공정층이 `Process`를 렌즈로 선언해도 …」 → **다른 층(공정층 포함)은 골격 카테고리(`Process`·`Unit`)를 선언하지 않는다** — 골격 이름은 선언 없이 붙고(부착·부모 후보가 골격에서 온다) 관계 패턴에만 쓴다 · 선언하면 골격 밖 이름은 ③으로 큐에 간다. 골격에 없는 노드(Component 등)를 다른 층 문서에서 뽑으려면 그 층이 선언한다(선언 = 뽑아도 된다는 허가 + 정의문 — 노드를 따로 만들지 않는다).
- **골격작성 §3-a 요청문 틀**: 출력 2의 「공정층(Property — Process는 렌즈로만)」 → 「공정층(Property · 부품을 말하면 Component — Process·Unit은 선언하지 않는다)」 · 출력 3 「common.json의 categories — home …」 → 공통 config는 `bootstrap`이 만든다 — 사람(또는 LLM)은 `also` 한 줄만 제안.
- **config작성 §0-a**: 42행의 겹침 예(「공정층도 `Unit`을 말할 수 있다」) → 골격이 아닌 예(불량층·이슈이력층의 `Failure`) · `used_by` 행 · **재사용 규칙**(같은 뜻이면 기존 이름 · 새 이름은 뜻이 다를 때만) · ② 경고 · **config 초안 요청 때 `common.json`을 첨부**(§7 첨부 표에 한 행).
- **걸어가기 §1-a**: 31행 「설비층과 공정층이 함께 선언한 `Unit` → 설비층」 → 공정층은 골격 카테고리를 선언하지 않는다(빈칸이 생기지 않는다).
- `2B_작업가이드` 증상표에 ③의 큐 한 행 · 구조도 `03_구축`(해소 순서 — 골격 카테고리 조회 전용) · `06_손잡이_대장` · `00_칸_대장` · `10_코드_지도`(생성).

**완료판정**: 테스트 세트(창작) — ⓐ `used_by`가 처음·추가·선언 추가/삭제마다 층 config와 같다 · 판 +1 · 로그 ⓑ 손으로 고친 `used_by`가 되돌아간다 ⓒ 판정이 `used_by`를 읽지 않는다(`used_by`를 틀리게 써 둬도 집·제거 결과 같음) ⓓ 새 카테고리 경고에 기존 카탈로그가 나온다 · 종료 코드 불변 ⓔ 골격 카테고리로 뽑힌 골격 밖 이름 → 노드 0 · 큐 +1 · 대장 ⓕ 같은 이름이 골격 별칭이면 매칭 · 골격이 아닌 카테고리 신규는 그대로 ⓖ mock 네 벌 diff 0.
