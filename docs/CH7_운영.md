## 7.1 로드맵 — 4국면과 현재 위치 [확정 — 국면 1 앞 증분 삽입은 가결정]

### 무엇인가 (구조)

```
국면 0  명세 마감 (외부)          ✅ 명세 v1.19 기준 마감 선언됨
   ⚠ 단, 틀 v2.2·v2.3이 그 뒤에 확정됨 → 착수 전 "구현문서 증분" 필요 (아래)
국면 1  외부 구현 (Claude Code, mock)   ← 다음
국면 2  사내 이식 (파서 반입·실데이터)
국면 3  운영·확장 (3층, C 공통 승격)
```

### 규약

1. **국면 1 (외부 구현)** — 기존 5단계: ①core+공정층+mock 인입 ②질의 4단+이원 채널(Q1~Q5·Q8 mock) ③품질층 config-only+층간 연결(**Rule of Three 관찰** — core 무수정 통과가 §3.5 성공 판정. **⑵-③′로 정밀화: 품질층은 기본 내장이 아니라 신규 층 등록 절차의 첫 검증 대상이다 — 카드 J10**) ④플랫폼 연동 ⑤수정 도구+계기판 최소. 병목은 코드 생성이 아니라 **사람 검수 시간**. **여기에 파서 공용 코어 6종(reader·preflight·normalizer·tagger·validator·기본 어댑터)+생성 하네스+어댑터 생성 킷이 추가된다**(2026-07-29 결정 + 세션 N ⑴⑻ 확정, 파서_명세 §3·§9) — 창작 표본으로 어댑터 생성 전 과정을 리허설 통과시킨 상태로 사내 반입하는 것까지가 외부 범위다. 신규 단위 전량은 CH6 6.2 규약 4(n1~n10)가 정본.
2. **[가결정] 국면 1 착수 앞에 "증분 0"이 삽입된다**: 틀 v2.2·v2.3이 국면 0 마감 이후에 확정되었으므로, 신규 단위의 단위 정의·순서·완료판정을 담은 **구현 증분 문서**를 먼저 만든다. 이것 없이 구현문서 v1.16(구 아키텍처)만으로 착수하면 안 된다(CH6 6.2 경계). **세션 N ⑸ 확정으로 증분 0의 재료가 완비되었다**(단위 10종·순서 원칙 4·완료판정 원칙·mock 시나리오 13종 — CH6 6.2·6.3).
3. **국면 2 (사내)** — ①role 배정 실험(첫 작업, 코딩 아님) ②doc_type 스키마 등록(구축 모드 실사용) ③**파서 반입 + 어댑터 생성 세션 실행·검수** — 구판의 "파서 구현(사내 최대 조각)"은 2026-07-29 결정으로 축소되었다: 파서 공용 코어·생성 하네스·어댑터 생성 킷은 **외부 구현·전달물**이며(파서_명세 §9), 사내에서 코딩하는 것은 없고 어댑터는 사내 LLM이 킷으로 생성한다 ④골격 seed 실명칭+골든셋 실데이터(**기준 구성 120 — CH5 5.5 가결정, 실물 제작하며 조정**) ⑤파일럿 인입 수십 건 → 계기판 첫 측정(**BM-25 대조군 병행 — 세션 N ⑹ 확정**) ⑥측정 기반 P7 결정.
4. **국면 3 · PoC 완료의 정의**: 공정층 plateau 도달 + 품질지식층 연결 동작 + Q1~Q5 골든셋 통과 + 계기판 가동. 이후는 운영 — 지속 인입, 큐 소화, 3층 결정(R5), 3층 진입 시 C 공통 승격.
5. **범위 원칙 (사용자 확정)**: 구현은 **기능 축소 없이 전 기능**을 대상으로 한다. 잘게 가는 것은 빌드 단위이지 범위가 아니다.

### 경계와 오해

- "국면 0 마감"은 **명세 v1.19 시점의 마감**이다. 틀 v2.2·v2.3 확정분은 명세에 아직 미분해 상태이며(7.3), 정본은 틀 > 챕터 > 명세 순서다 — 마감 선언이 틀 확정분을 무효화하지 않는다.

### 원천

## 7.3 문서 체계 — 정본 관계와 파일 대장 [확정]

### 무엇인가 (구조)

```
[정리층 — 현재 정본]
  00_틀_확정본(현행 v2.5) > 챕터 CH1~CH7(서술완료분) > [원천층] 명세(골격 챕터의 소유 절)
  00_불변식_카드(현행 v12)  — 불변식 ~90조. 정합 검사의 기준
  00_챕터_대장         — 챕터↔명세 분할표·서술 규격·검사 로그·세션 프로토콜
  00_용어_대장         — 용어 ~65개. "합의된 적 없는 단어" 방지
[원천층 — 분해 대기]
  ontology_system_명세(v1.19) · role_어휘_정의서 · ontology_system_구현용문서(v1.16)
[작업층]
  파서_명세(§1~§7·§9 확정)
  claude/구현트랙_PROGRESS_미러.md(구현 트랙 정산 미러 — **16회차 정본화**, 이 폴더의 유일 파일. 구 chapters/ 승격판(14-B)은 폐기됨. 미러는 보고이며 **결정 번호를 적지 않는다** — 장부는 레포 DECISIONS.md 하나)
  안건/(판정 대기 안건서·세션 운반물 — 구 claude/의 안건 운반 역할 대체, claude/는 미러 1파일 전용으로 존치(16회차). **정본 아님**, 판정 종결분은 archive/로. 명세트랙_여는프롬프트·논의안건서_적재전결정3건)
  참조/(외부 조사물 — 벤치마크 3부작·구현 참조. **정본 아님, 폐기도 아님**. 판정 종결분이 아니라 현행 정본이 인용하는 근거물이므로 archive/와 구분한다. 논의 없이 명세에 반영하지 않는다 — 쟁점 5(07-25). 핵심장치5_왜필요한가·그래프생성로직_구현참조·외부벤치마크_종합)
  archive/(폐기·이력 보관. 안건_핸드오프_M1_판정반영·세션기록_raw_mock_제작·반영검토후보_최종·메인스트림_전체정리)
```

### 규약

1. **정본 우선순위: 틀 > 챕터(서술완료) > 명세.** 충돌하면 상위가 이긴다. 명세 §가 챕터 서술과 다르면 그것은 "명세가 아직 분해 전"이라는 뜻이지 두 정본의 대립이 아니다.
2. **챕터 파일이 원천, 덱은 파생이다.** 관리 PPT는 챕터 머리표를 렌더러(관리덱_build_mgmt.js)가 읽어 생성한다 — 덱을 직접 고치지 않는다.
3. **버전은 파일명이 아니라 문서 머리에** 둔다(`version:` 필드 필수 — 세션 1 교훈: 버전 없는 챕터는 낡음이 늦게 발견된다). 파일명 규칙: `00_` 기준 문서 / `CH{n}_` 챕터 / `archive/` 보관.
4. **상태 태그 4종**을 절 단위로 단다: `[확정]` / `[가결정]`(전진용 임시 결정 — DECISIONS 기록) / `[보완필요]`(방향 확정·상세 미서술) / `[미결]`(판정 주체·시점 지정).
5. **명세 v1.19의 분해·클린업은 최후 작업이다.** 챕터가 전부 서술완료·안정된 뒤, 명세를 "챕터 소유 절의 원문 보관소"에서 "챕터로의 참조 목차"로 축소한다. 그 전까지 명세는 골격 챕터의 소유 절에 한해 정본이다.
6. **세션 프로토콜(대장 §6)**: 새 세션은 세 문서(틀·카드·용어)를 먼저 물려받고, 여는 문장에서 원천 대조를 수행한다.

### 원천

## 7.4 결정 현황판 [살아있는 절 — 결정마다 갱신]
