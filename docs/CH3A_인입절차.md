## 3.1 두 체제와 세 단계 [확정]
 
### 무엇인가 (구조)
 
운영 모드의 처리는 문서의 성격에 따라 두 체제로 갈리고, 비정형 체제는 세 단계로 나뉜다.
 
```
정형 (CP·PFMEA 표):   파싱 ──────────────────────→ 구축     (LLM은 개체 판정에만)
비정형 (PPT·Word 산문): 파싱 → 추출 (LLM: 내용 파악) → 구축   (구축 LLM은 연결에만)
```
 
| 단계 | 하는 일 | LLM |
|---|---|---|
| **파싱** | 형태 처리 — 포맷을 읽어 계약 JSON으로 (CH2.2). 비정형은 청크 분할(등록된 규칙의 결정적 실행)·이미지 요약·좌표 태깅까지 | 이해 보조만 (CH2.3) |
| **추출** (비정형만) | 내용 파악 — 청크를 읽고 ①개체 후보(닫힌 카테고리에서 선택) ②관계 후보(닫힌 관계 목록에서 선택 — 3.4) ③부착 이름(attach_to)을 출력 | 여기가 내용 이해의 자리 |
| **구축** | 연결 — 개체 판정(3.3), 부착·엣지 생성(3.4), 값 저장(3.6), 커밋과 큐(3.7) | 개체 판정에만 |
 
**분업의 원리 (틀 Q2·§3)**: 청크 분할은 **구축 모드에서 생성된 규칙이 결정적으로** 하고, 내용 파악은 추출 LLM이, 연결은 구축이 한다. 추출 LLM과 구축 LLM은 역할이 다르다 — 전자는 "이 글에 무엇이 있나"를, 후자는 "이것이 기존의 무엇과 같은가"를 판단한다. 두 판단을 한 호출에 섞지 않는 이유: 섞으면 실패 지점을 구분할 수 없고(추출이 틀렸나 연결이 틀렸나), 재실행 단위도 분리되지 않는다.
 
**청크 분할의 정확한 구조 (틀 Q2 — v1 서술 정정)**: "분할은 로직"이라는 말은 *운영 중에* 로직이라는 뜻이지, 분할 기준을 사람이 손으로 정한다는 뜻이 아니다. 기준을 정하는 것은 LLM이며, 다만 **문서 양식당 1회(구축 모드)** 한다.
 
```
[구축 모드] LLM이 문서 구조 관찰 → 분할 규칙을 코드로 생성 → 사람 검수 → 고정
[운영 모드] 고정된 규칙이 결정적으로 분할 — 매 문서마다 LLM에게 묻지 않는다
```
 
운영 중 매번 물으면 같은 양식인데도 결과가 흔들려 청크 경계가 문서마다 달라진다. 분할 신호는 타입별로 다르다: PPT=슬라이드, Word=스타일 헤딩 레벨, PDF=제목 서식·여백, **Excel=계층 판정 필요**(들여쓰기 값·열 위치·번호 패턴·서식·병합·빈 셀). 엑셀은 신호가 섞이면 100% 판정이 안 되므로 세 겹으로 받는다 — ①검수 시 계층 트리로 렌더해 눈으로 확인 ②운영 중 규칙 불일치 행은 계층 미확정 표시 + 큐 ③**폴백: 문서 계층 ≠ 그래프 계층**이므로(카드 M8) 계층 복원이 어려우면 평면으로 읽고 공정좌표만 태깅해도 그래프는 성립한다.
 
### 규약
 
1. **정형에는 추출 단계가 없다.** 표의 컬럼 의미는 등록 때 확정되었으므로(매칭 스키마), role 선언이 추출을 대체한다. LLM에게 아는 것을 추측시키지 않는다.
2. **추출의 입력은 좌표 태깅된 청크이고, 출력은 후보다** — 개체 후보 + 관계 후보 + 부착 이름. **추출 출력이 직접 그래프가 되는 일은 없다.** 모든 후보는 구축의 판정(3.3)과 게이트(3.4)를 거친다.
3. **추출 규칙 (프롬프트 계약)**: 이 청크가 **주제로서 서술하는** 개체만 추출한다. 스치는 언급·수치·날짜·측정값은 추출하지 않는다(수치는 노드가 아니라 값이다 — 3.6). 카테고리는 층의 닫힌 목록+정의문에서 선택하고, 어디에도 맞지 않으면 추출하지 않는다. 애매하면 빼는 쪽으로.
4. **추출 산출물은 체크포인트다.** 추출 결과는 JSON으로 저장되어 구축과 분리 재실행이 가능해야 한다 — 구축이 실패하거나 재빌드될 때 추출을 다시 돌리지 않는다. 그 JSON의 필드 계약은 **3.11**이 소유한다.
5. **인입 진입 시 중복 문서를 차단한다 (틀 v2.2 A6).** 문서 내용 해시(`doc_hash`)를 계산해 기존과 대조하고, **같은 해시가 다른 `doc_id`로 이미 있으면 인입을 보류하고 사람에게 확인**을 요청한다(파일명·크기·기존 doc_id를 함께 제시). 파일명과 크기는 판정 기준이 아니라 참고 표시다 — 파일명은 바뀌고 크기가 같아도 내용이 다를 수 있으므로 판정은 내용 해시로 한다. **같은 doc_id로 다시 들어오는 것은 중복이 아니라 재인입**(정상 경로, CH3B 3.8)이며 이 검증에 걸리지 않는다. 막지 않으면 같은 내용의 청크가 두 벌 생겨 검색 결과가 중복된다(의미 노드는 판정이 매칭시키므로 그래프 구조는 오염되지 않는다). 계산 주체는 에이전트다(틀 A7-2) — 인입 검증의 최종 순서는 ①doc_hash 대조 ②근거 축 id 계산 ③필드 검증(CH2 2.8).
### 경계와 오해
 
- **"비정형은 LLM이 다 한다"가 아니다.** 비정형에서도 청크 분할은 로직이고, 관계의 커밋은 게이트(코드)이고, 판정 실패는 큐(사람)다. LLM이 하는 것은 두 종류의 판단(내용 파악·동일성)뿐이다.
- **추출은 독립 단계로 확정되었다 (틀 Q1).** 파서 안도 구축 파이프라인 안도 아니다. 근거: ①추출은 비싸고 구축은 싸므로 재빌드 때 추출을 다시 돌리지 않으려면 산출물이 독립 체크포인트여야 한다 ②파서=형태 원칙이 지켜진다 ③플랫폼에서 "파싱 완료 → 추출 중 → 구축 대기"가 각각 상태를 갖는 단계로 보인다(카드 P-1).
- **청크 분할 기준의 실측 정확도(특히 엑셀 계층)는 사내 검증 대상이다** — 규칙 생성 구조 자체는 확정이고, 남은 것은 실물에서 얼마나 맞는지다(R4).
### 원천
명세 §5.5(개요), §5.4-1(추출 프롬프트 — 출력 확장은 개정 대기). 틀 Q1·Q2·A6·A7.

## 3.2 2-pass — 문서 단위 처리 [확정]
 
### 무엇인가 (구조)
 
한 문서의 인입은 두 번의 통과로 처리한다.
 
- **Pass 1 (해소)**: 문서 전체의 anchor·entity를 먼저 전부 해소해 버퍼에 담는다. 노드 생성/매칭이 여기서 일어난다.
- **Pass 2 (부착)**: 그 다음에 attribute·content·edges를 적용한다. 값 저장·describes 연결·엣지 생성이 여기서 일어난다.
### 규약
 
1. 부착(Pass 2)은 해소(Pass 1)가 끝난 뒤에만 시작한다 — 문서 안에서 뒤에 나오는 개체를 앞의 행이 참조해도 문제가 없다.
2. 이 분리 덕에 부착 실패의 원인이 구분된다: Pass 1에 없는 대상을 가리키면 "진짜 미해소"(큐로), 있는데 실패하면 구현 결함.
### 경계와 오해
 
- **2-pass는 문서 단위다.** 코퍼스 전체를 두 번 도는 것이 아니다. 문서 간 연결은 사전(3.3)과 재시도 배치(3.4)가 맡는다.
- 비정형에서 추출 단계(3.1)는 Pass 1 이전에 끝나 있다 — 2-pass의 입력은 정형의 record든 비정형의 추출 후보든 동일한 "해소 대상 목록"이다.
### 원천
명세 §5.5-1.

## 3.3 개체 판정과 동의어 사전 — "같은 개념인가" [확정]
 
### 무엇인가 (구조)
 
entity 값 하나가 노드가 되기까지의 경로:
 
```
표면형 → ①사전 조회 → (미스) ②후보 검색 → ③LLM 동일성 판정 → 3분기
```
 
- ①**사전 조회**: 전 층 공유 동의어 사전(dictionary.json)에서 표면형 → 노드 후보를 찾는다. 결정적·무LLM. 층 간 표면형 충돌은 허용하고 호출자가 카테고리·층으로 선별한다.
- ②**후보 검색**: 사전 미스 시 임베딩 유사도로 후보를 모은다. **판정용 임베딩은 저장하지 않는다** — 언제든 재계산 가능한 파생물이다(P5).
- ③**판정**: LLM이 "같은 개념인가"를 판정한다. 프롬프트에는 층의 카테고리 정의문과 표기 변형 안내가 들어가고, 판정 기준은 비대칭이다 — **확신이 없으면 uncertain**.
### 규약
 
1. **판정 3분기**: 매칭(≥0.85) → 기존 노드에 alias 자동 누적 / 신규 → 자동 생성(status=auto + provenance + auto_node 큐) / 불확실 → **신규로 생성 + uncertain_match 큐**. 불확실을 병합하지 않는 이유: 중복 2개는 병합이 쉽고 오병합은 사전 오염+복구 곤란 — 되돌리기 쉬운 쪽으로 틀린다.
2. **임계는 0.85 단일이다.** 이중 임계 등 세분화는 판정 보류율 데이터가 쌓인 뒤에만(P7).
3. **카테고리 불일치 안전망**: 추출된 카테고리와 최상 후보의 카테고리가 다르면 match를 금지한다. "노칭"(Process)과 "노칭 정밀도"(Property)가 유사도로 붙는 사고를 구조적으로 차단.
4. **alias는 매칭이 성립할 때만 누적된다** — 사전이 커지는 유일한 경로. 질의에서 온 표현은 배우지 않는다(P6).
5. **사전 등재에는 provenance가 필수다** — 이 표기가 어느 문서에서 왔는지 없이 사전에 들어가는 항목은 없다.
### 경계와 오해
 
- **판정은 "표기가 비슷한가"가 아니라 "같은 개념인가"다.** "노칭정밀도"와 "노칭 정밀도"는 표기 차이(매칭)지만, "cathode 노칭 프레스"와 "anode 노칭 프레스"는 표기가 거의 같아도 다른 노드다(3.5 극성). 그래서 최종 판단이 문자열 규칙이 아니라 LLM이다.
- **판정과 추출은 다른 지점이다.** 추출(3.1)은 "무엇이 언급됐나", 판정은 "그것이 기존의 무엇인가". 운영 시점 LLM 판단 지점은 이 둘뿐이다(3.10).
- **사전은 시스템의 영속 지식이다**(P4). 그래프가 날아가도 사전이 있으면 재인입으로 복원되고, 사전이 오염되면 이후 모든 판정이 오염된다 — 그래서 질의 미학습·provenance 필수·Tier1 보호가 전부 사전을 지키는 규칙들이다.
### 원천
명세 §5.4-2, §5.5-2, §8-R2. 카드 E1~E5.

## 3.4 관계의 생성 — 4경로와 커밋 게이트 [확정 · 명세 §7-2 개정 대기]
 
### 무엇인가 (구조)
 
그래프에 엣지가 생기는 경로는 넷뿐이며, 넷 모두 같은 관문을 지난다.
 
| 경로 | 관계를 정하는 자 | 예 |
|---|---|---|
| ① seed | 사람 (골격 파일) | 공정 트리의 part_of·precedes |
| ② edges 선언 | 스키마 (정형 — 행 구조가 관계) | 설비 ─has_property→ 관리항목 |
| ③ 추출 후보 | **LLM이 닫힌 관계 목록에서 선택** (비정형) | "이물 유입 ─causes→ 절연 파괴" 후보 |
| ④ 자동 규칙 | 코드 (결정적 패턴) | mirrors (극성 대칭, 3.5) |
 
**커밋 게이트**: 어느 경로의 관계든, 그래프에 쓰이기 전에 `(출발 카테고리, 관계, 도착 카테고리)` 패턴 선언과 대조된다.
 
```
관계 후보 (src_cat, rel, dst_cat)
  패턴 안                → 커밋
  패턴과 방향만 반대       → 커밋하지 않고 direction_conflict 큐 (자동으로 뒤집지 않는다)
  관계는 선언됐으나 패턴 밖 → 거부 + 사유 기록 (invalid_pattern)
  관계 자체가 미선언       → 발생 불가 (③이 닫힌 목록 선택이므로) — 방어적으로 거부 + 기록
```
 
①②④는 정의상 패턴 안이므로 게이트가 항상 통과된다 — 게이트는 이들에게 무비용 검증이고, ③에게 실질 관문이다. **거부는 버리는 것이 아니라 기록하는 것이다**: 거부 사유별 건수가 카테고리·관계 체계의 커버리지 신호가 된다.
 
### 규약
 
1. **LLM은 관계 타입을 발명하지 않는다.** ③에서 LLM이 하는 것은 층에 선언된 관계 목록(예: 품질층 causes·affects·occurs_in·controlled_by) 중에서 **선택해 출력**하는 것까지다. 목록 밖 관계는 출력 형식상 존재하지 않는다.
2. **자동 방향 교정 금지.** 후보의 방향이 패턴과 반대면(예: 공정→불량으로 causes) 뒤집어 커밋하지 않는다 — 인과 그래프에서 방향 반전은 틀린 사실을 확신 있게 기록하는 것이다. 큐에서 사람이 판정한다.
3. **attach_to는 ③의 폴백이다.** 추출 LLM이 관계까지 고르지 못하면 부착 대상의 **이름만** 출력한다(attach_to). 해소는 개체 판정 파이프라인(3.3)을 재사용하고, 관계는 게이트의 기본 패턴표(카테고리쌍→관계 매핑: Unit→Process=part_of, Property→Unit·Process=has_property)가 결정한다.
4. **부착 폴백 (규칙 B)**: 부착 대상이 없거나 미해소면 행/청크의 공정좌표에 부착한다 — 오류가 아니라 저해상도이며, 더 정밀한 소속이 확보되면(정형 edges·attach 해소·재시도 성공) 보강된다.
5. **미해소 attach는 orphan_attach 큐 + 주기 재시도 배치.** 재시도는 판정 파이프라인을 그대로 타고, 확신되면 자동 부착·불확실만 사람에게.
6. **동종 카테고리 쌍의 방향은 출처가 필요하다 (일반 규칙 — 틀 v2.2 A3).** 이종 쌍(Unit→Process 등)은 카테고리 조합 자체가 방향을 함의하므로 매핑이 방향을 준다. **동종 쌍(Failure→Failure 등)은 두 방향이 같은 매핑 키로 붕괴하므로 매핑이 방향을 줄 수 없다.** 따라서 방향성 있는 동종 쌍 관계는 방향 출처가 명시된 경로에서만 커밋된다 — ①seed(사람이 방향 포함해 심음) ②edges 선언(정형: `{from: cause, relation: causes, to: failure_mode}` — 필드 구분이 방향). **③비정형 추출 후보는 커밋하지 않는다**: LLM이 (출발, 관계, 도착) 순서로 출력하므로 방향 출처 자체는 있으나, **게이트가 검증할 수 없다**(동종 쌍은 양방향 모두 패턴 안). 후보는 버리지 않고 `direction_unverifiable` 큐에 근거 청크와 함께 보존하고, 사람이 방향을 확인하면 커밋한다. **대칭 관계(mirrors 등)는 이 제약 밖**이며, 관계 목록 선언 시 각 관계의 대칭 여부를 표시한다. **재인입 시 이 큐 항목은 회수 후 재생성한다** — 근거 문서가 개정되면 미확인 후보를 제거하고, 재추출되면 새로 등록한다(기존 항목을 수정하는 재평가 방식을 쓰지 않는다). 사람이 방향을 확인한 후보는 이미 커밋되어 큐를 떠났으므로 회수로 잃는 것이 없다. 이는 **문서에서 유래한 모든 후보성 큐 항목의 일반 규칙**이다(사람의 판단이 기록된 항목은 보존한다). 골든셋으로 방향 정확도가 측정되고 허용 수준이면 자동 커밋으로 승격할 수 있다(P7, R7).
7. **재부착 3분류**: (a) 같은 출처의 정밀화 = 자동 갈아끼움(저해상도 엣지의 해당 provenance 회수 — 단 2홉 도달성 검증 통과 전에는 보류) / (b) 문서끼리 충돌 = attach_conflict 큐, 판단 전에는 먼저 확보된 부착 유지 / (c) 사람의 정정 = 툼스톤(3.8).
### 경계와 오해
 
- **운영 중 새 관계가 생기는 일은 없다 (카드 I7).** 게이트 거부가 잦다면 그것은 "새 관계가 필요하다"가 아니라 "관계 목록이 부실하다"는 신호이고, 대응은 운영 중 생성이 아니라 층 config 개정(구축 모드 재진입)이다. 그래서 **관계 목록을 구축 모드에서 충실히 만드는 것**이 이 설계에서 가장 중요한 준비 작업이다.
- **이 절은 §7-2의 폐기가 아니라 일반화다.** "스키마 밖 관계는 그래프에 들어올 수 없다"는 보증은 문장 그대로 유지된다. 바뀐 것은 보증의 방식이다 — 구판은 LLM이 관계를 아예 출력하지 못하게 해서 보증했고, 신판은 닫힌 목록 선택+게이트 대조로 보증한다. 구판의 카테고리쌍 매핑은 "쌍당 관계 1개인 패턴표"로서 게이트의 특수형이었다.
- **왜 바꾸나**: 같은 카테고리끼리의 관계는 매핑이 원리적으로 결정 불가다 — Failure→Failure 인과의 방향이 그 사례이고, 명세 스스로 §15.4에 한계로 기록해 두었다. 닫힌 목록 선택은 그 빈칸의 **절반**(관계 타입)을 채운다. 나머지 절반(방향의 검증)은 게이트가 못 하므로 규약 6이 큐로 받는다.
- **§15.4의 "사내 확인 항목"은 삭제 대상이다.** 동종 쌍 방향 문제는 사내 문서를 봐야 아는 것이 아니라 **우리 자료구조의 성질**이므로 확인 항목이 아니다 — §15.4의 해당 문구는 규약 6의 일반 규칙 참조로 교체하고, §15.8·§13의 대응 항목은 삭제한다(명세 v1.19).
- **Failure 병합은 유지한다.** 고장모드와 고장원인을 쪼개면 같은 현상이 문서의 행 위치에 따라 두 노드가 되어 causes 연쇄가 끊긴다(노드 유일성 위반). **원인이냐 모드냐는 노드의 속성이 아니라 엣지에서의 위치다.** (FailureEffect는 별개 카테고리이고 affects는 이종 쌍이므로 이 논의와 무관하다.)
- **정형은 아무것도 바뀌지 않는다.** 표 문서의 관계는 여전히 edges 선언이 정하고 LLM은 개입하지 않는다.
- **게이트는 LLM이 아니다.** 패턴 대조는 코드의 결정적 연산이다. "LLM이 관계를 검증한다"가 아니다.
### 원천

## 3.10 LLM 역할 — 전역 지도 (확정판) [확정 · 명세 §7 개정 대기]
 
### 무엇인가 (구조)
 
"LLM이 어디까지 하나"의 전체 답이 한 표가 되었다. 원리: **사람=구조의 확정, 규칙(코드)=커밋·게이트·순서, LLM=식별과 초안 제안.** 그리고 시점 원리: **설계는 과감하게(1회+검수), 운영은 보수적으로(무검수+안전망).**
 
| 주체·단계 | 설계·등록 시점 (구축 모드 · 1회 · 사람 검수) | 운영 시점 (운영 모드 · 매 문서 · 무검수) |
|---|---|---|
| **파서** | **어댑터 코드 생성** — 표본 관찰 (정형 head ~10줄 / 비정형 구조 관찰 → 분할 규칙 생성) | 이미지 요약 · 좌표 태깅(닫힌 목록 선택). **청크 분할은 LLM이 아니다** — 등록된 규칙의 결정적 실행(카드 M6, I6 정정판 v5) |
| **등록(스키마)** | **메타데이터·매칭 스키마 초안 + (층 신설 시) config 초안** — 확정은 사람 | — (조회만, LLM 없음) |
| **추출** (비정형) | 프롬프트·정의문은 사람이 확정 | **내용 파악** — 개체 후보(닫힌 카테고리 선택) + 관계 후보(닫힌 관계 목록 선택, 3.4) + 부착 이름 |
| **구축** | — | **개체 판정**(같은 개념인가)만. 게이트 대조·엣지 생성·커밋·순서는 전부 코드 |
| **구조 개정** | — | 골격 빈틈 **감지·제안**(3.9) — 반영은 사람 |
| **질의** (CH5) | 프롬프트·템플릿은 사람 | 답변 생성 1지점 — 그래프를 직접 읽지 않고 시스템이 고른 근거만 받음 |
 
**발명 금지 3종 (전 지점 공통, 시점 무관)**:
1. 관계 타입 — 선언된 목록에서 선택만 (I5)
2. 카테고리 — 운영 중 선택만, 설계 시점 초안은 사람 확정 (I3)
3. 골격 — 제안까지, 반영은 사람 파일 경유 (P2)
**LLM이 아닌 것 (착각 주의)**: 모드 판별(등록 여부 조회), 커밋 게이트(패턴 대조), 관계 생성 경로 ①②④, mirrors, 재인입 회수, 2-pass 순서, 청크 분할의 운영 실행 — 전부 코드의 결정적 연산이다. 제어 흐름은 코드가 소유한다(I4).
 
### 규약
 
1. 운영 시점의 LLM 판단 지점은 **추출(내용 파악)과 개체 판정(연결) 두 곳**이다. 구조 개정 감지는 배치성 제안 작업으로 이 둘과 별도이며, 어느 것도 그래프를 직접 쓰지 않는다. (파서의 이미지 요약·좌표 태깅은 그래프 판단이 아니라 입력 정돈이다 — 오류의 착지점이 orphan 큐로 지정되어 있다.)
2. LLM 출력이 검증 없이 그래프가 되는 경로는 존재하지 않는다 — 추출 후보는 판정+게이트를, 스키마·config 초안은 사람 검수를, 구조 제안은 사람 반영을 거친다.
3. 실수의 착지점이 전부 지정되어 있다: 오태깅→orphan_anchor, 오추출→판정에서 걸러짐/게이트 거부 기록, 오판정→uncertain 큐 또는 중복(병합 가능), 스키마 오류→unknown_field. **안전망이 못 받는 위치에 LLM을 두지 않는 것**이 배치의 원칙이다.
### 경계와 오해
 
- **"LLM 자율 에이전트"가 아니다.** LLM이 파이프라인을 조종하거나 도구를 골라 쓰는 구조가 아니다 — 지정된 지점에서 지정된 형식의 판단만 한다. 재현·감사 가능성이 이유다.
- **대외 메시지와의 정합**: 경영진 보고의 "LLM 2층위(설계=구조 생성 / 운영=판단만)"는 이 지도의 요약으로 그대로 유효하다. "관계는 LLM이 결정 안 함"은 "관계는 시스템이 보증함(선언된 패턴 밖은 못 들어옴)"으로 다듬으면 더 정확해진다.
- **이 표는 틀 §3(전역 지도)과 같은 내용이어야 한다** — 다르면 틀이 이긴다. 이전 판의 "운영 시점 청크 분할 보조"는 M6과 충돌하는 서술이었고(세션 1에서 카드 내부 모순으로 검출) 카드 v5의 I6 정정과 함께 제거되었다.
### 원천
00_틀_확정본 §3. 카드 I1~I9(I6은 v5 정정판), M1~M6. **명세 §7(7-1·7-2·7-5·7-7)과 §5.4-1·§6.5는 이 절과 3.4, CH2.3·2.6의 내용으로 개정 대기(v1.19).**

## 3.11 추출 후보 JSON — 체크포인트 계약 [확정 — 세션 N ⑶, 2026-07-30]
 
### 무엇인가 (구조)
 
추출 단계(3.1)의 산출물이자 구축 단계의 입력인 파일의 계약. 파서↔에이전트 사이에 계약 JSON(CH2.2)이 있듯, 추출↔구축 사이에 이 계약이 있다(P1 — 단계 간 결합은 파일로만). 이것이 있어야 ①구축 재실행이 추출을 다시 돌리지 않고 ②플랫폼이 "추출 완료" 상태를 파일 존재로 판정하고 ③추출 규칙 개정의 영향 범위가 파일 버전으로 추적된다.
 
```json
{
  "doc_id": "PPT01",
  "stage": "extract",
  "adapter_version": "1.0",
  "prompt_version": "e-1.0",
  "config_version": "process-3",
  "layer": "process",
  "extracted_at": "...",
  "candidates": [
    {
      "chunk_id": "PPT01:a3f8...",
      "entities":  [ {"surface": "노칭 프레스", "category": "Unit"} ],
      "relations": [ {"src": "이물 유입", "rel": "causes", "dst": "절연 파괴"} ],
      "attach":    [ {"surface": "금형 클리어런스", "attach_to": "노칭 프레스"} ]
    }
  ]
}
```
 
- `chunk_id` = 에이전트가 계산한 정본 id — 인입 검증 ②단계(CH2 2.8)에서 이미 부여되어 있으므로 추출 전에 존재한다.
### 규약
 
1. **후보는 표면형으로만 말한다.** 노드 id 참조 금지 — "그것이 기존의 무엇인가"는 구축(판정)의 몫이며, 추출 파일에 노드 id가 들어가는 순간 추출이 그래프 상태에 의존하게 되어 체크포인트의 독립성이 깨진다.
2. **confidence 필드는 두지 않는다.** 판정·게이트가 별도 단계로 존재하므로 추출 자신의 확신도는 소비처가 없다 — 쓰이지 않는 숫자는 언젠가 잘못 쓰인다(P7). 애매하면 출력하지 않는 것(3.1 규약 3)이 확신도 표현을 대체한다.
3. **span·오프셋 필드도 두지 않는다.** LLM에게 문자 오프셋을 출력시키면 오프셋 자체가 자주 틀려 검증 코드가 또 필요해지고, 청크는 이미 작은 근거 단위다(질의의 수집·답변 근거도 청크 단위). 큐·검수 화면의 근거 표시는 **청크 전문 + 표면형 문자열 매칭 하이라이트**로 한다 — 추가 필드 0으로 같은 효과. 청크가 길어 하이라이트가 모호한 사례가 실측되면 인용문(quote) 필드를 그때 검토한다(P7). [⑶-①]
4. **재현성 3입력을 전부 버전으로 기록한다**: `adapter_version`(입력 청크가 잘린 규칙 — 봉투에서 복사) / `prompt_version`(추출 지시문 템플릿 — 전 층 공통의 사람 확정 관리 자산) / `config_version`(주입된 층 어휘 — 카테고리·정의문·관계 목록의 버전). 지시문과 층 어휘는 **따로 개정되는 별개 자산**이므로 한 번호에 뭉뚱그리지 않는다. [⑶-②]
5. **프롬프트·config 개정은 이후 인입 문서에만 적용한다** — 분할 규칙 변경(N6)과 동형. 기존 체크포인트의 자동 소급 재생성 경로는 두지 않는다(L9: 시스템이 자동으로 기존 문서를 다시 읽는 경로는 없다). 특정 문서의 추출을 소급 개선하려면 **그 문서만 doc_id 재인입**한다. 버전 기록(규약 4)이 있으므로 세대가 섞여 있어도 감사 가능하다. [⑶-②]
6. **attach_to의 해소 범위는 문서 해소 버퍼 전체(2-pass Pass 1) + 사전이다 — 청크 경계 제약은 없다.** 추출 LLM은 자기 청크 안에서 본 이름만 출력할 수 있지만, 그 이름이 같은 문서 **다른 청크**에서 해소된 개체와 붙는 것은 정상 경로다. 미해소면 orphan_attach 큐 + 공정좌표 폴백(3.4 규약 4·5) — 새 메커니즘이 아니라 기존 규칙의 명시화다. [⑶-③]
7. **재인입 시 그 doc_id의 추출 체크포인트는 무효화·재생성한다** — 청크가 바뀌었으므로. 회수 후 재생성 일반 규칙(3.4 규약 6)과 같은 결이다.
8. `relations`의 (src, rel, dst)는 LLM 출력 순서가 곧 방향 주장이다 — 검증은 게이트가(이종 쌍), 동종 쌍은 direction_unverifiable 큐가 받는다(3.4).
### 프롬프트 자산의 위치 (규약 4 부속 — 오해 방지)
 
추출 실행의 입력 자산은 **각자 제자리에서 각자 버전**을 갖고, 실행 시 조립된다:
 
| 자산 | 물리 위치 | 버전 |
|---|---|---|
| 지시문 템플릿 (전 층 공통) | 프롬프트 파일 — 사람이 확정하는 관리 자산(틀 §3) | `prompt_version` |
| 층 어휘 | `layers/{층}/config.json` — 층 폴더에는 코드 0 (B2) | `config_version` |
 
한 파일에 모으지 않는 이유: 층 어휘가 코드·프롬프트 파일에 들어가면 **B1(core 코드에 층 어휘 한 글자도 금지)이 깨진다.** 매칭 스키마(정형 role 번역)와 어댑터 스켈레톤(등록 세션·⑻킷)은 **추출의 입력이 아니다** — 이 절과 무관한 별개 자산이다.
 
### 경계와 오해
 
- **파서는 이 파일을 읽지도 쓰지도 않는다.** 계약은 두 개다 — **계약 A**(파서 출력 JSON: 파서↔에이전트의 경계, 정본 CH2 2.2)와 **계약 B**(이 절: 에이전트 내부의 추출↔구축 체크포인트). 파서의 일은 계약 A에서 끝난다. 파서가 계약 B를 알게 되면 층 어휘가 파서로 새는 통로가 되어 "파서는 형태만"(Q3)이 깨진다. [⑶-⓪]
- 추출 파일은 그래프가 아니다 — 모든 후보는 판정(3.3)과 게이트(3.4)를 거쳐야 그래프에 쓰인다.
- 확정 이력: 초안의 "`prompt_version` = 프롬프트·어휘 주입의 버전"은 따로 개정되는 두 자산을 한 번호에 뭉뚱그린 결함이었다 — `config_version` 분리로 정정(⑶-②). 초안의 논의 지점 ①(span)은 불채택, ③(청크 밖 attach)은 "계약에 등장할 필요가 없는 질문"으로 판명 — 해소 범위 규칙(규약 6)이 흡수한다.
