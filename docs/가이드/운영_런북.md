# 운영 런북 — 사내에서 치는 순서

> **누가 읽나**: 사내에서 시스템을 돌리는 사람. 이 문서 하나를 위에서 아래로 따라간다. 단계마다 **할 일 → 칠 명령 → 확인할 것 → 막히면**이다.
> **같이 쓰는 문서**: 사내 LLM에 넘기는 [골격 팩](팩/1_골격/골격_팩.md) · [층 config 팩](팩/2_층config/층config_팩.md) · 막혔을 때 [2B 작업가이드](2B_작업가이드.md)(명령 옵션 · §7 증상표 — 단계 번호가 이 런북과 같다) · 화면 한 줄의 뜻은 [인입 이해 가이드](인입_이해_가이드.md) · 표 열의 role은 [역할 판정 가이드](역할_판정_가이드.md).
> **「확인할 것」의 줄은 실제 화면이다** — mock 한 벌로 쳐서 옮겼고 `python tools/runbook_check.py`가 지금 화면과 대조한다. 수는 mock 표본의 것이라 사내 문서면 다르다 — 줄의 **모양**을 본다. mock으로 낼 수 없는 줄은 표지를 달았다: 〔실호출〕 〔사내〕 〔산문〕 〔PPT〕 〔다른 표본〕 〔단계 밖〕 〔조건〕 〔보기〕.

모든 명령은 **코드 폴더(레포 루트)에서** 친다. `$ONTO_HOME`은 상태 폴더다(코드 밖 · 코드를 바꿔도 그대로). 화면에 나온 줄은 전부 `$ONTO_HOME/work/logs/<명령>_<날짜>.log`에도 있다. **설정이 실호출(`USE_MOCK` 0)이어야 `ONTO_HOME`을 본다** — mock(설정 파일이 없을 때 포함)은 `ONTO_HOME`을 무시하고 코드 폴더의 `state_mock/`만 쓴다. 게이트웨이 없이 새 상태 폴더로 단계 1을 연습하려면 명령 앞에 `USE_MOCK=0`을 붙인다(LLM을 부르지 않는 명령은 그대로 돈다). mock에서 운영 명령(`register` · `ingest-*` · `rebuild` · `query`)은 `--allow-mock`을 붙여야 돈다.

## 0 준비 — 코드 · 상태 폴더 · 연결

**할 일** — 코드 폴더를 놓고, 상태 폴더 자리를 정하고, 설정 파일을 두고, 점검한다.

- **상태 폴더 자리**는 코드 폴더 옆(`<프로젝트>/onto_state`)이다. `ONTO_HOME`은 셸 설정(`~/.bashrc`)이나 가상환경 활성화 스크립트 끝에 둔다 — `export`만 치면 그 터미널에서만 산다.
- **새 상태 폴더로 처음 시작하면** 빈 폴더 하나면 된다(안의 폴더는 명령이 만든다). 옛 상태 폴더는 지우지 않고 그대로 둔다 — `ONTO_HOME=<옛 폴더> python run.py show tree`로 언제든 열린다.
- **설정 파일은 `$ONTO_HOME/llm.json` 하나**다(코드 폴더의 `llm.local.json`은 두지 않는다 — 두면 그것이 이긴다).
- **새 가상환경이면 패키지부터** — PPT · PDF를 넣으려면 python-pptx · PyMuPDF와 캡처 길 하나(LibreOffice)가 있어야 한다(`requirements.txt` 머리말).

**칠 명령**

```bash
echo "export ONTO_HOME=$(dirname "$(pwd)")/onto_state" >> ~/.bashrc && source ~/.bashrc   # 처음 한 번
mkdir -p $ONTO_HOME                                  # 새 상태 폴더 — 안의 폴더는 명령이 만든다
cat > $ONTO_HOME/llm.json <<'EOF'
{"LLM_GATEWAY_URL": "https://사내주소", "LLM_API_KEY": "키", "CHAT_MODEL": "모델명",
 "EMBED_BACKEND": "gateway", "EMBED_MODEL": "임베딩 모델명", "CANDIDATE_NARROW": "auto", "USE_MOCK": 0}
EOF
chmod 600 $ONTO_HOME/llm.json
python -m pip install -r requirements.txt            # 새 가상환경이면
python doctor.py --regress                           # 반입 직후 한 번 — 회귀(몇 분)
python doctor.py                                     # 점검(몇 초 · 운영 상태 폴더는 읽기만)
python run.py llm-check                              # ①설정 → ②도달 → ③인증 → ④응답 → ⑥임베딩 → ⑦그림 입력
```

**확인할 것**

- `doctor` 머리 줄이 운영 상태다(그 아래 ③ 현재 상태 · ④ 사내 전환 판정은 코드 폴더의 mock 루트를 잰 것이라 새 폴더에서도 mock 표본을 보인다) — 〔사내〕 새 폴더면 `층 0(상태 루트) · 좌표 층 **없다** · 공통 config 없다 — bootstrap이 초안을 만든다 · 문서 0`(층은 단계 1에서 선다) · 다른 폴더를 보고 있으면 이 줄의 경로가 다르다
- `[  OK ] 정합 — 사라진 노드를 가리키는 것` 아래 `큐 0 · 사전 표기 0 · 끝점 없는 엣지 0` · `[  OK ] 레포 정본 자산이 레포 판이다`
- 끝 줄 `결과: 반입물은 점검 통과(회귀는 python doctor.py --regress — 반입 직후 한 번). 다음은 ④의 권장 순서다` 〔단계 밖〕(`--regress`면 스위트마다 `[  OK ] <스위트> n PASS / 0 FAIL` · 끝 줄 `결과: 반입물은 온전하다. 다음은 ④의 권장 순서다`)
- `llm-check` — 〔실호출〕 ④까지 통과(임베딩을 쓰면 ⑥ · PPT · PDF가 있으면 ⑦). 막히면 그 자리에서 멈추고 원인을 말한다(설정이 없을 때의 실제 화면: `[ 필요 ] ① 설정` · `설정 파일 없음 (환경변수만)`)

**막히면** — [2B §7-0](2B_작업가이드.md#7-0-준비--연결) (그래프가 비어 있다 · 설정 파일 · 임베딩 · 「층 자산 먼저」 · 패키지).

## 1 골격 · 층 config — 팩으로

**할 일** — 사내 LLM에 팩을 **파일 통째로** 넘겨 골격과 층 config를 받고, 상태 폴더에 놓고, 심고, 사람이 확정한다. **한 번에 한 층 · 골격 층(설비층)부터** — 설비층 → 공정층 → 품질층. 층 폴더 이름은 첫 인입 전에 정한다(등록한 문서 종류가 그 이름을 가리킨다).

1. **골격** — [골격 팩](팩/1_골격/골격_팩.md) 두 파일 + 공정 목록 → `skeleton.json` · 「확인 필요」 목록을 사람이 정리한다.
2. **설비층 config** — [층 config 팩](팩/2_층config/층config_팩.md) 세 파일 + **층 결정 메모**(이 층의 목적 · 정의할 카테고리 — 팩 머리의 양식 · 바탕 세 층은 [바탕층 결정 메모](팩/2_층config/바탕층_결정_메모.md)) + 설비 문서 1~2부 + 받은 `skeleton.json` → `config.json` + 「공통 config에 더할 줄」.
3. 놓는다 — `mkdir -p $ONTO_HOME/layers/<층>` 뒤 `$ONTO_HOME/layers/<층>/config.json` · `skeleton.json` · 공통 줄은 `$ONTO_HOME/layers/common.json`에 손으로(파일이 없으면 그 줄로 새로 만든다 — `home` · `used_by`는 `bootstrap`이 채운다).
4. 심고 확인 → 확정(아래 명령).
5. **공정층 · 품질층**도 같은 팩으로 — 그 층의 메모 + 이미 세운 층의 `config.json`과 `common.json`을 함께 넘긴다(둘째 층부터는 실제 config가 기준이다) → 놓고 → `bootstrap` → 지도.

**칠 명령**

```bash
python run.py bootstrap --dry-run                    # 같은 검사 · 쓰기 0 — 멈출 것 0이 될 때까지 고친다
python run.py bootstrap
python run.py skeleton-status <골격 층>               # 문법만
python run.py skeleton-confirm <골격 층> --by <이름>  # 터미널에서 — 흐름을 보고 y
python run.py export config                          # config 지도 — export/config_map.html을 브라우저로
```

**확인할 것**

- `[bootstrap] --dry-run — 쓰기 0 · 바뀔 것 없음 · 멈출 것 0건` — 0이 아니면 파일 · 자리 · 다음 줄을 말한다
- 파생 흐름을 공정 문서와 대조한다 — 순서 · 무주장 · 모호 이름: `[조립]       노칭 → 스태킹 → 탭용접 → 패키징`
- `[bootstrap] process: 노드 30 · 엣지 51` — 공정 목록의 공정 수와 노드 수를 한 번 센다(빠진 공정은 화면이 못 잡는다 · 공정은 극성 없이 하나). 아래 줄의 `process`는 mock의 골격 층 이름이다 — 사내는 골격 층(설비층) 폴더 이름이 나온다
- 골격 겸 한 줄 — `[bootstrap] 골격 'Process'(process): 겸 없음 — …` 〔다른 표본〕(설비층 골격이면 `겸 Unit(sub·detail) · 겸 단 별칭 n개` — 꺼짐 · `별칭 0`이면 공통 config의 `also`와 별칭을 본다)
- `■ 골격 판정 — process: 문법 위반 0건 · layers/process/skeleton.json`
- 확정 — `이 흐름이 근거 문서와 맞습니까? [y/N]` → `확정 기록 → layers/process/confirmations.json (1번째 · <이름> · d2742e665b8a…)`
- 지도 요약 — `[export] config map(새 모양) — layers 2 · categories 5 · relation_patterns 4 · parent_pairs 3 · cross-layer edges 7 · uses 3 · reject 0 · warn 0 · info 0 · coord layer process (Process)`(창작 표본 — 칸 이름은 config 키 그대로)

**온톨로지 맵 보는 법** — `export/config_map.html` 맨 위 그림이 config가 선언한 카테고리 지도다(읽기만). 범례 한 줄(`점 = 카테고리 · 색 = home 층 process quality · … · 선 9`) 그대로 읽는다.

- **점** = 카테고리 · 색 = 그 카테고리의 `home` 층
- **선** = (src, rel, dst) 하나 — 회색 골격 관계 · 파랑 소속(`parent_pairs`) · 보라 사실 관계(`relation_patterns`) · 점선 = 층을 넘는 관계
- **고리** = 같은 카테고리끼리의 관계(실제 그래프에서는 다른 두 노드)
- 「선언만」 = config가 선언했는데 그래프에 엣지가 0(흐린 선) — 문서를 넣기 전에는 골격 관계만 수가 있다
- **attributes 표** = 값 칸(카테고리 · 속성 · 정의한 자리)
- **점검 줄** = 맨 아래 `reject` · `warn` · `info` — reject가 있으면 그 config로는 멈춘다

품질 문서를 넣기 전에 품질층 띠에서 셋을 본다: `uses`에 품질 문서가 말하는 다른 층 카테고리가 다 있나 · 소속(파랑)이 품질층에도 걸리나 · 문서가 말하는 관계가 사실 관계 선으로 있나(없으면 그 층 `relation_patterns`에 없는 것 — 인입에서 관문이 버린다).

**막히면** — [2B §7-1](2B_작업가이드.md#7-1-골격--층-config) (`[FAIL] K##` · 확정 거부 · 관계가 관문에서 막힌다 · 같은 이름 부품이 한 노드).

## 2 문서 종류 등록

**할 일** — 문서 종류마다 한 번: **생성 → 기계 관문 → 뷰 확인 → 확정**. 표(CP · PFMEA …)는 LLM이 어댑터 · 스키마 초안을 내고, 산문(PPT · PDF · Word · 목차형 엑셀)은 고정 어댑터(LLM 0)다. `<dt>`는 사람이 짓는 짧은 영문 이름(예: `cp` · `pfmea` · `rfq`)이고 `<층>`은 그 문서가 주로 만드는 노드의 `home` 층이다(층 config 팩 §3 표 — 설비 사양 값은 공정층 `Property`라 설비 사양 문서는 공정층). 사람은 뷰에서 판단(열마다 role · 대응 · 제외)만 본다 — role은 [역할 판정 가이드](역할_판정_가이드.md). 이미 등록한 종류는 다시 만들지 않는다(코드를 바꾼 뒤에는 `status`만).

**칠 명령**

```bash
python -m cli.register generate <dt> <층> <표본>                 # 표 — 생성 → 관문 → 뷰(registry/review/<dt>/view.html)
python -m cli.register generate <dt> <층> <표본> --use-basic      # 산문 — 고정 어댑터
python -m cli.register status <dt>                               # 관문을 지금 코드로 다시 · 다음 줄
python -m cli.register confirm <dt> --by <이름>
```

**확인할 것** 〔단계 밖〕

- `기계 관문(하네스): PASS — 41 PASS / 0 FAIL` → `■ 기계 관문 PASS — rfq` → 확정 `■ ③ 확정 — rfq 등록부 등재 (승인 <이름> @ …)`
- 산문 문서가 등록 층이 정의하지 않은 카테고리의 **값**을 말하면(설비 산문의 사양 · 세팅값 — 관리항목은 공정층 정의) 확정 뒤 렌즈에 그 home 층을 더한다: `python -m cli.register lenses <dt> <등록 층>,<home 층>` → `■ 렌즈 — <dt>: ['<등록 층>', '<home 층>']` · 안 더하면 이름만 서고 값은 0이다(층 config 팩 §4 `value_categories`)
- 시트 여럿인 산문 엑셀은 시트 역할 표가 먼저 뜬다 — `시트 역할 — prose 3 · ref 1 · skip 3 → registry/sheet_roles/RFQ01.json`(같은 파일은 다시 묻지 않는다)
- FAIL이면 같은 블록이 어디서든 뜬다 — `■ 기계 관문 FAIL — <dt>` · `[FAIL] <태그>` · `▶ 다음 줄:` — **다음 줄을 그대로 친다**

**막히면** — [2B §7-2](2B_작업가이드.md#7-2-문서-종류-등록) · 태그별 처방은 [2B §4](2B_작업가이드.md#4-등록).

## 3 문서 넣기

**할 일** — 원본은 `$ONTO_HOME/raw/`(하위 폴더 자유)에 둔다. **넣는 차례는 바탕층부터**: 설비 문서 → CP → PFMEA → 산문 엑셀 → PPT(뒤 문서가 붙을 자리가 앞 문서로 선다). 종류마다 첫 몇 건은 `--step`으로 단계마다 보고, 익숙해지면 폴더째. 산문 엑셀은 **문서 좌표**(어느 공정의 문서인가)를 `--coord`로 준다 — 한 번 주면 기록이 남는다. 시트 많은 산문 엑셀은 첫 인입에서 시트 역할(prose · ref · skip)을 묻는다. PPT는 덱이 슬라이드마다 다루는 공정을 판단한다(`--coord`는 힌트).

**칠 명령**

```bash
python run.py ingest-file <문서> --dry-run                         # 어느 doc_type으로 가나만
python run.py ingest-file <문서> [--doc-type <dt>] --step          # 단계마다 [계속 c / 멈춤 q] — 비용 전에 멈출 수 있다
python run.py ingest-file <산문 문서> --doc-type <dt> --coord <공정>  # 산문 — 문서 좌표
python run.py ingest-file <문서> --doc-type <dt> --extract-only    # 추출 · 판정까지 보고 멈춤(그래프 쓰기 0) — 같은 줄을 플래그 없이 치면 확정
python run.py ingest-dir                                           # $ONTO_HOME/raw/ 전체 — 배치는 묻지 않는다
python run.py show report <doc_id>                                 # 넣은 뒤 — 무엇이 없어서 못 붙었나(--md 잘림 없이)
```

**확인할 것**(표 CP01 · 품질 문서 PFMEA01 — mock 실제 화면)

- `--dry-run` — `[선택만] CP01.xlsx doc_id CP01 doc_type cp`
- `--step`이 **비용 전에** 멈추는 자리 — `── [3/7] 좌표 — 정확 일치 30 · … · 좌표 쌍 어긋남 1쌍(1행)` · 표 `[4/7] 판정 예고` · 〔산문〕 산문 `[4/8] 추출 예고`. 계속은 `c`(`ㅊ`)만 · 멈춤 `q` — 저장 전 멈춤은 그 문서를 되돌린다
- 골격에 없는 공정 표기 · 상위와 줄기가 다른 쌍 — **사람이 정하기 전에는 세우지도 붙이지도 않고 보류한다**: `── [3/7] 좌표 — 정확 일치 31 · 잠정 0종(부모 미정 0) · 보류 1(사람 확인 전 공정 표기) · LLM 호출 0 · 좌표 쌍 어긋남 0쌍(0행)` · 머리 아래 `골격 칸 — 공정 표기 10종: 골격에 있음 9(LLM 같다 0) · 문에 걸림 1종(1행) · 쌍 어긋남 0쌍(0행) · ref 빈 행 0(상위로 붙음) · 판단 못 받음 0` · 표 머리 `골격 칸 — 문에 걸린 표기 1종 · 쌍 어긋남 0쌍` · 줄마다 `1 레이저노칭 … 행 … 좌표 … 조립 …`(판단 칸 — LLM 확실도 · 까닭 또는 「LLM 0 — 사유」 · 처분 칸) · 후보 한 줄에 하나 · 골격 목록 한 줄 `골격 — 조립 아래 29: 1.노칭 2.전극 언와인딩 …`
  - 〔보기〕 답 — 번호 + 말(LLM이 읽고 해석을 보인다 · Enter면 쓴다 · 다른 말이면 다시) 또는 글쇠: 같다 `m 1 1`(후보 번호 또는 골격 이름 — 띄어쓰기 · `상위::` 무시) · 새로 `k 1`(잠정 골격 노드) · 버림 `d 1 오기` · 쌍 줄: 맞다 `a 2` · 같다 `m 2 1` · `? 1` 골격 전부 · `c` 계속 · 줄이 하나면 번호 생략. 승격은 인입 뒤 `ops review`의 잠정 골격 노드에서. 정한 것은 그 문서의 나머지 행부터 · 정하지 않은 것은 보류(단계 4에서). 배치(`ingest-dir` · `--step` 없이)는 묻지 않고 전부 보류
  - 〔산문〕 골격 단 — 목차 노드화 뒤 `골격 단 — 제목의 겸 값 n종이 문에 걸렸다`(줄마다 자리 · 이름 · 위 공정 · 판단 · 후보) · 같은 답 꼴에 위로 `u 1`(노드 0 · 그 아래 값은 위 공정에) · 말 「1 이건 부품이야」(해석 고침 — 카테고리를 고치면 문을 떠나 그 카테고리로 판정) · drop한 제목 아래 청크는 `[4/8]`에서 `거름 — 사람 drop` · 끝 줄 `확정한 공정 — 청크 n: 노칭 › 노칭 타발 3 · 노칭(상위만) 2` · `[5/8]` 머리에 쌍별 예고(값 · 붙을 자리 · 연결 · 판정 예정)와 본문 값의 골격 단 줄 · 저장 직전 `판정 결과 — 쓰기 전 — match a · new b · uncertain c` → `c` 쓴다 · `q` 쓰지 않고 멈춘다(판정은 남아 다시 넣으면 LLM 0)
- 판정 예고 — `── [4/7] 판정 예고 — 값 91건 · 표기 64종 · 사전 히트 23건 → LLM ≤ 68회 · 닫힌 분류 판단 ≤ 1회`(LLM 상한이 값 수 이하면 정상)
- 끝 — `[성공] PFMEA01.xlsx doc_id PFMEA01 doc_type pfmea record 32 · chunk 64 · 그래프 노드 이 문서 +44(그 층 quality 전체 48)`(보류한 「레이저노칭」 행은 단계 4에서 처분한 뒤 붙는다)
- 원인 묶음 — `원인 묶음 — 확인할 행 7 / 전체 187 — …`(무엇이 없어서 못 붙었나 · 행마다는 `show report <doc_id> --trace`)

**막히면** — [2B §7-3](2B_작업가이드.md#7-3-문서-넣기) (좌표를 못 알아본다 · 문서 좌표 없음 · 시트 역할 · 캡처 · 청크).

## 4 넣은 뒤 정리

**할 일** — 순서대로: ① 큐 요약 ② 좌표 어긋남 쌍 ③ 인입 뒤 한 화면(골격 칸 — 문에 걸린 표기 · 쌍 어긋남 · 잠정 골격 노드 · 애매 · 자리 추정 · 후보 있는 보류) ④ 문서 단위 확인 ⑤ 지도 다시 · 전체 수. 문에 걸린 표기는 있는 공정의 다른 표기면 **합침** · 새 공정이면 **새로**(잠정 골격 노드) 또는 **승격**(골격 파일) · 아니면 **drop**(사유) · 쌍 어긋남은 ref가 맞으면 **확인** · 상위가 맞으면 **정정**. 처분했거나 좌표 · 별칭을 고친 뒤에는 재인입 없이 `ops relink`로 보류 행을 붙인다.

**칠 명령**

```bash
python run.py platform queue                                    # 큐 요약
python run.py platform queue coord_mismatch                     # 좌표 어긋남 쌍 — 쌍마다 「이대로 둔다」 줄
python run.py ops review all --actor <이름>                     # 인입 뒤 한 화면 — 터미널에서(비대화형은 계획)
python run.py ops confirm all --doc <doc_id> --actor <이름>     # 그 문서가 만든 auto 노드 확정 — 계획 → --yes
python run.py ops relink all --actor <이름>                      # 재연결 계획 → --apply
python run.py export config                                     # 지도 다시 — 선마다 실제 엣지 수
python run.py show summary --save <이름>                         # 기준선(전체 수) — 바꾸기 전에 찍는다 · --diff <이름> 지금
python run.py viewer                                            # 「동의어」 탭 — LLM 검토(누르기 전 짝 · 예상 토큰) → 일괄 승인(행위자 이름)
python run.py ops alias-audit --llm                             # 사람 없는 LLM 검토(요약 한 줄 · 승인은 뷰어에서)
```

**확인할 것**

- `수정 큐 — 83건 · 닫힌 19종 (…)` — `orphan_anchor`가 예상 밖으로 많으면 골격 별칭이 모자란 것(골격 칸 보류는 `ops review`에서 처분)
- `■ 인입 뒤 한 화면 — 골격 칸 2(문에 걸림 1 · 쌍 어긋남 1) · 잠정 골격 노드 0 · 애매 0 · 자리 추정 0 · 후보 있는 보류 0` — 터미널에서 줄마다 답한다(문: 합침 · 새로 · 승격 · drop / 쌍: 확인 · 정정 · drop) · 처분이 있으면 끝 줄이 `ops relink all … --apply`를 낸다
- `[coord_mismatch] 쌍 묶음 — 어긋남 1쌍(1행) · 확인된 쌍 0(0행) · 큐 항목 1` — 쌍이 문서 전체면 열이 뒤바뀐 것(재등록) · 몇 행이면 별칭 또는 「이대로 둔다」
- 지도 다시 — PFMEA를 넣은 뒤 품질층 선마다 실제 엣지 수: `Failure | occurs_in | Process | 사실 관계 · 층을 넘는 관계 | relation_patterns · schema: pfmea | quality | | 17` · `Failure | causes | Failure | 사실 관계 | relation_patterns · schema: pfmea | quality | | 30` · `Failure | affects | FailureEffect | 사실 관계 | relation_patterns · schema: pfmea | quality | | 15` · `Failure | controlled_by | Property | 사실 관계 · 층을 넘는 관계 | relation_patterns · schema: pfmea | quality | | 25` — 품질층 선이 「선언만」으로 남으면 2B §7-4 「관계가 그래프에 없다」(골격 칸 보류를 처분하고 `ops relink`하면 그 행의 선이 더해진다)
- 전체 수 — `층 quality 엣지      엣지 87 — affects 15 · causes 30 · controlled_by 25 · occurs_in 17`
- 동의어 — bootstrap 끝 줄 「동의어 — 공유 n · …」이 있으면 뷰어 「동의어」 탭 맨 위 「LLM이 빼자는 것」(틀림 · 붙은 행 큰 차례)부터 본다 · 승인 끝 덩이에 「다시 붙일 행」이 있으면 그 줄의 ingest-file을 친다(승인만으로 붙은 행은 떨어지지 않는다)

**막히면** — [2B §7-4](2B_작업가이드.md#7-4-넣은-뒤-정리) (같은 것이 노드 둘 · 불확실이 많다 · 좌표 어긋남 · 별칭이 틀렸다 · 관계가 그래프에 없다).

## 6 코드 바꿀 때 · 재구축

**할 일** — 판정 · 이름 규칙이 바뀌는 반입이거나 골격의 이름 · 부모를 고쳤으면 **다시 짓는다**. 다시 짓기는 지난 판정을 대장에서 재생하고(LLM 0) 사람 판단(merge · confirm · 별칭 …)을 이름으로 되살린다. 산문은 지시문이나 층 config의 추출 칸이 바뀌었으면 다시 뽑는다(LLM — 끝 보고의 `추출 n`).

**반입 차례**

1. **옛 코드로** 기준선 — `python run.py show summary --save 반입전`(반입한 뒤에는 옛 화면을 못 찍는다)
2. 상태 폴더 통째 백업 → 코드 폴더 교체 → 단계 0의 점검
3. `bootstrap` — config가 옛 모양이면 새 모양 제안을 `work/config_next/`에 쓰고 멈춘다(쓰기 0) → 보고를 읽고 지도 대조(`export config --json` 둘 → `--diff`) → 화면의 복사 명령 → `bootstrap`
4. 다시 짓기 — 두 길 중 하나(아래)
5. `python run.py show summary --diff 반입전 지금` — 바뀐 줄만

**다시 짓는 두 길**

- **한 번에** — `rebuild`(계획 — 지울 것 · 남길 것 · 다시 넣을 순서) → `rebuild --yes`. 끊기면 같은 명령이 계획에서 이어 간다.
- **골라 넣기**(문서마다 보며 · 차례를 바꿀 때) — `rebuild`(계획만 보고 N — **이 명령이 지우기 전에 사람 판단 기록의 이름을 채운다**) → `init --fresh`(`--all`이 아니다) → `bootstrap` → 단계 3의 차례로 `ingest-file <문서> --step` → 끝에 `ops replay all --actor <이름>`(**빠뜨리면 사람 판단이 돌아오지 않는다** · 두 번 쳐도 같다). 차례를 바꾸면 그 문서의 대상 노드가 아직 없어 다시 판정하는 값이 는다(비용).

**무엇을 바꾸면 무엇이 다시 도나**

| 바꾼 것 | 칠 것 |
|---|---|
| 골격에 별칭 · 노드를 더함 | `bootstrap`(fresh 없이) → 보류는 다음 인입 마무리에서 붙는다 · 지금 붙이려면 `ops relink all --actor <이름> --apply` |
| 골격의 이름 · 부모를 고침 | 다시 짓기(그 아래 노드 이름이 바뀐다 · 옛 이름은 `ALIASES`에 남긴다) |
| 층 config `relation_patterns` · 공통 config(`parent_pairs` · `also` · `home`) | `bootstrap` → 끝 줄 `config 영향 — 재구축 때 LLM 0으로 다시 판정: …` → 다시 짓기 |
| 층 config 카테고리 · 정의문 · `uses` · 관련어 | `bootstrap` → 끝 줄 `config 영향 — 추출 다시: …` → 다음 인입 · 다시 짓기가 그 문서를 다시 뽑는다(LLM) |
| 원본 파일 | 그 문서만 다시 `ingest-file` |

**칠 명령**

```bash
python run.py show summary --save 반입전              # 옛 코드로 — 반입 전
cp -r $ONTO_HOME ${ONTO_HOME}_bak_$(date +%Y%m%d)    # 통째 백업 — 그래프 판을 되돌리는 길은 이것뿐
python run.py rebuild                                 # 계획(비대화형은 계획만)
python run.py rebuild --yes                           # 실행
python run.py ops replay all --actor <이름> --dry-run # 골라 넣기 길의 끝 — --dry-run 빼고 한 번 더
python run.py show summary --diff 반입전 지금
```

**확인할 것** 〔단계 밖〕

- 계획 — `■ 재구축 계획 — 문서 3(다시 넣을 것 3 · 원본 없음 0)` · `사람 판단 기록 42건 · 이름 채움 0 · 이름 없음 0(재구축하면 돌아오지 않는다)` — 이름 없음이 0이 아니면 그 연산은 뒤에 손으로
- 끝 보고 — `■ 재구축 끝 — 문서 3(성공 3 · 실패·보류 0 · 원본 없음 0)` · `판정 — 재생 93 · 재판정 1(…)` · `LLM 호출 — 추출 0 · 판정 0 · 태깅 0 · 그 밖 0` · `사람 판단 재생 — 한 일 40 · … · 대상 없음 0 · …` · `계획 파일 — 끝 (다음 재구축은 문서 대장에서)`
- 사전 점검에서 멈추면 지우기 전이다 — `■ 재구축 멈춤 — 지우기 전에 멈췄다 — 그래프 그대로 (계획 파일 · 상태 폴더 쓰기 0)`

**막히면** — [2B §7-6](2B_작업가이드.md#7-6-코드-바꿀-때--재구축) (재구축 뒤 사람이 한 것이 없다 · 재구축이 LLM을 다시 부른다 · 다시 넣을 문서가 없다).

## 7 허브로 보낼 것

**할 일** — 명세가 답하지 않거나 화면이 이상하면 추측으로 메우지 않고 재료를 모아 허브로 가져온다. **사내 문서 내용은 보내지 않는다** — 화면 줄과 수만. 레포 정본 자산(`prompts/` · `kit/` · `schemas/blocks.json` · 레포 `layers/`)은 사내에서 고치지 않는다(`doctor`가 ⚠).

- 무엇을 쳤나(명령 그대로) · 어느 단계에서 멈췄나 · 그 단계의 화면 줄(`work/logs/<명령>_<날짜>.log`에서)
- `python run.py show summary` 한 화면 · 문제 문서의 `show report <doc_id>` 머리와 원인 묶음
- 붉은 회귀는 화면의 「붉은 기록 — <자리>」 폴더를 그대로
