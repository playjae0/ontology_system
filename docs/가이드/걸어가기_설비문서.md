# 걸어가기 — 설비 문서(RFQ)를 처음부터 끝까지 넣는다

> **누구를 위한 한 장인가**: 공정층이 이미 서 있고(CP·PFMEA가 들어가 있다), 이제 설비 문서 — 시트가 수십 장인 RFQ 엑셀 — 를 넣으려는 사람. 명령 사전은 `2B_작업가이드.md`이고, 이 문서는 **그 명령을 어떤 순서로, 무엇을 보면서 치는가**다. 2026-09-22 설비 논의로 확정된 결정(층을 새로 만들지 않는다 · 골격은 그대로 · 시트는 문서마다 묻는다)이 바닥이다.

## 0. 먼저 알고 갈 것 셋

| Fact | Consequence |
|---|---|
| 조립 라인에서 **공정 = 설비**다. 골격 노드 「노칭」이 노칭 공정이자 노칭 설비(스테이션)다 | **골격 층은 하나다** — 골격을 두 벌 세우지 않는다. 그 층의 폴더 이름은 자유라 `equipment`로 불러도 된다(아래 §1-a). 스테이션이 설비이기도 하다는 사실은 공통 config의 **겸**으로 적는다(`"Process": {"also": {"Unit": [스테이션 단]}}` — config작성_가이드 §0-a) · 설비의 속살(Unit·Component)은 그 층에 어휘를 더해 받는다 |
| 파라미터·관리특성(**Property**)은 **공정층**에 산다 | 설비층(골격 층 — Process·Unit·Component)과 공정층(Property)이 같은 Process 노드에 와서 붙는다. 어느 카테고리의 노드가 어느 층 그래프에 사는지(집)는 공통 config 한 파일이 정한다 — 여러 층이 같은 카테고리를 말해도 노드는 집에 하나다 |
| 모든 문서의 좌표는 `process_ref`이고 그것은 골격 노드에 붙는다 | RFQ도 「어느 공정용 설비인가」로 붙는다 — 층간 연결은 인입 때 자동이다. 나중에 엮을 것이 없다 |
| 골격 아래 단(유닛·부품·사양)은 **문서가 만든다** | 골격에 유닛 층을 파지 않는다. 벤더가 바뀌면 골격이 아니라 문서만 바뀐다 |

무엇이 어디에 생기는지는 `상태_폴더_가이드.md` 한 장.

## 1-a. 골격 층 이름을 `equipment`로 바꾸려면 (한 번)

```bash
cp -r $ONTO_HOME ${ONTO_HOME}_bak_$(date +%Y%m%d)            # 먼저 통째로 보관
mv $ONTO_HOME/layers/process $ONTO_HOME/layers/equipment       # 폴더 이름
#   layers/equipment/config.json 의 "layer": "equipment" · 정의문을 스테이션(공정 = 설비) 기준으로 · skeleton.json 은 설비 라인업
grep -rln '"layer": "process"\|"target_layer": "process"' $ONTO_HOME/registry   # 등록 스키마의 층 키 — 나온 파일의 값을 equipment 로 
#   layers/common.json 의 "home": "process" 를 "equipment" 로 — 집은 층 이름을 가리킨다 (골격 카테고리 Process는
#   옛 집 그래프에 노드가 없으면 bootstrap이 고친다: 공통 config 'Process' home process → equipment (골격이 equipment에 있다 · …노드 0)
#   · 노드가 남아 있으면 노드 수를 말하고 멈춘다 — init --fresh 뒤라면 노드 0이다)
#   layers/<층>/config.json 에 canonical_scope 가 남아 있으면 지운다 — 이름 규칙은 공통 config의 bind_categories가 기준(config작성_가이드 §5)
python run.py skeleton-status equipment && python run.py skeleton-confirm equipment --by <이름>
python run.py init --fresh && python run.py bootstrap && python run.py ingest-dir   # 등록·어댑터·시트 역할은 남는다
python doctor.py | head -1                                    # … · 좌표 층 equipment
```

카테고리 라벨 `Process`는 그대로다. 폴더 이름만 바꾸고 등록 스키마의 층 키나 공통 config의 `home`을 안 고치면 그 doc_type·카테고리가 없는 층을 가리킨다 — `bootstrap`이 공통 config ⓒ(골격 카테고리 `Process`는 ⓖ 「home은 process인데 골격은 equipment에 있다」)로 층을 심기 전에 멈추고, 끝의 등록 스키마 재대조가 어긋난 doc_type을 줄로 말한다.

**공통 config가 아직 없으면**(처음 한 번): `python run.py bootstrap --dry-run`으로 계획을 보고 `python run.py bootstrap` — 층 config들에서 `layers/common.json`을 바로 만들고, 여러 층이 선언한 카테고리만 `home`이 빈칸으로 남아 멈춘다. 공정층은 골격 카테고리(`Process`·`Unit`)를 선언하지 않으므로 골격 카테고리에는 빈칸이 생기지 않는다(집 = 골격 층 자동 · 한 층만 선언한 카테고리는 이미 그 층이다) — 빈칸은 골격이 아닌 카테고리를 여러 층이 함께 선언했을 때만이고, 그때 채운다 → 층 config에서 `canonical_scope`를 지운다(공통 config로 옮겨졌다) → 스테이션 단에 `"also": {"Unit": [...]}` + 골격 `ALIASES`에 단별 설비 표기(뼈대 개념은 `골격작성_가이드.md` §3-a) → `python run.py bootstrap` → 끝 줄 `골격 'Process'(<설비층>): 겸 Unit(…) · 겸 단 별칭 n개`(「겸 없음」이면 겸이 꺼진 것 · ⚠ 「별칭 0」이면 반쪽) → `python doctor.py | head -5`(「좌표 층 <설비층> · 공통 config v<n>」 + 같은 겸 상태 줄).

## 1. 어휘 넓히기 — `$ONTO_HOME/layers/<골격 층>/config.json` (반나절)

설비의 속살을 받을 카테고리와 관계를 더한다. 절차·키는 `config작성_가이드.md` §1-a에 표로 있다. 요점만:

```
categories               + "Component": "유닛을 이루는 교체·정비 단위(예: 상부 금형·서보 모터). 유닛 자체·규격값 제외"
(공통 config)             canonical_scope.bind_categories에 + "Component" → 키가 노칭::상부 금형 (categories의 "Component" 줄은 bootstrap이 더한다 — 한 층만 선언)
relations / relation_patterns   + Component part_of Unit · Unit part_of Process · Property … Unit/Component
query_traverse           Unit → Component 는 recursive:false   → 설비를 물으면 유닛까지, 유닛을 물어야 부품
fact_templates · prompts  새 관계의 문장 틀 · 추출 정의문
config_version           올린다
```

```bash
python run.py bootstrap            # fresh 없이 — 골격이 그대로면 「노드 0 · 엣지 0」 추가로 끝난다
python doctor.py | head -3         # 같은 상태 폴더 · 등록 수 그대로
```

**하지 않는 것**: `init --fresh`(사전·큐 판정이 날아간다) · `skeleton.json` 수정(설비명을 붙이고 싶으면 `ALIASES`만 — 골격작성_가이드 §3).

## 2. doc_type 등록 — RFQ 한 부로 (반나절)

```bash
python -m cli.register generate rfq <골격 층> <RFQ 하나.xlsx>   # 층 이름은 골격 층의 이름(예: equipment)
#   시트가 여럿이면 먼저 **시트 역할 표**가 뜬다 — 3의 표와 같은 것이다. 여기서 답한다 
#   산문 엑셀이면 「산문 포맷이다, 고정 어댑터로 갈까? [Y/n]」 → Enter (LLM 생성 0)
python -m cli.register status rfq          # 관문 PASS 확인 · 매칭 스키마(어떤 카테고리를 뽑나)를 본다
python -m cli.register confirm rfq --by <이름>
```

등록은 **읽는 방법**을 정한다 — 다만 **표본도 문서 하나**라 시트 관문이 등록 때 한 번 뜬다. 답한 역할대로 관문·검수 리허설이 돌고(`skip` 시트는 아무도 보지 않는다 — 가격·일정 시트로 LLM을 쓰지 않는다), 답은 3과 **같은 기록**(`registry/sheet_roles/<doc_id>.json`)이라 **그 표본을 3에서 넣으면 다시 묻지 않는다**(「시트 역할 — 기록대로 진행」). 다른 RFQ는 시트 자리가 다르니 문서마다 3에서 묻는다. 터미널이 아니면(파이프·배치) 상태 거부이고 문면이 `--sheets "…"`를 붙인 등록 줄을 준다.

## 3. 첫 문서 — 시트 역할을 답하고 넣는다 (문서당 10분)

```bash
python run.py ingest-file <RFQ.xlsx> --doc-type rfq --dry-run     # 시트 표만 본다 (묻지 않는다 · 기록 0)
python run.py ingest-file <RFQ.xlsx> --doc-type rfq               # 실제 — 표 뒤에 한 줄을 묻는다
python run.py ingest-file <RFQ.xlsx> --doc-type rfq --coord 노칭  # 이 문서가 어느 공정의 것인지 사람이 준다
```

**문서 좌표 — 이 문서는 어느 공정(스테이션)의 것인가.** 시트 역할 표 바로 뒤에 한 줄이 뜬다:
`문서 좌표 — 노칭 (출처: 사람 | 기록 | 파일명 | 없음)`. 정하는 순서는 `--coord <골격 이름|none>` → 기록
(`registry/doc_coords.json` — 같은 doc_id는 다시 묻지 않는다 · `--coord`가 덮는다) → 파일명 제안(파일 이름을
`_ - . ( ) [ ]`·공백으로 나눈 조각이 골격 이름·별칭에 맞고 **가리키는 노드가 하나일 때만**). 터미널이면 제안이 있을 때만
한 번 묻는다(Enter=수락). 문서 좌표가 있으면:

- 시트명·제목이 골격 이름과 맞아도 **그 공정 서브트리 안의 것만** 좌표로 받는다 — 다른 공정 이름(인터페이스 서술)은
  좌표 줄의 「무시(문서 좌표 밖)」로 센다.
- 여러 공정이 나눠 가진 별칭(예: 「비전 검사」)은 문서 좌표 서브트리 안에서 하나일 때만 받는다 — 없으면 「공유 별칭
  건너뜀」.
- 그래도 빈 조각은 문서 좌표를 물려받는다(표·산문 같다).

문서 좌표도 없고 조각 좌표도 없으면 `Unit`·`Component`·`Property` 같은 **이름 규칙 카테고리는 노드를 만들지 않는다** —
재료는 큐 `missing_field`가 들고(`platform queue missing_field`), `--coord`를 주고 다시 넣으면 붙는다.

화면:

```
■ 시트 역할 — RFQ_노칭.xlsx · 32장 (기록 없음 — 이 문서는 처음이다)
   #   시트          행    열   글자셀  적중  앞부분                          로직   LLM    제안
   1   표지          12    3    40%     1     「RFQ / 노칭 설비 / 2026-09」    ref    ref    ref
   2   사양_기계     214   6    71%     9     「1. 개요 / 1.1 적용 범위 …」    prose  prose  prose
   3   사양_전장     180   6    68%     0     「1. 전장 사양 …」               ref    prose  ref
   4   도면목록      96    8    22%     4     「DWG-001 …」                    ref    ref    ref
   5   가격          40    9    18%     2     「항목 / 단가 / 수량」           ref    ref    ref
   …
      3 사양_전장 — LLM: 전장 부품 사양 서술 — Unit 정의에 맞다
   역할 — 번호:역할 (예 2-3:prose 4:ref *:ref · Enter=제안대로 · q=중단): 2-3:prose 4:ref *:skip
   시트 역할 — prose 2 · ref 1 · skip 29 → registry/sheet_roles/RFQ_노칭.json
```

| Role | Give it to | Then |
|---|---|---|
| `prose` | 지식이 되는 시트 — 사양·요구사항 | 청크 → 추출 LLM → 개체(Unit·Component·Property)·관계 → 판정 |
| `ref` | 나중에 찾아볼 시트 — 도면 목록·표지 | 저장만 · LLM 0. `show doc`·뷰어·`show bm25`에 보이고, 질의에서는 질문이 가리킨 노드(예: 「노칭 프레스」)의 이름이 든 ref 청크만 **[관련 원문]**으로 맨 뒤에 붙는다 |
| `skip` | 지식도 참조도 아닌 시트 — 가격·일정·양식 | 안 읽는다 |

**제안 열은 로직과 LLM이 같으면 그것, 어긋나면 `ref`다**(모르면 ref — 위 3번 시트). 로직은 모양 + 적중(설비층 어휘가 몇 종 나오나 — 사전 표기와 층 config `relevance_terms`), LLM은 층 정의문을 보고 판단하고 어긋나면 이유 줄이 붙는다. 둘 다 틀릴 수 있다 — **표를 읽고 직접 답한다.** 답은 `registry/sheet_roles/<doc_id>.json`에 남아 같은 문서(개정판 포함)는 다시 묻지 않는다. 틀렸으면 `--sheets "…"`로 다시 넣는다(기록을 덮는다).

**시트마다 제목 표기가 달라도 된다** — `1.` · `가.` · `(1)` · `Ⅰ.`을 섞어 써도 처음 나온 순서가 급이 되고, 그래도 제목이 안 서는 시트(글자 크기로만 제목을 쓴 사양서 등)는 그 시트만 LLM이 규칙을 선언한다: `계층 규칙 — 고정 규칙으로 안 선 시트 n장 → LLM ≤ n회` → `선언 적용 k시트 · 여전히 통째 j시트`. 선언은 기록되어 같은 파일을 다시 넣으면 호출 0이다. 3,000자 넘는 절은 행 경계에서 한 번 더 갈린다(`글자 상한 초과 …`).

**소속 — 이 부품은 어디의 것인가.** 추출은 개체마다 `belongs_to`(무엇의 일부 · 무엇의 특성)를 낸다. 근거는 청크
본문 · 맥락 줄(문서 · 공정 · 시트 · 경로)뿐이다 — 시트 「이송 유닛」의 「모터」는 소속 `이송 유닛 (from 시트)`. 시트명·제목은
**개체로는 뽑지 않고 소속으로만** 쓴다. 근거가 없으면 null(좌표에 붙는다) · 근거에 없는 이름을 내면 버리고 결함 로그에 남긴다.
소속 대상이 골격이면 그것이 좌표이고, 골격 밖(유닛)이면 같은 문서 → 사전 → 새 노드로 앉고 그 유닛도 좌표에 붙는다.

**이름에 소속**: 공통 config `canonical_scope.nest_categories`에 `Component`를 적으면 부품 이름이 소속 유닛 아래로
중첩된다 — `노칭::이송 유닛::모터` · `노칭::가압 유닛::모터`(다른 노드). 소속이 없거나 골격이면 `노칭::모터`. 적지 않으면
지금과 같다. `Property`는 적지 않는다 — 공정 스코프(`노칭::가압력`)에서 CP·PFMEA·RFQ가 만난다(config작성_가이드 §5).

그 뒤는 보통 인입과 같다 — 좌표 태깅 → 판정 예고 → 값 줄(`+ 노칭::상부 금형 new …`) → `인입 끝 — 노드 +n · 엣지 +m · 큐 …` → `로그 <상태>/work/logs/…`. 화면 줄의 뜻은 `인입_이해_가이드.md` §3.

## 4. 확인 — 여섯 줄

```bash
python run.py show extract <doc_id> --full   # 청크마다 맥락 줄 · 개체 · 소속(from) — 어디의 것으로 뽑혔나
python run.py show report <doc_id> --trace   # 표기 → 붙은 노드 · 관계 → 상대 (어느 노드에 어떻게 붙었나)
python run.py show doc <doc_id>          # 시트 역할 요약 · 참조 청크 수 · 이 문서가 만든 노드·큐
python run.py show log gate              # 관계가 안 붙었으면 여기 — relation_patterns에 없는 삼항
python run.py platform queue auto_node   # 새로 선 노드 — 사양 시트라면 유닛·부품이 여기 쌓이는 게 정상
python run.py viewer --no-browser        # 그래프 · 연결 현황(문서 깔때기) · 노드 → 원본 열기
```

`--trace`는 값마다 `이송 유닛!R2 · 모터 → 노칭::이송 유닛::모터  [new · none · 소속 출처 시트]` 아래에
`└ part_of ← 노칭::이송 유닛 (소속(시트))`처럼 읽는다 — 「표기 → 붙은 노드」, 「관계 화살표 상대 (붙은 길)」. 붙은 길은
`소속(<from>)` · `관계` · `폴백`(소속도 관계도 없어 좌표에) 셋이다.

이상하면 [`2B_작업가이드.md` §7 증상표](2B_작업가이드.md#7-증상표--증상--원인--칠-명령) — 가격·일정 항목이 뽑혔다 · 관계가 없다 · 노드가 0이다 · 시트가 통째로 한 청크다 · 부품이 전부 `new`로 선다가 거기 있다.

## 5. 둘째 문서부터

시트 판이 문서마다 다르면 **터미널에서 하나씩** `ingest-file`이 맞다 — `ingest-dir`(배치)는 물을 수 없어 그 문서를 「시트 역할 미정」으로 건너뛰고 `--sheets "…"` 문자열을 화면에 준다(복사해서 치면 된다). 문서가 많아지면 **자동 모드** `python run.py ingest-dir <폴더> --sheets auto` — 로직과 LLM이 같은 시트만 자동으로 정하고 어긋난 시트는 `ref` + 승격 후보로 남긴다(화면과 기록). 몇 부를 사람 지정으로 넣은 뒤 `python run.py show dist sheets`의 일치율을 보고 넘어간다.

**설비 문서가 품질 이야기도 한다면** — doc_type의 렌즈(그 문서 종류가 보는 층 목록)를 늘린다: `python -m cli.register lenses rfq <골격 층>,quality`. 청크마다 층마다 그 층의 어휘로 따로 뽑고(개체는 같은 노드로 모인다), 층 어휘가 한 종도 안 나오는 청크는 그 층에서 LLM을 부르지 않는다. 인입 전에 `렌즈 예고 — 렌즈 2 × 청크 n → 거름 뒤 LLM ≤ m회` 한 줄이 뜬다.

## 6. 여기서 정하지 않은 것

- **시트 제안 문턱**(손잡이 `sheet_thresholds` 0.8/8/15 · `sheet_min_hits` 1) — 사내에서 `knobs.json`으로 정한다. 재료는 `python run.py show dist sheets`(로직 제안 = 사람 답 일치율).
