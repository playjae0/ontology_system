# 골격 작성 가이드 — 사내 공정을 seed로 만드는 법

> **골격이 무엇인가**: 이 시스템의 **좌표계**다. 모든 문서의 좌표(anchor)가 여기 해소되고, 질의의 출발점이 여기다.
> **사람 몫 중 가장 무겁다** — 명세 18KB · 금지 규칙 23개. 그러나 **양식은 파일 하나**고, 초안은 LLM에게 시킬 수 있다(§3.7 규약 3 — 2A 개정).
> 실증: 배터리 골격을 기계가공 골격으로 통째로 갈아도 **코드 변경 0**으로 부팅·질의가 됐다.

## 1. 양식 — `layers/process/skeleton.json` (seed_format 3)

```json
{
  "seed_format": 3,
  "AXIS_LABELS": { "cathode": "양극", "anode": "음극" },
  "TREE": [
    { "조립": [
      { "노칭": ["::cathode", "::anode",
                 "전극 언와인딩", "노칭 타발", "비전검사"] },
      { "스태킹": [
          {"@unordered": "전극 시트 공급"},
          "적층", "비전검사", "스택 테이핑"] },
      { "탭용접": ["::cathode", "::anode",
                   {"pre용접": "@split"}, {"main용접": "@split"}] }
    ]}
  ],
  "ALIASES": { "노칭": ["notching", "NC"] }
}
```

**칸 넷이 전부다:**

| 칸 | 뜻 | 규칙 |
|---|---|---|
| `seed_format` | 양식 판 번호 | `3` 고정 |
| `AXIS_LABELS` | 극성 축 이름과 한글 라벨 | 축이 없는 공정이면 생략 가능 |
| `TREE` | 공정 트리 | **중첩 = 구조(part_of) · 배열 순서 = 흐름(precedes)** |
| `ALIASES` | 사람이 보증하는 별칭 | **정확 일치로만 쓰인다** — 포함 규칙 아님 |

## 2. TREE의 문법 — 두 축과 마커 4종

**대원칙 (§3.9): 분해는 구조, 순서는 지식.**
- **중첩**이 `part_of`를 낳는다 — "노칭은 조립의 하위다"
- **배열 순서**가 `precedes`를 낳는다 — "노칭 다음은 스태킹이다". **순서는 회사 표준의 「대표 흐름」 한 벌**이다 — 공장·세대별 미세 차이는 "대표"라는 지위가 흡수한다

| 마커 | 뜻 | 언제 쓰나 |
|---|---|---|
| `"::축값"` | 이 공정에 극성 인스턴스가 있다 (`노칭::cathode` 자동 생성) | 양/음극처럼 같은 공정이 축별로 따로 도는 경우 |
| `{"이름": "@split"}` | 이 하위 공정도 축별로 갈린다 | 부모가 `::`를 가질 때 그 아래서 |
| `{"@unordered": "이름"}` | **순서 무주장** — 흐름에 넣지 않는다 | 공급·회수처럼 병행하는 것 |
| `@noflow` | 이 형제 전체의 순서를 주장하지 않는다 | 순서가 문서에 없을 때 |

**쓰지 않는 것**: `tier` · `polarity` · `parent` — **loader가 파생한다**(조항 J23). 손으로 적으면 실물과 어긋난다.

## 3. 함정 — 실측으로 확인된 것들

| 함정 | 귀결 |
|---|---|
| 순서를 모르면서 형제로 나열 | **거짓 순서**가 박힌다 — precedes는 지식 주장이다. 모르면 `@unordered`/`@noflow` |
| ALIASES에 포함 규칙 기대 | alias는 **정확 일치만**이다. 포함을 걸면 「cathode 노칭 프레스」가 무극성 노드에 흡수된다(실측) |
| 설비를 골격에 넣기 | 골격은 **공정(Process)만**이다. 설비(Unit)는 문서 인입이 만든다 |
| 층마다 골격 사본 | **골격은 1벌**(J7) — 사본은 노드 유일성(P4)을 깨고 개정을 N배로 만든다 |
| 짧은 모호 이름("비전검사"가 두 곳) | 시스템이 접두 키로 처리하지만, **사전 미등재**로 남는다 — 뷰가 경고를 낸다 |

## 4. LLM 초안 절차 (§3.7 규약 3 — 조건 셋)

**①입력은 표본이 아니라 공정 설명 문서** · **②초안은 시스템 밖에서** · **③확정 전 bootstrap 뷰로 대조.**

### 초안 프롬프트 — **실물 seed를 함께 붙인다**

양식을 프롬프트에 베껴 쓰지 않는다. **`layers/process/skeleton.json`(2.9KB)을 그대로 첨부**하고 그 구조를 따르게 한다 — 자산이 정본이다.

**붙일 것 둘**: ①기존 `skeleton.json` (양식 + 마커 4종의 실제 용례) ②사내 공정 설명 문서

### 초안 프롬프트 (복사해서 쓴다)

```
당신은 공정 문서를 읽고 공정 트리 seed를 만든다. 출력은 JSON 하나뿐이다.

[첨부] ①기존 층의 skeleton.json (양식) ②사내 공정 설명 문서

[출력] 새 seed JSON — **첨부 ①의 구조를 그대로 따른다.**
- 중첩 = 소속(part_of), 배열 순서 = 공정 순서(precedes)
- 마커는 넷뿐이다: "::축값" · {"이름": "@split"} · {"@unordered": "이름"} · "@noflow"
- tier·polarity·parent는 적지 않는다 — 시스템이 파생한다

[규율 — 어기면 좌표계 전체가 오염된다]
1. 문서에 없는 공정을 만들지 않는다. 문서가 안 말하면 없는 것이다.
2. 순서가 서술되지 않은 형제는 @unordered로 낸다 — 나열 순서를 흐름으로 지어내지 않는다.
3. 골격에는 공정만 넣는다 — 설비·인자·결함은 넣지 않는다.
4. 확신 없는 이름은 ALIASES에 넣지 않는다 — 별칭은 사람의 보증이다.
5. 판단이 갈린 자리는 JSON 뒤에 "확인 필요:" 목록으로 따로 적는다.

[문서]
(공정 설명 문서를 여기 붙인다)
```

### 확정 절차

```
1. LLM 출력 JSON을 layers/process/skeleton.json으로 저장 (시스템 밖에서)
2. python3 run.py init --fresh && python3 run.py bootstrap
3. 화면의 「파생 대표 흐름 (사람 대조용)」을 문서와 대조:
   - 순서가 실제 공정 순서인가          ← 지어낸 순서 검출
   - (무주장: …) 목록이 맞는 위치인가
   - (짧은 이름 모호 …) 경고 확인
   - mirrors 쌍 수가 극성 공정 수와 맞나
4. 틀리면 seed 수정 → 2로. 맞으면 확정 — 이 대조가 승인이다
```

**뷰 대조의 한계 하나**: 뷰는 **있는 것**의 검증이다 — **빠진 공정**은 못 잡는다. 문서의 공정 목록과 노드 수를 사람이 한 번 세어 맞춘다.

## 5. 규모 감각

배터리 mock 골격 = **TREE 노드 30(중복 이름 제외 29)**·3단 트리·극성 축 1벌 → **2.9KB**. 실제 사내 골격이 공정 100개라도 **하루 안의 일**이다 — 어려움은 양이 아니라 **"대표 흐름을 무엇으로 선언하나"**라는 판단이고, 그것이 사람 몫인 이유다.

## 6. config는 왜 여기 없나

골격을 심으면 config 19종 중 `skeleton`·`skeleton_version`·`polarity`가 따라온다. 나머지는 **config 작성 가이드**(별도)의 몫 — 실질 작성 대상은 11종이고 절반은 비워도 돈다.
