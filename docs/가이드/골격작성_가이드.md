# 골격 작성 가이드 — 사내 공정을 seed로 만드는 법

> **골격이 무엇인가**: 이 시스템의 **좌표계**다. 모든 문서의 좌표(anchor)가 여기 해소되고, 질의의 출발점이 여기다.
> **사람 몫 중 가장 무겁다** — 명세 18KB · 금지 규칙 23개. 그러나 **양식은 파일 하나**고, 초안은 LLM에게 시킬 수 있다(§3.7 규약 3 — 2A 개정).
> 실증: 배터리 골격을 기계가공 골격으로 통째로 갈아도 **코드 변경 0**으로 부팅·질의가 됐다.

## 1. 양식 — `layers/<골격 층>/skeleton.json` (seed_format 3)

> **폴더 이름은 자유다** — 골격 층은 폴더 이름이 아니라 config `categories`에 **`Process`를 선언한 층**이다. 사내처럼 설비 라인업을 골격으로 쓰면 `layers/equipment/`로 세워도 된다(config `"layer": "equipment"`). 카테고리 라벨 `Process`는 바꾸지 않는다(좌표 대상 라벨 — 뜻은 정의문이 정한다). `doctor` 첫 줄의 `좌표 층 <이름>`으로 확인한다. 아래 예시의 `process`는 레포 mock seed의 이름일 뿐이다.

```json
{
  "seed_format": 3,
  "AXIS_LABELS": { "cathode": "양극", "anode": "음극" },
  "TREE": [
    { "조립": [
      { "노칭": ["::cathode", "::anode",
                 "전극 언와인딩", "노칭 타발", "비전검사"] },
      { "스태킹": [
          {"@unordered": "전극 시트 공급"},
          "적층", "비전검사", "스택 테이핑"] },
      { "탭용접": ["::cathode", "::anode",
                   {"pre용접": "@split"}, {"main용접": "@split"}] }
    ]}
  ],
  "ALIASES": { "노칭": ["notching", "NC"] }
}
```

**칸 넷이 전부다:**

| 칸 | 뜻 | 규칙 |
|---|---|---|
| `seed_format` | 양식 판 번호 | `3` 고정 |
| `AXIS_LABELS` | 극성 축 이름과 한글 라벨 | 축이 없는 공정이면 생략 가능 |
| `TREE` | 공정 트리 | **중첩 = 구조(part_of) · 배열 순서 = 흐름(precedes)** |
| `ALIASES` | 사람이 보증하는 별칭 | **정확 일치로만 쓰인다** — 포함 규칙 아님 · 영문 대소문자만 다른 표기는 2차 대조로 맞는다(가리키는 노드가 하나일 때만) |

**언어 병기 — canonical은 한 언어다.** 사내 표준명 하나를 canonical로 두고(인입 전에 확정 — 바꾸면 새 노드 · 재구축 `python run.py rebuild`) 다른 언어 표기는 `ALIASES`에 둔다. canonical에 두 언어를 함께 쓰지 않는다(「노칭(Notching)」 — 문서에 그대로 나오지 않는 표기라 적중 0이고 화면만 복잡해진다).

**별칭 체크리스트** — 노드마다 아래를 본다(창작 예시 `노칭`):

| 변형 | 예 | 넣나 |
|---|---|---|
| 다른 언어 | `Notching` | 넣는다 |
| 약칭 | `NC` | 넣는다 |
| 설비 접미 | `노칭 설비` · `Notching M/C` | 넣는다(겸 단이면 §3-a 6) |
| 띄어쓰기·붙여쓰기 | `노칭설비` | 넣는다 — 한글 변형은 자동 대조가 없다 |
| 영문 대소문자 | `notching` · `NOTCHING` | **넣지 않는다** — 사전 조회·층 어휘 적중·좌표가 2차로 대소문자를 무시해 맞춘다. 대소문자만 다른 표기가 노드 둘을 가리키면 맞추지 않는다(미스 + 로그) |

## 2. TREE의 문법 — 두 축과 마커 4종

**대원칙 (§3.9): 분해는 구조, 순서는 지식.**
- **중첩**이 `part_of`를 낳는다 — "노칭은 조립의 하위다"
- **배열 순서**가 `precedes`를 낳는다 — "노칭 다음은 스태킹이다". **순서는 회사 표준의 「대표 흐름」 한 벌**이다 — 공장·세대별 미세 차이는 "대표"라는 지위가 흡수한다

| 마커 | 뜻 | 언제 쓰나 |
|---|---|---|
| `"::축값"` | 이 공정에 극성 인스턴스가 있다 (`노칭::cathode` 자동 생성) | 양/음극처럼 같은 공정이 축별로 따로 도는 경우 |
| `{"이름": "@split"}` | 이 하위 공정도 축별로 갈린다 | 부모가 `::`를 가질 때 그 아래서 |
| `{"@unordered": "이름"}` | **순서 무주장** — 흐름에 넣지 않는다 | 공급·회수처럼 병행하는 것 |
| `@noflow` | 이 형제 전체의 순서를 주장하지 않는다 | 순서가 문서에 없을 때 |

**쓰지 않는 것**: `tier` · `polarity` · `parent` — **loader가 파생한다**(조항 J23). 손으로 적으면 실물과 어긋난다.

## 3. 함정 — 실측으로 확인된 것들

| 함정 | 귀결 |
|---|---|
| 순서를 모르면서 형제로 나열 | **거짓 순서**가 박힌다 — precedes는 지식 주장이다. 모르면 `@unordered`/`@noflow` |
| ALIASES에 포함 규칙 기대 | alias는 **정확 일치만**이다(영문 대소문자만 2차로 무시). 포함을 걸면 「cathode 노칭 프레스」가 무극성 노드에 흡수된다(실측) |
| 설비를 골격에 넣기 | 골격은 **공정(Process)만**이다(뼈대층이면 공정 두 단 — 상위 공정 = 설비 단위 · 하위 공정 = unit 단위 · §3-a). 조립 라인에서는 공정 = 설비라 골격 노드 하나가 「노칭 공정」이자 「노칭 설비」다 — 유닛·부품(Unit·Component)은 문서 인입이 만든다. 골격 아래에 유닛 층을 더 파면 그 노드가 전부 Process가 되고 벤더가 바뀔 때마다 골격 확정을 다시 한다 |
| 골격 노드 이름을 바꾸기(`노칭` → `노칭 설비`) | canonical이 바뀌면 **새 노드**다 — 기존 엣지(품질층 `occurs_in` 포함)·문서 좌표가 옛 이름을 본다 → 재구축 한 명령 `python run.py rebuild`(그 아래 키만 재판정 · 옛 이름을 쓰던 사람 연산은 끝 보고의 「대상 없음」 목록 — 2B 가이드 §7). 설비명은 **`ALIASES`에 얹는다**(bootstrap만 · 그래프·사전 보존) |
| 층마다 골격 사본 | **골격은 1벌**(J7) — 사본은 노드 유일성(P4)을 깨고 개정을 N배로 만든다 |
| 짧은 모호 이름("비전검사"가 두 곳) | 시스템이 접두 키로 처리하지만, **사전 미등재**로 남는다 — 뷰가 경고를 낸다 |

### 바꾸는 종류에 따라 뒤가 다르다 (2026-09-22 · 설비 논의)

| Change in skeleton.json | Effect | After edit |
|---|---|---|
| `ALIASES` 추가(공정명에 설비명·약칭) | 노드 그대로 · 사전 등재 | `skeleton-status` → `skeleton-confirm` → **`bootstrap`(fresh 없이)** |
| 형제 끝에 노드 추가(신규 공정 · 화성 같은 것) | 노드 추가 · 기존 불변 | 같음 |
| 노드 이름 변경 · 부모 변경 · 층 추가 | 구조 변경 — 옛 노드가 남고 좌표가 갈린다 | **재구축 한 명령 `python run.py rebuild`**(계획 → `--yes` · 판정은 대장에서 재생하고 바뀐 키만 재판정 · 사람 판단은 이름으로 되살리고 못 찾은 것은 「대상 없음」 목록 — 2B 가이드 §7) |

골격을 설비 관점으로 읽고 싶으면 **이름을 바꾸지 말고 별칭을 얹는다** — 문서의 `process_ref`는 공정명으로 와 있고, 얻는 건 화면 이름 하나, 잃는 건 전량 재인입이다.

### 스테이션을 몇 단에 두나 = 겸이 걸리는 단

공정 = 설비(스테이션)인 라인에서는 골격 노드가 공정이자 설비다. 그 사실은 골격이 아니라 **공통 config의 겸**으로 선언한다 — `"Process": {"home": …, "also": {"Unit": ["sub", "detail"]}}`(config작성_가이드 §0-a). 단은 loader가 깊이에서 파생한다(1단 = `main` · 2단 = `sub` · 3단 이하 = `detail`) — **스테이션을 두는 깊이가 곧 겸의 단**이다. 대공정(`main`)이 설비가 아니면 `main`은 빼고 적는다.

| 표기 | 자리 | 귀결 |
|---|---|---|
| 「노칭 unit」·「노칭 설비」(스테이션 이름 + 설비어) | 그 스테이션의 `ALIASES` | 문서가 그 좌표 아래서 이 표기를 Unit으로 뽑으면 **스테이션 자신**으로 해소된다(새 Unit 0 · 대장 `self_coord`) — 겸이 선언된 단일 때만 |
| 하위 공정(unit 단위 — 설비 안에서 한 동작을 맡는 단) | **골격 노드다**(하위 단 `Process` · 겸 `Unit`) | 상위 공정(설비 단위)과 같은 골격 · 단만 다르다(§3-a) |
| 그 아래 구성 기계·부품(프레스 금형·커터 날 같은 것) | 골격에 두지 않는다 — `Component` | 문서 인입이 골격 노드에 붙인다 · 골격에 없는 설비 표기는 인입이 Unit으로 만든다(뼈대가 빠뜨린 것 — 사람이 볼 자리) |

별칭 없이 겸만 두면 「노칭 unit」은 사전에서 스테이션으로 해소되지 않아 새 Unit이 된다 — 둘 다 필요하다.

## 3-a. 뼈대층(설비·공정)을 처음 세울 때 — 이 절은 그때만 쓴다

> **한정**: 통용 규칙이 아니다. **설비층·공정층의 config·골격을 처음 뽑을 때**(사람이 쓰거나 사내 LLM에 초안을 맡길 때)만 주는 정보다. 다른 층(품질 등)의 설계·추출에는 쓰지 않는다 — 런타임 지시문(`prompts/`)에도 넣지 않는다(넣으면 모든 층 추출에 들어간다).

1. **골격은 공정 두 단이다** — 상위 공정(설비 단위)과 하위 공정(unit 단위). 둘 다 골격 `Process` 노드이고, 둘 다 설비이기도 하다 → 공통 config의 겸 `"Process": {"also": {"Unit": [두 단]}}`. 단은 loader가 깊이에서 파생한다 — 대공정이 1단(`main`)이면 두 단은 `["sub", "detail"]`.
2. **카테고리를 나누는 기준은 엣지다** — 다른 엣지가 붙어야 하면 다른 노드·카테고리로 나눈다. 지금은 두 단에 다른 관계가 필요 없어 나누지 않는다(`Process` + 겸 `Unit`).
3. **단별 설비 표기는 그 노드의 `ALIASES`** — 「○○ 설비」·「○○ unit」 같은 표기를 언어·약칭·띄어쓰기 변형마다 넣는다(§1 별칭 체크리스트). 정확 일치라 빠진 변형은 해소되지 않는다 — 영문 대소문자만은 2차 대조가 맞춘다(넣지 않아도 된다).
4. **구분은 그 아래부터다** — 골격 노드 아래에 `Component`(설비층 — 구성 기계·부품)와 `Property`(공정층 — 파라미터·관리 특성)가 갈라 붙는다. 골격에 없는 설비 표기는 인입이 Unit으로 만든다 — 뼈대가 빠뜨린 것이니 큐(`auto_node`)에서 사람이 본다.
5. **다른 층(공정층 포함)은 골격 카테고리(`Process`·`Unit`)를 선언하지 않는다** — 골격 이름은 선언 없이 붙는다(부착·부모 후보가 골격에서 온다) · 관계 패턴(`relation_patterns`)에만 쓴다. 선언하면 그 층 문서에서 골격 밖 이름을 골격 카테고리로 뽑을 수 있게 되고, 그 이름은 노드가 되지 않고 큐(`orphan_anchor`)로 간다 — 골격은 사람이 만든다. 골격에 없는 노드(`Component` 등)를 다른 층 문서에서 뽑으려면 그 층이 그 카테고리를 선언한다(선언 = 뽑아도 된다는 허가 + 정의문 — 노드는 집에 하나다).
5-1. **다른 층 문서의 공정 이름은 좌표로 들어간다** — 표의 상위 공정 열은 `process_group`, 하위 공정 열은 `process_ref`다. **열 이름이 「Process」·「Product」·「공정」·「Operation」 무엇이든 값이 골격 이름·별칭이면 좌표**이고, `Property`·`Component` 같은 개체로 매핑하지 않는다. 그 층의 개체(관리항목 등)는 이 좌표 아래 붙는다(예: 「cutter · 관리항목 X · 관리값 000」 → 좌표 cutter · `Property` 「cutter::X」 · 000은 attribute). **등록 뒤 확인**: `python run.py show schema <dt>`에서 공정 이름 열이 anchor(`process_group`·`process_ref`)인가 — entity로 나오면 등록을 다시 한다. 정본은 문서 3 §3.6 공정 운영 원칙(9개).
6. **겸을 켜는 셋** — 공통 config `also` · 골격 `ALIASES` · 층 config 정의문(「○○ unit은 그 공정 자신이다」). 셋이 다 있어야 문서가 좌표 아래에서 「○○ unit」을 Unit으로 뽑았을 때 **그 공정 노드 자신**으로 해소된다(새 노드 0). 없으면 **같은 실물이 두 노드**가 된다. 확인: `python run.py bootstrap` 끝 줄 `골격 'Process'(<층>): 겸 Unit(…) · 겸 단 별칭 n개`(꺼짐·반쪽이면 그렇게 말한다 — `doctor`도 같은 줄) · `python run.py show node <상위 공정>`의 「겸 Unit」 · 판정 대장 `path=self_coord`.
7. **요청문 틀 — 사내 LLM에 초안을 맡길 때** (이 절 1~6과 공장의 공정 목록을 함께 넣는다 · 아래 이름은 창작 예시):

```
당신은 지식 그래프의 뼈대층(설비층·공정층) 초안을 만든다. 출력은 아래 셋이고 각각 JSON 하나다.

[개념 — 이 작업에만 쓴다]
- 골격은 공정 두 단이다: 상위 공정(설비 단위) · 하위 공정(unit 단위). 둘 다 Process이고 설비(Unit)를 겸한다.
- 그 아래 구성 기계·부품은 Component(설비층), 파라미터·관리 특성은 Property(공정층)다. 골격에 넣지 않는다.
- 단별 설비 표기(「<공정> 설비」·「<공정> unit」 등)는 그 골격 노드의 ALIASES에 변형마다 넣는다.
- 다른 층(공정층 등) 문서에 나오는 공정 이름은 좌표다(상위 → process_group · 하위 → process_ref) — 그 층은 Process·Unit을 선언하지 않고, 공정 이름 열을 Property로 만들지 않는다.
- 공정층 Property 정의문에는 제외 서술 「공정·설비 단위의 이름은 제외 — 그것은 좌표」를 넣는다.

[출력]

2. 층 config의 categories 정의문 — 설비층(Process·Unit·Component) · 공정층(Property · 부품을 말하면 Component —
   Process·Unit은 선언하지 않는다)
3. 공통 config는 bootstrap이 만든다(집·쓰는 층) — 제안할 것은 두 줄: 겸 "Process": {"also": {"Unit": [두 단]}} ·
   이름 규칙 "canonical_scope": {"bind_categories": [...]} — 질문 「공정을 모르면 뜻이 없는가」로
   (부품·파라미터 = 넣음 · 공정 자체·불량 유형·영향 = 넣지 않음). 층 config에는 canonical_scope를 넣지 않는다.

[규율] 첨부에 없는 공정 이름을 만들지 않는다 · 판단이 갈린 곳은 「확인 필요:」에 적는다.
(예: 상위 공정 「코팅」 · 하위 공정 「코팅 헤드 정렬」 · 별칭 「코팅 설비」「Coating unit」 — 창작)
```

## 4. LLM 초안 절차 (§3.7 규약 3 — 조건 셋)

**①입력은 표본이 아니라 공정 설명 문서** · **②초안은 시스템 밖에서** · **③확정 전 bootstrap 뷰로 대조.**

### 초안 프롬프트 — **실물 seed를 함께 붙인다**

양식을 프롬프트에 베껴 쓰지 않는다. **`layers/process/skeleton.json`(2.9KB)을 그대로 첨부**하고 그 구조를 따르게 한다 — 자산이 정본이다.

**붙일 것 둘**: ①기존 `skeleton.json` (양식 + 마커 4종의 실제 용례) ②사내 공정 설명 문서

### 초안 프롬프트 (복사해서 쓴다)

```
당신은 공정 문서를 읽고 공정 트리 seed를 만든다. 출력은 JSON 하나뿐이다.

[첨부] ①기존 층의 skeleton.json (양식) ②사내 공정 설명 문서

[출력] 새 seed JSON — **첨부 ①의 구조를 그대로 따른다.**
- 중첩 = 소속(part_of), 배열 순서 = 공정 순서(precedes)
- 마커는 넷뿐이다: "::축값" · {"이름": "@split"} · {"@unordered": "이름"} · "@noflow"
- tier·polarity·parent는 적지 않는다 — 시스템이 파생한다

[규율 — 어기면 좌표계 전체가 오염된다]
1. 문서에 없는 공정을 만들지 않는다. 문서가 안 말하면 없는 것이다.
2. 순서가 서술되지 않은 형제는 @unordered로 낸다 — 나열 순서를 흐름으로 지어내지 않는다.
3. 골격에는 공정만 넣는다 — 하위 공정(unit 단위)은 공정이다(이름에 unit·설비가 붙어도 넣는다) · 그 아래 구성 기계·부품·인자·결함은 넣지 않는다.
4. 확신 없는 이름은 ALIASES에 넣지 않는다 — 별칭은 사람의 보증이다.
5. 판단이 갈린 자리는 JSON 뒤에 "확인 필요:" 목록으로 따로 적는다.

[문서]
(공정 설명 문서를 여기 붙인다)
```

### 확정 절차

```
1. LLM 출력 JSON을 layers/process/skeleton.json으로 저장 (시스템 밖에서)
2. python3 run.py init --fresh && python3 run.py bootstrap
3. 화면의 「파생 대표 흐름 (사람 대조용)」을 문서와 대조:
   - 순서가 실제 공정 순서인가          ← 지어낸 순서 검출
   - (무주장: …) 목록이 맞는 위치인가
   - (짧은 이름 모호 …) 경고 확인
   - mirrors 쌍 수가 극성 공정 수와 맞나
4. 틀리면 seed 수정 → 2로. 맞으면 확정 — 이 대조가 승인이다
```

**뷰 대조의 한계 하나**: 뷰는 **있는 것**의 검증이다 — **빠진 공정**은 못 잡는다. 문서의 공정 목록과 노드 수를 사람이 한 번 세어 맞춘다.

## 5. 규모 감각

배터리 mock 골격 = **TREE 노드 30(중복 이름 제외 29)**·3단 트리·극성 축 1벌 → **2.9KB**. 실제 사내 골격이 공정 100개라도 **하루 안의 일**이다 — 어려움은 양이 아니라 **"대표 흐름을 무엇으로 선언하나"**라는 판단이고, 그것이 사람 몫인 이유다.

## 6. config는 왜 여기 없나

골격을 심으면 층 config 문법 키 19종 중 `skeleton`·`skeleton_version`·`polarity`가 따라온다. 나머지는 **config 작성 가이드**(별도)의 몫 — 실질 작성 대상은 11종이고 절반은 비워도 돈다.
