# 역할(role) 판정 가이드 — 이 열을 무엇으로 두면 나중에 무엇이 돌아오나

> **누가 읽나**: 등록 검수에서 열마다 role을 확인·교정하는 사람(`review --instruct "D열은 attribute"` · 열 판정 대장 `<상태>/registry/review/<dt>/columns.json` — 행은 열 프로파일 ∪ 어댑터가 쓰는 열 전부이고 스키마 필드마다 행이 있어야 한다(G4G · B76 ②)). 정의의 정본은 문서 2 §2.4 — 이 문서는 **판정하는 사람 순서**로 다시 쓴 것이고, 각 role이 **구축에서 무엇을 하고 질의에서 어떻게 돌아오는지**를 코드 실물(`core/build/build.py` · `core/query/query.py`)로 답한다.
> **한 문장**: role은 의미 분류가 아니라 **쓰기 동작**이다 — anchor로 골격에 닻을 내리고, entity로 노드를 데려오고, attribute로 노드에 값을 붙이고, content는 청크로 보존해 노드에 연결하고, meta는 출처 장부에만 적는다. 같은 글자 「노칭」도 anchor면 「찾아라」, entity면 「데려와라」다.

## 0. 먼저 — 답이 돌아오는 길은 둘뿐이다

질의(`run.py query`)는 두 채널로 답한다. **role은 그 열의 값이 어느 채널로 돌아올지를 정한다.**

| Channel | What it carries | Which roles feed it |
|---|---|---|
| `[그래프 사실]` | 링킹된 노드 주변의 엣지와 값을 층 config `fact_templates`로 **문장화**한 것 — 순서(precedes)·구조(part_of)·규격(attr) | anchor · entity(노드와 엣지) · attribute(값 — **템플릿이 있을 때만**) |
| `[문서 근거]` | 링킹된 노드에 `describes`로 붙은 **청크 원문** — 직접 링킹 노드 우선, 상한 8, 최신순 | content(청크) |

돌아오지 않는 것: meta(장부만) · 템플릿 없는 attribute · 노드에 못 붙은 content(부착 대상 미해소). **임베딩·하이브리드 검색은 아직 없다** — 청크는 「노드를 거쳐서」만 돌아온다(BM-25는 골든셋 대조군이지 답 경로가 아니다 — 문서 5 §5.5-1). 그래서 「content로 두면 검색되나」의 답은: **그 청크가 붙은 노드가 질문에서 링킹되면** 돌아온다.

## 1. 판정 순서 — 위에서부터 첫 「예」가 role이다

| # | Question about the column | Role | Then check |
|---|---|---|---|
| 1 | 값이 **골격(사람이 확정한 공정 트리·닫힌 목록)의 이름**인가 — 대공정·세부공정·고장영향 분류처럼 | **anchor** | 정확 일치·alias만 해소한다(LLM·유사도 없음). 골격에 없는 표기는 `orphan_anchor` 큐 → alias 등록 또는 골격 수정. 리스트 값 불가 |
| 2 | 이름을 갖고 **다른 문서에서도 같은 것을 가리킬 수 있는** 개체인가 — 설비·관리항목·고장모드·원인 | **entity** | `category`가 **그 층 config의 categories 안**이어야 등록이 통과한다(G4C). 사전 → 후보 → LLM 동일성 판정 → 매칭/신규/불확실 큐. 리스트면 파서가 전개 |
| 3 | **어떤 것에 붙는 값**인가 — 규격·공차·주기·샘플 수·심각도·측정방법 | **attribute** | `attach_to_field`(붙을 열) · `attr_name`(저장 키). **답에 나오려면 층 config `fact_templates`에 `attr:<attr_name>` 템플릿이 있어야 한다** — 지금 실물: process는 `attr:spec`·`attr:측정방법`, quality는 `attr:severity`뿐. 없으면 저장은 되고 화면(`show node`)에는 보이나 **질의 답에는 안 나온다** |
| 4 | **문장으로 읽히는 서술**인가 — 조치·대응·설명·비고. **길이는 기준이 아니다** — 짧아도 조치·설명 계열이면 content | **content** | `attach_to_field`(어느 노드에 붙일지 — table은 추출 없이 직접 지정). 필드마다 별도 청크(`{record}-{필드}`). 부착 대상이 미해소면 청크는 보존되지만 답에는 안 나온다 |
| 5 | 내용이 아니라 **내용의 신상정보**인가 — 문서번호·개정일·작성자·행 번호·공정번호(`process_no`) | **meta** | 저장만 · 그래프 무기록 · 질의 불가. 「나중에 필요할지 모른다」는 meta의 근거가 아니다 — 필요하면 attribute다 |
| — | 위 어느 것도 아니거나 지금 판단이 안 선다 | **unmappable** (`excluded` / `undecided`) | 등록 판단의 기록. `undecided`는 열 판정 대장에 `open`으로 남아 다음 회차가 묻는다 |

## 2. 각 role — 구축에서 하는 일 · 질의에서 돌아오는 것 · 안 돌아오는 경우

| Role | Build (write action) | Query (how it comes back) | Silent cases (stored but never answered) |
|---|---|---|---|
| anchor | 골격 노드를 **찾는다**(만들지 않는다). 해소된 노드는 edges의 `@좌표필드`·부착 폴백·좌표 태깅에 쓰인다 | 질문의 표기가 링킹되는 출발점. `part_of`·`precedes` 사실이 여기서 나온다 | 골격에 없는 표기 → `orphan_anchor`(큐 해소 전까지 그 행의 attribute·content도 보류) |
| entity | 노드 생성/매칭 + `edges` 선언대로 엣지 | 링킹 대상 · 그래프 사실의 주어/목적어 · describes 청크의 부착점 | category가 층 목록 밖(등록에서 막힘) · relation이 `relation_patterns` 밖(커밋 게이트 거부 — `show log gate`) |
| attribute | 노드 필드에 `{value, provenance}`(맥락형은 `{context, value, provenance}`) | `fact_templates["attr:<name>"]`이 있으면 `[그래프 사실]` 한 줄 | 템플릿 없음 · 부착 대상 미해소(보류) · 값이 dict/list인데 템플릿이 스칼라만 찍음 |
| content | 청크 저장 + 대상 노드에 `describes` | 대상 노드가 링킹되면 `[문서 근거]`에 원문(직접 > 확장 · 상한 8) | 대상 미해소(`orphan_chunk_link`) · 질문이 그 노드를 링킹하지 못함(표기 불일치 — 사전 alias) |
| meta | 출처 장부(provenance) | — | 전부(설계) |

## 3. 「실제 문서를 넣으면 이 내용이 살까」 — 살리려면 셋을 맞춘다

1. **노드가 서야 한다** — anchor가 골격에 맞고 entity의 category가 층 목록 안. `그래프 노드 0`이면 role이 아니라 골격 미확정·좌표 불일치다(가이드 §5.3).
2. **값이 문장이 돼야 한다** — attribute를 새로 두면 `layers/<층>/config.json::fact_templates`에 `attr:<attr_name>` 한 줄을 같이 둔다(config작성_가이드 §5). 템플릿이 없는 attribute는 **보이지 않는 저장**이다.
3. **청크가 붙을 노드가 있어야 한다** — content의 `attach_to_field`가 entity/anchor 열이어야 한다. attribute 열에 붙일 수 없다.

확인은 인입 뒤 `show node <이름>`(값·근거 청크가 달렸나) → `query "<그 노드를 부르는 질문>"`(두 채널에 나오나). 이 둘이 role 판정의 실행 판정이다.

## 4. 흔한 오판

| Mistake | Symptom later | Right call |
|---|---|---|
| 조치·대응 열을 attribute로 | 템플릿이 없어 답에 0건 · 문장이 값 필드에 통째로 | content + `attach_to_field` |
| 규격 열을 content로 | 「노칭 규격은?」에 청크 원문만 오고 사실 문장이 없다 · 개정 충돌 집계 불가 | attribute(`attr_name: spec` · 구조체 통째) |
| 골격 이름 열을 entity로 | 골격과 별개의 노드가 새로 생겨 트리가 둘 | anchor |
| 관리번호·개정일을 attribute로 | 노드마다 관리 필드가 붙고 문장화 대상이 아님 | meta |
| 같은 열을 여러 필드에 | `columns` 리스트는 「합치기」(첫 비지 않은 값)지 「둘 다」가 아니다 | 필드 하나 · 필요하면 두 필드에 각각 열문자 |
| PFMEA 문장형 원인 셀(「금형 이물 고착에 따라 punch 동작 이상」)을 entity로 | 동일성 판정이 문장을 노드로 만든다 | 짧은 원인은 entity(Failure) · 문장형은 content — table content에 추출을 켜는 `extract: true`는 이연대장 1-e ③(사용자 확정 대기) |

| Column | Role | Why |
|---|---|---|

| 영향 상세 · 예방관리 · 검출관리 | content → 고장영향 / 원인 / 고장모드 | 서술 — 청크로 붙는다 |
| 공정번호 · 문서번호 · 개정일 | meta | 신상정보 |
