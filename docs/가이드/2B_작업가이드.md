# 2B 작업 가이드 — 사내에서 당신이 하는 일, 순서대로

> **누가 읽나**: 사내에서 2B를 진행하는 사람(= 당신). 각 단계마다 **무엇을·어떻게·확인은 무엇으로**를 적었다.
> **막히면**: 명세가 답하지 않는 지점은 BLOCKER 형식(①근거 원문 ②선택지 2~3 ③귀결)으로 적어 허브 세션에 가져온다. **추측으로 메우지 않는다.**

## 0단계 · 반입 — 30분

1. 레포 클론(태그 `2a-complete` 이후 main). 사내 반입 절차는 회사 규정대로.
2. `pip install -r requirements.txt` (선택 의존 — 코어는 표준 라이브러리만으로 돈다)
3. **건강 확인**: `python3 doctor.py` → 회귀 526/526 PASS 확인. 이게 "가져온 것이 온전하다"의 판정이다.

## 1단계 · 게이트웨이 연결 — 반나절 (사내 스펙에 따라)

```bash
export LLM_GATEWAY_URL="https://…"   # 사내 게이트웨이 주소
export LLM_API_KEY="…"               # 인증 (없으면 생략)
export CHAT_MODEL="…"                # 모델명
export USE_MOCK=0
```

- **사내 게이트웨이가 OpenAI 호환**(`/chat/completions` · `choices[0].message.content`)이면 **이걸로 끝**이다.
- **다른 모양이면** `core/llm.py` 한 파일만 고친다 — `_post()`와 응답 파싱. 설정 접근이 이 파일 하나로 수렴하게 설계돼 있다.
- **확인**: `USE_MOCK=0`에서 아무 환경변수나 하나 빼고 실행 → **지점 이름을 말하며 시끄럽게 실패**해야 정상. 조용히 돌면 그게 결함이다.

## 2단계 · 골격 seed — 하루 (판단이 핵심)

`docs/가이드/골격작성_가이드.md` 따라:

1. 사내 공정 설명 문서 준비 → LLM 초안 프롬프트(가이드 §4)로 seed JSON 초안
2. `layers/process/skeleton.json` 교체 (**시스템 밖에서** — 초안을 직접 파이프라인에 넣지 않는다)
3. `python3 run.py init --fresh && python3 run.py bootstrap`
4. **화면의 「파생 대표 흐름 (사람 대조용)」을 문서와 대조** — 순서·무주장·mirrors 쌍·모호 이름. 이 대조가 승인이다.
5. **빠진 공정은 뷰가 못 잡는다** — 문서의 공정 수와 노드 수를 한 번 센다.

## 3단계 · 층 config — 반나절

`docs/가이드/config작성_가이드.md` 따라. **기존 config를 베이스로 이름만 바꾸는 게 기본이고**, 카테고리·관계만 실제 판단이다:

1. `categories` — 정의문에 "무엇과 헷갈리는가" 필수. 후보마다 3테스트
2. `relations`·`relation_patterns`·`category_pair_map` — 한 묶음. 정의문 없는 관계 금지
3. 나머지 — 베이스 복사 후 이름 수정
4. **확인**: `python3 run.py init --fresh && python3 run.py all` — 부팅 실패면 명시적 실패가 어느 키인지 말해 준다

## 4단계 · 첫 doc_type 등록 — 문서 종류당 반나절

**구축 모드가 한다 — 어댑터·스키마를 손으로 쓰지 않는다:**

```bash
python -m cli.register generate <doc_type> <층> <표본.xlsx> [힌트]
# → 검수 뷰 HTML이 생긴다. 열어서 확인:
#   ①표본 파싱 결과(트리)  ②필드→role 배정표  ③어댑터 요약
python -m cli.register review <doc_type>       # 재생성 루프 (필요 시)
python -m cli.register confirm <doc_type> --approved-by <이름>   # 승인 1회
```

- 표본은 **실물 문서**다. 등록 뒤 같은 문서를 운영 인입으로 다시 넣는다(등록은 doc_type당 1회, 인입은 문서마다).
- UNMAPPABLE로 뜬 열은 억지로 배정하지 않는다 — 스키마·출력 제외가 정상.

## 5단계 · 첫 실 인입 — 여기가 고비다. 눈으로 본다

```bash
python3 run.py all          # 또는 개별: parse → build
```

**계기판이 아니라 눈으로 확인할 것 둘** (mock으로는 검증이 안 끝난 항목):

| 볼 것 | 어떻게 | 틀리면 |
|---|---|---|
| **지도·이미지 요약이 매 인입 새로 산출되지 않는지** | 같은 문서 2회 인입 → `extract/struct_maps/{doc_id}.json`의 `source_hash` 불변 + chunk_id 동일 | chunk_id가 문서 단위로 전량 이동 — 재인입·근거 추적이 다 깨진다 |
| **`used_facts` 필터가 실제로 좁히는지** | 질의 응답의 `facts_before_filter` vs 최종 건수 | 확장 결과 전량이 상한 8에서 잘려 오답 |

**추가 확인**: `python -m cli.show node <이름>` (답의 뒷면) · `python -m cli.export html` (그래프 눈으로) · 수정 큐 확인 — auto_node·uncertain_match가 쌓이는 건 **정상**이다(사람이 자기 리듬으로 처리).

## 6단계 · 질의 확인과 골든셋 — 첫 주

1. 실제 궁금한 질문 10개를 던져 본다: `python -m cli.query ask "…"`
2. 답의 근거([그래프 사실]·[문서 근거])가 실제 문서와 맞는지 눈으로
3. **골든셋 문항 제작 시작** — 유형당 15문항(§5.3 Q1~Q5·Q8), 기준 120. 계기판이 인상이 아니라 측정이 되는 조건이다.

## 언제 허브로 가져오나

| 상황 | 형식 |
|---|---|
| 명세가 답하지 않는다 | BLOCKER 3요소 — ①근거 원문 ②선택지 2~3 ③귀결 |
| 명세와 실물이 어긋난다 | 어긋난 두 문면 + 실측 |
| 판정이 필요하다 (예: 값 충돌·구조 개정) | 해당 큐 항목 + 판단 재료 |

**명세는 사내에서 고치지 않는다** — 허브가 개정 대장 규율로 고친다. 코드 수정은 사내에서 하되 `DECISIONS.md`에 남긴다.
