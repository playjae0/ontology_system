# 2B 작업 가이드 — 사내에서 당신이 하는 일, 순서대로

> **누가 읽나**: 사내에서 2B를 진행하는 사람(= 당신). 각 단계마다 **무엇을·어떻게·확인은 무엇으로**를 적었다.
> **막히면**: 명세가 답하지 않는 지점은 BLOCKER 형식(①근거 원문 ②선택지 2~3 ③귀결)으로 적어 허브 세션에 가져온다. **추측으로 메우지 않는다.**

## 0단계 · 반입 — 30분

1. 레포 클론(태그 `2a-complete` 이후 main). 사내 반입 절차는 회사 규정대로.
2. `pip install -r requirements.txt` (선택 의존 — 코어는 표준 라이브러리만으로 돈다)
3. **건강 확인**: `python3 doctor.py` → **회귀 749/749 PASS** 확인. 이게 "가져온 것이 온전하다"의 판정이다.
   화면 중간의 **`[3] LLM 지점 9/9종의 실호출 갈래가 호출자로부터 도달 가능하다`**도 함께 본다 — 「9종에 분기가 있다」가 아니라 **실행으로 잰 배선**이다(B48).

## 1단계 · 게이트웨이 연결 — 반나절 (사내 스펙에 따라)

**설정은 파일 하나로 끝낸다.** 환경변수 export는 쓰지 않는다.

**자리를 먼저 정한다 — 셋 중 하나이고 위가 이긴다:**

| 우선 | 자리 | 언제 |
|---|---|---|
| 1 | `ONTO_CONFIG=<절대경로>` | 자리를 명시할 때. **지정하면 그 파일만 본다** |
| 2 | `~/.onto/llm.json` | 홈이 정상일 때 |
| 3 | **레포 루트 `llm.local.json`** | **홈이 예상과 다를 때 — 사내 실측: `echo $HOME` → `/config`** |

`~`가 `/config`로 풀리면 `~/.onto/llm.json`은 영영 안 잡힌다(실측 — 「설정 파일 없음(환경변수만)」). **레포 루트에 `llm.local.json`을 두는 것이 가장 확실하다:**

```bash
echo $HOME                       # 먼저 확인한다 — /config 같으면 아래 3번으로
cat > llm.local.json <<'EOF'
{
  "LLM_GATEWAY_URL": "https://사내주소",
  "LLM_API_KEY": "키",
  "CHAT_MODEL": "모델명",
  "USE_MOCK": 0
}
EOF
chmod 600 llm.local.json
python3 run.py llm-check         # ①설정 → ②도달 → ③인증 → ④응답, 단계별로 갈라 준다
```

`llm-check`가 **어느 파일을 읽었는지 경로로** 말해 준다 — 그 줄이 안 나오면 자리가 틀린 것이다.

**`LLM_CONTEXT_TOKENS`는 지금 적지 않는다 — 무제한으로 둔다.**

이 키는 게이트웨이 컨텍스트 한도이고, **적으면** 보내기 전에 크기를 재서 초과 시 보내지 않는다(B41). **안 적으면 대조 자체를 생략한다** — 무제한이다. 기본값은 코드에 없으므로 **키를 빼는 것이 곧 무제한**이고, 따로 끄는 스위치는 없다.

지금 빼 두는 이유: 사내 게이트웨이의 실제 한도를 아직 모른다. **틀린 수치를 적으면 보내도 되는 요청을 막는다** — 그 손해가 지금은 더 크다. 무제한이어도 초과 요청이 조용히 새지는 않는다: 게이트웨이가 400으로 거부하고, **응답 본문이 로그에 남는다**(B44). 원인이 늦게·게이트웨이의 말로 보일 뿐이다.

**나중에 적을 때**: `llm-check`나 사내 게이트웨이 문서에서 실제 한도를 확인한 뒤 그 값을 넣는다. 넣는 순간부터 크기 대조가 살아난다.

- `"USE_MOCK": 0`이 실호출 스위치다 — 이 키가 없으면 시스템은 mock(기본)으로 돈다.
- **셸에 남아 있는 환경변수가 파일을 덮는다** — 이전에 export한 게 있으면 `unset LLM_GATEWAY_URL LLM_API_KEY CHAT_MODEL USE_MOCK`.
- LLM을 부르는 명령은 실행 머리에 **`모드: mock` / `모드: 실호출`** 1줄을 표시한다.

### mock 관문 — 표시를 지나쳐도 막힌다 (B48)

표시는 안 읽을 수 있어서, **사람이 치는 운영 명령은 mock이면 실행 전에 멈춘다:**

```
  모드: mock (기본 — 실호출은 llm.json의 "USE_MOCK": 0 또는 USE_MOCK=0)
[register generate] mock 모드입니다 — 실산출이 아닙니다. 계속하려면 --allow-mock (실호출: llm.json의 "USE_MOCK": 0 또는 USE_MOCK=0)
```

- **대상**: `register generate/review/confirm` · `parse run` · `build` · `ingest-file` · `ingest-dir` · `query`
- **비대상**: `doctor` · `init` · `bootstrap` · `llm-check` · `skeleton-confirm`
- 일부러 mock으로 돌려볼 때만 `--allow-mock`을 붙인다. **이 문면이 뜨면 게이트웨이 설정이 안 잡힌 것이니, 먼저 위 표의 자리를 확인한다.**
- **사내 게이트웨이가 OpenAI 호환**(`/chat/completions`)이면 이걸로 끝. 다른 모양이면 `core/llm.py` 한 파일만 고친다.

**`EMBED_MODEL`은 넣지 않는다** — 임베딩은 호출부가 0건인 이연 항목이다(R6). 질의 3단(임베딩 검색)은 "구현하지 않는다"가 명세이고(§5.1-4·P7), 지금 검색은 순수 그래프다: 사전 스캔 → query_traverse 확장 → 그래프 근거.

## 2단계 · 골격 seed — 하루 (판단이 핵심)

`docs/가이드/골격작성_가이드.md` 따라:

1. 사내 공정 설명 문서 준비 → LLM 초안 프롬프트(가이드 §4)로 seed JSON 초안
2. `layers/process/skeleton.json` 교체 (**시스템 밖에서** — 초안을 직접 파이프라인에 넣지 않는다)
3. `python3 run.py init --fresh && python3 run.py bootstrap`
4. **화면의 「파생 대표 흐름 (사람 대조용)」을 문서와 대조** — 순서·무주장·mirrors 쌍·모호 이름. 이 대조가 승인이다.
5. **빠진 공정은 뷰가 못 잡는다** — 문서의 공정 수와 노드 수를 한 번 센다.

## 3단계 · 층 config — 반나절 · **건너뛸 수 있다**

> **공정층 하나로 시작하면 이 단계가 필요 없다.** `layers/process/`는 내장 층이라 이미 존재하고, 카테고리(Process·Unit·Property)와 관계(part_of·precedes·has_property·mirrors)는 어느 제조업에나 그대로 맞는다. **골격만 갈면 4단계(doc_type 등록)로 바로 간다.**
> config가 필요해지는 때: ①품질층 같은 **두 번째 층**을 세울 때 ②정의문의 예시를 사내 것으로 바꿀 때(급하지 않다 — 추출 품질에만 영향).



`docs/가이드/config작성_가이드.md` 따라. **정의문 초안은 `층정의_프롬프트.md`로 사내 LLM에서 뜨고 사람이 검수한다** — 기본층 보강도 같은 프롬프트다(현행 config를 첨부하면 보강 모드). **기존 config를 베이스로 이름만 바꾸는 게 기본이고**, 카테고리·관계만 실제 판단이다:

1. `categories` — 정의문에 "무엇과 헷갈리는가" 필수. 후보마다 3테스트
2. `relations`·`relation_patterns`·`category_pair_map` — 한 묶음. 정의문 없는 관계 금지
3. 나머지 — 베이스 복사 후 이름 수정
4. **확인**: `python3 run.py init --fresh && python3 run.py all` — 부팅 실패면 명시적 실패가 어느 키인지 말해 준다

## 4단계 · 첫 doc_type 등록 — 문서 종류당 반나절

**구축 모드가 한다 — 어댑터·스키마를 손으로 쓰지 않는다:**

```bash
python -m cli.register generate <doc_type> <층> <표본.xlsx> [표본2 …] --interview --hint "자유 텍스트"
#                              ^이름     ^층    ^표본(여러 개 가능)     ^문답     ^힌트는 --hint 뒤에
# → 검수 뷰 HTML이 생긴다. 열어서 확인:
#   ①표본 파싱 결과(트리)  ②필드→role 배정표  ③어댑터 요약
python -m cli.register review <doc_type> [--rows N]      # 재생성 루프 (필요 시)
python -m cli.register confirm <doc_type> --by <승인자>   # 승인 1회
```

**확정 화면이 다음 명령을 그대로 낸다** — 등록은 그래프를 만들지 않는다:

```
■ ③ 확정 — cp 등록부 등재 (승인 홍길동 @ …)
   다음 — 인입은 이 명령으로 (등록이 그래프를 만들지는 않는다):
     python run.py parse run adapters/cp.py <doc_id> <문서>
     python run.py build parsed/<doc_id>.json
     (한 번에: python run.py ingest-file <문서> --doc-type cp)
```

### 산문 문서도 등록이 먼저다 — 예외 없다

**표든 산문이든 doc_type 하나에 어댑터 하나가 있어야 파싱이 된다.** 산문이라고 등록을 건너뛰고 바로 `parse run`으로 갈 수 없다 — 파싱은 "확정된 어댑터로" 돌기 때문이다.

표와 산문의 차이는 **어댑터가 없느냐가 아니라 어댑터 안의 `payload_kind`**다:

| `payload_kind` | 무엇 | 인입 경로 |
|---|---|---|
| `table` | 행 하나가 record (관리계획서·PFMEA·검사기준서) | record 직행 — LLM 없이 그래프까지 |
| `prose` | 행이 record가 아님 (PPT·목차형 보고서·RFQ) | 청크로 나눈 뒤 추출(LLM) |

산문 등록에서 갈리는 것은 **어떻게 등록하느냐** 둘뿐이다:

| 표본 | 방법 |
|---|---|
| **`.pptx`만** | `--use-basic` — LLM 생성 0회 |
| **그 외 산문**(목차형 엑셀·docx·RFQ 등) | 보통대로 `generate` — LLM이 어댑터를 쓴다. 구조가 판본마다 다르면 `--interview`를 붙인다 |

`--use-basic`은 **표본이 전부 `.pptx`일 때만** 제안·적용된다(`basic_adapter_proposal`) — 다른 확장자에 붙이면 제안이 안 뜬다.

### `--use-basic` — PPT는 분할이 자명하니 LLM 생성을 건너뛴다

```bash
python -m cli.register generate <doc_type> <층> <표본.pptx> --use-basic
```

코어가 제공하는 **기본 어댑터를 위임 래퍼로** 등재한다(복사가 아니다 — 임계 등 판단 상수는 코어 한 곳). **LLM 호출 0회**로 등록이 끝나고, **검수·승인 1회는 그대로다.** 슬라이드 텍스트량이 임계를 넘어도 거부가 아니다 — 기본 어댑터 안에서 ①shape 분할 ②구조 지도 패스 ③통청크+큐 순으로 처리한다.

### `--resume` — 문답이 몇 라운드 돌다 죽었을 때

```bash
python -m cli.register generate <doc_type> <층> <표본…> --resume
```

**패키지 조립도 문답도 건너뛰고 초안만 다시 받는다.** 문답은 라운드마다 `review/{doc_type}/input_package.json`에 즉시 저장되므로, 죽어도 그때까지의 대화가 남아 있다.

> **주의**: `--resume`은 층·표본을 쓰지 않는데도 **자리는 요구한다**(빠뜨리면 `IndexError`). 아무 값이나 넣으면 무시된다 — `generate cp process x --resume`. 다음 회차에 고친다.

### `review` → `confirm` 관문 — 무엇이 막고 무엇이 안 막나

**`confirm`은 조건 셋을 본다** [`cli/register.py:1055-1062`]:

| # | Condition | If missing |
|---|---|---|
| 1 | `review/{doc_type}/state.json` 존재 | `[확정] '…' 생성·검수가 먼저다` |
| 2 | **`machine_gate == "PASS"`** | `[확정] 기계 관문 미통과 — 검수를 먼저 통과시켜라 (현재 FAIL)` |
| 3 | `--by <승인자>` | `[확정] 승인자 미지정 — 무수정 자동 통과는 금지다` |

**`machine_gate`를 정하는 것은 둘뿐이다:**

```
machine_gate = PASS  ⟺  하네스 PASS  그리고  전 표본 파싱 성공
```

| Blocks confirm | Does NOT block |
|---|---|
| 하네스 FAIL (`kit/run_adapter.py` 항목 중 하나라도) | **`[question]` UNMAPPABLE 열** — 아래 |
| 표본 파싱 FAIL | `[warning]` 부분 리허설 · 표본 1부 |
| `review`를 아예 안 돌림 | 좌표 미스 (인입에서 `orphan_anchor` 큐로 간다) |

> **UNMAPPABLE 열 줄은 질문이 아니라 표시다.** `[question]` 태그가 붙어 질문처럼 읽히지만 **입력을 받지 않고 confirm을 막지도 않는다.** 화면에서 확인하고 그대로 confirm 하면 된다.
>
> **왜 이미 뺀 열을 또 보여주나**: 지금 코드는 UNMAPPABLE을 **차집합**(원본 헤더 전량 − 어댑터가 출력하는 열)으로 되짚는다. 그래서 「판정해서 뺀 열」과 「판단이 안 선 열」이 같은 줄로 나온다. **설계 결함이고 B49로 고친다** — 스키마가 전 열의 판정(`excluded`/`undecided`)을 싣게 하고, review는 그것을 읽는다. 그때까지는 표시로만 보면 된다.
>
> `--interview`에서 답한 내용도 지금은 review로 이어지지 않는다(같은 결함) — B49가 함께 닫는다.

**review에서 실제로 입력을 받는 것은 하나뿐이다:**

```
   좌표 미스 1,240건 (예: 노칭프레스, 탭웰딩 …)
   LLM 보조를 켜면 최대 1,240회 호출한다. 켤까? [y/N]
```

미스를 그대로 두는 것은 오류가 아니다 — 인입에서 `orphan_anchor` 큐로 가는 정상 경로가 있다. **켜면 미스 수만큼 실호출**이므로 기본은 끔이다. 미리 정하려면 `--llm-coord` / `--no-llm-coord`.

### 하네스가 FAIL이면 — 무엇을 봤길래

하네스는 어댑터를 **실제로 실행해** 4단계를 본다:

| Stage | Checks |
|---|---|
| ① 로드 | 문법 · **순수 함수 계약**(어댑터가 네트워크·LLM을 부르지 않는다) · **규약 10**(`parser.normalizer`를 재구현하지 않고 부른다) · `ADAPTER` 필수 4키 · `extract` 존재 |
| ② preflight | 분할 신호 상수 선언 · `header_row`에 헤더 존재 · **원본 헤더가 전부 `expects`에 실림**(문서 표류 감지) |
| ③ extract | 예외 없이 실행 · `list[dict]` 반환 · **조각 0건 아님** · `source_locator` 존재·문서 내 유일 · 정본 id 미부여 · 상동(〃) 해소 |
| ④ 스키마 정합 | 헤더 4키 · `use_blocks` 전개 · **role이 닫힌 5종 안** · entity에 category · edges의 from/to가 선언된 필드 · 스키마 밖 필드 없음 · **UNMAPPABLE이 `fields`에 안 들어감** |

FAIL 줄이 화면에 그대로 나온다. **고치는 방법은 손으로 어댑터를 고치는 게 아니라 재생성이다:**

```bash
python -m cli.register review <doc_type> --instruct "3~7행 병합은 위 값으로 채운다. 헤더는 2행이다"
```

지시가 이력에 남고(`state.json`의 `instructions`), **상한은 없다** — 중단은 사람 판단이다. 승인 기록에도 지시 이력이 실린다.

### `--interview` — 생성 **전에** 이해를 맞춘다 (붙여야 돈다)

**`--interview` 없이 실행하면 LLM이 표본을 읽고 바로 결론을 냅니다.** 문답은 기본값이 아니라 옵션이다 — 단순한 표는 물어볼 게 없어서 라운드가 낭비이기 때문이다.

붙이면 매 라운드 이렇게 돈다:

```
■ 생성 전 문답 — 이해 요약을 보고 교정한다. 끝내려면 «진행» (상한 없음)

[라운드 1] 이해 요약
   … 열별로 "이렇게 읽겠다"를 LLM이 요약
   Q1. …?
       선택지: … · …
   답/교정 (빈 줄 2회 또는 «진행»이면 종료) >
```

- **끝내는 것은 사람뿐이다** — 「진행」을 입력할 때까지 계속된다. LLM은 "충분히 이해했다"를 판단하지 않는다(조항 I4). 라운드 상한은 없다.
- 답/교정을 넣으면 **다음 라운드 요약이 그 교정을 반영해 바뀐다.** 바뀌지 않으면 그건 결함이니 가져오라.
- 문답 전문은 입력 패키지의 힌트에 구조화돼 남는다 — 같은 등록을 재현할 근거다.
- **언제 붙이나**: 열 간 상하 구조가 판정을 가르는 문서(다단 헤더·그룹 열 — **PFMEA가 대표적**), 무엇을 힌트로 적어야 할지 모르겠을 때. 단순 표(관리계획서 등)는 없어도 된다.
- `USE_MOCK=1`에서는 규칙 요약만 나온다 — **문답의 값은 실호출(`USE_MOCK=0`)에서만 확인된다.**

- 표본은 **실물 문서**다. 등록 뒤 같은 문서를 운영 인입으로 다시 넣는다(등록은 doc_type당 1회, 인입은 문서마다).
- UNMAPPABLE로 뜬 열은 억지로 배정하지 않는다 — 스키마·출력 제외가 정상이고, **confirm을 막지 않는다**(위 관문 절).

## 5단계 · 첫 실 인입 — 여기가 고비다. 눈으로 본다

**`run.py all`은 mock 픽스처 전용이다** — 사내에는 그 픽스처가 없어 "인입할 계약 JSON이 없다"만 뜬다(정상). **실문서는 두 명령이다 — 문서마다 반복**:

```bash
# ① 파싱
python3 run.py parse run adapters/cp.py CP-라인1-2026 ~/docs/관리계획서_라인1.xlsx
#                        └─ 인자1 ─┘  └─ 인자2 ─┘ └────── 인자3 ──────┘
# ② 인입 — 계약 JSON을 그래프로
python3 run.py build parsed/CP-라인1-2026.json
```

**인자 셋이 각각 무엇인지 헷갈리기 쉽다:**

| # | 인자 | 무엇 | 네가 하는 일 |
|---|---|---|---|
| 1 | `adapters/cp.py` | **어댑터 코드** — `confirm`이 여기 놓은 파이썬 파일 | **없다.** `confirm`이 `review/`에서 `adapters/{doc_type}.py`로 자동으로 옮긴다 |
| 2 | `CP-라인1-2026` | **doc_id** — 이 문서의 이름표 | 네가 정한다. 같은 문서엔 항상 같은 id(개정판도 같은 id) |
| 3 | `~/docs/관리계획서_라인1.xlsx` | **실제 문서** | **아무 데나 두면 된다.** 네가 놓은 그 경로를 그대로 적는다 |

> **`adapters/`는 문서를 넣는 곳이 아니다.** 확정된 어댑터 코드가 사는 자리이고 코드가 알아서 채운다. **문서는 편한 곳에 두고 그 경로를 3번 인자로 준다** — `docs/`든 홈이든 상관없다.

### 일괄 투입 — 위 두 줄을 한 줄로 (B46)

```bash
python run.py ingest-file <문서> [--doc-type X] [--dry-run]   # 1건
python run.py ingest-dir  <경로> [--doc-type X] [--dry-run]   # 경로 전부
```

**기존 두 명령은 그대로 살아 있다** — 이건 그 위의 편의 명령이고 같은 코드를 부른다.

- **doc_type을 안 주면** 지문 스캔이 후보를 낸다. **유일 일치면 자동 선택**하고 근거를 화면·인입 기록에 남긴다. **둘 이상이거나 0건이면 사람에게 올린다.**
- **`--dry-run`을 먼저 돌린다** — 무엇이 어느 doc_type으로 갈지 미리 본다.
- **`doc_id`는 파일명 기준이고 경로와 무관하다** — 문서를 옮겨도 같은 문서다. 대장 경로와 다르면 화면에 경고.
- `ingest-dir`는 **문서 단위 독립**이다 — 한 건이 실패해도 나머지는 간다.

**같은 doc_type의 다른 문서 = 그냥 위 두 줄을 새 doc_id로 반복이다.** register는 다시 안 간다(등록은 doc_type당 1회). 같은 문서의 개정판은 **같은 doc_id로** 다시 — 재인입이 이전 몫을 회수하고 새로 쓴다. 처음 넣는 문서인데 실수로 기존 doc_id를 쓰면 개정판 취급되니 doc_id 규칙(예: `{doc_type}-{라인}-{연도}`)을 정해 두라.

### 산문 문서(PPT·보고서·RFQ)는 구조 지도를 LLM이 만든다 — B48부터

산문은 표와 달리 **어디서 잘라 청크를 만들지**가 문제다. 두 단계로 나뉜다:

1. **구조 지도**(LLM) — 어느 행이 제목이고 몇 급인지만 판정한다. 자르지 않는다.
2. **분할**(결정적 코드) — 그 지도에서 목표 구간(5~40행)에 가장 많이 드는 레벨을 골라 자른다.

**B48 이전에는 이 LLM 경로가 코드에 없었다** — 번호 붙은 제목(`1.` `1.1`)만 잡는 정규식으로 돌았다. PPT처럼 번호 없는 제목이면 제목 0건 → 통청크였다.

> **재인입 대상**: B48 이전에 넣은 산문 문서는 **전부** 휴리스틱 지도다. 청크 경계가 바뀌므로 **산문 doc_type은 전수 재인입**한다. 표(table) 문서는 해당 없다.

**확인**: 인입 후 `extract/struct_maps/{doc_id}.json`의 `source`가 `live`인가. `heuristic`이면 게이트웨이가 안 잡힌 것이다.

**계기판이 아니라 눈으로 확인할 것 둘** (mock으로는 검증이 안 끝난 항목):

| 볼 것 | 어떻게 | 틀리면 |
|---|---|---|
| **지도·이미지 요약이 매 인입 새로 산출되지 않는지** | 같은 문서 2회 인입 → `extract/struct_maps/{doc_id}.json`의 `source_hash` 불변 + chunk_id 동일 | chunk_id가 문서 단위로 전량 이동 — 재인입·근거 추적이 다 깨진다 |
| **`used_facts` 필터가 실제로 좁히는지** | 질의 응답의 `facts_before_filter` vs 최종 건수 | 확장 결과 전량이 상한 8에서 잘려 오답 |

**추가 확인**: `python -m cli.show node <이름>` (답의 뒷면) · `python -m cli.export html` (그래프 눈으로) · 수정 큐 확인 — auto_node·uncertain_match가 쌓이는 건 **정상**이다(사람이 자기 리듬으로 처리).

## 6단계 · 질의 확인과 골든셋 — 첫 주

1. 실제 궁금한 질문 10개를 던져 본다: `python -m cli.query "…"`
2. 답의 근거([그래프 사실]·[문서 근거])가 실제 문서와 맞는지 눈으로
3. **골든셋 문항 제작 시작** — 유형당 15문항(§5.3 Q1~Q5·Q8), 기준 120. 계기판이 인상이 아니라 측정이 되는 조건이다.

## 언제 허브로 가져오나

| 상황 | 형식 |
|---|---|
| 명세가 답하지 않는다 | BLOCKER 3요소 — ①근거 원문 ②선택지 2~3 ③귀결 |
