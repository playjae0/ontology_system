> **누가 읽나**: 사내에서 2B를 진행하는 사람. 단계마다 같은 모양이다 — **목적 → 명령 → 화면에서 확인 → 막히면**.

> **명세가 답하지 않으면** 추측으로 메우지 않는다 — §8 형식으로 허브에 가져온다.

| 뭔가 이상하다 | §7 |
| 허브에 가져갈 게 있다 | §8 |

모든 명령은 레포 루트에서 친다. 이 가이드는 등록 명령을 **`python -m cli.register …` 한 형태로만** 적는다. 화면이나 다른 문서에 `python run.py register …`가 보이면 같은 함수(패키지 `cli/register/`의 `main`)를 부르는 껍데기이지 다른 명령이 아니다 — 어느 쪽을 쳐도 결과는 같다.

화면의 `[Y/n]`·`[y/N]`은 **대소문자를 가리지 않는다** — 대문자 쪽이 그냥 Enter 쳤을 때의 기본값이다. `[Y/n]`은 Enter가 「예」(안전한 쪽 — LLM 0, 되돌릴 수 있는 쪽), `[y/N]`은 Enter가 「아니오」(돈이 들거나 되돌릴 수 없는 쪽은 사람이 직접 `y`를 친다).

**B78 뒤 코드를 새로 옮길 때 — 상태는 손대지 않는다.** 코드 폴더를 통째로 교체하고 `ONTO_HOME`이 같은 곳을 가리키면 원본·층·등록·진실·작업 전부 그대로다. 옮길 것은 없다. `python doctor.py | head -3` 첫 줄이 같은 상태 폴더 · 같은 등록 수 · 「층 k(상태 루트)」면 끝. **B79 이전 판(B78-3 · `551de6b`)에서 넘어올 때 한 번**: 층이 아직 코드 폴더에 있으니 `python run.py platform migrate --assets --from <B78 코드 폴더>`(상태 루트에 이미 층이 있고 다르면 덮지 않고 멈춘다 — 사람이 정한다).

**B78 이전 배치(레포 루트에 `data/`·`review/`·`parsed/`가 있던 코드)에서 처음 넘어올 때 — 한 번만, 여섯 줄**(사용자 확정 · 이관은 복사라 옛 폴더가 남는다):

상태 루트의 자리는 **프로젝트 폴더 안, 코드 폴더 옆**이다 — 홈이나 `/data` 같은 공용 자리가 아니다(공용 서버 실측: 예시 경로 `/data/…`를 그대로 쳐서 디스크 루트에 생겼다). 명령은 **새 코드 폴더 안에서** 치고, 상태 폴더는 그 **부모**에 둔다:

```
<프로젝트 폴더>/            예: …/ontology/
   ontology20/              옛 코드 (--from 이 가리키는 곳 — 안에 옛 등록부 `data/`가 있다)
   ontology23/              새 코드 (여기서 명령을 친다)

```

```bash
cd <새 코드 폴더>                                   # 1. 새 코드 폴더로 교체(태그 B78-3 이후) · 여기서 친다

python run.py platform doctypes
```

## §1 게이트웨이 연결 — 반나절

**목적**: 사내 LLM에 붙인다. **설정은 파일 하나 — `$ONTO_HOME/llm.json`**(B78 — 상태와 같이 사는 자리 · 코드 폴더를 갈아 끼워도 남는다). 환경변수 export는 쓰지 않고, **코드 폴더 안에 `llm.local.json`을 두지 않는다**(두면 그것이 이긴다 — 아래 우선순위).

```bash
cat > $ONTO_HOME/llm.json <<'EOF'
{
  "LLM_GATEWAY_URL": "https://사내주소",
  "LLM_API_KEY": "키",
  "CHAT_MODEL": "모델명",
  "EMBED_MODEL": "임베딩 모델명 — 게이트웨이에 있으면(예: bge-m3) · 없으면 이 줄을 빼면 된다",
  "CANDIDATE_NARROW": "auto",
  "USE_MOCK": 0
}
EOF
chmod 600 $ONTO_HOME/llm.json
python run.py llm-check               # ①설정 파일(읽은 경로를 찍는다) → ②도달 → ③인증 → ④응답 → ⑥임베딩(EMBED_MODEL 있으면)
```

이관(§0)으로 넘어왔으면 옛 `llm.local.json`이 이미 `$ONTO_HOME/llm.json`으로 복사돼 있다 — 새로 만들지 말고 그 파일에 `EMBED_MODEL`·`CANDIDATE_NARROW`를 더한다.

설정 자리는 넷이고 **앞이 이긴다**: 환경변수 → 코드 폴더의 `llm.local.json` → `~/.onto/llm.json` → `$ONTO_HOME/llm.json`. 앞 셋을 비워 두면 새 코드를 받아도 설정을 건드릴 일이 0이다.

**확인**: `llm-check`가 **읽은 파일 경로**를 찍고 ④까지 통과. 이후 LLM을 쓰는 명령은 머리에 `모드: 실호출`이 뜬다.

| Setting | Rule |
|---|---|
| 파일 자리 (위가 이긴다) | ①`ONTO_CONFIG=<절대경로>` ②`~/.onto/llm.json` ③레포 루트 `llm.local.json` |
| `USE_MOCK` | `0`이 실호출. 키가 없으면 mock |
| `LLM_CONTEXT_TOKENS` | **적지 않는다** = 무제한. 사내 한도를 확인한 뒤에만 적는다 (틀린 값은 정상 요청을 막는다) |
| `EMBED_MODEL` | 게이트웨이가 OpenAI 호환 `/embeddings`로 내주는 임베딩 모델명(한국어·영어 섞인 표기라 다국어 모델 — bge-m3 등). **없어도 인입은 돈다**(B75 ① — 후보 좁히기가 2-gram 겹침으로 떨어지고 화면에 「임베딩 미설정」 한 줄) · `llm-check` ⑥이 「미설정 — 겹침 폴백」으로 보인다 |
| `CANDIDATE_NARROW` | `auto`(기본 — 있으면 임베딩·없으면 겹침) · `embed`(강제 · 미설정이면 중단) · `overlap`(임베딩 있어도 겹침). 한 문서만 바꿔 비교할 땐 `ingest-file --narrow …` |

| Symptom | Do |
|---|---|
| `설정 파일 없음(환경변수만)` | 자리가 틀렸다 — `$HOME` 확인 후 레포 루트 `llm.local.json` |
| 파일을 고쳤는데 값이 안 바뀐다 | 셸 환경변수가 파일을 덮는다 — `unset LLM_GATEWAY_URL LLM_API_KEY CHAT_MODEL USE_MOCK` |
| `mock 모드입니다 — 계속하려면 --allow-mock` | 게이트웨이가 안 잡혔다. 운영 명령(`register`·`parse run`·`build`·`ingest-*`·`query`)은 mock이면 멈춘다. 일부러 mock으로 볼 때만 `--allow-mock` |
| 게이트웨이가 OpenAI 호환(`/chat/completions`)이 아니다 | `core/llm/gateway.py` 한 파일만 고친다 — 허브에 보고 |

## §2 골격 seed — 하루

**목적**: 사내 공정 트리를 좌표계로 세운다. 판단이 핵심이고 명령은 짧다. 작성법은 `골격작성_가이드.md`.

```bash
# 1. 공정 설명 문서 → LLM 초안(골격작성_가이드 §4 프롬프트) → 사람이 검수 → $ONTO_HOME/layers/process/skeleton.json 교체 (B79 — 코드 폴더의 layers/가 아니다 · 그건 mock seed)
python run.py init --fresh && python run.py bootstrap
python run.py skeleton-status process                 # 판정만 — 위반이 있으면 [FAIL] K## 줄과 seed 줄 번호
python run.py skeleton-confirm process --by <확정자>
```

**막히면** — `skeleton-confirm`이 거부하면 같은 블록이 뜬다: `[FAIL] K02  canonical 중복 — '노칭' — main·sub 자리에 2번 (6행 · 16행)` 식으로 **위반 전건 + seed 줄 번호**. seed의 그 줄을 고치고 `skeleton-status`로 다시 본다. 태그: `K01` 파일을 못 읽음(JSON) · `K02` 같은 자리 같은 이름 · `K05` `::축값`·`@마커` 오타 · `K09` loader 위반.

**확인**: `bootstrap` 화면의 **「파생 대표 흐름 (사람 대조용)」**을 공정 문서와 대조 — 순서·무주장·mirrors 쌍·모호 이름. 문서의 공정 수 = 노드 수인지 한 번 센다(빠진 공정은 뷰가 못 잡는다).

| Symptom | Do |
|---|---|
| 흐름 순서가 문서와 다르다 | seed의 `precedes`·`@unordered` 수정 후 다시 `init --fresh && bootstrap` |
| `(짧은 이름 모호 …)` | 같은 이름이 여러 공정에 있다 — 그대로 둬도 되지만 질의는 접두 키로만 잡는다 |

## §3 층 config — 반나절 · **보통 건너뛴다**

**건너뛰는 조건**: 공정층 하나로 시작한다. `layers/process/`는 내장이고 카테고리(Process·Unit·Property)·관계(part_of·precedes·has_property·mirrors)는 그대로 맞는다 → **§4로**.

**필요한 때**: ①품질층 같은 두 번째 층 ②정의문 예시를 사내 것으로 바꿀 때(급하지 않다). 작성법은 `config작성_가이드.md`, 정의문 초안은 `층정의_프롬프트.md`로 사내 LLM에서 뜬다.

**새 층을 세우는 순서** (품질층 `layers/quality/`가 실물 예시다):

```bash
mkdir layers/<층>                                    # 1. 폴더 이름 = layer 이름
#   2. layers/<층>/config.json — config작성_가이드 §0~§6 (사람이 쓰는 11키 · 나머지는 베끼거나 한 줄) · 정의문은 층정의_프롬프트로 초안
#   3. 골격이 있는 층(source 쓰는 층)만 layers/<층>/skeleton.json — 골격작성_가이드. 품질층처럼 config의 "skeleton": {"type": "flat", "data": [...]}로 닫힌 목록만 두는 층은 파일이 없다
python run.py init --fresh && python run.py bootstrap   # 4. layers/ 아래 폴더를 전부 발견해 층 등록부(data/registry.json)에 올린다 — 화면에 「<층>: 노드 n · 엣지 m」
python run.py skeleton-status <층>                      # 5. 골격 있는 층만 — [FAIL] K## 없으면 skeleton-confirm <층> --by <확정자>
python run.py platform registry                         # 6. 층이 registered로 보이는지
```

그다음은 §4 — `register generate <doc_type> <층> <표본>`에서 **층 이름을 이 층으로** 준다. 관문 G4C·G4D·G4E가 스키마의 카테고리·관계·삼항을 **이 층의 config**와 대조하므로, config의 `categories`·`relations`·`relation_patterns`가 비면 등록이 거기서 막힌다(막히는 문면이 어느 키인지 말한다). 품질 문서가 공정 좌표(공정명)를 쓰면 `cross_layer_traverse`를 선언층(품질층)에 둔다 — config작성_가이드 §4.

```bash
python run.py init --fresh && python run.py all      # 부팅 확인(내장 픽스처가 있을 때) — 사내에서는 bootstrap까지만 돌고 「인입할 계약 JSON이 없다」로 끝나는 것이 정상
```

## §4 doc_type 등록 — 문서 종류당 반나절

**목적**: 문서 종류 하나에 어댑터·스키마 한 벌을 만든다. **손으로 쓰지 않는다** — LLM이 생성하고 사람은 검수·승인만 한다.

**산문(pptx · pdf · 산문형 xlsx/csv)은 세 줄이고 LLM 0이다** (B58 · B65):

```bash
python -m cli.register generate <doc_type> <층> <표본.pptx> --use-basic   # 고정 어댑터 · 관문 · 뷰 — 생성 세션 없음
python -m cli.register confirm <doc_type> --by <승인자>
python run.py ingest-file <문서.pptx> --doc-type <doc_type>            # 산문은 헤더 지문이 없어 --doc-type 필수
```

**확정 전에 보는 것** — 관문 줄 다음에 시트(프레임)마다 분할 줄이 뜬다: `분할 — <시트> 기준 어댑터 신호(번호 n · 가로병합 m · 굵게+들여쓰기 k) · 레벨 L (평균 x행 · 목표 5~40) · 청크 c · 행수 a~b · 짧음 s · 긺 g`. **짧음이 많으면 헤딩 신호가 과한 것**(번호 패턴·굵게가 본문에도 걸린다), 긺이 많으면 모자란 것. 구간 밖이면 줄 끝에 「구간 밖 — 최근접 레벨」(B68).

xlsx/csv는 관문이 먼저 **형태 판정**(신호 5 · 투표)을 찍는다 — 자동으로 안 서면 `[table/prose]`를 묻고, 답이 곧 플래그다(`--use-basic` = prose · `--no-basic` = table). 고정 어댑터 doc_type에는 `--instruct`·`--revise`가 **안 된다**(재생성 대상이 아니다 — 화면이 다음 줄 셋을 준다: 분할 상수 · 스키마 · `--as <새이름> --no-basic`).

**표(table)는 보통 두 줄이다** (B58):

```bash
python -m cli.register generate <doc_type> <층> <표본…>     # 만들고 · 관문 지나고 · 뷰까지
python -m cli.register confirm  <doc_type> --by <승인자>    # 뷰 보고 괜찮으면
```

`review`는 **뷰를 바꾸고 싶을 때만** 들어간다(§4.2). **막히면 `status`** — 왜 막혔고 무엇을 치면 되는지를 다시 보여 준다(§4.1 「막힐 때」). **표(table)와 산문(prose)이 다르다**:

| Kind | Generate does | LLM calls |
|---|---|---|
| table (CP·PFMEA·IPQC…) | LLM이 어댑터·스키마 초안 → 관문 → 뷰 | 생성 1회 + 문답 |
| **prose** (PPT·PDF·**목차형 엑셀**) | **고정 기본 어댑터** 등재 → 관문 → 뷰 | **0** |

xlsx는 **어느 쪽인지 시스템이 먼저 판정**한다(§5.1 형태 판정). **산문이면 플래그 없이도 고정 어댑터로 간다** — `generate`가 「산문 포맷이다, 고정 어댑터로 갈까? [Y/n]」를 묻는다(B59). LLM 생성으로 가려면 `--no-basic`. 「사람」으로 뜨면 `--use-basic`(산문) 또는 `--no-basic`(표)으로 정해 준다.

### §4.1 생성

```bash
python -m cli.register generate <doc_type> <층> <표본.xlsx> [표본2 …] [--interview] [--hint "…"]
#                                ^이름      ^process  ^실물 문서 — 등록 뒤 §5에서 다시 넣는다
```

| Option | When | What |
|---|---|---|
| (`columns` 값) | 어댑터의 `columns`에는 **헤더 라벨을 그대로** 써도 된다 — 열문자는 관문이 정한다(C38). 같은 이름이 둘이면 `["Center","G"]`처럼 리스트(앞이 우선 — 「둘 다면 첫째」) |
| `--interview` | 열 간 상하 구조가 판정을 가른다(다단 헤더·PFMEA) · 힌트로 뭘 적을지 모르겠다 | 생성 **전에** LLM이 **한 번에 질문 하나**씩 묻는다. 답하고, 「진행」을 치면 **확정 요약**이 뜬다:<br>`1. [병합된 좌측 열] 위 값 채움 — 1라운드 사람 답`<br>`확정 요약이 맞나? [Y/n/수정(번호)]`<br>**생성은 이 요약으로 한다** — 대화 전문이 아니다(B60). `n`은 다시 요약(1회), `수정 3`은 3번 항목만 다시 묻는다 |
| `--hint "…"` | 표본만으로 안 보이는 것 | 자유 텍스트 — "3~7행 병합은 위 값 채움" |
| `--use-basic` / `--no-basic` | 표본이 **산문** — `.pptx` · `.pdf` · **목차형 `.xlsx`/`.csv`** | **산문이면 이게 기본이다** — 플래그 없이 넣으면 물어보고 고정 어댑터로 간다. LLM 생성 0회. `--no-basic`은 굳이 LLM 생성으로 가는 예외 |
| `--resume` | 관문 FAIL로 끝났거나 문답 도중 죽었다 | `generate <doc_type> --resume` — **이어하기 = 같은 입력 + 열 판정 대장 + 지난 실패**. 초안이 있으면 관문부터 돌려 FAIL 문면과 지시 이력을 실어 새 판을 받는다. 관문 PASS면 다시 받지 않는다(다음 줄 = confirm). 처음부터 하려면 `--resume` 없이 |

**확인**: `기계 관문 PASS` 뒤 **`review/<doc_type>/view.html` 경로가 찍힌다 — 뷰는 여기서 이미 만들어졌다.** 그 파일을 열어 §4.2의 3구획을 보고, 괜찮으면 바로 §4.3.

**막힐 때 — `기계 관문 FAIL` 블록** (B59). `generate`가 FAIL로 끝나면, 그리고 그 뒤 `confirm`·`review`·`status` 어느 것을 쳐도 **같은 블록**이 뜬다:

```
■ 기계 관문 FAIL — <doc_type>
  [FAIL] G13  규약 10 — 자기완결 연산을 재구현하지 않았다 — 재구현 정의 ['_expand_merged', …]
  ▶ 다음 줄:
     python -m cli.register review <doc_type> --instruct "규약 10 — …"
     python -m cli.register status <doc_type>
```

| Line | Meaning | Do |
|---|---|---|
| `[FAIL] G13 …` | 왜 막혔나 — **태그(`G13`)를 읽어서 허브에 말하면 된다**, 복사 안 해도 | — |
| `▶ 다음 줄` | **그대로 치면 된다** — `--instruct` 문면까지 채워져 있다 | 그 줄을 친다 → 재생성 → 관문 다시 |
| `status` | **관문을 그 자리에서 다시 돌리고** 블록을 찍는다(B60) — 저장된 판정을 읽는 게 아니다. 옛 버전에서 만든 어댑터도 이걸로 지금 관문에 맞춰 본다. LLM 0 | |

**「기계 관문」은 자동 검사다. 사람 검수가 아니다.** 사람이 통과시키는 게 아니라 위 `--instruct` 줄로 재생성하는 것뿐이다. 다음 줄이 여러 개면 위에서부터.

| Symptom | Do |
|---|---|
| `G1B` (없는 normalizer 함수) | LLM이 `normalizer`에 없는 이름을 불렀다. 문면에 있는 이름 목록이 있고 **자동 재생성**된다 — 손댈 것 없음 |
| `G4C`·`G4D`·`G4E` (층 어휘 밖) | 스키마의 카테고리·관계·삼항이 층 config 목록 밖이다. 자동 재생성. 그 값이 **정말 필요하면** 관문이 아니라 `layers/<층>/config.json`(06 손잡이 3.4·3.6)에 더한다 |
| `G13`·`G14` (규약 10 — 재구현) | **가장 흔하다.** LLM이 병합 처리를 직접 짜 넣은 것. `▶ 다음 줄`의 `--instruct`를 그대로 |
| 문답이 열린다 (`G51`~`G53`) | 파서가 죽었거나 계약이 깨진 것. **예외 원문이 문답에 실려 있다** — 모델이 통역한다. 답하면 재생성 |
| `G4F`가 붉다 | LLM 산출의 **형**이 표와 다르다(예: `unmappable[].field`가 리스트) — 문면의 「키 · 받은 형 · 허용 형」대로 재생성 지시(`--instruct`) · 새 키가 정말 필요하면 표(`kit/run_adapter.py::SHAPE_*`)에 형을 적는 것은 회차 일 |
| 「등록돼 있지 않다」는데 `review/<dt>/`는 있다 | 등록부(`registry/doc_types.json`)만 빠진 것 — 문면의 근거 줄이 말한다. 옛 환경의 등록부 항목을 옮기거나 `generate`로 신규 등록(문답·대장은 이어진다) |
| `G4G`가 붉다 | 스키마 필드가 열 판정 대장에 없다 — 어댑터 `columns`가 프로파일 밖 열을 쓴다. 재생성으로는 안 고쳐진다(GATE_SELF) — 대장(`review/<dt>/columns.json`)과 어댑터 `columns`를 대조 |
| `G31`이 붉다 | 어댑터 `extract`가 죽었다 — 문면의 **`파일:줄` + 소스**가 자리다. `ditto_mark` 없이 `None`을 넘기던 결함은 B76 뒤 없다 · 셀에 직접 문자열 연산을 걸었으면 규약 11 |
| 관문·뷰 다 지났는데 `[결함] 파일:줄 …` 한 줄로 끝났다 | 파이썬 예외(B76 ③). `show log defects`에 전문 · `ONTO_TRACEBACK=1`이면 화면에도. 그 파일:줄을 구현 세션에 보고 |
| `GATE_SELF` (`G54`) | 어댑터 결함이 아니라 **관문 자체**다 — 재생성해도 안 낫는다. 태그와 함께 허브로 |
| `더 돌릴까? [Y/n]` | 자동 수정 1회 뒤에도 FAIL일 때. **Enter(Y)** = 문답을 열고 재생성(LLM) · n = 여기서 끝(관문 FAIL이라 confirm 막힘, `--instruct`로 이어간다). 같은 FAIL이 되풀이되면 시스템이 스스로 멈춘다 |
| `G26 columns 값 'X'가 n행에 2개 (D · G)` / `'X'는 n행 헤더에 없다` / `D열 n행이 비었다` | 매핑이 틀린 것이지 원본 데이터가 빈 게 아니다. 중복이면 `--instruct "X: [\"D\",\"G\"]"`(합치기) 또는 열문자 하나 · 없음이면 헤더 목록에서 고른다 · 빈 헤더면 `header_row`. 줄 아래 열 프로파일(비지 않은 행/전체)이 「몇 값이 읽혔나」다 |
| `헤더 문자열은 시스템이 채운다 — LLM 선언 n / 실물 n · 다른 것 k` | 정보다. 어댑터의 `header_labels`·`adapter_version`은 **관문이 표본에서 채운다** — 손으로 고치지 않는다(고쳐도 다음 관문에서 덮인다). CSV는 `sheet`를 선언하지 않는다 |
| `G27 시트가 정해진다` | 워크북에 시트가 둘 이상인데 `expects.sheet`가 없다. `--instruct "sheet: <시트 이름>"` |
| `mock 모드입니다` | §1 |

### §4.2 뷰 확인 — `review`는 바꿀 때만

뷰에 오르는 것은 관문을 **전부** 지난 산출뿐이다 — B76 뒤에는 형(G4F)·대장 커버리지(G4G)·셀 None(G3A)까지 관문이 먼저 잰다. 뷰에서 사람이 보는 것은 「모양이 맞나」가 아니라 「판단이 맞나」(role·열 대응·제외)다.

**뷰는 §4.1이 이미 만들었다.** `review/<doc_type>/view.html`을 열어 아래 3구획을 본다. **명령을 칠 일은 셋 중 하나일 때뿐이다** — 고칠 게 있어서(`--instruct`) · 좌표 LLM 보조를 켜서 · prose 추출 리허설을 켜서.

(이 절을 「검수」라 부르지 않는다 — 화면도 안 쓴다. 자동 검사는 「기계 관문」(§4.1), 여기는 「뷰 확인」이다. 둘을 한 단어로 부르면 「검수를 통과시켜라」 같은 사람이 할 수 없는 지시가 생긴다.)

```bash
python -m cli.register review <doc_type> [--instruct "…"] [--llm-coord] [--extract] [--rows N|all]
```

**확인 — `review/<doc_type>/view.html` 3구획**:

| Section | Table | Prose | Approve when |
|---|---|---|---|
| ① 파싱 결과 | 표본을 실제로 파싱한 record 트리 | 청크 트리(제목·구획) | 행·청크 수가 기대와 맞다 |
| ② 무엇이 개체·값이 되나 | 필드→role 배정표 + `excluded`/`undecided` 열 — 값의 정본은 **열 판정 대장** `review/<dt>/columns.json`(B67). **role을 무엇으로 둘지·그러면 질의에서 어떻게 돌아오는지는 `역할_판정_가이드.md`** | **분할 분포** — 레벨별 청크수·행수, **규칙이 고른 레벨과 사유 · 분할 기준**(어느 신호로 헤딩을 잡았나 — B68), 구간 밖은 짧은 쪽·긴 쪽 따로. (추출 리허설을 켰으면 추출 결과도) | table: 배정이 맞다 · **prose: 청크가 제대로 잘렸다 — 이게 승인 근거다** |
| ③ 어댑터 요약 | expects · adapter_version | 같음 | 헤더 목록이 원본과 같다 |
| (머리) 형태 판정 | 「사람」으로 올라온 xlsx면 **신호 5 값과 표** | 같음 | 표인지 산문인지 당신이 정한다 |

**review가 묻는 것 둘** (기본은 끔·묻기, 미리 정하려면 플래그):

| Prompt | Cost | Flag |
|---|---|---|
| `좌표 미스 N건 … LLM 보조를 켤까? [y/N]` | 미스 행마다 1회 | `--llm-coord` / `--no-llm-coord` |
| `추출 리허설 N청크 → LLM N회. 켤까? [Y/n]` (prose) | 청크마다 1회 — **확정 뒤 인입에서 재사용되므로 추가 비용은 아니다** | `--extract` / `--no-extract` |

| Symptom | Do |
|---|---|
| ②가 이상하다 (table) | `review --instruct "헤더는 2행이다. '비고' 열은 optional"` — 손으로 어댑터를 고치지 않는다. 재생성분도 기계 관문을 다시 지난다 |
| ②가 이상하다 (prose) | 고칠 곳은 어댑터가 아니라 **층 정의문**(`layers/<층>/config.json` categories) — §7 |
| 기계 관문 FAIL | 화면의 FAIL 줄이 이유다 — `--instruct`로 재생성. 상한 없음. **관문을 못 지난 산출은 기존 뷰를 덮지 않는다** |
| **관문은 PASS인데 뷰에 기계 오류가 보인다** | 있으면 안 되는 상태다(B58 ②) — 재현 절차와 함께 허브로 |
| prose 청크가 너무 잘거나 굵다 | 뷰의 분포에서 **짧은 쪽·긴 쪽 중 어느 쪽**인지 본다. 처방이 다르다 — 성능모듈 카드 01(PPT)·03(엑셀 산문) |
| prose 검수를 켰더니 `data/`에 청크가 생겼다 | 정상 — 추출을 켠 검수는 표본을 그 시점에 인입한다. 확정 뒤 같은 파일 인입은 재인입이다 |

### §4.3 확정

```bash
python -m cli.register confirm <doc_type> --by <승인자>
```

**막는 것**: 기계 관문 FAIL — **`confirm`도 관문을 그 자리에서 다시 돌린다**(B60). 저장된 PASS만으로 확정하지 않는다 → FAIL이면 §4.1 「막힐 때」 블록이 뜬다 · `--by` 없음. **막지 않는 것**: UNMAPPABLE 열(표시일 뿐) · `[warning]` · 좌표 미스(인입에서 큐로 간다).

**확인**: 확정 화면이 **다음 명령(§5)을 그대로 낸다**. 등록은 그래프를 만들지 않는다 — 표본도 §5에서 다시 넣는다.

### §4.4 이미 등록한 doc_type을 다시 손볼 때 (B58)

어댑터가 틀렸거나 문서 양식이 바뀌었을 때. **그냥 `generate`를 다시 부르면 「이름 중복」으로 멈춘다** — 어느 쪽인지 골라야 한다.

| 하려는 것 | 명령 | 결과 |
|---|---|---|
| 같은 doc_type의 **새 판** | `python -m cli.register generate <doc_type> --revise` | `revision`이 오르고 정본 어댑터가 교체된다. 승인 이력은 **누적** |
| **다른 이름**으로 새로 등록 | `python -m cli.register generate <doc_type> --as <새이름>` | 기존은 그대로 두고 새 doc_type이 선다 |

이후는 §4.1~§4.3과 같다 — 검수 보고 `confirm`.

**확인**: 확정 화면이 **「이 doc_type으로 인입된 문서 N건」**을 보인다. **자동으로 다시 읽지 않는다** — 옛 판으로 들어간 문서를 새 어댑터로 다시 넣을지는 사람이 정한다. 다시 넣으려면 §5의 인입을 그 문서에 한 번 더 돌리면 된다(같은 파일명 = 같은 `doc_id` = 재인입).

**막히면**: 플래그 없이 부르면 화면이 위 두 경로를 명령줄까지 적어 보여 준다.

## §5 문서 인입 — 문서마다

### §5.1 보통은 한 줄

```bash
python run.py ingest-file <문서> --dry-run          # 먼저 — 어느 doc_type으로 가나만 본다. 결과 「[선택만]」 = doc_type·형태 판정까지만 했고 파싱·인입은 안 했다는 뜻 — 정상. 다음 줄을 친다
python run.py ingest-file <문서> [--doc-type X]     # 1건: parse → extract → build (B72 뒤: --step 으로 7단계마다 멈춰 본다 · 안에서 무슨 일이 나는지는 인입_이해_가이드)
#   --step-every N   판정 안에서 값 N개마다 누적 토큰을 보고 [c/q] (B75 ③ · q면 그 문서 되돌림 · 체크포인트는 남는다)
#   --narrow embed|overlap   후보 좁히기 방법을 이 문서만 바꾼다 (B75 ① · 비교는 show report --diff)
#   실패하면:  ■ 인입 실패 — <파일>  블록 — [FAIL] P##  <종류> — <원문> · 큐 요약 · ▶ 다음 줄 둘
#   P31 계약/validator(예: 필수 결측 행)면 문서를 고쳐 다시 ingest-file · 양식이 바뀐 거면 generate <dt> --revise
python run.py ingest-dir  <경로> [--doc-type X]     # 폴더 전부 (하위 폴더 제외)
```

| Rule | |
|---|---|
| doc_id | **파일명**(확장자 제외, 공백→`_`). 경로는 안 들어간다 |
| 같은 파일명 | 같은 문서 = **개정판 재인입** — 이전 몫을 회수하고 새로 쓴다 |
| **함정** — 이름만 같은 다른 문서 | 라인별 `관리계획서.xlsx`처럼 이름이 겹치면 서로 덮어쓴다. 파일명을 구분하거나 `parse run … --doc-id X`로 지정 |
| `--doc-type` 생략 | 헤더 지문으로 찾는다(xlsx·csv 전부 — 포맷을 가리지 않는다, B66). 대조 대상은 **등록부뿐**이다(`USE_MOCK=0` — 내장 cp·pfmea·ipqc는 안 뜬다, B70). 유일 일치면 자동(화면에 `← 어댑터 경로`), 둘 이상이면 `--doc-type`으로 고른다. **0건은 네 갈래** — 화면의 「다음」이 갈래마다 다르다: 비정형 포맷 → `--doc-type` 지정 · 어댑터 0건 → `register generate` · 자격 없는 어댑터만 → `--doc-type` 또는 `--revise` · 일치 0건 → `run.py scan <문서>`로 누락·잉여를 본다 |
| **형태 판정** (B58) | xlsx·csv는 **표인지 산문인지 시스템이 먼저 가른다.** 화면에 판정과 신호값이 두 줄로 뜬다. `--doc-type`을 준 것과 어긋나면 **경고만 하고 지정대로 간다** — 사람의 지정이 이긴다 |
| `ingest-dir` | 문서 단위 독립 — 한 건 실패해도 나머지는 간다 |
| **좌표 태깅** (B69) | 골격 이름과 정확히 안 맞는 `process_ref` **표기마다 한 번** LLM에게 「목록 중 고르거나 null」을 묻는다(행 아님). 호출 전에 예고 줄이 뜬다: `좌표 태깅 — 조각 N · 정확 일치 a · 목록 밖 표기 k종(행 m) → LLM 최대 k회 (상한 100)`. 기본 상한 100종 — 넘는 표기는 묻지 않고 `orphan_anchor` 큐로 간다(`--coord-llm 200`으로 올리거나 골격 alias를 늘린다) · `--coord-llm off`면 정확 일치만. 진행 줄은 `[좌표 태깅] 표기 i/k · 채택 · 목록 밖` |

**확인**: `[성공] <파일>  doc_id … record N · chunk M · 그래프 노드 K  [추출 실행|체크포인트 재사용]`.
그 위에 **형태 판정 두 줄**이 먼저 뜬다 — `형태 table (자동 · 찬성 5 · 반대 0)` + 신호값 다섯. **「사람」으로 뜨면 멈춘 것이다** — 신호값을 보고 `--doc-type`으로 지정해 다시 넣는다.

문서 전체를 한 번에 보려면:

```bash
python run.py scan --form          # 폴더의 문서마다 형태 판정 한 장
```

### §5.2 한 단계씩 보고 싶을 때

| Stage | Table | Prose | Command | Output |
|---|---|---|---|---|
| parse — 형태 | records | chunks | `run.py parse run adapters/<doc_type>.py <문서> [--doc-id X]` | `parsed/<doc_id>.json` |
| extract — 의미 | (없음 — 스키마가 등록 때 정했다) | 청크별 개체·관계 후보 | `python -m cli.extract parsed/<doc_id>.json [--force]` | `extract/<doc_id>.json` |
| build — 그래프 | graph | graph | `run.py build parsed/<doc_id>.json` | `data/` |

`build`는 `extract/<doc_id>.json`이 있으면 재사용한다. 프롬프트·정의문을 고쳐서 다시 뽑고 싶으면 `cli.extract --force`.

### §5.3 인입 뒤 확인 — 5가지

**정본은 넷이다** — `data/<층>/graph.json`(노드·엣지 · `status: auto`는 문서가 만든 것, `confirmed`는 사람이 확정한 것) · `data/dictionary.json`(동의어 사전 — 판정이 끝난 표기는 여기 쌓여 다음엔 LLM 0) · `data/chunks.json`(청크·describes) · `data/review_queue.json`(사람 판정 대기 20종 — orphan 수는 `platform queue`가 kind별로 센다). 나머지 json은 장부·로그다(§5.4 표). **보는 법**: 그래프는 `run.py viewer`(브라우저) 또는 `export html`, 큐는 `platform queue [kind]`, 로그의 `onto.llm`·`onto.store`는 모듈 이름(문서 7 §7.8 — LLM 호출·저장 쓰기 한 줄씩)이다. 큐 항목 「자동 생성: A :: B :: C」는 C가 B(공정) 아래 스코프로 생긴 노드라는 뜻 — 이름에 부모가 접두된다. 그런 `auto` 노드는 사람이 끝낸다 — `platform queue auto_node`가 항목마다 세 줄을 준다: `ops confirm`(맞다 → confirmed) · `ops merge`(이미 있는 것) · `ops obsolete`(아니다), 전부 `--actor` 필수(B73 ④). 확정한 노드는 다음 판정에서 후보로 더 신뢰된다(auto 후보에는 표기가 같을 때만 붙는다 — B73 ③).

```bash
python run.py show doc <doc_id>          # 이 문서가 만든 것 전부 + 큐 kind별 건수
python run.py show report <doc_id>       # 행별 결과표 — 값마다 경로(사전/스코프/임베딩→판정)·판정·큐 (B74 ④) · --json
python run.py show extract <doc_id>      # prose — 청크마다 뭐가 뽑혔나
python run.py show node <이름>           # 값·별칭·근거 청크가 달렸나 (답의 뒷면)
python run.py platform queue [kind]      # 큐 20종
python run.py show log gate              # 관계가 없을 때 — 게이트 거부
```

| Check | Expect | If not |
|---|---|---|
| record·chunk 수 | 기대한 규모 | 0이면 스키마 `fields`나 추출을 의심 — §7 |
| `show extract` (prose) | 층 어휘로 말이 되는 후보 | §7 「엉뚱한 것을 뽑는다」 |
| `show node` | 값·근거 청크가 붙어 있다 | 큐를 본다 |
| 큐 | `orphan_anchor`가 예상 밖으로 많지 않다 — 요약 줄의 「k표기(n행)」로 본다(집계는 표기 단위 · B72 ②) | 골격 alias 부족이 가장 흔하다 — §7 · 화면 「▶ 다음 줄」 |
| 비용 | 요약 줄 `판정 — 호출 k · 사전 h · 스코프로 끝 s · 임베딩 e · 후보 평균 n.n(상한 12)` — 같은 문서 2회째는 사전 히트로 호출 0(B74 ① 뒤 · 허브 재현 60 → 0) | 호출이 값 수에 가깝고 사전 0이면 표기가 매번 다른 것(공백·기호) — 어댑터의 정규화 · 후보 평균이 12에 붙고 스코프 0이면 스코프 카테고리 선언(config `canonical_scope`) 누락 |
| 임베딩 | `EMBED_MODEL` 없어도 인입이 끝까지 돈다 — 머리에 「임베딩 미설정 — 겹침으로 좁힌다」 · 요약 줄 `좁힘 — 임베딩 0 · 겹침 o` | 중단됐다면 `CANDIDATE_NARROW=embed`가 켜진 것 — 설정을 `auto`로 |
| 임베딩 효과 비교 | 같은 문서를 `--narrow embed`·`--narrow overlap`으로 각각 넣고(재인입 전에 `work/ingest_log/<doc_id>.json` 복사) `show report --diff a.json b.json` — 판정·node(canonical)가 다른 행만 | 다른 행이 많으면 그 행들을 사람이 본다 — 도구는 차이만 보인다 |
| 재시도 | `platform queue <kind>`의 「N회 재시도 · 첫 발생」이 5에서 멈춘다(사람 판정 대기) | 같은 항목이 계속 돌면 그래프가 자라고 있는 것(정상) · 5회면 alias·골격을 보라 — 재시도는 그래프가 안 바뀌면 돌지 않는다(B73 ②) |
| 관계 | 그래프에 있다 | `show log gate` 먼저 — config `relation_patterns` 밖이면 저장 안 된다 |
| **`그래프 노드 0`** (record는 있는데) | 노드 > 0 | 골격이 **확정 전**이거나(§2 `skeleton-confirm`) 좌표가 전부 목록 밖(`unresolved_endpoint` — `show log gate`)이다. 허브 실측: 클린 상태에서 골격 미확정이면 xlsx·csv 둘 다 노드 0 — 문서 탓이 아니다 |

### §5.4 현황·이력은 어디에 — 한 표

경로는 전부 상태 루트 `$ONTO_HOME/` 아래다(§0 표 · `doctor` 첫 줄이 지금 루트를 말한다).

|---|---|---|

| 등록된 doc_type · 어댑터 | `registry/doc_types.json` · `registry/adapters/<doc_type>.py` · `registry/schemas/<doc_type>.json` | `platform doctypes` · `register list` · `show schema <doc_type>` |
| 층 | `layers/<층>/` · `data/registry.json` | `platform registry` |
| 사람이 판정할 것 (큐 20종) | `data/review_queue.json` | `platform queue [kind]` |
| 관계가 왜 안 붙었나 · 결함 · 링킹 미스 · 잘림 | `work/gate_rejects.json` · `work/defects.log` · `link_miss.log` · `chunk_truncated.log` | `show log` (4종 요약) · `show log <이름> [N]` |

| 문서의 값마다 어떻게 해소됐나 (판정 대장 — 장부) | `work/ingest_log/<doc_id>.json` | `show report <doc_id> [--json]` — 비교하려면 재인입 전에 파일을 복사해 둔다(재인입이 덮는다) |

| LLM 호출 수·토큰 | 실행 화면 머리·끝 + INFO 로그 | 명령마다 |

**`adapters/`·`schemas/`는 새로 생기는 폴더가 아니다** — 레포에 이미 있고, `confirm`이 `review/<doc_type>/`의 산출을 그리로 **옮긴다**. `review/`는 작업 폴더(추적 안 함), `adapters/`·`schemas/`가 정본이다.

### §5.5 새로 만들까, 누적할까 — 기준은 doc_id다

| Situation | Do | What survives |
|---|---|---|
| 새 문서 | `ingest-file <새파일>` — 누적 | 전부 |
| 같은 문서의 개정판 · 어댑터/스키마를 고쳐 다시 넣는다 | 같은 파일명으로 `ingest-file` — **개정판 재인입**: 그 doc_id가 만든 노드·엣지·청크·큐를 회수하고 다시 쓴다(D-110). 사전은 남아 판정이 대부분 LLM 0 | 그래프 · 사전 · 다른 문서 |
| 골격 alias·노드를 더했다 | seed 편집 → `python run.py bootstrap`(**`--fresh` 없이**) → 관련 문서 재인입. 노드·사전이 보존되고 alias만 붙는다 | 전부 |
| 골격 **구조**가 바뀌었다(트리 재배치·극성 패턴 변경) | `init --fresh && bootstrap && skeleton-confirm` → **전량 재인입**. 노드 id(ULID)가 새로 나므로 사전도 무효 — 판정을 전부 다시 한다(토큰도 다시) | 등록(doc_types.json)만 |
| 잘못 넣은 문서 하나를 빼고 싶다 | 아직 명령이 없다(이연 — `ingest retract`) — 지금은 개정판 재인입으로 덮거나 전량 renew | — |

**함정**: 이름만 같은 다른 문서는 개정판으로 취급돼 서로 덮어쓴다 — 파일명을 가르거나 `parse run … --doc-id X`. 지운 자산은 되돌릴 수 없으니 `init --fresh` 전에 `data/`를 복사해 둔다.

**보는 법**: 인입 뒤 `run.py viewer`(브라우저 · 그래프 + 질문 칸 · 링킹 켜짐 · B52) · `show doc <doc_id>`(그 문서가 만든 것) · `show node <이름>`(값·별칭·근거) · `export html`(정적 파일). 화면 한 줄이 무슨 단계인지는 `인입_이해_가이드.md`.

## §6 질의 — 첫 주

```bash
python run.py query "노칭 다음 공정은?"            # 텍스트 답 — 두 채널
python run.py query "노칭 다음 공정은?" --json     # 같은 답을 JSON으로 (화면·스크립트용)
python run.py viewer                              # 그래프 뷰어 + 질문 칸 — 브라우저 주소가 찍힌다 (B52)
```

```bash
python run.py golden init                    # golden/queries.json 120건 틀 (B54)
#   ① q를 쓴다 (유형 정의는 문서 5 §5.3) ② expected_linked(「층:canonical」)·expected_docs(doc_id)를 아는 만큼 — 비우면 그 축은 채점하지 않는다
python run.py golden score                   # 4축(path·linking·evidence@8) + BM-25 대조군
python run.py show bm25 "<질문>" 8            # 대조군만 따로
#   ※ golden/ 은 추적하지 않는다 — 문항이 사내 정보다. 골든셋이 서면 계기판 1의 분모가 골든셋으로 바뀐다
```

**뷰어**: 그래프를 그려 놓고 질문을 치면 두 채널 답이 오른쪽에 뜨고 **링킹된 노드가 그래프에서 켜진다**. 머리에 `mock`/`실호출` 배지가 있다 — mock이면 답은 정형 나열이다. 닫으려면 Ctrl+C.

**플랫폼으로 넘길 때** — 플랫폼이 읽는 것은 넷뿐이다: `data/<층>/graph.json`(그래프 정본) · `data/doc_registry.json`·`review_queue.json`(문서·큐) · `query --json`의 답 계약(B52 — 문서 5 · `플랫폼안건/요청문_v0_뷰어와질의.md`) · `run.py viewer`가 그리는 html(같은 계약의 참조 구현). 플랫폼이 그래프를 **쓰는** 경로는 없다 — 고치는 것은 `run.py ops`뿐(문서 1). 인입 한 건이 그래프를 만들고 `viewer`에서 링킹이 켜지는 것까지 본 뒤 넘긴다 — 그 화면이 플랫폼의 첫 수용 기준이다.

**확인**: 답의 `[그래프 사실]`·`[문서 근거]`가 실제 문서와 맞는가 — 눈으로 10문항. 이후 **골든셋** 제작(유형당 15문항, 기준 120) — 계기판이 측정이 되는 조건이다.

## §8 허브로 가져올 때

| Situation | Format |
|---|---|
| 명세가 답하지 않는다 | BLOCKER — ①근거 원문 ②선택지 2~3 ③귀결 |
| 명세와 실물이 어긋난다 | 어긋난 두 문면 + 실측 화면 |
| 판정이 필요하다 (값 충돌·구조 개정) | 큐 항목 + 판단 재료 |

**명세는 사내에서 고치지 않는다.** 코드 수정은 사내에서 하되 `DECISIONS.md`에 남긴다.
