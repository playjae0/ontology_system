## 1. 기본 구조 (그래프와 층)

| 용어 | 뜻 (1줄) | 예시 | 원천 |
|---|---|---|---|
| **정보층 (층)** | 성격이 같은 지식의 묶음 단위. 층마다 카테고리·관계·골격을 따로 정의한다 | 공정정보층, 품질지식층 | 명세 §3·4 |
| **노드** | 그래프의 개체 하나 | "노칭"(공정), "노칭 프레스"(설비) | 명세 §5 |
| **엣지** | 노드 사이의 관계 한 줄 | 노칭 프레스 ─part_of→ 노칭 | 명세 §5.3 |
| **카테고리** | 그 층에서 노드가 될 수 있는 종류의 닫힌 목록. 사람이 정의문으로 고정, LLM은 이 중에서 고르기만 | 공정층: Process/Unit/Property | 명세 §5.4 |
| **골격 (skeleton)** | 사람이 직접 심는 고정 뼈대. 자동 생성 금지 영역 | 공정 트리, FailureEffect 목록 | 명세 §5.2 |
| **Tier1 / Tier2** | Tier1=사람이 파일로 고정하는 구조(골격·유형), Tier2=문서에서 자동 생성되는 인스턴스. 구조적 차이는 "원천의 위치"(파일 vs 그래프) 하나 | 공정 트리는 Tier1, 발견된 설비는 Tier2 | P2, 명세 §9.1 |
| **canonical** | 노드의 대표 이름(층 안에서 유일) | "노칭::cathode 노칭 정밀도" | 명세 §5.2 |
| **alias (표면형)** | 같은 노드를 가리키는 다른 표기. 판정에서 매칭되면 자동 누적 | "notching" → 노칭 | 명세 §5.4 |
| **동의어 사전** | canonical과 alias를 모아 "표기→노드 후보"를 찾아주는 전 층 공유 장부. 시스템의 영속 지식 | dictionary.json | P4, §8-R2 |
| **attribute (속성값)** | 노드에 붙는 값. 노드를 만들지 않고 필드에 저장 | 규격 ±0.1mm | 정의서 §3.3 |
| **청크** | 문서에서 잘라낸 원문 조각. 전부 보존하고 관련 노드에 연결(describes) | PPT 슬라이드 1장의 텍스트 | 명세 §5.6.6 |
| **provenance (출처 이력)** | 이 노드/엣지/값이 어느 문서 어느 행에서 왔는지의 기록. 모든 자동 생성물에 필수 | ["CP01-C8"] | 구현문서 §0-5 |
| **진실 / 파생물** | 진실=그래프 JSON+청크 저장소. Neo4j·시각화·임베딩 인덱스는 언제든 재생성 가능한 파생물(뷰) | graph.json이 진실 | P5 |
| **GraphStore** *(세션 N+3 등재)* | graph.json 읽기·쓰기의 **유일한 코드 경계**(core/graph.py) — graph.py 밖에서 graph.json을 직접 여는 코드는 금지. 직렬화는 orjson(표준 json 폴백). 저장 방식 전환(R10)이 와도 이 경계 안만 바뀐다 | `GraphStore.load("process")` | 틀 §4B-A8-2, 카드 B6 |
| **T0~T3** *(M1 등재)* | 정보의 4계층 — T0 골격(파일·사람 보증) / T1 의미(그래프 본체·문서 수 비례) / T2 근거(청크 저장소) / T3 관측(생산 발생 데이터 — 시간 비례·무한이므로 **그래프에 적재하지 않고 참조만**). 현 구축 범위는 T0~T2 | 검사 실측값은 T3, 그 스펙은 T1 | 틀 §4B-A9, 카드 J11 |
| **SeriesRef** *(M1 등재 — 개념만, 설계는 R11)* | 그래프 노드에서 외부 T3 데이터(시계열 태그 등)로 가는 참조 핸들 — 설비당 1개라 데이터 포인트 수와 무관. T3을 넣지 않고도 "어느 태그를 볼지"를 그래프가 답하게 하는 장치 | 설비 → PI 태그 "NOTCH03.TEMP" | 틀 §4B-A9-2, R11 |

## 2. 문서와 인입 (쓰기 경로)

| 용어 | 뜻 (1줄) | 예시 | 원천 |
|---|---|---|---|
| **파서** | 사내 문서(Excel/PPT 등)를 계약된 JSON으로 바꾸는 사내 실행 프로그램(코어·킷은 외부 전달물 — 파서_명세 §9). 시스템과는 JSON으로만 만난다 | CP.xlsx → CP01.json | 명세 §12 |
| **doc_type** | 문서 양식의 종류. 종류마다 매칭 스키마 1개 | cp, pfmea, ppt_report | 명세 §6 |
| **정형 / 비정형** *(세션 1 등재)* | **파일 포맷이 아니라 payload_kind의 구분이다.** 정형=`table`(행=record, role 선언이 추출을 대체하므로 추출 LLM 불요) / 비정형=`prose`(청크, 추출 LLM 필요). **줄글·목차형 엑셀은 비정형으로 취급한다** — 확장자가 아니라 내용의 형태가 정한다 | CP.xlsx=정형 / 목차형 xlsx=비정형 | 틀 §4-Q2, CH2 2.2 |
| **어댑터 (어댑터 코드)** *(세션 N 정정)* | 한 doc_type의 문서를 정규 조각으로 분해하는 **파서 측 코드 — 선언 1개(ADAPTER)+함수 1개(extract)**. extract는 조각마다 source_locator를 담아 반환하고(별도 locate 없음), 이미지는 placeholder 조각만 낸다(요약 LLM 호출은 코어 소유). 순수 함수(상태·네트워크·LLM 금지). 구축 모드에서 LLM이 생성, 사람이 결과 뷰로 검수. 버전(`adapter_version`)은 봉투에 1회 | adapters/cp.py | 파서_명세 §5, 카드 C11·C12 |
| **기본 어댑터** *(세션 N 등재)* | 분할이 자명한 계열(PPT=슬라이드 1장이 청크 1개)에 쓰는 **코어 제공 고정 어댑터** — LLM 생성 없이 등록 시 그대로 붙인다. 등록 절차(층 지정·검수·승인)는 생략하지 않는다 | PPT 계열 등록 | 파서_명세 §5 규약 5, 카드 C13 |
| **expects (관찰 상수)** *(세션 N 등재)* | ADAPTER 선언 안의 "이 어댑터가 기대하는 양식의 지문"(헤더 행·열 매핑·분할 신호) — 코드 본문 밖 **데이터**로 분리. 용도 셋: 검수 뷰 표시 · preflight 대조 기준 · 생성 스켈레톤의 빈칸 | header_row: 3 | 파서_명세 §5 규약 4, 카드 C11 |
| **preflight** *(세션 N 등재)* | 운영 인입에서 extract 실행 **전에** 문서 실물 지문(헤더)을 지정 어댑터의 expects와 결정적으로 대조하는 검사(코어 소유, LLM 아님). 불일치면 문서 중단+`adapter_mismatch` 큐 — 운영 모드 안의 **양식 표류**를 잡는다. 등록 조회(M2)를 대체하지 않는다 | 헤더가 등록 시점과 다름 → 중단 | 파서_명세 §5 규약 6, 카드 C15 |
| **투입 분류 (지문 스캔)** *(세션 N 등재)* | doc_type 지정의 규칙 — **지정은 사람이 기본**(투입함/선택 UI), 미지정 **정형** 문서만 헤더를 전체 어댑터 expects와 일괄 대조(지문 스캔)해 후보 제안+사람 1클릭 확정. 비정형은 지정 필수. 자동 라우팅은 측정 후(P7). preflight(지정 검증)·doc_hash(중복 차단)와 답하는 질문이 다르다 | 미지정 엑셀 → "cp 양식과 일치" 제안 | 파서_명세 §5, 카드 C15 |
| **role** | 문서 필드 하나가 그래프에 일으키는 쓰기 동작의 이름표 5종. 코드는 필드명이 아니라 role만 본다 | 관리항목 열 = entity | 정의서 §1 |
| **anchor (닻)** | role ①: "이미 있는 골격 노드를 **찾아라**" — 새로 만들지 않음. **동작은 해소이지 부착이 아니다** — 찾은 노드를 무엇에 쓰는지(부착점 / edges의 `@좌표필드` / 다른 anchor의 검증)는 스키마가 정한다 | process_ref: "노칭" | 정의서 §3.1, 틀 §4B-A7-4 |
| **entity (개체)** | role ②: "노드 후보를 데려와라" — 판정을 거쳐 매칭 또는 신규 | 설비: "노칭 프레스" | 정의서 §3.2 |
| **content (서술)** | role ④: 자유 텍스트 — 청크로 보존하고 관련 노드에 연결 | 대응계획 열 | 정의서 §3.4 |
| **meta** | role ⑤: 그래프에 넣지 않고 출처 장부에만 적는 관리 정보 | 개정번호, 작성일, source_locator | 정의서 §3.5 |
| **edges 선언** | "이 필드와 저 필드 사이에 이 관계를 그어라"는 스키마 레벨 선언(필드 role이 아님) | 설비 ─has_property→ 관리항목 | 정의서 §4 |
| **핸들러** *(세션 1 등재)* | role 하나를 처리하는 함수. 코드는 필드명이 아니라 role로 핸들러를 고른다. 모든 핸들러는 **규칙 → LLM 폴백(훅) → 수정 큐**의 3단 구조를 따른다. edges는 핸들러가 없고 루프 후처리다 | handle_entity | 명세 §6.6, 정의서 §6 |
| **매칭 스키마** | 한 doc_type의 필드→role 번역표 파일. 등록 때 1회 작성(LLM 초안+사람 검수). 헤더(doc_type·schema_version·layer·use_blocks) + fields + edges | schemas/pfmea.json | 명세 §6.5, CH2 2.5 |
| **메타데이터 스키마** *(세션 1 등재)* | "그 doc_type에서 무엇이 나와야 하는가"의 필드 선언. **별도 파일을 두지 않고 매칭 스키마의 `fields` 키 목록이 겸한다**(Q5 확정) — 같은 필드 목록이 두 파일에 살면 반드시 어긋나기 때문 | pfmea.json의 fields 키 목록 | 틀 §4-Q5, CH2 2.5 |
| **블록 (fragment)** *(세션 1 등재)* | 여러 doc_type에서 반복되는 필드 묶음을 스키마 레벨에서 재사용하는 단위. `use_blocks`로 조립하며, 승격은 2~3개 스키마에서 관찰된 뒤(스키마 레벨의 Rule of Three). 블록도 값이라 코드 리스크 0 | common_core, process_coord | 정의서 §5.4 |
| **UNMAPPABLE** *(세션 1 등재)* | 등록 검수에서 "이 필드는 role 5종 어디에도 안 맞는다"는 판정값(필드당 6지선다의 6번째). 스키마에 넣지 않고 L3(새 role 필요) 또는 L4(그래프 모델 밖) 판정으로 넘긴다 | 자재 열 → UNMAPPABLE 검토 | 명세 §6.5, 정의서 §8.1 |
| **source_locator** *(세션 1 등재)* | 파서가 붙이는 "이 조각이 원본 문서 어디서 왔나"의 위치 표기. role=meta이며 **그래프 id가 아니다** — 정본 `chunk_id`·`record_id`는 에이전트가 내용에서 계산한다. 요구는 "문서 안에서 유일할 것" 하나 | "Sheet1!R12", "슬라이드 5" | CH2 2.2, 카드 C7 |
| **payload_kind** *(세션 1 등재)* | 봉투 필드. `table` \| `prose` **닫힌 2값**이며, payload가 `records[]`인지 `chunks[]`인지를 가르는 결정적 스위치다. **"정형/비정형"이라는 말이 실제로 가리키는 것이 이 값이다** | `"payload_kind": "table"` | CH2 2.2, 카드 C9 |
| **canonical 스코프** *(세션 1 등재)* | 같은 인자명이라도 소속 공정이 다르면 다른 노드가 되도록, canonical에 부모를 접두하는 규칙. 대상 카테고리는 층 config의 `canonical_scope.bind_categories`가 지정하는 **값**이며 코드는 모른다. 공정층에서는 Property가 대상이고 부모는 **세부공정**(설비 아님) | "노칭::노칭 정밀도" | 명세 §5.2(G1), 카드 F4, CH3.5 |
| **걸침 문서** | 한 문서가 여러 층의 카테고리를 담는 경우. 필드의 target_layer가 기록될 층을 지정(생략 시 스키마 헤더의 layer) | PFMEA의 관리항목→공정층 | 명세 §15.7 |
| **공정좌표** | 모든 조각이 달고 들어오는 "공정 트리 어디 소속" 이름표(process_group/ref). 둘 다 anchor이며 부착 기본 대상은 process_ref | process_ref: "노칭" | 명세 §6.2, 카드 C3 |
| **classification** *(M1 등재)* | 봉투의 선택 필드 — 문서 등급의 **자리**(널 허용·자유 문자열). 현 국면에서는 아무도 채우지 않으며 권한 일체는 R12 이연. 등급은 노드가 아니라 문서의 성질이다 | `"classification": null` | CH2 2.2, 틀 §4B-A10, 카드 C16 |
| **극성** | cathode/anode 구분(electrode_type). 조건 3개를 모두 만족할 때만 노드 이름에 결합 | "cathode 노칭 프레스" | 명세 §5.2 |

## 5. 원칙·약어

| 용어 | 뜻 (1줄) |
|---|---|
| **P1** | 단계 간 결합은 파일 계약(JSON)으로만 |
| **P2** | 골격·유형(Tier1)은 사람이 고정, 인스턴스(Tier2)는 자동 생성+사후 수정 |
| **P3** | 코어 코드는 최소·안정 — 사람이 전부 읽고 파악 가능해야 |
| **P4** | id 불변, 사전이 영속 지식. 노드 유일성 불변식: 같은 개념은 언제나 한 노드 |
| **P5** | 진실 = 그래프 JSON + 전 청크. 나머지는 재생성 가능한 파생물 |
| **P6** | 질의는 읽기 전용 — 질문 표현을 사전에 누적하지 않음 |
| **P7** | 측정이 복잡도를 정당화한다 — 근거 없는 구조 선반영 금지 |
| **L1~L4** | 변경 등급: L1 필드 변경(스키마 1줄) / L2 새 doc_type(파일 1개) / L3 새 role(함수 1개) / L4 그래프 모델 밖(재검토) |
| **A/B/C** | 범용성 경계: A=전 층 공유 코드(core) / B=층별 값(config) / C=층별 절차 — 원칙적으로 비어 있어야 하며, 남으면 명시적 실패로 드러냄 |
| **Rule of Three** | 추측으로 미리 일반화하지 말고, 표본이 관찰된 만큼만 공통으로 승격 |
| **명시적 실패** | config로 표현 안 되는 경우 조용히 우회하지 않고 시끄럽게 실패해 core 확장을 요구하는 규칙 |
| **여섯 칸** | 층 정의의 6요소: ①메타데이터 스키마 ②골격 ③관계 목록 ④카테고리 정의문·프롬프트 ⑤쓰기 절차 ⑥읽기 절차 |
| **국면 0~3** | 로드맵: 0 명세(종료) → 1 외부 mock 구현(진행 중) → 2 사내 이식 → 3 운영·확장 |
| **USE_MOCK** | LLM·외부 의존 없이 규칙 폴백으로 전체 파이프라인을 돌리는 개발 토글 |
| **PoC 범위** | 공정층 구축 + 품질지식층 구축 + 층간 연결까지. 질의는 Q1~Q5·Q8 |
| **3축** | 이 프로젝트의 상위 프레임: 축1 문서→그래프(쓰기) / 축2 정보층 추가·연결 / 축3 RAG 질의(읽기) |
| **두 모드** *(틀 §2 확정)* | 운영 모드 = 등록된 층·doc_type의 문서가 사람 개입 없이 흐르는 것 / 구축 모드 = 처리 방식이 없는 입력(새 doc_type·새 층)에 대해 어댑터 코드·매칭 스키마(+층이면 config)를 먼저 만드는 것. 모드 판별은 등록 여부 조회(결정적) |
| **부트스트랩** *(세션 N 등재)* | 시스템 최초 가동 시의 층 구성 규칙 — **기본 내장 층은 공정정보층 1개**(구현 시 seed·config로 내장, 층 등록 세션 불경유). **품질지식층은 신규 층 등록 절차의 첫 검증 대상**(J3 판정의 실전 시험). 층 등록 기능(R1)은 신규 층 전용 |
| **추출 단계** *(틀 §4-Q1 확정 — 독립 단계)* | 비정형 처리에서 청크를 읽고 개체 후보 + 관계 후보(닫힌 목록 선택) + 부착 이름을 출력하는 LLM 단계 — "내용 파악" 담당. 판정·게이트·커밋(연결)은 구축 단계 담당. 산출물 계약은 추출 후보 JSON(CH3A 3.11) |
| **근거 축 / 의미 축** *(틀 §4B-A4 · N+3 정정)* | 근거 축 = 문서·청크·레코드(개명·동의어 없음 → id를 내용에서 해시로 계산, **계산 주체는 에이전트**) / 의미 축 = Unit·Property·Failure 등(개명·alias 있음 → id 발급 유지 — **발급 방식은 ULID**, 틀 §4B-A8-4). id 규칙이 두 축으로 갈린다 |
| **ULID** *(세션 N+3 등재)* | 의미 축 노드 id의 발급 방식(틀 §4B-A8-4 — 구 전역 시퀀스 N####를 대체). 시간순 정렬 가능·충돌 없음·중앙 카운터 파일(id_seq.json) 불요. **id에 의미를 넣지 않는다** — 소속·순서는 그래프가, 가독성은 canonical이 담당(카드 N1). 발효는 A0의 N#### 하드코딩 지점 계수 확인 후 |
| **인스턴스 변경 (I축)** *(틀 §4B-A2)* | 이미 만들어진 노드에 대한 사후 연산 4종 — I1 개명 · I2 병합 · I3 분리 · I4 폐기. 스키마 변경 등급(L1~L4)과 직교한다 |
| **obsolete / merged_into** *(틀 §4B-A2)* | 노드를 삭제하지 않고 남기는 두 종결 표식. obsolete = 더 이상 유효하지 않음(+replaced_by), merged_into = 다른 노드에 흡수됨(+target). **내용·provenance는 생존자로 이관되므로 정보 손실이 없고, 표식의 용도는 옛 id 참조의 리다이렉트 하나다.** 질의는 둘 다 전이적으로 따라가며 순환은 쓰기·읽기 양쪽에서 막는다 |
| **doc_hash** *(틀 §4B-A6)* | 문서 전체 내용의 해시. **에이전트가 인입 진입점에서 계산**해 대조하고, **같은 내용이 다른 doc_id로 들어오는 것**(파일 복사·개명)을 차단한다. 파일명·크기는 판정 기준이 아니라 사람 확인용 참고 표시다 |
| **occ (출현 순번)** *(틀 §4B-A4)* | 한 문서 안에서 동일한 (섹션, 내용) 조합이 몇 번째로 나왔는지(0부터). 청크·레코드 id 해시의 입력에 넣어 **처리 순서에 의존하지 않는 유일성**을 만든다 — 충돌 접미(`#2`)를 쓰면 순서가 바뀔 때 id가 뒤바뀌어 멱등성이 깨진다 |
| **direction_unverifiable** *(틀 §4B-A3)* | 동종 카테고리 쌍의 방향성 관계 후보가 비정형 추출에서 나왔을 때, 게이트가 방향을 검증할 수 없어 커밋하지 않고 보존하는 큐. 사람이 방향을 확인하면 커밋된다 |
