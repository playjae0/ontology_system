## 0. 전체 flow 조감 — 챕터가 어디에 사는가

```
[구축 모드]  미등록 입력(새 doc_type / 새 층)
             → LLM 표본 관찰(정형 head ~10줄 / 비정형 10~30줄·패턴 2~3회) → 어댑터 코드(+분할 규칙)·매칭 스키마·(층이면) config 초안
             → 실행 하네스(기계 관문 — D-27) → 사람 검수(결과 뷰 확인 · 승인 1회) → 등록   …… CH2 (층: CH4.7, 파서 내부: 파서_명세)

[운영 모드]  문서 투입 → 등록 조회(결정적)
             → 인입 진입 검증: doc_hash 대조 → 근거 축 id 계산 → 필드 검증    …… CH2 2.8
             → 파싱: 어댑터 실행 → 계약 JSON (record/청크 + 공정좌표)         …… CH2(계약) · CH3A · 파서_명세
             → 추출(비정형만): 청크별 LLM → 개체·관계 후보+부착 이름 [체크포인트 — 계약은 CH3A 3.11] …… CH3A
             → 구축: 2-pass 해소(판정) → 부착·관계 생성(게이트) → 자동 커밋+큐  …… CH3A
                └ 이름·값의 규칙(극성·스코프·맥락)                            …… CH3B
             → 그래프(JSON=진실, 접근은 GraphStore 경유 — 틀 §4B-A8) → 파생물(임베딩·시각화) …… CH3B · CH6
             → 수명주기: 재인입 · 큐 처리 · 구조 개정 제안 · I축 4연산          …… CH3B
[질의]       링킹 → 확장 → 수집 → 답변(이원 근거)                             …… CH5
[층]         여섯 칸 · config-only · 층간 연결(A안 + 허브 규칙)               …… CH4
[기반]       목적 · 원칙 P1~P7 · 용어                                        …… CH1
[구현·운영]  코드 배치 · 근거 축 id 산식 · mock · 플랫폼 훅 / 로드맵 · 문서 체계 …… CH6 · CH7
```

## 3. 챕터 파일 서술 규격 (필수 준수)

### 3.1 파일과 이름
- 파일 1개 = 상위 챕터 1개. 이름 `CH{n}_{제목}.md`.

chapter: 2
title: 문서 계약과 등록 — 구축 모드
axis: 축1 (쓰기)
question: 시스템은 문서로부터 무엇을 어떤 약속으로 받으며, 처리 방식이 없는 새 입력은 어떻게 처리 가능해지는가?

> **`version:` 필드는 필수다.** 개정할 때마다 갱신하고 근거가 된 틀 버전을 함께 적는다.

### 3.4 서술 원칙 — 오해의 여지 0
1. 조건을 흘리지 않는다. 2. "등·류·같은"으로 목록을 닫지 않는다. 3. 부정형을 반드시 쓴다. 4. 수치·임계·상한에 출처와 근거를 붙인다. 5. 예시 1개를 붙인다. 6. 미확정은 미확정이라 쓰고, **확정된 것을 미결로 남기지 않는다.**

### 3.5 슬라이드 규칙
슬라이드는 요약하지 않는다 — ①주장 ②조건의 존재와 개수 ③원천 앵커. **단독으로 읽어 틀린 문장이 되는 서술은 올리지 않는다.**

### 3.6 갱신 규칙
- 챕터를 고치면 **같은 커밋에서** 이 대장의 상태를 갱신한다.
- **틀을 고치면 영향받는 `서술완료` 챕터를 같은 커밋에서 고치거나 상태를 내린다.**
- 용어를 새로 쓰면 `용어_대장.md`에 등재한다.
- **파생 문서를 새로 만들면 §1 파생 문서 표에 그 커밋에서 등재한다** — 미등재 파생 문서는 다음 세션이 존재를 모른다(11회차의 `실행검증_1차` 누락이 실례. 13회차에서 정정).
- **정본을 고칠 때는 고치기 직전에 그 정본의 현행판을 다시 읽는다(재독 규칙 — 18회차 신설).** 세션 시작 시점의 사본·요약 위에 재구성하면 그 사이의 개정이 소실된다 — 14-B 기록 소실(M2 세션이 구판 사본 위에 대장을 재구성)이 실례다.
- **작업이 생기거나 담당이 바뀌면 CH7 7.5에 같은 커밋에서 등재한다(19회차 신설).** 계획의 단일 원천은 7.5이고, 이 대장 §5.1·§7 ③은 명세 트랙 부분을 소유하되 7.5와 어긋나면 7.5가 이긴다 — 단 §5.6 진행 원칙은 7.5의 상위다.

### 5.5 순서 근거

- 전체 정리 패스(배치 1~7)로 서술을 선완료했다 — CH4~7이 틀 v2.2·v2.3과 한 번도 대조되지 않은 상태로는 [보완필요]와 구현 범위를 확정할 수 없었다.

### 5.6 진행 원칙 — 전량 구현 + 충돌 등급 분류 [사용자 확정 · 2026-07-30]

1. **해야 할 것은 다 하고 넘어간다 — 범위는 전 기능이되 깊이는 무한하지 않다.**
2. **명세 문서 다듬기는 차단물이 아니다.**
3. **충돌은 등급으로 가른다**: 차단급(계약·불변식 모순) = 즉시 해소 / 비차단급 = 기록하고 전진. 감사도 범위 한정.

5. **3요소(인풋·조절점·아웃풋)를 단위 정의에 내장한다.**
6. **구현 중 막힘**: 카드·계약과 충돌 = BLOCKERS(멈춤, **판단 재료 3요소 첨부**) / 그 외 세부 = 가결정 + DECISIONS(전진).

## 6. 세션 운영 프로토콜

### 6.1 여는 문장

> `chapters/00_틀_확정본.md`, `chapters/00_불변식_카드.md`, `chapters/00_용어_대장.md` 기준으로 진행한다.
> 세션 N — `chapters/CH#_____.md` 검토(또는 상세화).
> **대조 원천**: 대장 §1의 해당 챕터 소유 절 + `role_어휘_정의서.md`·`ontology_system_구현용문서.md`의 해당 부분.
> 대장 §5 계획, §6 운영 프로토콜을 따른다.

**착수 시 첫 동작은 검사 3.5(버전 대조)다.** 이전 대화의 내용을 요약해 옮기지 않는다 — 요약이 곧 왜곡이고, 현재 진실은 언제나 프로젝트 문서에 있다.

### 6.2 파일 명명 규칙

| 접두 | 대상 | 예 |
|---|---|---|
| `00_` | 기준 문서 | `00_틀_확정본` · `00_불변식_카드` · `00_챕터_대장` · `00_용어_대장` |
| `CH#_` | 챕터 | `CH2_문서계약` · `CH3A_인입절차` |
| `archive/` | 보관 | `archive/제작기록/...` |

- **버전은 파일명이 아니라 문서 머리(`version:`)에 넣는다.**
- 절 번호는 분할·병합·재정의되어도 유지한다.
- **구현 레포로 반입할 때는 소문자 `.md`·평면 `docs/`로 정규화한다**(Ubuntu는 대소문자를 구분한다 — 13회차).

### 6.3 outputs와 프로젝트

- **프로젝트 = 원본(현재 진실). outputs·구현 레포 사본 = 그 시점의 사본.**
- **레포 사본을 고쳤으면 같은 커밋 정신으로 프로젝트 원본도 고친다** — 두 곳이 갈라지면 다음 세션이 어느 쪽을 믿을지 알 수 없다(13회차).

### 6.4 세션 진행 방식

1. **검토는 절 단위로.** 판정을 요청할 때는 판단 재료(실물 서술·선택지별 귀결)를 함께 제시한다.
2. **결정이 나면 그 자리에서 반영한다.**
3. **세션 종료 시**: 대장 §5 상태 갱신 + §4 검사 로그 1줄 + §5.4 원천 정정 목록 추가 + **파생 문서 §1 등재**.
4. **문맥이 틀어졌다고 느끼면** `00_틀_확정본` §1~§4로 돌아간다.
