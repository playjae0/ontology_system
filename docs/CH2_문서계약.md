# CH2 · 문서 계약과 등록 — 구축 모드

> 이 챕터가 답하는 질문: **사내 문서가 시스템에 들어올 때 누가 무엇까지 책임지고 어떤 약속으로 넘기는가, 그리고 처리 방식이 없는 새 입력(새 문서 양식·새 층)은 어떻게 처리 가능해지는가.**
> 시스템은 두 모드로 동작한다(카드 M1). **구축 모드** — 모르는 입력에 대해 처리 방식(어댑터 코드·매칭 스키마)을 먼저 만드는 것 — 가 이 챕터의 후반(2.3, 2.6)이고, 만들어진 방식 위에서 문서가 흐르는 **운영 모드**는 CH3A·CH3B다. 모드 판별은 등록 여부 조회로 결정적이다(M2) — LLM이 판별하지 않는다.
> 서술 규격: 챕터_대장 §3. 용어는 용어_대장 등재어만 무설명 사용.
> **원천 기준: `00_틀_확정본.md` v2.3 (구 `틀_확정_기록.md`는 폐기 — v1 참조는 전부 대체했다).**

## 2.1 파서의 위치와 경계

### 무엇인가 (구조)

파서는 사내 문서(Excel·PPT·Word·PDF)를 읽어 **온톨로지 에이전트가 소비하는 JSON**으로 바꾸는 프로그램이다. 사내에서만 실행되며, 시스템의 나머지 부분(온톨로지 에이전트, 플랫폼)과는 **코드가 아니라 JSON 파일로만 만난다.**

```
사내 문서 → [파서: 사내 구현] → 파서 출력 JSON → [에이전트: 외부 설계] → 그래프
                                      ↑
                                유일한 접점
```

파서가 사내에 있는 이유는 설계상의 선택이 아니라 제약이다 — **데이터가 사내 반출 불가**이기 때문에 문서를 직접 읽는 부분은 사내에서만 돌 수 있다. 반대로 파서 출력 JSON을 소비하는 에이전트와 플랫폼은 실물 데이터 없이 설계·구현이 가능하므로 외부에서 만든다. 이 분리가 프로젝트의 물리적 구조를 결정한다.

**계약 언어는 role이다.** 파서와 에이전트를 잇는 사슬은 아래와 같고, 이 사슬에서 파서의 종착점은 "메타데이터 JSON"이며 그 다음 칸(role 번역표)부터가 에이전트다.

```
사내 문서 →[파서]→ 메타데이터 JSON →[매칭 스키마 = role 번역표]→ 그래프 쓰기 동작 → 온톨로지
```

### 규약

1. **결합은 파일 계약(JSON)으로만 한다.** 파서와 에이전트 사이에 함수 호출·라이브러리 공유·데이터베이스 공유가 없다. 한쪽을 고쳐도 다른 쪽 코드는 건드리지 않는다. (P1의 파서 적용)
2. **파서 내부 구현 방식은 에이전트 호환성과 무관하다.** 파서가 내부에서 LLM을 쓰든, 어댑터 코드를 생성하든, 규칙 기반으로 짜든 시스템은 관여하지 않는다. **에이전트는 파서 출력 JSON 계약(2.2)만 의존하고 검증한다.**
3. **파서에 대한 요구는 "예쁘게 파싱하는 것"이 아니라 "출력의 각 필드가 role 배정 가능한 형태일 것"이다.** 즉 파서의 목표는 파싱 정확도가 아니라 **계약 준수**다. 필드가 명확히 분리되어 있고 각 필드의 값이 스칼라 또는 명시적 구조체이면 계약을 만족한다. 예: 규격 열이 `"−0.1~+0.1mm"` 한 문자열이 아니라 `{min:-0.1, center:0, max:0.1, unit:"mm"}` 구조체로 나오면 계약 만족.
4. **골격 파일은 파서와 에이전트의 공유 자산이다.** 좌표 태깅에 쓸 닫힌 목록(골격 노드의 canonical + alias)은 시스템이 파서에 공급한다. 이것이 두 쪽이 공유하는 유일한 데이터이며, 코드가 아니라 데이터이므로 P1을 위반하지 않는다. **공급 형태는 스냅샷이다 [U1/D-11 확정 — 21회차]**: 그래프의 골격 전 노드(auto alias 포함 — seed에는 없는 파생 표기까지)를 한 시점에 추출해 고정한 `data/skeleton_closed_list.json` + 그 안의 `skeleton_version`(어느 골격 판 기준의 태깅인지 추적 — orphan 원인 진단의 근거). 킷에 동봉하며, 사내 배포 경로는 [사내 확인]. 실물 검증: 템플릿 v0.3의 골격 목록 주입(D-45)·3차 블라인드 생성.

### 경계와 오해

- **파서는 개체 판정을 하지 않는다.** "이 설비 이름이 기존 노드와 같은 개념인가"는 에이전트의 일이다(CH3.3). 파서가 이름을 정규화해서 보내는 것도 요구하지 않는다 — 표기 변형은 에이전트의 사전과 판정이 흡수한다.
- **파서는 관계를 만들지 않는다.** 필드 사이의 관계는 매칭 스키마의 edges 선언이 정한다(2.4·2.5). 파서가 "이 설비는 이 공정에 속한다"는 형태의 출력을 만들 필요도, 만들 권한도 없다.
- **파서는 카테고리를 발명하지 않는다.** 카테고리는 층 config에 사람이 고정한 닫힌 목록이다(CH4.4).
- **파서는 그래프 id를 부여하지 않는다.** 근거 축의 정본 id(chunk_id·record_id)는 에이전트가 인입 시점에 계산한다(2.2 계약 ①-id 소유, 2.8). 파서가 내는 것은 **원본 문서 안의 위치 표기(`source_locator`)**뿐이다.
- **"파서 명세"와 "에이전트 명세"는 다른 문서다.** 이 절이 정하는 것은 **경계**이고, 파서 내부의 설계(3단 파이프라인, 어댑터 구조 등)는 별도 파일 `파서_명세.md`가 소유한다. 그 파일은 이 챕터의 2.2와 2.3을 상속 전제로 참조하며, 계약 3종의 원천은 여기(에이전트 측)에 유지한다.

## 2.2 파서 출력 계약 3종

### 무엇인가 (구조)

파서가 반드시 지켜야 하는 약속은 세 가지다. 이 셋을 만족하는 JSON이면 파서 내부가 어떻게 생겼든 시스템은 받는다.

### 규약

**계약 ① — 메타데이터 양식(3층 구조) 준수**

출력 JSON은 아래 3층으로 구성된다.

| 층 | 필드 | 성격 |
|---|---|---|
| 문서 봉투 (doc 단위) | `doc_id`, `doc_type`, `payload_kind`, `source_path`, `revision`, `parsed_at`, `parser_version`, `adapter_version`, `classification?`, `context?` | 재인입의 단위(CH3.8). doc_id가 같으면 같은 문서의 개정으로 취급 |
| 조각 공통 (모든 record/chunk) | `source_locator`, `doc_type`, `process_group`, `process_ref`, `process_no?`, `electrode_type`, `context?` | 모든 정보 조각이 달고 들어오는 원본 위치·좌표·소속 정보 |
| payload (doc_type별) | table → `records[]` (행=record) / prose → `chunks[]` — 텍스트 청크(`text`, `section`, `meta`) 또는 이미지 placeholder(`image_ref`, `section?`) | 문서 성격별 본문 |

- `?` 표시는 선택 필드다. `process_no`는 없어도 되고, `context`는 봉투나 레코드 중 어디에도 없을 수 있다.
- **`payload_kind`는 `"table"` 또는 `"prose"` 두 값의 닫힌 집합이다.** payload가 `records[]`인지 `chunks[]`인지를 가르는 결정적 스위치이므로 봉투에 명시한다.
- **`adapter_version`은 봉투에 1회만 둔다.** 한 문서는 한 어댑터로 파싱되므로 조각마다 반복할 이유가 없다. 청크 저장 시 에이전트가 봉투 값을 복사해 각 청크에 붙이므로, "이 청크가 어느 분할 규칙으로 잘렸나"의 조회는 그대로 성립한다(카드 N6). 어댑터는 doc_type별로 따로 개정되므로 `parser_version`으로 대체할 수 없다.
- **`classification`은 자리만 있는 선택 필드다**(널 허용·자유 문자열 — 틀 §4B-A10, 카드 C16). 문서 등급의 좌석이며 **현 국면에서는 아무도 채우지 않는다** — 어댑터가 채우지 않아도 계약 위반이 아니고, 인입은 이 값을 읽지 않는다. 권한 로직·값 어휘·검증은 전부 R12로 이연. 등급은 문서의 성질이므로 위치는 봉투다(조각 단위 등급은 R12의 검토 대상).
- **각 필드의 값은 role 배정 가능한 형태여야 한다** — 스칼라이거나, 의미가 한 덩어리인 구조체(예: 규격 `{min, center, max, unit}`)이거나, 배열이다. 여러 의미가 한 문자열에 뭉쳐 있으면 계약 위반이다.
- **payload 고정 키 4종(`text`·`section`·`meta`·`image_ref`)은 payload 구조 필드다 [D-31 확정 — 20회차].** role 배정 대상이 아니고(카드 C17), 매칭 스키마 `fields`에 넣지 않는다(2.5 규약 3). 바로 위의 "role 배정 가능한 형태" 요구는 **role 배정 대상 필드**(table의 열)에 대한 것이다 — prose의 고정 키는 애초에 그 대상이 아니다. `section`은 청크의 소속 표기(헤딩 경로 등)이자 `chunk_id` 산식의 성분이며(틀 A4), 그 의미가 문서마다 달라 하나의 role로 고정할 수 없다는 관찰(실행검증 §4.3)은 결함이 아니라 이 지위의 증거다. `image_ref`는 이미지 placeholder 조각의 키로 이번에 계약 문면에 등재되었다(실물은 파서_명세 §5 규약 3과 실행 하네스가 이미 사용 중이었다 — 계약 누락의 사후 등재).
- `context`는 소속 맥락을 담는 임의 딕셔너리다. **축 이름은 열린 집합이다** — 실물에서 관찰되는 것만 쓰며(현재 관찰 후보: 모델·사이트·라인), 새 축이 필요하면 스키마 한 줄 추가(L1, 2.7). **봉투에 있으면 전 레코드의 기본값, 레코드에 있으면 그 레코드만 덮어쓴다**(상속). 값은 스칼라 또는 리스트(`{line:[1,2,3]}` = 공통 소속).

**계약 ①-부속 — id의 소유: 파서는 위치를, 에이전트는 정체성을**

근거 축(문서·청크·레코드)의 정본 id는 **내용에서 계산**한다(틀 §4B-A4, 카드 N1·N3). 계산 주체는 **에이전트**이며, 파서는 계산하지 않는다.

| 값 | 누가 | 무엇 |
|---|---|---|
| `doc_id` | **파서** | 문서 식별자. 해시가 아니다 — 재인입 단위이므로 **개정판이 같은 doc_id를 가져야 한다**(개정 구분은 `revision`이 담당). **파서가 같은 문서에 항상 같은 doc_id를 부여하는 것이 계약이다** — 이것이 지켜지지 않으면 재인입 자체가 성립하지 않는다 |
| `source_locator` | **파서** | 그 조각이 원본 문서 어디서 왔는지의 위치 표기(예: `"Sheet1!R12"`, `"슬라이드 5"`). role은 `meta` — 그래프에 들어가지 않고 출처 장부에만 남는다. 형식은 파서 자유이며, 요구는 **같은 문서 안에서 유일할 것** 하나뿐이다 |
| `chunk_id` / `record_id` | **에이전트** | 인입 시점에 A4 산식으로 계산하는 정본 id. 파서 출력에 이 필드는 없다 |
| `doc_hash` | **에이전트** | 문서 전체 내용 해시. 중복 문서 차단에 쓴다(2.8) |

계산 주체를 에이전트로 두는 근거 셋: ①멱등성의 근거를 사내 파서 구현에 위임하지 않는다 — 파서 버전마다 산식이 갈리면 "두 번 넣으면 그래프가 같다"가 깨진다 ②산식은 재인입·저장 규칙에 종속되므로 소유가 에이전트여야 한다(P1의 정신: 계약은 데이터, 산식은 로직) ③파서 계약이 산식 개정의 영향을 받지 않는다.

**계약 ② — 공정좌표 태깅 의무**

1. 모든 조각(record 또는 chunk)에 **공정좌표**를 태깅한다: `process_group`(대공정) 및 `process_ref`(선택된 골격 노드). **둘 다 role은 `anchor`다** — 둘 다 사람이 고정한 골격 노드를 가리키기 때문이다. `process_no`는 anchor가 아니라 `meta`다(아래 경계와 오해).
2. 태깅에 쓸 **닫힌 목록은 시스템이 공급한다** — **골격 전 노드(개념+극성 인스턴스)의 canonical과 alias 목록이다**(M2 — 틀 §4B-A11-6, 구 "세부공정 목록" 대체). 파서는 이 목록에서 고르거나, 해당 없으면 `null`을 넣는다. **목록에 없는 이름을 지어내지 않는다.** 목록의 물리 형태는 스냅샷 파일이다(2.1 규약 4 — U1/D-11). 문서가 상위·개념 해상도로만 말하면("탭용접") 개념 노드를 고른다 — 오류가 아니라 **저해상도 부착**이다(규칙 B의 철학).
3. **`process_group`은 별도 목록을 주지 않고 선택된 노드의 tier:main 조상에서 파생한다**(M2 — 틀 §4B-A11-7, 구 "골격 트리 부모" 규칙 대체 — 깊이 가변에서 트리 부모는 대공정이 아닐 수 있다). 대공정을 따로 고르게 하면 두 좌표가 어긋날 수 있기 때문이다. `process_ref`가 `null`이면 `process_group`도 `null`이다.
4. **한 레코드에 anchor는 둘이지만 부착의 기본 대상은 `process_ref` 하나로 고정한다.** 규칙 B의 폴백 대상(`@process_ref`)과 규칙 A의 좌표 조회는 process_ref를 쓴다. **`process_group`은 해소만 하고 부착에는 쓰지 않는다** — 용도는 `process_ref`의 골격 조상이 맞는지 대조하는 검증이며, 어긋나면 `coord_mismatch` 큐로 표면화한다(조용히 한쪽을 택하지 않는다). **record의 electrode_type과 부착 골격 노드의 polarity가 둘 다 확정인데 다를 때도 같은 큐다**(M2 — 틀 §4B-A11-9). 이것이 anchor의 동작이 "해소"이고 "부착"이 아닌 이유다(2.4 ①).
5. 좌표가 골격과 맞지 않으면(목록 밖 값 또는 오태깅) 시스템이 `orphan_anchor` 큐로 받는다(CH3.7). **따라서 파서 LLM에 요구되는 것은 "완벽"이 아니라 "일관"이다** — 같은 문서의 같은 대상에 항상 같은 좌표를 붙이면, 틀렸더라도 사람이 한 번에 고칠 수 있다.

이 계약이 중요한 이유: `process_ref`가 role `anchor`이기 때문에(2.4), 좌표가 붙어 있으면 **그래프 부착이 LLM의 추측이 아니라 사전 조회라는 결정적 연산**이 된다. 즉 파서의 좌표 태깅 품질이 그래프 정확도를 직접 좌우한다.

**계약 ③ — 레코드 자기완결성**

행(record) 하나가 **단독으로 읽어도 의미가 성립**해야 한다. 구체적으로 파서가 해소해야 하는 것은 넷이다.

| 대상 | 해소 방법 | 예 |
|---|---|---|
| 상동 기호(`〃`, 따옴표, 빈칸=위와 같음) | 실제 값으로 채워 넣기 | `공정: 〃` → `공정: 노칭` |
| 병합 셀 | 병합된 값을 각 행에 복제 | 3행 병합된 "노칭" → 3행 모두 "노칭" |
| 복수값 셀 | 개별 값으로 행 전개 — **전개 소유는 normalizer, 구분자는 기본 닫힌 목록 `[",", "/", 개행]` + 어댑터 `expects` 재정의 [U2/D-12 확정 — 21회차. 실물: 3차 어댑터 `multi_value_sep`·S11/S14 잠금]** | `설비: A, B` → 2개 행 |
| 중첩 구조 | 쌍으로 평탄화 | PFMEA 고장모드 1 : 원인 3 → (모드,원인) 3행 |

추가로 지켜야 할 것 둘:

- **표면형에 극성을 결합하지 않는다.** 극성(cathode/anode)은 `electrode_type` 필드로만 전달하고, 이름 문자열에는 붙이지 않는다. 이름과 극성의 결합은 에이전트가 **조건 3개를 확인한 뒤** 수행하며(조건은 CH3.5), 파서가 미리 붙이면 이중 접두("cathode cathode 노칭 프레스")가 발생한다.
- **원문을 무손실로 보존한다** (틀 §4B-A1-3, 카드 N4). `text`에는 원문을 그대로 넣고, 정돈본·요약본이 필요하면 **별도 필드로 두고 원문을 덮지 않는다.** 근거: 나중에 다른 임베딩 모델을 쓸 때 원문을 볼 수 없으면 되돌릴 방법이 없으며, 이것은 구축 시점에 결정되어 사후 복구가 불가능한 항목이다. **예외는 이미지 페이지 하나** — 텍스트 원문이 존재하지 않으므로 LLM 요약이 곧 `text`이며, 그 사실을 `meta.image_summary=true`로 표시한다.

### 경계와 오해

- **계약 위반은 조용히 통과하지 않는다.** 스키마에 없는 필드가 오면 `unknown_field` 큐(2.8), 필수 값이 없으면 `missing_field` 큐, entity 필드에 리스트가 오면(계약 ③ 미이행) 값을 문자열로 뭉개지 않고 드롭 + `missing_field` 큐. 즉 시스템은 계약 위반을 **오염이 아니라 신호**로 바꾼다.
- **전 청크 보존은 파서의 의무다.** 개체가 하나도 없는 일반 서술 청크도 버리지 않는다. 이것은 하이브리드 서치(CH5.4)의 전제조건이며 되돌릴 수 없는 결정이다 — 인덱싱할 원본이 없으면 나중에 켤 수 없다(카드 N5). 부하는 크지 않다: 저장하는 것은 원본 바이너리가 아니라 텍스트 조각(청크당 1~2KB)이고 원본은 `source_path` 참조만 남긴다.
- **이미지 페이지는 예외 처리가 아니다.** 파서가 LLM으로 요약해 `text`에 넣고 `meta.image_summary=true`를 붙이면, 다운스트림은 그것이 이미지였는지 모른 채 텍스트 청크와 동일하게 처리한다.
- **`process_no`(사내 공정번호)는 조회 키가 아니다.** 사내 번호 체계가 비표준·가변이라 키로 쓸 수 없다(변하는 값을 키로 쓰면 P4 실질 위반). anchor 조회 키는 이름(canonical+alias)이고, 번호는 role `meta`로 노드에 참고 값으로만 저장된다.
- **`source_locator`는 그래프 id가 아니다.** 파서가 붙이는 위치 표기일 뿐이며, 재인입 시 이 값이 달라져도 정본 id는 내용에서 계산되므로 그래프는 흔들리지 않는다. 반대로 `doc_id`가 달라지면 재인입이 아니라 새 문서가 되므로, 계약상 안정성이 요구되는 것은 `doc_id`뿐이다.

## 2.3 파서·등록의 LLM 활용 수준 [틀 v2.2로 확정]

### 확정된 것 (구조)

같은 "LLM 사용"이라도 **시점**에 따라 성격이 완전히 다르며, 두 시점의 허용 수준이 확정되었다. 원리는 **설계는 과감하게(1회+검수), 운영은 보수적으로(무검수+안전망)**다.

| 시점 | 빈도 | 사람 검수 | 확정된 허용 수준 |
|---|---|---|---|
| **설계·등록 시점** (구축 모드) | doc_type/층당 1회 | **있음 (생략 불가)** | **어댑터 코드 생성까지 허용.** 정형: 문서 표본을 관찰해 형식·내용을 파악하고 어댑터 코드 + 매칭 스키마를(층 신설이면 config 초안까지) 한 세션에서 연쇄 산출. 비정형: 문서 구조를 관찰해 **청크 분할 규칙을 코드로 생성** (틀 §3·§4-Q2, 카드 M3·M4·M5·M6) |
| **운영 시점** (운영 모드) | 매 문서 | 없음 | **이해 보조까지가 파서 몫** — ①이미지 요약 ②좌표 태깅(닫힌 목록에서 선택) ③**고정된 분할 규칙의 결정적 실행**. 이 목록은 닫힌 집합이다. 비정형의 "내용 파악"은 파서가 아니라 **추출 단계**의 일이다(아래) |

- **운영 중 LLM이 청크를 나누지 않는다.** 분할 판단("문단이나 끊어야 할 위치에서 끊는다")은 LLM이 하되 **문서 양식마다 1회, 등록 때** 하고 그 결과를 코드로 굳힌다. 매 문서마다 물으면 같은 양식인데 결과가 흔들린다(틀 §4-Q2). 구판에 있던 "청크 분할 보조"는 이 정정으로 운영 시점 목록에서 삭제되었다.
- **[확정 — 2026-08-18, 틀 v2.8 Q2 개정 · 카드 v16 I6-④/M6]** 위 규칙에 예외 1종이 확정되었다: **구조 가변 prose**(같은 doc_type 안에서 판본·작성자별 구조 상이 — RFQ류)는 분할 규칙을 등록 상수로 고정하지 않고 **운영 인입마다 구조 지도 패스**를 거친다 — 공용 코어 소유 LLM이 지도(데이터: 행/단락 → 헤딩 여부·레벨)를 산출하고, 분할은 결정적 코드가 하며, 지도는 보존된다(타당성 검사 실패 = 평면 폴백+기존 큐). **어댑터는 여전히 doc_type당 1개·등록 1회다** — 어댑터가 구조 파악 기능을 선언·힌트 제공하고 호출은 코어가 소유(C11 순수 함수·C12 이미지 요약과 동형). "운영 중 LLM이 청크를 직접 나누지 않는다"와 "내용 파악은 추출 단계"는 불변이다. 판정: `안건/D31_판정문안_section지위.md` 제2부 · 구현은 P1/P2, 파서_명세 동반 개정은 세션 1P.
- 검수가 이 확정의 전제다. "설계 시점은 과감해도 된다"의 근거가 "1회 + 사람 검수"이므로, 검수 없는 산출물이 flow에 들어가는 일은 없다(M4). **검수의 대상은 코드가 아니라 결과 뷰다** — 상세는 2.6.
- 셀 정돈·자유 서술 속 값 추출 같은 중간 수준은 하류 안전망이 받는 형태일 때만 개별 검토한다 — 기본 허용이 아니다.

### 추출 단계 — 파서의 "전면 추출 금지"가 재배치된 자리 [확정]

구판의 "비표준 양식 전면 추출 = 에이전트 경계 침범이라 불허"는 이렇게 정리된다: 비정형의 내용 파악은 **파서의 확장이 아니라 독립된 추출 단계**다(틀 §4-Q1 확정, 카드 M6·M7).

```
[파싱] → 계약 JSON(청크) → [추출] → 후보 JSON → [구축] → 그래프
          ↑ 파서 소관              ↑ 체크포인트        ↑ 에이전트 소관
```

**추출은 파서 안도 아니고 구축 파이프라인 안도 아닌 독립 단계이며, 산출물은 체크포인트 JSON이다.** 근거 셋: ①추출은 비싸고 구축은 싸다 — 재빌드 때 추출을 다시 돌리지 않으려면 산출물이 독립 체크포인트여야 한다 ②"파서는 형태만 다룬다"는 원칙이 지켜진다 ③플랫폼 관점에서 "파싱 완료 → 추출 중 → 구축 대기"가 각각 상태를 갖는 단계로 보인다. 추출 단계는 좌표 태깅된 청크를 입력받아 개체 후보 + 관계 후보(닫힌 목록 선택) + 부착 이름을 출력한다 — 상세는 CH3.1.

### 수준과 무관한 금지선 (불변)

1. **개체 동일성 판정** — "이 이름이 기존 노드와 같은 개념인가"는 구축 단계의 판정 파이프라인만 수행한다(CH3.3). 파서·추출 단계는 판정하지 않는다.
2. **관계의 커밋** — 관계 후보가 무엇이든, 그래프에 쓰이는 것은 커밋 게이트(패턴 대조)를 통과한 것뿐이다(CH3.4). 파서·추출 단계의 출력이 직접 엣지가 되는 일은 없다.
3. **카테고리의 운영 중 발명** — 운영 중 카테고리는 층 config의 닫힌 목록에서 선택만 한다(카드 I3). 층 등록 시점의 카테고리 초안 제안은 허용되며 확정은 사람이다.

이 셋이 금지선인 이유는 권한 분리다. **파서·추출은 "후보"를 만들고, 구축이 "사실"을 만든다.** 후보 생산이 아무리 과감해져도 사실 확정의 관문(판정·게이트·검수)이 코드와 사람에게 있는 한 그래프는 오염되지 않는다.

### 유지되는 비대칭 (파서 명세에 명시할 것)

에이전트 측 산출물은 데이터(매칭 스키마·config — 범용 실행기 core가 있으므로), 파서 측 산출물은 코드(어댑터 — 포맷별 실행이 필요하므로). 같은 "LLM이 만든다"라도 산출물 형태가 다른 것은 정당하다. 이 논증을 파서 명세에 명시해 "왜 한쪽만 코드 생성인가"를 반복 논의하지 않는다.

## 2.4 role 어휘 — 필드 role 5종 + edges 선언

### 무엇인가 (구조)

**role은 그 필드의 값으로 온톨로지 에이전트가 그래프에 수행하는 쓰기 동작이다.** 문서의 각 필드에 role을 배정하면, 에이전트는 필드의 **이름**이 아니라 **role**만 보고 동작한다.

한 문장 요약: *anchor로 기존 골격에 닻을 내리고, entity로 노드 후보를 데려오고, edges로 그들 사이에 선을 긋고, attribute로 노드에 값을 붙이고, content는 청크로 보존해 연결하고, meta는 출처 장부에만 적는다.*

### 왜 이 목록이 충분한가 (봉쇄의 근거)

role 목록은 "문서가 이렇게 생겼을 것이다"라는 **예상에서 만든 것이 아니라**, 그래프 데이터 모델이 허용하는 **쓰기 동작을 전수 열거**해서 도출했다.

```
그래프 = 노드 + 엣지 + 노드 필드 + 청크 연결 + 이력(provenance)
```

| # | 그래프 쓰기 동작 | 대응 |
|---|---|---|
| 1 | 기존 노드를 찾아 부착점으로 쓴다 | `anchor` |
| 2 | 노드를 만든다(제안한다) | `entity` |
| 3 | 노드의 필드에 값을 쓴다 | `attribute` |
| 4 | 두 대상 사이에 엣지를 만든다 | `edges` 선언 |
| 5 | 청크를 노드에 연결한다 | `content` |
| 6 | 그래프에 쓰지 않고 이력만 남긴다 | `meta` |

어떤 필드가 오든 그 값은 이 여섯 동작 중 하나를 하거나 하지 않을 뿐이며, **제7의 동작은 그래프 모델상 존재하지 않는다.** 따라서 커버리지가 경험이 아니라 구조로 보장된다. 이 보장이 깨지는 유일한 경우는 property graph 모델 자체가 담을 수 없는 정보가 등장할 때이며, 그것은 L4로 분리된다(2.7).

**"role 6종"이라고 부를 때의 6번째는 edges를 가리키지만, edges는 필드에 붙는 것이 아니라 스키마 레벨 선언이며 전용 핸들러가 없다.** 코드상으로는 필드 role 5개 핸들러 + edges 후처리로 구현된다. 이 챕터는 "필드 role 5종 + edges 선언"으로 표기를 통일한다.

### 규약 — role별 정의와 처리

**① `anchor` — 닻**
- 뜻: 이 필드의 값은 **이미 존재하는 골격 노드를 가리킨다.**
- **anchor의 동작은 "해소"이지 "부착"이 아니다.** anchor가 하는 일은 그 골격 노드를 찾아내는 것까지이고, 해소된 노드를 무엇에 쓰는지는 role이 아니라 **스키마가 정한다** — `edges` 선언의 `@좌표필드` 참조 / 규칙 B의 폴백 대상 / 다른 anchor의 검증 기준. 한 레코드에 anchor가 둘이어도 부착점은 하나이며, `process_group`은 해소만 하고 부착하지 않는다(2.2 계약②-4). **구판의 "이 행의 정보를 그곳에 붙들어 맨다"는 anchor가 `process_ref` 하나였을 때의 서술이며, 두 anchor 체제에서는 거짓이 되므로 이 문안으로 대체한다.**
- **대상 골격의 형태는 무관하다** — 트리(공정 트리)일 수도, 평평한 분류 목록(FailureEffect)일 수도 있다. 조건은 "사람이 보증한 Tier1 노드"인 것 하나다.
- 처리: 동의어 사전 조회 → 골격 노드로 해소. 사전 미스 시 후보검색+판정 → 그래도 미해소면 `orphan_anchor` 큐(사람).
- **anchor는 entity 생성으로 폴백하지 않는다.** 골격은 유형이고 유형은 사람이 고정하므로(P2) 자동 생성이 금지된다.
- **Tier1 한정**: 조회 결과가 auto 노드(발견형)뿐이면 anchor로 쓰지 않고 `orphan_anchor` 큐에 후보 id를 실어 사람 판단으로 넘긴다. 산문에서 스쳐 언급된 auto 노드가 골격 행세하는 P2 우회로를 차단하기 위함이다. anchor 대상은 사람이 보증한 것(seed provenance 또는 승격된 confirmed)뿐이다.
- **극성 모호 시**: 구 규칙(양 극성 골격 동시 지시 → orphan_anchor)은 **M2로 구조 소멸했다** — 극성 무관 표면형은 개념 노드에 해소된다(저해상도 부착, CH3B 3.5 규약 10). **쓰기는 좁게, 읽기(질의 링킹)는 넓게**가 원칙이다.
- 선택 속성: `target_category` — 조회 대상 카테고리 지정(예: `FailureEffect`). 생략 시 좌표 블록의 기본(공정 골격).
- 예: `process_ref: "노칭"` — "노칭 노드를 만들어라"가 아니라 "노칭 노드를 찾아라". 찾은 뒤 이 행의 정보를 거기 거는 것은 스키마의 `edges`(`{"to": "@process_ref"}`)와 규칙 B가 한다.

**② `entity` — 개체**
- 뜻: 이름을 갖고 다른 것과 구별되어 **노드가 될 자격이 있는 것**.
- 처리: 사전 조회 → 후보 검색 → LLM 동일성 판정 → 3분기(매칭: alias 누적 / 신규: 자동 생성 status=auto+provenance+큐 / 불확실: **신규 생성 + 큐**). 상세는 CH3.3.
- 필수 속성: `category` — 해당 층의 닫힌 카테고리 목록에서 지정.
- 선택 속성: `attach_to_field`(어느 필드의 개체에 붙는지), `target_layer`(**걸침 필드** — 이 필드는 다른 층 그래프에 기록. 예: PFMEA의 관리항목 → 공정층 Property). **`target_layer`를 생략하면 스키마 헤더의 `layer` 값이 쓰인다**(2.5) — 즉 걸침 필드만 명시하면 된다.
- **부착 폴백(규칙 B)**: attach 대상이 없거나 미해소면 행의 공정좌표(`@process_ref`)에 부착한다. 이것은 오류가 아니라 **저해상도 부착**이며, 후속 문서가 더 정밀한 소속을 주면 보강된다.
- **리스트 값은 계약 위반이다.** entity 필드에 리스트/구조 값이 오면(파서가 전개하지 않은 것, 계약 ③ 미이행) 값을 문자열로 뭉개 노드를 만들지 않고 **드롭 + `missing_field` 큐**. 핸들러는 단일 값만 본다는 전제를 코드가 방어한다.
- **맥락형의 대상이 아니다.** "모델 A에만 있는 설비"처럼 존재 자체가 맥락별로 다른 것은 context 태그로 표현하지 않는다 — 그것은 노드 분화 문제이며 실물 관찰 후 별도 판단한다.
- **canonical 스코프**: 층 config의 `canonical_scope.bind_categories`가 지정한 카테고리(공정층: Property)는 canonical이 `{세부공정 canonical}::{표면형}`으로 유일화된다. 어느 카테고리가 대상인지는 값(config)이며 코드는 모른다. 규칙과 근거는 **CH3.5** 소유 — 이 절은 존재만 지시한다.
- 예: `설비: "노칭 프레스"`.

**③ `attribute` — 속성값**
- 뜻: 어떤 것 자체가 아니라 어떤 것**에 붙어 있는** 성질/값. 노드를 만들지 않고 노드의 필드에 저장된다.
- 값 타입: 스칼라뿐 아니라 **구조체(JSON object)·배열**도 허용하며 **통째로 하나의 값으로 저장·비교**한다. 예: `spec: {min, center, max, unit, type, is_cc}`를 6개로 흩뿌리지 않고 한 필드에 통째 저장한다 — 사람이 스펙을 세트로 파악하는 단위와 일치하고, 개정 시 충돌이 실체대로 1건으로 집계되기 때문이다. 구조체 내부 필드는 정의서가 고정하지 않는다(문서마다 세트가 다르므로 스키마 파일 몫, L1).
- **provenance 필수**: 값 항목은 provenance를 보유한다 — 단순형은 `{value, provenance}`, 맥락형은 `{context, value, provenance}`. 노드·엣지·alias와 대칭이며, 재인입이 doc_id로 회수·교체하는 근거가 된다(CH3.8).
- 부착 대상: entity뿐 아니라 **anchor로 해소된 골격 노드에도 붙을 수 있다**(예: severity → effect_category).
- 선택 속성: `attach_to_field`(저장 대상 필드), `attr_name`(저장 키 이름, 생략 시 필드명), `contextual`(true면 맥락형).
- 판별 테스트: **"이것에 대해 더 말할 게 생기는가?"** — 노칭 프레스는 금형·마모주기 등 더 말할 게 있다(→entity). 규격 ±0.1mm는 더 말할 게 없다(→attribute).
- 충돌 규칙 상세는 CH3.6.
- 예: `규격: {min:-0.1, center:0, max:0.1, unit:"mm"}` → 관리항목 노드의 `spec` 필드.

**④ `content` — 서술**
- 뜻: 구조화되지 않은 자유 서술 텍스트. 필드 단위 규칙 처리가 불가능한 산문.
- 처리(prose): 청크로 보존 → LLM 언급 추출 → 해소된 노드에 `describes` 연결. 미해소 언급은 `orphan_chunk_link` 큐.
- 처리(table): 행 문맥이 이미 명확하므로 **LLM 추출 없이 `attach_to_field`로 describes 대상을 직접 지정**한다. 예: PFMEA의 `prevention_control`은 행의 `cause`에, `detection_control`은 행의 `failure_mode`에.
- **table의 청크 입도**: 한 record에 content 필드가 여럿이면 **필드별 별도 청크**를 만들고 id는 `{record_id}-{필드명}`으로 한다. 한 청크로 합치면 원인을 검색할 때 검출 관리 텍스트가 노이즈로 딸려온다.
- **링킹 0건 청크도 원문 그대로 보존한다**(전 청크 보존).
- 예: `대응계획: "공정 정지 후 금형 교체"`.

**⑤ `meta` — 관리 정보**
- 뜻: 내용물이 아니라 내용물의 신상정보. 지식(그래프)에는 들어가지 않으나 출처 추적을 위해 보관한다.
- 처리: 저장만. 그래프 무기록.
- 예: `source_locator`, `process_no`, 개정번호, 작성일.
- 주의: "가공 전 원료"라는 뜻이 아니라 **"내용 바깥의 관리 정보"**라는 뜻이다.

**⑥ `edges` 선언 (스키마 레벨)**
- 관계는 필드 하나의 성질이 아니라 필드 **사이**의 성질이므로, 필드 role이 아니라 스키마 레벨에 선언한다.
- 형식: `{from, relation, to, optional?}`. `from`/`to`는 필드명 또는 `@좌표필드` 참조(예: `@process_ref`).
- 처리 시점: 모든 필드가 해소된 **뒤**, 루프 후처리로 엣지를 생성한다. 전용 핸들러가 없다.
- **`optional: true`의 의미**: from/to 필드가 빈 행에서는 **해당 엣지만 조용히 생략**한다. 레코드 전체를 보류하는 것이 아니다.
- 예: `{"from": "설비", "relation": "has_property", "to": "관리항목"}`.

### 규약 — 리스트 값의 role별 처리 (전수)

한 필드에 값이 여럿일 때의 처리는 role마다 다르며, 아래가 전부다. **별도의 cardinality 규칙은 두지 않는다.**

| role | 처리 | 근거 |
|---|---|---|
| `entity` | **파서가 개별 값으로 전개**(계약 ③). 전개되지 않고 오면 드롭 + `missing_field` 큐 | 값이 아니라 여러 개체이므로 핸들러는 단일 값만 본다 |
| `attribute` | 배열로 **통째 저장** | 배열도 하나의 값이며 deep-equal로 비교된다 |
| `content` | 텍스트로 보존 — **무영향** | 청크는 원문 조각이므로 리스트 여부가 의미를 바꾸지 않는다 |
| `anchor` | 리스트를 허용하지 않는다 — **해소 대상은 하나다** | 둘 이상이면 어느 골격 노드를 가리키는지가 미정이 되므로 `orphan_anchor` |
| `meta` | 저장만 — 무영향 | 그래프에 쓰지 않는다 |

### 기능·계약

핸들러 공통 시그니처: `handle(value, spec, ctx) → resolved_id | value | None`
- `ctx` = `{graph들(layer별), dic, queue, record, schema}`
- 반환값: anchor·entity는 노드 id, attribute·content는 처리 결과, meta는 저장 후 값.

### 경계와 오해

- **같은 글자라도 role에 따라 동작이 완전히 다르다.** "노칭"이 anchor면 "이미 있는 노칭 노드를 가리켜라"이고, entity면 "노칭이라는 노드 후보를 데려와라"다. 필드명이 아니라 role이 동작을 정한다.
- **role은 필드의 의미 분류가 아니라 쓰기 동작의 분류다.** "이 필드가 중요한가"가 아니라 "이 필드의 값으로 그래프에 무엇을 하는가"로 판단한다.
- **role 어휘를 "미래까지 완벽하게 지금 완성"하는 것은 목표가 아니다.** 그것도 예측 게임이다. 목표는 부족했을 때 확장이 국소적이도록(핸들러 함수 1개, L3) 구조를 잡아두는 것이다(2.7).
- **table 문서에는 추출 LLM이 필요 없다.** role 선언이 추출을 대체하기 때문이며, LLM은 개체 판정에만 남는다. 이것이 "정형=규칙+매칭, 산문=판단+추출" 원칙의 자동 구현이다.

### 원천
명세 §6.1. 정의서 §1·§2·§3·§4(개념). **필드 spec 속성 일람(정의서 §5.5)은 2.5가 소유한다** — 여기는 role의 정의와 처리만 다룬다.

## 2.5 매칭 스키마 — 필드 인벤토리와 role 번역표를 겸하는 한 파일

### 무엇인가 (구조)

매칭 스키마는 **한 doc_type의 필드에 role을 배정하고 필드 사이의 엣지를 선언하는 파일**이다(`schemas/{doc_type}.json`). 등록 시점에 1회 작성하고(2.6) 런타임에는 doc_type 문자열로 조회만 한다.

**메타데이터 스키마 — "그 doc_type에서 무엇이 나와야 하는가"의 선언 — 를 별도 파일로 두지 않는다. 매칭 스키마의 `fields` 키 목록이 그것을 겸한다** (틀 §4-Q5 확정).

왜 겸용인가. 먼저, **어댑터 코드에만 둘 수는 없다** — 근거 셋:

1. **어댑터는 사내(파서)에 있고 매칭 스키마는 외부(에이전트)에 있다.** 둘은 코드로 만나지 않고 JSON으로만 만나므로, 필드 목록이 어댑터 코드 안에만 있으면 에이전트 쪽에서 그것을 알 수 없다.
2. **검증할 근거가 없어진다.** 파서 출력이 계약을 지켰는지 보려면 "무엇이 나와야 하는가"의 선언이 필요하다. 어댑터 코드는 "무엇을 만드는가"이지 "무엇이어야 하는가"가 아니다.
3. **어댑터는 자주 손보고(파싱 튜닝) 계약은 안정적이어야 한다.** 한 파일에 있으면 튜닝할 때마다 계약을 건드리게 된다.

그러면서도 **세 번째 파일을 만들지 않는 이유는 하나다: 같은 필드 목록이 두 파일에 살면 반드시 어긋난다.** 매칭 스키마에는 이미 `fields`가 있고 각 필드에 role이 붙어 있으므로, 그것이 곧 필드 선언이다.

```
어댑터 코드 (파서)        : 어떻게 뽑는가          — 자주 손봄
매칭 스키마 (공유 계약)    : 무엇이 나와야 하고     — 안정적
                            그것이 무슨 role인가
        └─ 둘은 "필드명"으로 만난다 (얇은 약속)
```

등록 세션에서 둘이 함께 생성되므로 초기 정합은 보장되고(2.6), 이후 어댑터를 고칠 때 매칭 스키마의 `fields`와 대조 검증한다.

### 규약

**1. 파일은 헤더 + `fields` + `edges` 세 부분이다.**

| 헤더 키 | 의미 |
|---|---|
| `doc_type` | 이 스키마가 적용되는 문서 양식의 종류. 런타임 조회 키 |
| `schema_version` | 이 스키마 파일의 개정 번호. 파서의 `adapter_version`과 짝을 이뤄 "어느 규칙으로 읽었나"를 추적한다 |
| `layer` | 이 스키마가 기본으로 기록하는 층. **`entity`의 `target_layer`가 생략되면 이 값이 쓰인다** — 걸침 필드만 `target_layer`를 명시한다 |
| `use_blocks` | 조립할 블록 목록 (아래 규약 3) |

**2. 필드 spec 속성 일람 — 스키마 작성에 쓸 수 있는 문법은 아래가 전부다.** 이 표 밖의 속성은 존재하지 않으며, 필요해지면 그것이 L1(속성 추가) 또는 L3(role 추가) 판정 신호다.

| 속성 | 적용 role | 의미 |
|---|---|---|
| `role` | 전체 (필수) | `anchor` / `entity` / `attribute` / `content` / `meta` |
| `category` | `entity` (필수) | 층의 닫힌 카테고리 목록에서 지정 |
| `target_category` | `anchor` | 조회 대상 골격 카테고리. 생략 시 공정 골격 |
| `attach_to_field` | `entity`·`attribute`·`content` | 부착 / 저장 / describes의 대상 필드 |
| `attr_name` | `attribute` | 저장 키 이름. 생략 시 필드명 |
| `target_layer` | `entity` | 걸침 필드 — 기록될 층. 생략 시 헤더의 `layer` |
| `contextual` | `attribute` | true면 맥락형 — 값을 `[{context, value, provenance}]`로 저장하고 충돌은 context 그룹 내에서 판정 |
| `optional` | 전체 | true면 빈 값 허용(검증 통과). **그 필드가 관여하는 edges도 조용히 생략된다** — 레코드 전체 보류가 아니다 |

`edges` 항목의 문법: `from` / `to`(필드명 또는 `@좌표필드`), `relation`, `optional`.

**3. `fields`에 나열하는 것은 payload 필드와 "role 배정이 필요한 조각 공통 필드"뿐이다.** 후자는 전 문서 공통임이 확정이므로 첫날부터 블록으로 조립한다.

| 블록 | 내용 |
|---|---|
| `common_core` | `source_locator: meta` |
| `process_coord` | `process_group: anchor`(대공정) · `process_ref: anchor`(골격 노드) · `process_no: meta`(optional) |

**나머지 계약 필드는 `fields`·블록의 대상이 아니다 — 구조 필드다**(판정 3조건은 카드 C17). 아래는 role 핸들러를 타지 않고 시스템이 직접 읽는다.

| 필드 | 왜 role이 없나 |
|---|---|
| **봉투 전체**(`doc_id`·`doc_type`·`payload_kind`·`source_path`·`revision`·`parsed_at`·`parser_version`·`adapter_version`·`classification`·`context`) | 문서 단위의 처리 정보다. 재인입 단위 결정·스키마 조회·payload 분기·진입 검증에 쓰이며 그래프 쓰기 동작이 아니다 |
| 조각 공통의 `doc_type` | 스키마 조회 키(봉투 값의 반복) |
| 조각 공통의 `context` | 맥락 상속 처리의 입력. 값은 attribute 저장 시 소비된다(CH3.6) |
| **조각 공통의 `electrode_type`** | **구조 필드 [M2 확정 — 구 R9 종결, 틀 §4B-A11-8]** — entity 해소 코드가 직독해 극성 결합을 판정하고 노드에 polarity 파생 필드를 기록한다(CH3B 3.5). role 핸들러를 타지 않으며, 스키마가 이 필드의 처리를 바꿀 수 없다 |
| **payload 고정 키 `text`·`section`·`meta`·`image_ref`** (prose) | **payload 구조 필드 [D-31 확정 — 20회차]** — 청크의 몸체·주소·부속이지 그래프 쓰기 동작이 아니다. 소비자는 시스템 코드다(청크 저장 · `chunk_id` 산식[틀 A4 — `section`이 성분] · 이미지 요약 경로). `section`의 의미가 문서마다·절마다 다르다는 관찰(실행검증 §4.3)은 결함이 아니라 이 지위의 증거다 — 비정형은 문서마다 목차가 다른 것이 정의다 |

**4. 블록 승격은 관찰 후에 한다.** 여러 doc_type에서 반복되는 필드 묶음은 블록으로 올리되, **2~3개 스키마에서 같은 묶음이 실제로 관찰될 때** 승격한다(스키마 레벨의 Rule of Three). 예: PFMEA와 CP 양쪽에 `측정방법·주기·샘플` 세트가 같은 형태로 나오면 그때 `measurement` 블록으로 올린다. 블록도 값이라 코드 리스크가 0이다 — 로더가 dict를 합칠 뿐이다.

**5. prose는 스키마 등록 부담이 사실상 없다 — `fields`는 빈 목록이다 [D-31 확정 정밀화 — 20회차].** payload가 고정형(`text`·`section`·`meta`·`image_ref`)인데 그 고정 키는 전부 구조 필드(규약 3)이므로, **prose 매칭 스키마의 `fields`는 `{}`이고 층 배정(`layer`)과 블록 선언(`use_blocks`)이 계약의 전부다.** 개체·관계는 등록 시점의 role 배정표가 아니라 **인입 시점의 추출(n3) 후보**가 낸다 — 층 배정을 코드가 추측하면 그 자체가 층 어휘다(B1). ⚠ 구판 문면("payload가 고정형이라 doc_type이 달라도 `fields`가 같다")은 "고정 키 목록이 fields에 들어간다"로도 읽혔고, 그 이중 독해가 킷 템플릿 v0.2의 prose 오배정(`section` UNMAPPABLE — 실행검증 §4.2·§4.3, 하네스 FAIL 2건의 전체 원인)의 명세 측 뿌리였다. **따라서 등록 비용은 "Excel 표준양식 종수 × 1회"다.**

### 기능·계약 — 파일 실례 (PFMEA)

```json
{
  "doc_type": "pfmea", "schema_version": 1, "layer": "quality",
  "use_blocks": ["common_core", "process_coord"],
  "fields": {
    "failure_mode":           {"role": "entity",    "category": "Failure"},
    "cause":                  {"role": "entity",    "category": "Failure"},
    "effect_category":        {"role": "anchor",    "target_category": "FailureEffect"},
    "severity":               {"role": "attribute", "attach_to_field": "effect_category", "optional": true},
    "effect_detail":          {"role": "content",   "attach_to_field": "effect_category", "optional": true},
    "control_item_for_fm":    {"role": "entity",    "category": "Property", "target_layer": "process", "optional": true},
    "control_item_for_cause": {"role": "entity",    "category": "Property", "target_layer": "process", "optional": true},
    "prevention_control":     {"role": "content",   "attach_to_field": "cause", "optional": true},
    "detection_control":      {"role": "content",   "attach_to_field": "failure_mode", "optional": true}
  },
  "edges": [
    {"from": "cause",        "relation": "causes",        "to": "failure_mode"},
    {"from": "failure_mode", "relation": "affects",       "to": "effect_category"},
    {"from": "failure_mode", "relation": "occurs_in",     "to": "@process_ref"},
    {"from": "failure_mode", "relation": "controlled_by", "to": "control_item_for_fm",    "optional": true},
    {"from": "cause",        "relation": "controlled_by", "to": "control_item_for_cause", "optional": true}
  ]
}
```

읽는 법 세 가지. ①`layer: "quality"`가 기본이므로 `control_item_*`만 `target_layer: "process"`로 걸침을 명시한다 — 한 번의 인입이 두 층에 기록된다. ②`effect_category`가 entity가 아니라 anchor인 것은 FailureEffect가 닫힌 Tier1 골격이라 auto 생성이 금지되기 때문이다. ③`severity`가 `failure_mode`가 아니라 `effect_category`에 붙는 것은 표준 FMEA에서 S가 영향 기준값이기 때문이며, 이로써 Failure 병합 노드의 우발 `spec_conflict`가 구조적으로 소멸한다.

Control Plan은 같은 문법으로 이렇게 배정된다: 공정번호/공정명 → `anchor` / 설비·지그 → `entity(Unit)` / 관리항목 → `entity(Property)` + edges `설비 has_property 관리항목` / 규격·공차 → `attribute(attr_name: spec)` → 관리항목 / 측정방법·주기·샘플 → `attribute` → 관리항목 / 대응계획 → `content`.

### 경계와 오해

- **파서 출력 양식(2.2)과 매칭 스키마는 두 개의 스키마가 아니다.** 같은 필드 목록을 파서 쪽에서 본 것(2.2 계약 ①)과 에이전트 쪽에서 본 것(이 절)이다. 3층 구조의 원천 서술은 **2.2에 일원화**되어 있으며 이 절은 그것을 반복하지 않는다.
- **매칭 스키마는 데이터이지 코드가 아니다.** 어댑터가 코드인 것과 대비되며, 그 비대칭의 근거는 2.3에 있다.
- **`fields`에 나오지 않는 필드가 레코드에 있으면 그것은 신호다.** 조용히 무시하지 않고 `unknown_field` 큐로 올린다(2.8) — 파서가 앞서갔다는 뜻이므로 스키마를 갱신한다. **단 구조 필드(규약 3의 표 — payload 고정 키 4종 포함)는 예외다** — fields 밖에 있는 것이 정상이다.
- **맥락 축을 미리 발명하지 않는다.** model·site·line 중 무엇이 실제로 쓰일지는 실물이 정한다. 축 추가는 스키마 한 줄(L1)이므로 미리 정해둘 이득이 없다.

### 종결된 미결

- **`electrode_type`의 role** — 구 R9. **M2(2026-08-10)에서 구조 필드로 확정 종결**(틀 §4B-A11-8, 카드 C10). 원천 3건 중 다수(정의서 §5.1 attribute·구현문서 §2.4 role:attribute)는 문법적 불가능(극성 결합 대상이 한 행에 둘, attach_to_field는 하나)으로 기각되었다. 극성 결합·polarity 파생 필드의 규칙은 CH3B 3.5가 소유한다.
- **`section`의 role (D-31)** — **20회차(2026-08-18)에서 payload 구조 필드로 확정 종결.** `section` 단독이 아니라 payload 고정 키 4종(`text`·`section`·`meta`·`image_ref`)을 한 번에 편입했다 — 소거법으로 유일해였고(role 5종 전부 기각, UNMAPPABLE은 계약 ①[section 필수]×D-30[출력 제외] 모순), 실물 3곳(`ppt_process.json`·`ppt_quality.json`의 `fields:{}` · 하네스의 4종 면제)이 이미 이 규칙으로 동작 중이었다. 판정 전문: `안건/D31_판정문안_section지위.md`.

### 원천
명세 §6.5(겸용 확정). 정의서 §4·§5.1~§5.5. 구현문서 §2.4(blocks·스키마 전문 — M2 개정 대기). 틀 §4-Q5·**§4B-A11-8(electrode_type)**. 카드 **C17(D-31 — payload 구조 필드)**. 핸드오프 ①②. **3층 구조의 원천 서술은 2.2가 소유한다.**

## 2.6 구축 모드 — 등록 워크플로우와 산출물

### 무엇인가 (구조)

**구축 모드는 "처리 방식이 없는 입력을 처리 가능하게 만드는" 모드다**(카드 M1). 발동 조건은 결정적이다 — 문서가 오면 doc_type 등록 여부를 조회하고, 미등록이면 구축 모드로 넘어간다(M2). 시점별 3단계 구도:

| 시점 | 누가 | 무엇을 |
|---|---|---|
| **지금 (외부)** | 사람 | 문법 확정 — role 어휘와 스키마 파일 형식. **완료됨** |
| **등록 시점 (사내, doc_type/층당 1회)** = 구축 모드 | LLM 초안 + **사람 검수 확정** | 실물 문서를 보고 산출물 생성 (아래). **지능이 필요한 유일한 순간** |
| **런타임 (매 문서)** = 운영 모드 | 코드 | doc_type 문자열로 스키마 조회(dict 1회) → 기계 적용 |

**구축 모드의 산출물**

카드 M3이 열거하는 논리 산출물은 3종(어댑터 코드 · 메타데이터 스키마 · 매칭 스키마)이지만, **Q5 확정(2.5)에 따라 물리 파일은 2종이다** — 메타데이터 스키마는 매칭 스키마가 겸한다. 층 신설이면 config가 더해져 3종.

| 물리 산출물 | 소유 측 | 형태 | 내용 |
|---|---|---|---|
| **어댑터 코드** | 파서(사내) | 코드 | 포맷→필드 파싱. 정형: 어느 행/열을 어떻게 읽는가. 비정형: **청크 분할 규칙** + 이미지 요약 훅 |
| **매칭 스키마** | 에이전트 | `schemas/{doc_type}.json` | 필드 인벤토리 + role 배정 + edges 선언 (2.5). **prose는 `fields: {}`** — 층·블록 선언이 전부(2.5 규약 5) |
| **config** (층 신설 시만) | 에이전트 | `layers/{층}/config.json` | 카테고리·정의문·**관계 목록**·골격 — LLM 초안, 사람 확정 (CH4.7) |

### 규약

1. **한 등록 세션이 연쇄 산출한다.** LLM이 문서 표본을 관찰해 형식·내용을 파악하고 → 어댑터 코드를 만들고 → 그 구조가 role과 어떻게 연결되는지 아므로 매칭 스키마까지 함께 낸다. 구판의 "방법 A(실물 표본 직접) / 방법 B(어댑터 과정 차용)" 선택지는 이 통합 경로로 수렴되었다.
2. **표본 크기는 문서 성격이 정한다.**
   - **정형**: head 약 10줄 — 헤더와 몇 행이면 형식·내용이 드러난다(카드 M5).
   - **비정형**: head 10~30줄을 기본으로 하되, **목차형처럼 같은 패턴이 반복되는 문서는 계층 패턴이 2~3회 반복해 나타날 때까지 확장**한다. 반복이 두어 번 보이면 구조가 드러난다(틀 §4-Q2).
3. **판정이 안 서면 LLM이 추측하지 않는다.** 한 문서 안에서 신호가 섞이는 경우(같은 계층 높이인데 앞 형태가 다른 등) 규칙을 지어내지 않고 **"판정 불가"로 검수 화면에 올린다.** 사람이 그 자리에서 기준을 정해준다.
4. **산출물 형태의 비대칭은 정당하다.** 매칭 스키마·config는 데이터(범용 실행기 core가 있으므로), 어댑터는 코드(포맷별 실행이 필요하므로). (2.3)
5. **role이 메타데이터 확정의 상류 제약이다.** 필드는 role(닫힌 5종)에 매핑 가능한 것만 확정하며, 매핑 불가 필드는 스키마에 넣지 않고 **UNMAPPABLE로 사람이 판정**한다(L3/L4 판정, 2.7). 근거: role 밖 필드는 매칭 불가 → 그래프 진입 불가 → 파싱해도 무효다. **즉 최종 규격은 role이며, 파서 출력 사양도 이 규격에 맞춰 정렬된다.** **이 규약의 적용 대상은 role 배정 대상 필드(table의 열)다 [D-31 정밀화]** — prose payload 고정 키 4종은 구조 필드(2.5 규약 3)라 애초에 6지선다 대상이 아니며, UNMAPPABLE로 올리는 것 자체가 잘못 세워진 물음이다(실행검증 §4.3의 물음 재설정 — 20회차).
6. **검수는 생략 불가이며, 검수 대상은 코드가 아니라 결과 뷰다** (틀 §2, 카드 M4·M9).
   - 사람이 보는 것: ①표본 문서를 어댑터로 파싱한 결과 — **계층이 있으면 트리로 렌더**해서 보여준다(틀린 계층은 트리로 보면 즉시 보인다) ②필드→role 배정표(필드당 6지선다: anchor / entity / attribute / content / meta / UNMAPPABLE) ③(층 신설이면) 카테고리 정의문·관계 목록.
   - **구조 필드는 6지선다에 올리지 않는다**(M2 — 카드 C17): `process_group`·`process_ref`·`process_no`·`electrode_type`·`context`·`source_locator`, 그리고 **payload 고정 키 `text`·`section`·`meta`·`image_ref`(prose — D-31)**는 role 배정 대상이 아니다. UNMAPPABLE(미해결 — L3/L4 판정 대기)과 달리 구조 필드는 **정상·완결 범주**다. 이 구분이 프롬프트에 없으면 판정이 흔들린다는 것이 실측되었다(판정대조 1차의 극성·적용모델 2건 — 템플릿 v0.3 지시, D-46[구 M2 내부 채번 D-40 — 16회차 재번호]).
   - **통과 = 승인 1회.** 클릭 수준·분 단위 작업이다. 문제가 없으면 그대로 승인하고 끝, 문제가 있으면 그 자리에서 수정 지시(재생성) 후 재확인한다.
   - **"무수정 = 자동 통과"로 하지 않는다.** 등록 산출물은 이후 그 타입의 **모든** 문서에 곱해지는 지렛대이므로, 명시적 승인 기록 1건이 "운영은 무개입"의 근거가 된다. 무게는 클릭 수준으로, 기록은 명시적으로.
7. **등록은 런타임의 자동 기능이 아니다 — 운영 flow 밖에서 사람이 여는 별도 워크플로우(구축 모드)다 [U5 문면 정정 — 21회차. 구판 "오프라인 작업"은 시스템 밖 수작업으로 오독됨].** 시스템 밖이라는 뜻이 아니다 — 등록 파이프라인(n6)·검수 뷰·승인 기록은 시스템 기능이다. 운영 중 미등록 문서가 오면 구축 모드로 사람에게 넘어가지, 시스템이 즉석에서 스키마를 만들어 흘리지 않는다(무음 폴백은 계약 위반 — 울트라 점검 B3·G6.5 수리).

### 로직 — 등록 절차 (정형 기준)

1. role 어휘 정의서 + mock 스키마 + 실물 문서 표본(규약 2)을 사내 LLM에 제시한다.
2. LLM이 형식·내용을 파악해 어댑터 코드 + 매칭 스키마 초안(필드 목록·role 배정·edges)을 작성한다.
3. 시스템이 **결과 뷰를 자동 생성**한다 — 표본 파싱 결과와 role 배정표.
4. 사람이 그 뷰를 보고 승인하거나 수정 지시한다(규약 6).
5. 파일로 저장한다. **core 코드 배포·수정 없음.**
6. LLM이 "어느 role에도 안 맞는다"고 답하면 그것 자체가 검증 신호다 — L3(새 role 필요) 또는 L4(그래프 모델 밖) 판정으로 넘긴다.

비정형은 어댑터가 얇다 — **청크 분할 규칙 + 이미지 요약 훅**뿐이고, 매칭 스키마는 **`fields: {}` + 층·블록 선언**으로 사실상 정해져 있다(2.5 규약 5). 분할 규칙의 생성·검수 방식은 규약 2·3·6이 그대로 적용된다.

> **플랫폼 훅**: 구축 모드는 **생성 → 검수 → 확정**의 3단계가 코드 레벨에서 분리되어 있어야 화면이 붙는다(카드 P-2). 등록도 다른 단계와 마찬가지로 CLI 진입점 + 파일 입출력으로 노출한다(명세 §16.1 플랫폼화 인지 계약 1). 이 워크플로우가 플랫폼 "문서 타입 등록" 기능의 원형이다.

### 사내에서 할 일 (지정)

- **[검증] 실물 2~3종(PFMEA, Control Plan 우선)의 전 열에 role 배정 실험.** 이것이 **사내 첫 작업이며 코딩이 아니다.** 배정 가능성 자체는 2.4의 봉쇄 논증으로 보장되므로, 검증 대상은 **배정의 정확성**(이 열이 entity인가 content인가 같은 판단)이다. 막히는 필드는 L3/L4 판정. 이제 어댑터 생성 실험(표본 관찰)과 결합해 한 세션으로 돌릴 수 있다.
- [확정] doc_type별 스키마 내용, 블록 목록.

### 경계와 오해

- **"연결"이 어려운 작업처럼 보이지만 런타임에는 조회 1회다.** 별도의 연결 에이전트를 두지 않는 이유가 이것이다 — 런타임 연결이 dict 조회 1회이므로 에이전트는 과하다. 어려움은 등록 시점에 몰려 있고, 그것도 doc_type당 1회다.
- **정합성 감시는 양방향이다.** 레코드에 스키마에 없는 필드가 등장 → `unknown_field` 리뷰(파서가 앞서갔다는 신호 → 스키마 갱신). 스키마에 있는데 레코드에 없음 → optional 검사. 어긋남이 조용한 오염 대신 큐에 시끄럽게 나타난다.
- **검수는 구축 모드에만 있다.** 운영 모드에는 검수가 없다 — 등록이 끝난 타입의 문서는 사람 없이 흐른다. 검수는 flow의 관문이 아니라 등록 때 1회 내는 통행료다.

## 2.7 변경 등급 L1~L4

### 무엇인가 (구조)

무엇이 바뀌면 무엇을 고쳐야 하는지를 4등급으로 나눈 표. **이 표가 "범용성"이라는 말의 조작적 정의다.**

| 등급 | 사건 | 고치는 것 | 코드 변경 |
|---|---|---|---|
| **L1** | 필드명 변경, 필드 추가/삭제 | 스키마 파일 한 줄 | **0** |
| **L2** | 새 doc_type (기존 role로 표현 가능) | 스키마 파일 1개 추가 | **0** |
| **L3** | 기존 role로 표현 불가한 필드 성격 | role 1종 + 핸들러 함수 1개 추가 | 함수 1개 (기존 핸들러 무수정) |
| **L4** | 그래프 모델 자체가 못 담는 정보 | 설계 재검토 | 구조 변경 |

### 규약

1. **범용성의 정의: L1~L2가 사건의 대부분이 되게 하고, L3의 비용을 함수 1개로 봉쇄하는 것.**
2. **L4는 어떤 설계로도 예방 불가한 영역임을 정직하게 기록한다.** 예방하는 척하지 않는다.
3. **L3에서 기존 핸들러는 수정하지 않는다.** 새 role은 함수 1개 작성 + 등록 1줄이며, 기존 5개 핸들러는 건드리지 않는다. 이것이 "봉쇄"의 코드 형태다. 예: 문서에 "이 값은 다른 노드를 가리키는 참조다"라는 성격의 필드가 나와 기존 5종으로 안 되면, `reference` role과 핸들러 1개를 더하고 나머지는 그대로 둔다.

### 경계와 오해

- **이 표는 스키마 축만 다룬다.** 노드 병합·분리·개명·폐기 같은 인스턴스 축의 변경은 **직교 축(I축)**으로 별도 확정되어 있다 — I1 개명 / I2 병합 / I3 분리 / I4 폐기(틀 §4B-A2, 카드 L5~L9). **소유 절은 CH3B 3.7**이며, 이 표에 없는 것은 공백이 아니라 축이 다르기 때문이다.
- **L1이 "쉽다"는 뜻이지 "안전하다"는 뜻은 아니다.** 예를 들어 `canonical_scope`의 대상을 세부공정에서 설비로 바꾸는 것은 스키마 한 줄이지만, 걸침 필드의 병합 규칙을 선행 마감하지 않으면 CP와 PFMEA의 키가 갈라진다. **"L1 한 줄이 지뢰"가 될 수 있는 지점은 해당 절에 경고로 명시한다**(CH3.5).

명세 §6.3. 정의서 §7. 틀 §4B-A2(I축 — 참조).

## 2.8 핸들러 루프와 인입 검증

### 무엇인가 (구조)

role이 정해지면 처리는 단순한 루프가 된다. **코드에는 필드명이 등장하지 않고, role만이 분기 스위치다.**

```python
HANDLERS = {"anchor": .., "entity": .., "attribute": .., "content": .., "meta": ..}

def ingest_record(record, schema, graph, dic):
    resolved = {}
    for field, spec in schema["fields"].items():
        resolved[field] = HANDLERS[spec["role"]](record.get(field), spec, graph, dic)
    for e in schema.get("edges", []):
        graph.add_edge(resolved[e["from"]], e["relation"], resolved[e["to"]])
```

**위는 개념 예시이며 핵심 골격만 보인 것이다.** 실제 구현은 아래 규약이 더해진다.

### 규약

1. **모든 role 핸들러는 3단 구조를 따른다: 규칙 → LLM 폴백(훅) → 수정 큐.**
   - anchor·entity는 본래 이 구조다(사전조회 → 판정 → orphan).
   - attribute·content·edges에는 **폴백 훅의 자리만 확정하고 실제 채움은 사내 갭 관찰 후로 미룬다**(P7). 관찰 대상 갭 넷: 빈 셀 부착(부착 대상 부재) · 상동/병합 셀 · 복수값 셀 · entity 칸에 섞인 산문. 단 상동·병합·복수값의 1차 방어선은 파서의 자기완결 계약(2.2 계약 ③)이다.
2. **실제 ingest는 2-pass로 구현한다** — Pass1에서 전 레코드의 anchor·entity를 해소해 버퍼에 담고, Pass2에서 attribute·content·edges를 적용한다. 상세는 CH3.2.
3. **edges는 HANDLERS에 없다.** 필드 해소가 끝난 뒤 루프 후처리로 처리한다(위 예시의 두 번째 for).

### 로직 — 인입 검증 3단

**검증 순서의 전체 배열 [U3/D-2 확정 — 21회차, struct-map 편입]**:

```
투입 분류(사람 + 지문 스캔 — C15) → [파서] preflight → (struct-map — 구조 가변 prose 한정, D-58)
→ extract → normalizer → tagger → validator → [에이전트] ①doc_hash → ②id 계산 → ③필드 검증
```

파서 측 = **문서 단위 실패**(parse_failure·adapter_mismatch — 상세 정본은 파서_명세 §3), 에이전트 측 = **큐 착지** — 역할이 겹치지 않는다. 아래 3단은 에이전트 구간이다.

문서가 들어오면 아래 순서로 검사하며, **어느 단계의 실패도 조용히 통과하지 않는다.**

**① 진입 검증 — 중복 문서 차단** (틀 §4B-A6, 카드 N8)
- 문서 전체 내용의 해시(`doc_hash`)를 계산해 기존 문서와 대조한다.
- **같은 `doc_hash`가 다른 `doc_id`로 이미 존재하면 인입을 보류하고 사람에게 확인을 요청한다** — 두 문서의 파일명·크기·인입 시점·기존 doc_id를 함께 제시한다. 사람이 "다른 문서다"라고 판정하면 진행하고, "중복이다"라고 판정하면 취소한다.
- **파일명·파일 크기를 판정 기준으로 쓰지 않는다** — 파일명은 바뀔 수 있고 크기가 같아도 내용이 다를 수 있다. 이 둘은 사람이 판단할 때 참고하도록 화면에 표시만 한다. 판정은 내용 해시로 한다.
- **같은 `doc_id`로 다시 들어오는 것은 중복이 아니라 재인입이다**(정상 경로, CH3.8). 이 검사가 잡는 것은 "같은 내용이 다른 이름으로 올라오는 것"(파일 복사·개명)뿐이다.
- `doc_hash`는 아래 ②의 청크 해시를 계산하는 과정에서 함께 얻으므로 추가 비용이 없다.

**② 근거 축 id 계산** (틀 §4B-A4, 카드 N3)
- 각 조각의 내용에서 `chunk_id` / `record_id`를 계산한다. 파서가 준 `source_locator`는 계산 입력이 아니라 출처 장부에만 기록된다 — 위치를 해시 입력에 넣으면 앞에 한 문단만 추가되어도 뒤의 모든 id가 바뀌기 때문이다.
- 산식과 그 근거(occ·구분자·절단 길이)는 **CH6.1** 소유. 이 절은 계산 지점이 여기라는 것만 정한다.
- 계산된 id가 이미 존재하면(occ 계산 오류 등) **조용히 덮어쓰지 않고 결함으로 로그**한다.

**③ 필드 검증**
- 스키마에 없는 필드가 레코드에 등장 → `unknown_field` 리뷰(파서가 앞서갔다는 신호 → 스키마 갱신). 구조 필드는 예외(2.5 규약 3 — payload 고정 키 4종 포함).
- 스키마에 있는데 레코드에 없음 → `optional` 검사. 선언되지 않았으면 `missing_field` 큐. **`optional: true`면 통과시키고, 그 필드가 관여하는 edges도 조용히 생략한다** — 레코드 전체를 보류하지 않는다.

### 경계와 오해

- **이 루프가 단순한 것은 층별 처리를 어딘가로 밀어냈기 때문이 아니라, 개수·이름·경우를 분기하는 코드가 없기 때문이다.** core는 스키마를 순회할 뿐이다. 이것이 "모든 문서를 수용하는 똑똑한 실행기"가 아니라 "가정을 안 하는 단순한 순회기"인 이유이며, 만능 엔진(과설계)과 정반대인 지점이다.
- **핸들러가 예외를 삼키지 않는다.** 처리 못 한 값은 조용히 버려지지 않고 반드시 큐로 간다. 큐 종류별 건수가 파이프라인 건강 지표가 되므로, 조용한 실패는 커버리지를 과대평가하게 만들어 신뢰 문제를 일으킨다. 알 수 없는 role 값은 크래시 대신 `invalid_role` 결함 로그로 방어한다(D-30).
- **진입 검증(①)은 파서가 하지 않는다.** `doc_hash`는 에이전트가 계산한다(2.2 계약 ①-부속) — 파서 계약을 굵게 만들지 않기 위해서이고, 같은 이유로 파서는 다른 문서의 존재를 알 필요가 없다.

> **플랫폼 훅**: 큐는 처리 대상 목록이자 화면이다 — kind별 조회·처리·재시도가 API 형태로 노출 가능해야 한다(카드 P-3). 진입 보류(①)는 "사람 확인 대기" 상태를 갖는 첫 화면 지점이다.
