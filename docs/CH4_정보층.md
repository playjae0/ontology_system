## 4.1 층의 정의 — 여섯 칸 [확정]

### 무엇인가 (구조)

한 정보층은 여섯 칸을 채우면 정의된 것이다.

| 칸 | 내용 | 실물 위치 |
|---|---|---|
| ① 메타데이터 스키마 | 이 층에 들어오는 문서의 doc_type별 필드→role 번역표 | schemas/*.json |
| ② 골격 | 사람이 심는 고정 뼈대 (Tier1) | layers/{층}/skeleton.json (seed v3.2 — M2) + config 선언 |
| ③ 관계 목록 | 이 층이 쓰는 관계 이름들 + 각 관계의 대칭 여부 | config.relations |
| ④ 카테고리 정의문·프롬프트 | 추출·판정 LLM에게 주입할 닫힌 카테고리와 정의문 | config.categories, config.prompts |
| ⑤ 쓰기 절차 | 무엇을 먼저 뽑아 무엇에 어떤 순서로 잇는가 | config(polarity·canonical_scope·category_pair_map 등) + core 공통 절차 |
| ⑥ 읽기 절차 | 질의 때 어느 관계로 얼마나 뻗는가 | config.query_traverse, fact_templates |

### 규약

1. **⑤와 ⑥은 방향이 반대이므로 반드시 분리한다.** 쓰기의 순서(무엇을 먼저 해소하나)와 읽기의 확장(어디까지 뻗나)은 다른 결정이다. 예: `precedes`는 쓰기에서 seed로 심기지만 읽기 확장에서는 제외된다(CH5.1).
2. **새 층의 첫 작업은 언제나 카테고리 목록과 정의문이다.** 운영 중 LLM이 카테고리를 발명하는 일은 어느 층에도 없다(카드 I3). 구축 모드에서 LLM이 정의문 초안을 낼 수 있으나 확정은 사람이다(틀 D5). 카테고리 후보의 자격 심사는 **그래프 입주 3테스트**(4.7 게이트 — 틀 A9-5)가 맡는다.
3. **정의문의 규격**: "무엇인가"만이 아니라 **"무엇과 헷갈리는가"**를 담는다. 예: Property 정의문은 "규격값·측정값·판정결과는 제외(그것은 attribute)"를 포함한다 — 추출·판정 LLM의 오분류가 정의문의 경계 서술에서 걸러진다.
4. 관계 목록에는 **대칭 여부를 표시한다**(카드 I8) — 동종 쌍 방향 규칙의 적용 대상을 가르기 위함이다.
5. **[M3 편입 — A9] 층이 담는 정보의 계층은 T0~T2다.** T0 골격(파일·사람 보증) / T1 의미(그래프 본체 — **문서 수 비례**) / T2 근거(청크 저장소). **T3(생산 발생 데이터 — 시간 비례·무한)은 어느 층에도 적재하지 않는다** — 참조 핸들(SeriesRef, R11)만 둔다. 경계 판정은 A9-4가 정본: 로트·셀·Event Frame·개별 측정 레코드는 전부 T3, 문서로 들어온 사건은 T1, T3→T1 승격 절차는 없다(필요하면 그것은 승격이 아니라 신규 층 도입 — 4.7).

### 경계와 오해

- **여섯 칸은 문서 양식이 아니라 체크리스트다.** 칸의 실물은 config·스키마 파일이며, 별도의 "층 정의서" 문서를 만들지 않는다.
- **칸이 얇은 층도 있다.** 품질지식층의 mirrors는 비활성이고 skeleton은 평평한 목록이다 — 칸을 채우는 것이지 채워 넣을 내용을 발명하는 것이 아니다.

## 4.2 범용성 전략 — A/B/C와 Rule of Three [확정]

### 규약

1. **A = 전 층 공유 코드(core).** id 발급·사전·판정·저장·탐색·핸들러 루프·범용 쓰기/읽기/골격 심기. **층 어휘가 한 글자도 등장하지 않는다**(구현문서 §0-1).
2. **B = 층별 값(config).** 카테고리·정의문·관계·프롬프트·매핑·템플릿·확장 규칙·골격 데이터·mirrors 여부. 층마다 다른 것은 전부 여기로 내린다.
3. **C = 층별 절차(코드). 원칙적으로 비어 있어야 한다.** config로 표현 안 되는 절차를 만나면 층별 예외 코드가 아니라 **명시적 실패**로 드러내고 core에 패턴을 추가한다(4.3).
4. **Rule of Three**: 일반화는 관찰된 만큼만 한다. 공정층+품질층 2개 표본에서 실측된 공통만 core로 올렸고, 3층에서 안 맞는 지점이 다음 승격 재료다. **미래 층의 코드를 미리 쓰지 않는다**(§3.4) — 불량이력층용 처리를 지금 넣는 것은 예측 게임이다.

### 경계와 오해

- **범용성의 정의는 "모든 미래를 지금 커버"가 아니다.** L1~L2(스키마 수정)가 사건의 대부분이 되게 하고 L3(새 role) 비용을 함수 1개로 봉쇄하는 것이다(CH2.7). 같은 논리로, 층 추가가 config 파일 추가로 끝나게 하는 것이 층 축의 범용성이다.

### 원천
명세 §3.1~3.4. 카드 B1·B2·B5.

## 4.3 config-only 구조와 명시적 실패 [확정]

### 규약

1. **층 폴더에는 코드가 0이다.** layers/{층}/config.json(+skeleton.json) + schemas/*.json 뿐이다. 라우터가 층 폴더를 자동 발견하므로 등록 배선도 없다.
2. **core는 "가정 없는 순회기"다.** 관계·카테고리·골격 축의 **개수·이름·유무를 가정하지 않고** config에 있는 만큼만 처리한다. 만능 엔진(모든 경우를 아는 코드)과 정반대다.
3. **명시적 실패**: config로 표현되지 않는 절차(예: skeleton.type이 tree/flat 밖)를 만나면 core가 시끄럽게 raise한다 — "config 표현 밖, core 패턴 추가 필요". 층별 오버라이드 코드로 조용히 우회하지 않는다(관리 지점 일원화).
4. **층 추가의 성공 판정은 기계적이다**: 새 층을 붙인 뒤 `git diff core/`가 비어 있으면 성공(J3). **품질층 추가가 이 판정의 첫 실측이었고 성립했다** — G4 정산(08-18)에서 core/ 품질 어휘 0을 grep으로 재확인, 실질 성립 인정. 이때의 교훈(등록 커밋에 다른 작업이 섞여 문자적 판정이 불가능했던 것)은 4.7의 게이트 문면이 됐다.

### 원천
명세 §3.5~3.6. 구현문서 §0·§5. 카드 B1~B3, J3. G4 정산 기록(미러).

## 4.4 공정정보층 [확정 — 골격 실명칭은 사내 확정]

### 무엇인가 (구조)

공정 구조 지식의 층. 기능 중심이고 안정적이며, 전 층이 공유하는 좌표축(공정 골격)을 소유한다.

### 규약

1. **카테고리 3종 (닫힌 목록 · 정의문 원문)**
   - **Process**: 제품을 만들기 위해 수행하는 작업 단계. 기능으로 정의되며 설비 기종이 바뀌어도 존재한다(예: 노칭, 스태킹). 설비 이름이 아니라 "하는 일"의 이름.
   - **Unit**: 공정을 수행하는 물리 장비의 기종/표준 명칭(예: 노칭 프레스). 지그·금형 등 도구류 포함. **호기·특정 공장 개체는 제외.**
   - **Property**: 공정/설비에서 관리·측정·통제되는 항목의 이름(예: 노칭 정밀도). 관리항목/특성/CTQ 포함. **규격값·측정값·판정결과는 제외**(그것은 attribute).
2. **골격 = 공정 기능 트리** (`type: tree` · **seed v3.2 — M2 확정, A11이 정본**): 두 축을 가른다 — **part_of는 구조**(공장·제품·세대 무관으로 참인 분해 계층 = 주소 체계), **precedes는 지식**(대표 흐름 — 회사 표준 기준 한 벌, seed 자식 배열 순서로만 선언·옵트아웃 마커 존재). 극성은 3패턴(무관/주소만/@split 스텝 분화 + 단극성)으로 표현하고, tier(main/sub/detail)·polarity·parent는 loader가 파생한다 — 사람이 적는 것은 트리와 마커뿐. 코드가 아는 마커는 구문 4종(`::` 접두·@split·@unordered·@noflow)이고 축의 값은 seed AXIS_LABELS 키에서 데이터로 읽는다(D-49·D-53, B1). PoC seed는 46노드 체계(실명칭·전체 범위는 사내에서 확정 교체), 닫힌 목록 스냅샷은 `data/skeleton_closed_list.json`(D-11 — 파생물 P5).
3. **관계 4종**: `part_of`(자식→부모) · `precedes`(순서 — **seed에서만 생성**되고 문서에서 만들어지지 않으며, 질의 확장에서 제외되고 flow 특례가 통째로 공급) · `has_property`(설비·공정→관리인자) · `mirrors`(극성 대칭 — **대칭 관계**, 자동 규칙 산출·polarity 필드 비교).
4. **카테고리쌍→관계 매핑**: Unit,Process→part_of / Process,Property→has_property / Unit,Property→has_property. 전부 이종 쌍이므로 방향 규칙(카드 I8)의 제약을 받지 않는다.
5. **주 공급 문서**: CP(정형), PPT 보고서(비정형). 극성 결합(polarity)과 canonical 스코프(Property = `{세부공정}::{표면형}`)는 이 층의 config가 선언한다. **부착 대상 좌표가 개념 노드인데 record 극성이 확정이면 동일 극성 인스턴스로 하강해 부착한다**(A11-9 ⓪ 하강 부착 — 판정필요-6 종결, D-75. 인스턴스 없으면 F1 결합 유지 — 임의 인스턴스 생성 금지).

### 경계와 오해

- **이 층의 골격이 전 층의 좌표축이다.** 파서의 좌표 태깅(계약 ②), anchor 조회, 규칙 B 폴백, cross 연결이 전부 이 트리를 가리킨다. 골격 개정은 그래서 이 층만의 일이 아니라 전 시스템의 일이고, 사람이 파일로만 한다(CH3B 3.9).
- **Unit에 호기(개체)가 들어오면 안 된다.** "노칭 프레스 3호기"는 현행 카테고리에 자리가 없다 — 설비 개체 축은 미래 층(이력층)의 몫이며, 그때도 이 층의 사본이 아니라 **그 층의 보조 골격**으로 선다(4.6 일반 규칙 ⑶).

### 원천
명세 §5.1~5.3, §5.4(정의문). 틀 §4B-A11(M2 — 골격 두 축·seed v3.2·하강 부착 ⓪). config 전문은 구현문서 §4.

## 4.5 품질지식층 [확정 — FailureEffect 실물 목록은 사내 확정]

### 무엇인가 (구조)

PFMEA류가 담는 **정적 품질 지식**(잠재 고장모드/원인/영향의 체계). 실제 발생 사건을 담는 불량이력층(3층 후보)과 성격이 다르다 — "일어날 수 있는 것"과 "일어난 것".

### 규약

1. **카테고리 2종**
   - **Failure**: 공정에서 발생할 수 있는 불량·고장 현상. **고장모드와 고장원인의 병합**(열린 집합). 같은 현상이 어떤 행에선 원인, 다른 행에선 모드로 등장하므로 한 노드로 해소되어야 causes 연쇄가 이어진다. **원인이냐 모드냐는 노드의 속성이 아니라 엣지에서의 위치다**(카드 I9 — 쪼개지 않는다).
   - **FailureEffect**: 셀 관점의 결과 분류. **닫힌 Tier1 목록, anchor 전용, entity 생성 금지.** PoC seed: 단락·화재·방전기능상실·충전기능상실(실물 목록은 사내 확정 교체).
2. **골격 = 평평한 목록** (`type: flat`, 엣지 없음) — 공정층의 트리와 형태가 다른 것 자체가 "골격 심기가 층마다 다르다"의 실측 표본이다(Rule of Three 관찰 재료).
3. **층 내 관계**: `causes`(Failure→Failure — 동종 쌍·방향성. 정형 edges 선언이 방향을 준다: from=cause, to=failure_mode) · `affects`(Failure→FailureEffect — 이종 쌍).
4. **severity는 FailureEffect(anchor 해소 노드)에 attribute로 부착**된다. 같은 effect면 같은 값이 되도록 문서가 정렬되어야 우발 spec_conflict가 없다.
5. **주 공급은 PFMEA(정형)다.** 비정형(8D 자유기술 등) 경로는 훅만 있다 — 이 층에서 동종 쌍 방향 후보가 비정형에서 나오면 카드 I8대로 `direction_unverifiable` 큐로 간다(PoC는 정형 위주라 영향 없음).
6. **불량 간 인과("이물→절연 파괴")는 골격이 아니라 발견되는 causes 엣지다** — 분류 체계가 아니라 인과 지식이므로. 문서 근거 없는 도메인 지식은 사람이 넣는 Tier1 seed 엣지 옵션으로만 넣는다.

### 경계와 오해

- **FailureEffect에 entity 폴백이 없다.** 골격에 없는 effect 표기(예: "셀 부풀음")는 auto 생성되지 않고 `orphan_anchor` 큐로 간다 — 분류 체계의 확장은 사람 판단이다(P2).
- **§15.8의 "동종 쌍 방향은 사내 케이스로 판단" 항목은 삭제 대상이다**(틀 A3) — 자료구조의 성질이지 사내 확인 항목이 아니다. 남는 사내 확인은: FailureEffect 실물 목록, effect_detail의 성격(attribute vs content), PFMEA에 설비 직접 지목 열의 존재 여부.

### 원천
명세 §15. 틀 A3. 카드 I8·I9.

## 4.6 층간 연결 [확정 — 일반 규칙 승격(M3) · J8 세부는 미결 R2]

### 층 구조 일반 규칙 [M3 확정 — 사용자 판정 08-19 · A안(J7) 재확인·승격]

> 경위: "층별 공정 노드 사본 + 층간 same-as"(B안 계열)를 근본에서 재검토했다(사용자 발의). **기각 재확인** — 사본은 P4(노드 유일성) 위반이고 질의가 사본 정렬을 요구해 연결 문제가 중복 비용을 얹고 재등장하며, 골격 개정이 N배가 되고, matcher 동명 모호가 전면화된다(G3 과매칭 실사고의 계보). "자립"은 착시다 — 사본은 의존의 캐시이고, 독자 어휘 정의는 사일로 회귀다. 층간 독립성(층내 확장이 타층 무영향)은 오히려 A안이 강하다. B안의 알맹이(연결 집약·층 고유 좌표)는 아래 ⑶·⑸가 사본 없이 제공한다. 전문: `안건/M3_판단재료.md` §7.

1. **층이 공유하는 것은 노드가 아니다** — 좌표축(공정 골격 1벌)·동의어 사전·골격 닫힌 목록 스냅샷, 이 셋뿐. 노드는 층 소유이며 **골격 사본 금지**. 층은 위상적 섬이 아니라 **어휘·규칙·수명의 관리 단위**다(그래프는 하나다 — 행정구역이지 건물 층이 아니다).
2. **타층 어휘는 생성 대상이 아니라 해소 대상이다**(anchor — 찾아서 연결). 자기 층 어휘만 entity로 생성한다. 층 구성의 첫 판단이 이 구분이다 — 예: PFMEA의 공정·설비 열 = anchor(공정층 골격 해소), 고장모드 열 = entity(Failure 생성).
3. **좌표 판별 질문**: *그 어휘를 다른 층도 좌표로 쓰는가.* 쓰면 **공유 1벌**(cross로 가리킴 — 사본 금지), 그 층만 쓰면 **층 보조 골격**(층 안에 두고, 보조 골격을 공유 좌표에 건다. 예: 이력층의 라인·호기).
4. **미해소 참조는 임시 노드가 아니라 큐로 보존한다**(orphan_anchor — 표면형 보존·주기 재시도. P2 골격 자동 생성 금지의 이행).
5. **연결의 통제 3종**: 연결 카테고리는 층당 소수 지정(아래 원칙 2) · 대량 인스턴스는 유형·집계 경유 2홉(J8) · 질의는 브리지 1홉·비재귀(J6) + 허브 차수 계기판(J9). **층간 엣지의 많음 자체는 실패가 아니라 통합의 실측이다** — 층들이 같은 좌표 위에서 만나는 것이 이 그래프를 만드는 이유다.
6. **연결의 발견은 스캔이 아니라 문서와 스키마가 한다.** cross 후보는 문서의 표면형에서 오고(연결 시점 = 인입 — 별도 연결 프로그램 없음), 해소는 사전→후보검색→판정의 3단 색인 구조이며, 좌표는 닫힌 목록·서브트리로 한정된다. **층×층 배치 대조는 만들지 않는다.** 비용은 문서 행 수 비례이고, 매칭된 표기가 alias로 누적되므로(P4 — 사전이 영속 지식) 단가는 시간이 갈수록 내려간다.

**반증 조건 [R2 판정 시 함께 심사 — 하나라도 실측되면 B안 재심]**: ⓐ유형 경유로도 허브 노드 차수가 계기판 임계를 지속 초과 ⓑ신규 층의 보조 골격이 공정 골격과 대량 개념 중복을 요구 ⓒ질의 실측에서 사본 정렬 비용이 cross 조회보다 싸다는 증거.

### 규약 (연결의 5원칙)

1. **공정 골격은 공정층에 1벌만 있다 (A안 — 카드 J7 확정 · 위 일반 규칙 ⑴⑶이 승격형).** 다른 층의 노드는 cross 엣지로 그 골격을 가리킨다.
2. **연결 노드는 층당 소수의 지정 카테고리다.** 현행 2층에서는 Failure 하나뿐이다: `occurs_in`(Failure→Process, 기본 닻, 다중 정상) · `controlled_by`(Failure→Property, 보조). FailureEffect는 직접 층간 엣지가 없다 — "단락을 유발하는 공정은?"은 Effect←affects←Failure→occurs_in→Process 2홉 경로로 답하며, 직접 엣지를 달면 "어떤 불량을 통해서"라는 경유 정보가 사라진다. **cross의 도착점은 골격만이 아니다** — controlled_by는 Tier2 노드(Property)에 닿는다: 연결은 "골격 공유"가 아니라 "타층 노드 참조"다.
3. **생성은 단방향이다.** cross 엣지는 상위(공정)층을 모르는 쪽이 아니라 **가리키는 층(품질층)이 생성·저장**하고, 공정층은 품질층의 존재를 모른다(층 독립성). 질의의 역방향 탐색은 저장 방향과 무관하다.
4. **연결 시점은 인입 자체다.** 걸침 문서(PFMEA)의 필드가 `target_layer`로 층을 지정해 한 번의 인입이 여러 층에 기록된다(규칙 A — **G6.5가 배선을 실장했고 클린 기준선에서 걸침 편입이 관측된다**: 정본 CH3B). 부착 대상이 미해소면 공정좌표 폴백(규칙 B). 별도 "연결 프로그램"은 없다.
5. **대량 인스턴스는 허브에 직접 매달지 않는다 (카드 J8).** 공정 노드에 직접 붙는 것은 **유형(type) 수준**뿐이다. 사건 스트림(불량 이력 등)의 개체(instance)는 집계·기간 노드 또는 유형 노드(예: Failure)를 경유해 2홉으로 공정에 닿는다. **경유 노드의 구체 형태(집계 노드 vs 유형 경유)는 [미결 R2] — 3층 성격이 확정될 때 정한다(위 반증 조건과 같은 자리에서 심사).**

### 질의에서의 통제 (CH5와 공유)

- cross 관계는 **1홉·비재귀·양방향 브리지**로만 확장된다(카드 J6) — 허브를 지나 다른 층으로 번지지 않는다.
- 넓은 질의("노칭 관련 전부")는 전부 긁지 않고 **층별 요약 제시 후 좁히게** 한다(카드 J9). **허브 노드 차수를 계기판에 추가**해 폭증을 조기 관측한다(CH5.5).

### 경계와 오해

- **§8의 현행 서술은 2층 특수형이다.** "연결 노드 하나·단방향"은 2층에서의 실체이고, 3층이 양쪽과 이어질 때의 일반형(연결 노드 복수·방향 교차)은 **3층 실측으로 일반화한다**(§8-8 자리표시). 코드는 관계 목록을 순회할 뿐이라 구조는 이미 열려 있다 — 남은 것은 규약의 일반화다. 위 일반 규칙 ⑴~⑹은 그 일반화의 상수 부분(층 수와 무관하게 참인 것)이다.

### 원천

연결 외의 그래프 구축 로직은 기존 층과 완전히 같다(틀 D5 — core 범용 파이프라인 재사용, 신규 코드 0).

### 규약 1 · 그래프 입주 3테스트 — 1단계의 통과 조건 [틀 A9-5의 R1 편입 — M3 안건 2]

카테고리 후보마다 판정표를 채운다(LLM이 근거 붙인 초안 판정, 확정은 사람). **전건 판정 완료 전에는 2단계로 넘어가지 않는다.**

| 테스트 | 질문 | 탈락 시 |
|---|---|---|
| ① 동일성 | 이름이 있어 다른 문서가 같은 것을 가리킬 수 있는가 | — |
| ② 연결 | 다른 정보로 가는 경유지가 되는가 | 노드가 아니라 attribute |
| ③ 기수 | 개수가 문서 수 비례인가 **시간 비례**인가 | 시간 비례 = 무한 → **T3 참조(SeriesRef)** |

- 심사 대상은 **카테고리(종류)이지 노드(개체)가 아니다.** 탈락은 반려가 아니라 **강등**(제자리 찾기 — attribute 또는 T3 참조). 층 전체가 시간 비례 스트림인 경우는 이 게이트가 아니라 층 후보 선정(R5)의 몫이다.
- 판정표는 층 검수 뷰 구획 2에 그대로 실린다 — **승인의 대상이 감이 아니라 표가 된다.**

### 규약 2 · 표본 추가 루프와 설계 시점 plateau [M3 안건 2 — 사용자 발의]

3부는 착수 최소치다. 세션 안에서 **표본 추가 → 재판정 루프는 상한이 없다**(매회 무엇을 추가했고 판정표가 어떻게 변했는지 이력 기록 — n6 재생성 루프의 동형). 승인은 마지막 1회. **루프가 개선하는 것은 후보 목록의 완전성이다**(3테스트 판정 자체는 개념 판단이라 표본 수와 무관) — 종료 신호는 **설계 시점 plateau**: 표본을 추가해도 새 카테고리 후보·새 관계 패턴이 나오지 않으면 수렴(운영 계기판 plateau의 설계 시점 판). 검수 뷰에 "직전 추가에서 신규 후보 0건"으로 표시한다. 부수는 커버리지를 보증하지 않음을 함께 표시한다(D-22 동형). doc_type 단위 등록(n6)의 1부 허용 규칙은 불변이다.

### 규약 3 · 골격 — 데이터는 입력이지 산출물이 아니다 [M3 안건 1]

- **형태**(tree/flat)는 사람이 제안한다(입력 ④). **데이터(seed)는 사람 소유다**(입력 ⑤) — v1의 "config 초안 산출에 골격(형태·데이터) 포함" 문면은 **철회**한다. 근거: 표본은 정준 구조의 원천이 아니고(표집 편향이 좌표계에 유입), 골격에는 어댑터의 하네스 같은 기계 검증망이 없어 LLM 초안의 위험이 통제되지 않는다.
- LLM의 골격 관여 최대치: 표본에서 관찰된 골격 후보 어휘를 **층 검수 뷰에 참고 목록으로 표시**한다 — seed에 자동 기입하지 않는다.

### 규약 4 · cross 연결 선언 — 표본 근거 필수 [M3 안건 3]

cross 제안이 초안에 오르려면 **표본의 실 필드·실 문장을 인용**해야 한다. 형식: `{후보 카테고리쌍, 관계 후보, 근거: 표본 locator, 방향 근거}`. 검수는 그럴듯함 심사가 아니라 **근거 대조**다. 표본에 없는 연결(도메인 지식)은 LLM 경로가 아니라 **사람 직접 선언**으로만 — 입력 통로는 층 설명 항목 4(4.5 규약 6·P2와 동형). 두 통로는 겹치지 않는다.

### 규약 5 · 층 검수 뷰 [M3 안건 4 — M11 규약 재사용, 구획만 층용]

물리 형태 = 뷰 데이터 JSON → 정적 HTML(렌더러 교체 가능 — n8 렌더러 계열), 승인 1회, 재생성 루프 상한 없음·이력 기록.

| 구획 | 내용 |
|---|---|
| 1 | **여섯 칸 채움 현황** — 칸별 실물 경로, 비었으면 사유 |
| 2 | **카테고리 판정표** — 3테스트 ①②③·강등 기록 + 표본 추가 루프 이력 + plateau 표시 |
| 3 | **cross 제안표** — 근거 locator 인용 + 사람 직접 선언분 별도 표기 |
| 4 | **골격** — 형태·seed 초안(사람 입력) + LLM 관찰 어휘 참고 목록(자동 기입 아님 명시) |
| 5 | **기계 판정** — `git diff core/` 공백(J3) · 표본 인입 스모크 · 등록 커밋 단독 여부 |

### 규약 6 · 층 등록 커밋은 단독 커밋이다 [M3 안건 2-⑵ — G4 실사고의 재발 방지]

층 등록 커밋에는 층 등록만 담는다. 그래야 `git diff core/` 공백 = J3 증명이 커밋 1회로 성립한다(G4에서 등록 커밋에 다른 작업이 섞여 문자적 판정이 불가능했던 실측 — 소급 grep으로 정산해야 했다).

### 무엇이 남아 있나

| 항목 | 상태 | 정해질 방법 |
|---|---|---|
| 절차 전체의 실효성 | **[미결 R1 — 실험 트리거만 잔류]** | **국면 2 진입 게이트**(M3 안건 5): 품질층을 이 절차로 재등록해 현행 quality config와 비교. 구조 검증(J3)은 이미 실측 종결 — 남은 것은 절차 문서의 검증이며, 층 등록 코드는 국면 1 범위 밖(부트스트랩 — 기본 층은 내장, 층 등록 기능은 신규 층 전용)이므로 국면 2 준비 구간에 자연 합류한다 |

### 경계와 오해

- **층 등록은 운영 중 자동 기능이 아니다.** 미등록 층의 문서가 와도 시스템이 층을 즉석 생성하지 않는다 — 구축 모드로 사람에게 넘어간다(카드 M2·M4).
- **"신규 층 프로토콜"이라는 별도 문서는 만들지 않는다.** 이 절차의 정본은 이 절이며, 확정 시 명세 §8·§4 개정으로만 반영한다(같은 사실은 한 곳에만).
