# 01 · PPT 판독 — 무엇을 읽고 어떻게 자르나

> **실물 기준**: `parser/reader.py::read_pptx` · `parser/adapters/basic_ppt.py` · `parser/tagger.py`(④ 이미지 요약 · ⑨ 좌표) — 원격 `55f9c59` (B58 ⑤). 정본은 문서 6 §6.1·§6.4-3·§6.4-5.
> **확정**: 미확정. 사내 실측 대기.

## 한 줄

**PPT는 「슬라이드 1장 = 청크 1개」가 기본이고, 한 장이 너무 길면 쪼갠다.** 청크가 곧 답의 근거 단위라 — 너무 굵으면 근거 8개 상한을 한 장이 다 먹고, 너무 잘면 문맥이 끊긴다. 이 모듈이 정하는 것은 **그 굵기**다.

## 무엇을 받아 무엇을 내나

```
.pptx ─▶ reader(읽기) ─▶ basic_ppt(자르기) ─▶ tagger(④ 그림 요약 · ⑨ 좌표) ─▶ parsed/{doc_id}.json
```

**받는 것**: 파일 하나. **내는 것**: 청크 목록 — 청크마다 `text` · `section`(경로) · `source_locator`(슬라이드 N / S8-TB1) · `meta.split_path`(어느 갈래로 잘렸나).

## 어떻게 동작하나

### 1단 — 읽기: 텍스트 프레임만이 아니다 (B53)

슬라이드마다 이것들을 **시각 순서(위→아래, 왼→오른)**로 읽는다.

| Shape | Read as | Note |
|---|---|---|
| 텍스트 프레임 · 제목 · 부제 | 텍스트 | |
| **표** | 행을 텍스트로 푼다 | 형태 변환이지 의미 판정이 아니다 — 무엇이 개체인지는 추출(①)이 정한다 |
| **차트** | 계열·값을 텍스트로 | `chart_type` 함께 |
| **그림** | 바이트를 잡아 둔다 → ④가 요약 | 바이트는 계약 JSON으로 안 나간다 |
| **그룹 · SmartArt** | 풀어서 텍스트 | |
| 노트 | 텍스트 | 슬라이드에 딸린다 |
| **숨김 슬라이드** | 읽되 표시 | 어댑터가 거른다 |

### 2단 — 자르기: 네 갈래 (임계 조건화)

슬라이드 하나를 보고 **결정적으로** 고른다. LLM 판정이 아니다.

```
텍스트 ≤ 600자 이고 shape ≤ 5개   →  ⓐ 슬라이드 1장 = 청크 1개        (기본)
임계 초과 · shape 여럿             →  ⓑ shape 단위로 쪼갠다           (결정적)
임계 초과 · 큰 shape 하나           →  ⓒ 구조 지도 패스 (⑦ LLM)       (코어에 위임)
지도도 실패                         →  ⓓ 통청크 + hierarchy_unresolved 큐
```

**왜 조건화인가.** 항상 1장=1청크면 빽빽한 슬라이드가 근거 상한을 먹고, 항상 쪼개면 정상 슬라이드에서 문맥이 끊긴다. **대부분의 슬라이드는 ⓐ로 가야 정상이다** — ⓑⓒ가 많으면 임계가 이 덱에 안 맞는 것이다.

### 3단 — 경로: 슬라이드가 어느 구획에 속하나

`section` = 「덱 제목 › 구획 › 슬라이드 제목」. **구획 판정도 결정적이다**:
- 레이아웃 이름에 `Section`/`구획`이 있거나, **제목만 있고 본문이 빈 슬라이드** → 구획 헤더. 그 뒤 슬라이드가 그 구획에 속한다.
- 표지(1번)는 구획이 아니다. 헤더 슬라이드 자신도 구획에 안 속한다.
- 목차 슬라이드(제목에 「목차」·「Contents」)는 따로 본다.
- 헤더가 하나도 없으면 경로는 두 단(덱 › 슬라이드).

### 4단 — 그림 요약 (④): 그림만 보내지 않는다

그림 바이트 + **같은 슬라이드의 제목·본문·표·차트 텍스트**를 맥락으로 함께 보낸다. 그림만 보내면 「무엇의 그림인가」를 모델이 지어낸다(B53 실측). **앞뒤 슬라이드는 안 보낸다** — 비용 3배에 잡음이고, 사람이 쓰는 맥락은 경로다.

## 조절 손잡이

| Knob | Where | Value now | Effect | When |
|---|---|---|---|---|
| **`max_chars`** | `basic_ppt.py` `ADAPTER.expects` | **600** | 이 넘으면 ⓑⓒ로 | 다음 인입부터 |
| **`max_shapes`** | 같은 자리 | **5** | 이 넘으면 ⓑⓒ로 | 다음 인입부터 |
| 구획 레이아웃 이름 | `_SECTION_LAYOUT` | `Section`·`구획` | 사내 템플릿 이름이 다르면 못 잡는다 | 다음 인입부터 |
| 목차 제목 | `_TOC_TITLE` | 「목차」·「Contents」 | 같음 | 같음 |
| 맥락 길이 | `CONTEXT_CHARS` | (코드 상수) | ④에 보내는 맥락 크기 | 다음 인입부터 |
| 이미지 요약 지시문 | `prompts/image_summary.md` | 파일 | 요약의 문면·길이 | 다음 인입부터 |

**둘 다 초기값이고 P7이다 — 측정 후 조정.** 사내 덱 서너 개에서 ⓐⓑⓒ 비율을 보고 정한다.

## 실측에서 볼 것

1. **`meta.split_path` 분포** — `parsed/{doc_id}.json`에서 청크마다 `slide`/`shape`/`struct_map`/`flat`. **대부분 `slide`여야 정상.** `shape`가 절반이면 `max_chars`가 사내 덱에 너무 낮은 것이다.
2. **`section` 경로가 맞나** — `show chunk`로 두세 개. 구획 헤더를 못 잡으면 전부 두 단으로 나온다 → `_SECTION_LAYOUT`에 사내 레이아웃 이름을 넣는다.
3. **표·차트가 텍스트로 풀렸나** — 표 있는 슬라이드의 청크 `text`에 행이 보이는가.
4. **그림 요약이 그림을 말하나** — `extract/struct_maps/{doc_id}.json`의 이미지 요약을 열어 「무엇의 그림」이 맞는지. 지어낸 것 같으면 ④ 맥락이 안 실린 것.
5. **숨김 슬라이드가 안 들어왔나** — 청크 수 = 보이는 슬라이드 수 언저리.
6. **`hierarchy_unresolved` 큐** — ⓓ로 떨어진 슬라이드가 있으면 그 슬라이드를 직접 본다.
7. **그림 청크가 노드에 걸렸나** — `show node <공정>`의 근거 청크에 `image_summary` 청크가 있는가. 없으면 ④ 요약이 공정 이름을 안 담은 것이다 — 「공장 배치도」로만 요약되면 `orphan_chunk_link`로 떨어진다. **레이아웃·도면처럼 내용은 그래프가 안 되지만 「어느 공정에 어느 파일 어느 슬라이드」는 이 경로로 남는다.**
8. **추출이 받은 재료가 맞나** — `show extract <doc_id>`. 뽑힌 개체가 그 슬라이드 내용인가 · **경로(`[덱 › 구획 › 제목]`)의 말을 개체로 잘못 낸 게 없는가**. 추출은 청크 하나만 본다(앞뒤 안 봄 — 의도). 앞 슬라이드가 이름 붙인 것을 뒤 슬라이드가 「본 설비」로 받는 덱이면 여기서 끊긴다 — 그게 카드 06의 손잡이다.

## 고치는 경로

| Symptom | Fix |
|---|---|
| 청크가 너무 굵다 (한 장이 근거 8개를 먹는다) | `max_chars` ↓ · `max_shapes` ↓ |
| 청크가 너무 잘다 (한 슬라이드가 대여섯 개로) | `max_chars` ↑ · `max_shapes` ↑ |
| 구획을 못 잡는다 | `_SECTION_LAYOUT`에 사내 레이아웃 이름 · 또는 구획 슬라이드를 「제목만」으로 만든다 |
| 그림 요약이 엉뚱하다 | `prompts/image_summary.md` 문면 · `CONTEXT_CHARS` |
| 표를 못 읽는다 | 표가 그림으로 붙어 있는 경우다 — ④가 요약하는 수밖에 없다. reader 한계 |
| 슬라이드가 통째로 ⓓ | 그 슬라이드의 구조를 본다 — 대개 텍스트 상자 하나에 전문이 들어간 경우. ⓒ의 지도(⑦)가 왜 실패했는지 `source` 확인 |

**임계를 층 config에 두지 않는다**(문서 6 §6.4-5) — PPT 스키마가 두 층에 걸쳐 있어 층마다 다른 임계로 돈다. 조정은 `basic_ppt.py` 한 곳.
