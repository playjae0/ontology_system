## 6.1 코드 배치와 두 축 id [확정 · 저장 계층은 08-06 쟁점 A 판정 반영]

### 무엇인가 (구조)

```
ontology/
├── core/       처리 코드 — 전 층 공용, 층 어휘 0 (A)
├── layers/     층별 폴더 — {층}/config.json + {층}/skeleton.json(seed) — 코드 0 (B)
├── schemas/    doc_type별 매칭 스키마 + 공용 블록(blocks.json)
├── parser/     파서 공용 코어 6종 + 기본 어댑터 (P1 — n7)
├── kit/        어댑터 생성 킷 6종 — 외부 전달물 (P2 — n8)
├── cli/        플랫폼·질의·I축·스캔 CLI (G5·G6)
├── tools/      passthrough 등 보조 도구
├── mock/       raw 실물·parsed 계약·fixture(봉인)·참조 어댑터·지도 mock
├── tests/      회귀 9종
├── router.py   층 폴더 자동 발견 (등록 배선 없음)
├── run.py      파이프라인 진입점
└── data/       진실(생성물 — 미추적) — 층별 graph.json + 공유: dictionary.json · chunks.json ·
                review_queue.json · skeleton_closed_list.json(파생물 P5) · registry.json ·
                doc_registry.json · gate_rejects.json (· ops_log.json — I축 연산 시 생성)
```

> **관리 자산의 원칙 (세션 N 명문화)**: 판단·성능에 영향을 주는 자산은 **코드 안에 박지 않고 자산별 지정 파일**로 둔다 — 층 어휘는 `layers/{층}/config.json`(B1·B2), 매칭 스키마는 `schemas/`의 JSON, 프롬프트(추출 지시문 등)는 프롬프트 파일(사람 확정 관리 자산, prompt_version), 어댑터의 판단 상수는 `ADAPTER.expects`(C11). 실물은 각자 파일, **목록·버전의 한눈 파악은 등록부(registry — M2의 등록 조회가 읽는 것)가 담당**한다.

### 규약

1. **공유 자원은 전 층 단일이다**: 동의어 사전, id 시퀀스, 청크 저장소, 수정 큐(§8-R3, 카드 B4). 층 간 표면형 충돌은 사전이 허용하고 호출자가 카테고리·층으로 선별한다.
2. **id는 두 축이다 (틀 A4·A8, 카드 N1~N4)** — 이 절이 산식의 소유처다.
   - **의미 축**(Process·Unit·Property·Failure 등): **발급**, 발급 후 불변(P4). 개명·alias가 있는 축이라 해시 불가. **발급 방식은 ULID**(틀 A8-4, 쟁점 A C안 — 구 전역 시퀀스 N####): 중앙 카운터 없이 유일·시간순 정렬 가능·내용 무관. **발효는 A0의 N#### 하드코딩 계수 확인 후**이며, 발효 시 id_seq.json은 폐지한다. **id에 의미(공정·순서)를 담지 않는다** — 소속·순서는 그래프(part_of·precedes)가, 사람이 읽을 이름은 canonical이 담당한다.
   - **근거 축**(문서·청크·레코드): **내용에서 계산.**
     ```
     doc_id    = 파서 봉투 부여 (해시 아님 — 재인입 단위, 개정 구분은 revision)
     chunk_id  = f"{doc_id}:{sha256(norm(text)+'\x00'+section+'\x00'+str(occ))[:12]}"
     record_id = f"{doc_id}:{sha256(norm(join(values,'\x1f'))+'\x00'+str(occ))[:12]}"
     occ       = 그 문서 내 동일 (section, norm(text)) 조합의 출현 순번 (0부터)
     ```
   - **계산 주체는 에이전트다(틀 A7-1).** 파서가 내는 것은 doc_id와 source_locator(문서 내 위치 표기, role=meta)뿐 — 정본 chunk_id·record_id는 에이전트가 인입 시점에 이 산식으로 계산한다. 멱등성의 근거를 사내 파서 구현에 위임하지 않기 위해서다.
   - `norm()` = 연속 공백 정리 + 앞뒤 공백 제거까지만. 원문은 정규화 없이 그대로 저장(해시 계산에만 사용).
   - 구분자 필수. 문서 내 위치(seq)는 해시 입력 금지(앞 문단 추가 시 뒤 전부 변경). 충돌 접미 금지(처리 순서 의존 — occ가 대체). 계산 id가 이미 존재하면 조용히 덮지 않고 결함 로그.
   - 절단 12자(48비트)는 doc_id 스코프 내 유일성용 — 충돌 공간이 문서 하나라 충분.
3. **doc_hash**(문서 전체 해시)를 인입 진입에서 계산·대조한다 — 중복 문서 차단(카드 N8, CH3A 3.1). 계산 주체는 역시 에이전트(틀 A7-2, 청크 해시 계산의 부산물이라 추가 비용 0). 어댑터 버전은 봉투에 `adapter_version` 1회 — 청크 저장 시 에이전트가 복사(틀 A7-3).
4. **판정용 임베딩은 저장하지 않는다**(재계산 가능한 파생물). 청크 인덱스는 재생성 캐시.
5. USE_MOCK=1(기본)에서 외부 의존(LLM·임베딩) 없이 전체가 동작해야 한다(구현문서 §0-8).
6. **저장 계층 — GraphStore 경계 (틀 A8, 카드 B6 — 쟁점 A 판정 08-06)**
   - 그래프 저장 접근(로드·저장·노드/엣지 갱신)은 **core/graph.py(GraphStore) 경유로만** 한다. **graph.py 밖의 코드(run.py·viz.py·cli·테스트 포함)가 graph.json을 직접 열지 않는다** — 현존 직접 접근 지점은 증분 0 단위 A0가 계수·교체한다.
   - 저장 방식은 현행 유지: 층별 단일 JSON. 직렬화는 **orjson**(미설치 환경 대비 표준 json 폴백 — "외부 패키지 0" 원칙은 폴백으로 보존).
   - **알람선 = 층별 최대 graph 파일 200MB 또는 build 30초** — 계기판 7·8번(CH5 5.5)이 관측하고, 도달 시 저장 전환(B-1 샤딩/B-2 SQLite — R10) 판정을 개시한다. P1의 "파일"은 단일 JSON이 아니라 "DB 서버 없이 원천 복원 가능"이다(A8-1).

## 6.2 파이프라인 형상 — 3단계와 두 모드의 코드 모양 [확정 — 세션 N ⑸, 2026-07-30]

### 규약

1. **운영 모드는 3단계다 (틀 Q1)**: `파싱 → 추출(비정형만) → 구축`. **각 단계는 CLI 진입점 + 파일 입출력**이고(카드 P-1, §16.1 계약 1), 단계 산출물(계약 JSON, 추출 후보 JSON — CH3A 3.11)은 체크포인트다 — 구축 재실행이 추출을 다시 돌리지 않는다.
2. **구축 모드는 3단 워크플로우다**: 생성(LLM) → 검수(사람) → 확정(등록). **코드 레벨에서 세 단계가 분리**되어야 화면이 붙는다(카드 P-2).
3. **플랫폼화 인지 계약** (§16.1 — 유지): ①모든 단계는 subprocess로 호출 가능한 CLI+파일 ②파이프라인은 그래프를 직접 수정하지 않고 수정 재료(status·provenance·큐)를 빠짐없이 기록 ③**build는 직렬 실행**(id 발급·저장이 비원자적 — 호출부가 직렬화 보장. ULID 발효로 id 축 원인은 제거되나 저장이 전체 재기록인 동안 직렬 계약 유지 — 카드 H5).
4. **신규 구현 단위 — 10종 닫힌 목록 [⑸-A 확정].** 기존 단위(1a~1d 코어·인입, 2 질의, 3 품질층 config-only, 3.5 재인입 사전 보존, 4 플랫폼, 5 수정 도구)는 유지하고, 다음 10종을 추가한다. 각 단위는 "빼면 어느 확정 사항이 구현되지 않는가"의 필요성 시험을 통과했다(A8).

   | # | 단위 | 근거 확정 |
   |---|---|---|
   | n1 | 근거 축 id 전환 — chunk_id·record_id·doc_hash 산식(인입 검증 ②) | 틀 A4·A7 |
   | n2 | doc_hash 중복 차단 (인입 진입 ①) | 틀 A6 |
   | n3 | 추출 단계 분리 + 추출 후보 JSON 체크포인트 | 틀 Q1 + CH3A 3.11(⑶) |
   | n4 | 커밋 게이트 + direction_unverifiable | 틀 A3 |
   | n5 | I축 도구 4연산 (+canonical 선택·순환 방어) | 틀 A2 |
   | n6 | 구축 모드 등록 파이프라인 — 입력 패키지(M10)→생성→검수 뷰(M11)→승인·등록 | ⑵⑺ |
   | n7 | 파서 공용 코어 6종(reader·preflight·normalizer·tagger·validator·기본 어댑터) + 생성 하네스 — **외부 전달물** | ⑴ + 파서_명세 §3·§9 |
   | n8 | 어댑터 생성 킷 5종 — 완료 = mock 전 과정 리허설 통과 | ⑻-A |
   | n9 | 투입 분류 지문 스캔 — 미지정 정형 문서의 doc_type 후보 제안 로직(UI는 플랫폼 몫). **편의 기능** — 없는 동안은 사람 지정(⑴-C″/C15)만으로 운영 성립, 배치 순서는 증분 0 재량 | ⑴-C″ |
   | n10 | 부트스트랩 seed·config — 공정정보층 내장 | ⑵-③′(J10) |

   기존 단위 1a~5와의 **통합 배열은 증분 0(구현 증분 문서)**이 확정한다.
5. **순서 원칙 4개 [⑸-C 확정]** — 상세 배열은 증분 0, 원칙은 여기가 정본: ①**주소 체계 먼저** — n1·n2·n3은 다른 단위가 읽고 쓰는 id·체크포인트의 전제 ②**파서 측(n7·n8)과 에이전트 측(n1~n6)은 병렬** — 계약 JSON으로만 결합되므로(P1) 에이전트 측은 mock 계약 JSON으로 파서 없이 진행 ③**n6은 n7 이후** — 배선할 코어가 먼저 있어야 함 ④**n10은 인입보다 먼저** — 골격 없이는 anchor 해소가 성립하지 않음.
6. **완료판정 원칙 [⑸-B 확정]**: 단위 완료 = 그 단위에 배정된 mock 시나리오(6.3) 전부 통과. 품질 측정은 완료판정이 아니다(6.3 규약 1). n7·n8은 ⑻-A의 리허설 기준(표본 투입→생성→검수 뷰→등록→파싱의 전 과정)이 곧 완료판정.
7. 막힘 프로토콜 유지(구현문서 §9.4): 문서로 결정 안 되는 지점은 추측하지 않고 BLOCKERS 기록 후 독립 작업으로 이동. **여기에 결정 위임 규칙을 추가한다**: 카드·계약과 충돌하면 BLOCKERS(멈춤), 그 외 세부는 **가결정 + DECISIONS 기록**(전진). — 구현 증분 문서에 명문화.

### 경계와 오해

- **구현문서 v1.16은 구 아키텍처다.** 추출 단계·게이트·구축 모드·I축·근거 축 id가 없다. 구현 착수 전 구현문서 증분(또는 v1.17 동기화)이 필수이며, 그 원천이 이 챕터와 카드다.
- **파이프라인을 LLM이 조종하지 않는다**(카드 I4). 단계 순서·재시도·커밋은 전부 코드다.
- **n9는 n2·preflight와 헷갈리기 쉽다** — 셋은 답하는 질문이 다르다: n9="지정 없이 온 문서, 등록 양식 중 맞는 게 있나"(후보 제안) / preflight(n7)="지정된 어댑터와 실물이 맞나"(검증·중단) / n2="같은 내용이 이미 들어와 있나"(중복 보류). 제목·파일 크기로 판정하는 기능은 셋 중 어디에도 없다(N8 — 내용 해시가 기준).

## 6.3 mock 체계 [확정 — 세션 N ⑸ · 15종 개정 08-06 (D-18·D-20 채택)]

### 규약

1. **mock의 목적은 메커니즘 검증으로 한정한다.** 품질 측정은 mock으로 불가·유해(가짜 데이터의 점수는 가짜 확신) — 품질은 국면 2의 실데이터·골든셋 몫이다. 데모도 실데이터로 한다.
2. **모든 mock 항목은 검증할 메커니즘을 최소 하나 짊어진다**(행별 주석 명시 — 구현문서 §6의 PFMEA 13행·CP 10행[D-15]·PPT 8청크·질의 12문항이 현행 세트. raw 실물 10종의 행별 주석은 `raw_mock_대장`이 소유).
3. 사내 유래 정보는 모양만(공정 단계명·열 이름 — 업계 일반 수준), 내용물은 전량 창작.
4. **mock 시나리오 — 15종 닫힌 목록 [⑸-D 확정 13종 + 사용자 판정 08-06으로 S14·S15 추가].** 시나리오는 단위(6.2 규약 4)의 시험지다 — 단위 완료판정이 이것으로 내려진다(6.2 규약 6).

## 6.4 파생물 — 시각화와 외부 적재 [확정]

### 규약

1. **진실은 data/의 JSON이다(P5 — 해석은 틀 A8-1: "파일" = DB 서버 없이 복원 가능, 단일 JSON 한정 아님).** Neo4j 적재·HTML 시각화·Mermaid·임베딩 인덱스는 전부 읽기 전용 파생물이며 언제든 재생성한다. 파생물에서 그래프를 수정하는 경로는 없다.

3. 파생물이 늘어도(벡터 인덱스 추가 등) 이 지위는 불변이다 — 파생물 장애는 재생성으로 복구하고, 진실 장애만이 백업 문제다.
