# 실행 검증 1차 — LLM이 짠 adapter·schema를 실제로 돌린다
 
---
 
## §1 성공 판정의 정정 [사용자 확정, 2026-08-01]
 
### 무엇이 바뀌었나
 
지금까지 국면 1 리허설의 성공 판정은 암묵적으로 "파이프라인이 도는가"였고, 등록 세션의 LLM 호출은 가결정 D-10에 따라 **fixture 반환으로 대체**되었다. 그런데 **구현 코드 안에 LLM API가 없다.** 따라서 "코드에서 LLM이 동작하는 것"은 국면 1에서 볼 수 없고, 봐야 할 것도 그것이 아니다.
 
> **정정된 성공 판정**
> 보려는 것은 **"문서와 프롬프트를 넣었을 때 LLM이 매칭 스키마와 어댑터 코드를 제대로 짜는가"**이고,
> 그것이 제대로 되었는지의 확인 방식은 **"나온 스키마와 코드를 실제로 파이프라인에 꽂아 도는지 보는 것"**이다.
 
즉 판정은 **LLM 출력의 문면**이 아니라 **그 출력의 실행 결과**로 내린다. 사람이 배정표를 읽고 "맞는 것 같다"고 하는 것은 판정이 아니다.
 
### 이 정정이 바꾸는 것 (3건)
 
**① `USE_MOCK` fixture의 정의가 바뀐다 [D-26].** 지금까지 fixture는 "미리 준비한 정답 파일"로 읽혔다. 그러나 위 판정 아래에서 fixture는 **"외부 세션에서 실제 LLM이 산출한 결과물을 고정해 둔 것"**이다. 가짜 정답이 아니라 진짜 산출물의 스냅샷이며, 그래서 fixture로 돌린 리허설이 의미를 갖는다. 반대로 사람이 손으로 써서 fixture에 넣으면 그 리허설은 아무것도 검증하지 않는다.
 
**② 킷 구성물에 실행 하네스가 추가된다 [D-27].** 파서_명세 §9의 킷 5종은 산출물을 **만드는** 도구만 담고 있고 산출물을 **검사하는** 도구가 없다. 사내에서 어댑터 생성 세션을 돌린 뒤 그 결과가 쓸 만한지 판단할 방법이 검수 뷰(사람 눈)뿐이라는 뜻이다. 실행 하네스는 검수 뷰 **이전**에 기계가 거르는 관문이므로 킷 6번째 구성물로 신설한다.
 
**③ 표본 규모가 판정에 영향을 준다 [D-28].** 관찰 범위 규칙(M5)은 "정형 head 약 10줄"인데 문서 전체가 10줄이면 head = 전체가 되어 규칙 자체가 시험되지 않는다. 또 패턴이 몇 회 반복되어야 LLM이 규칙과 그 문서만의 특이점을 구분한다. 그래서 전 raw mock을 2~3배로 확대했다(`raw_mock_대장` v2.0).

## §2 실행 하네스 — 무엇을 어떻게 검사하는가
 
`run_adapter.py <adapter.py> <schema.json> <문서…>` — 4단으로 검사한다.
 
| 단 | 검사 내용 |
|---|---|
| ① adapter 로드 | 문법 오류 / **순수 함수 계약**(네트워크·LLM import 금지, §5 규약 2) / `ADAPTER` 선언 4키 / `payload_kind` 닫힌 2값 / `extract` 존재 / **`locate` 부재**(폐지된 인터페이스, §5 규약 1) / adapter.doc_type == schema.doc_type |
| ② preflight | **양식 표류를 감지할 수 있는 지문이 `expects`에 실려 있는가.** 정형은 원본 헤더 문자열 전량 포함 여부, 비정형은 분할 신호 상수 선언 여부 |
| ③ extract 실행 | 예외 없이 실행 / `list[dict]` 반환 / 조각 0건 아님 / **`source_locator` 전건 존재·문서 내 유일** / **정본 id(`chunk_id`·`record_id`·`doc_hash`) 미부여**(틀 A7-1) / prose는 `text` 또는 `image_ref` 보유 / **상동 기호 잔존 0**(계약 ③) |
| ④ 스키마 정합 | 헤더 키 / `fields` 존재 / **role이 닫힌 5종 안** / entity에 `category` 필수 / **edges의 from·to가 선언된 필드를 가리키는가** / 조각 키 ↔ `fields` 대조(`unknown_field`·`missing_field` 큐의 드라이런) / **role 루프 드라이런**(핸들러 분기별 처리 건수) |
 
핵심은 ②와 ④다. ②는 **preflight가 실제로 기능하는가**를, ④는 **인입 루프가 이 스키마로 돌 수 있는가**를 본다. 둘 다 배정표만 읽어서는 절대 알 수 없다.

## §3 실행 결과
 
### 3.1 정형 — `ipqc` (표본 IPQC01 32행 + IPQC02 20행, 16열)
 
| 단 | 결과 |
|---|---|
| ① 로드 | **전항 PASS** — 문법·순수성·인터페이스 계약 전부 준수 |
| ② preflight | **FAIL 1건** — §4.1 |
| ③ extract | **전항 PASS** — 33조각(복수값 1건 전개 포함)·`source_locator` 유일·정본 id 미부여·상동 잔존 0 |
| ④ 스키마 | **전항 PASS** — role 5종·entity category·edges 참조 무결·`unknown_field` 0·`missing_field` 0 |
 
role 루프 드라이런: `anchor=0 · entity=66 · attribute=97 · content=33 · meta=99`
 
배정 결과는 v0.1 대비 크게 개선되었다. 1차에서 갈렸던 4건 중 **3건이 수렴**했다 — 공정번호를 `meta`(구조 필드)로, 극성과 적용모델을 `electrode_type`·`context` 구조 필드로 정확히 매핑했고, **"부적합 조치"를 `content`로** 배정했다(1차에서는 양쪽 다 `attribute`였다). UNMAPPABLE 2열도 그대로 유지되었다. 즉 **프롬프트 개정 지시 7건이 유효했다.**
 
### 3.2 비정형 — `toc_report` (표본 TOC01 31행 + TOC02 25행, 목차형)
 
| 단 | 결과 |
|---|---|
| ① 로드 | **전항 PASS** |
| ② preflight | **PASS** — 분할 신호 상수 선언(`heading_pattern`·`split_on`·`indent_by_level_observed` 등) |
| ③ extract | **전항 PASS** — 11조각(본문 9 + 이미지 placeholder 2) |
| ④ 스키마 | **FAIL 2건** — §4.2 |
 
채택된 분할 규칙: 1행은 제목(청크 아님), 헤딩 판별은 **번호 패턴 단독**(`^\d+(\.\d+)*`, 레벨 = 마디 수), bold·indent는 보조 신호로 기록만 하고 분할에 미사용, 청크 경계 = 헤딩 등장 지점 + 이미지 위치, `section`은 헤딩 경로를 `" > "`로 이음.
 
**들여쓰기를 분할 근거에서 배제한 판단이 정확하다.** TOC01의 이상치 1건(indent 5)을 보고 *"단발 이탈이라 규칙인지 오타인지 구분 불가 → indent 기반 규칙을 만들지 않는다"*고 판정했다. 추측으로 규칙을 만들지 말라는 지시(M5)가 그대로 작동했다.

## §4 도출된 결함
 
### 4.1 [원천 결함] `expects.columns`의 키가 무엇인지 명세가 정하지 않았다
 
파서_명세 §5의 예시는 `"columns": {"공정명": "B", "관리항목": "D"}` 인데, 여기서 `공정명`이 **원본 헤더 텍스트**인지 **출력 필드명**인지 규정이 없다. cp 양식에서는 둘이 우연히 일치해서 문제가 드러나지 않았다.
 
ipqc에서는 갈린다. 프롬프트가 "대공정 → `process_group`으로 내보내라"고 지시했으므로 어댑터는 `"process_group": "A"`로 선언했고, 그 결과 **원본 헤더 문자열 5개(`대공정`·`공정No`·`공정명`·`극성`·`적용모델`)가 `expects` 어디에도 남지 않았다.**
 
**귀결: preflight가 그 5개 열에 대해 무력화된다.** 사내 양식이 "대공정"을 "공정구분"으로 개정해도 `adapter_mismatch`가 발생하지 않고 조용히 잘못 파싱된다. preflight의 존재 이유(운영 모드 안의 양식 표류 감지, C15)가 절반 무너진다.
 
**처방 [D-29]**: `expects`에 **`header_labels`(원본 헤더 문자열의 순서 배열)를 필수 키로 신설**한다. `columns`는 출력 필드명 매핑으로 용도를 확정하고, 표류 대조는 `header_labels`로 한다. 두 관심사가 한 키에 섞여 있던 것이 원인이다.
 
### 4.2 [프롬프트 결함] UNMAPPABLE 열을 스키마에 넣을지 말지가 지시에 없다
 
같은 지시문 v0.2를 받은 두 판정이 **정반대로 처리했다.** ipqc는 UNMAPPABLE 2열을 `fields`에서 빼고 조각으로도 내보내지 않았고, toc_report는 `section`에 `{"role": "UNMAPPABLE"}`을 그대로 넣었다.
 
지시문은 "5종에 맞지 않으면 UNMAPPABLE을 고르고 이유를 적어라"까지만 말하고, **그 필드가 스키마에 남는지 빠지는지를 말하지 않았다.** 원천(CH2 2.6 규약 5)은 "매핑 불가 필드는 **스키마에 넣지 않고** UNMAPPABLE로 사람이 판정한다"로 이미 정해 놓았는데 템플릿이 그 절반을 안 실었다.
 
`role` 값이 닫힌 5종이 아니면 핸들러 조회(`HANDLERS[spec["role"]]`)가 `KeyError`로 죽는다 — 실제로 하네스가 그 자리에서 죽었다. **즉 이건 취향 문제가 아니라 런타임 크래시다.**
 
**처방 [D-30]**: 템플릿 v0.3에 명시 — *"UNMAPPABLE로 판정한 열은 스키마 `fields`에 넣지 말고 어댑터 출력에서도 제외한다. 산출물 3(판정 불가)에만 적는다."* 더불어 인입 코드에 방어를 넣는다(알 수 없는 role → 크래시 대신 `invalid_role` 결함 로그).
 
### 4.3 [원천 미비] `section`의 지위가 정해져 있지 않다
 
toc_report 판정자가 `section`을 UNMAPPABLE로 올린 근거가 정확하다. TOC01은 1장이 공정명(→`Process`), 2장이 품질 이슈명, 3장이 개선 활동명이고, **TOC02는 같은 번호 위치의 2장이 설비명(→`Unit`)**이다. 즉 헤딩 경로의 의미가 문서마다·절마다 다르므로 하나의 role로 고정할 수 없다.
 
그런데 `section`은 파서 출력 계약(CH2 2.2)의 prose payload에 **고정 필드로 들어 있다**(`text`·`section`·`meta`). 계약 고정 필드인데 role이 미정인 것이다 — `electrode_type`(D-1)과 같은 성격의 미결이다.
 
**처방 [D-31]**: `section`은 role 배정 대상이 아닌 **구조 필드**로 확정하는 것이 유력하다(청크의 소속 표기이지 그래프 쓰기 동작이 아니다). 다만 CH2 2.2와 CH5(질의·하이브리드 서치)에서 `section`을 어떻게 쓰는지와 함께 판정해야 하므로 세션 1로 넘긴다. **표본 2부가 아니었으면 이 결함은 드러나지 않았다** — TOC01만 봤으면 "2장도 공정명이겠거니" 하고 넘어갔을 것이다.
 
### 4.4 [하네스 한계] `use_blocks`를 로드하지 않아 anchor 경로가 드라이런되지 않는다
 
ipqc의 role 루프 드라이런에서 `anchor=0`이 나왔다. 좌표 필드를 공용 블록(`process_coord`)에 위임했으므로 `fields`에 없고, 하네스가 블록 파일을 조립하지 않기 때문이다. 스키마는 옳고 **하네스가 미완**이다.
 
**처방**: 하네스에 `use_blocks` 로더를 붙여 `common_core`·`process_coord`를 합친 뒤 드라이런한다. 블록 파일 실물이 아직 레포에 없으므로 n7 구현과 함께 처리한다.

## §5 이 실행 검증이 증명한 것과 못 한 것
 
**증명한 것**
 
LLM은 처음 보는 양식에서 **실행되는 어댑터 코드와 로드되는 스키마를 산출한다.** 정형·비정형 둘 다에서 문법 오류 0, 예외 0, 순수 함수 계약 준수, `source_locator` 유일성 보장, 정본 id 미부여, 자기완결성(병합·상동·복수값) 처리까지 지켰다. 이건 배정표만 받았을 때는 확인할 수 없던 수준이다.
 
그리고 **프롬프트 개정이 실제로 판정을 수렴시킨다.** 1차에서 갈렸던 4건 중 3건이 v0.2에서 정정되었다. "정확도를 올리는 방법은 더 좋은 모델이 아니라 확정된 규약을 프롬프트에 싣는 것"이라는 1차 결론이 재확인되었다.
 
**증명하지 못한 것 (정직하게)**
 
인입 파이프라인 자체는 아직 돌리지 못했다. 하네스가 검사한 것은 "스키마가 role 루프를 통과할 수 있는 형태인가"까지이고, **실제 그래프 쓰기(노드 생성·엣지 커밋·큐 적재)는 n1~n4 구현이 있어야 한다.** 즉 이번 검증은 **계약 층위의 실행**이고, 그래프 층위의 실행은 구현 착수 후다.
 
또한 파싱 **정확도**는 재지 않았다. mock으로 품질을 재지 않는다는 원칙(CH6 6.3 규약 1)이 그대로 적용된다 — 조각 33건이 나온 것은 확인했지만 "그 33건이 옳은가"는 창작 표본으로 판정하지 않는다.
