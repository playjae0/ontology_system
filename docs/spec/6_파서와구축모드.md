# 정제본 6 · 파서와 구축 모드 — 내부 구조, 어댑터, 등록 워크플로우, 검수 뷰, 전달물

> **소유**: 파서 내부 3단 구조, 어댑터 인터페이스(expects·preflight·기본 어댑터·투입 분류), 구조 지도 패스, doc_type 등록 워크플로우(입력 패키지·절차·검수 뷰), 전달물 경계(공용 코어·생성 킷).
> **경계**: 파서 출력 계약은 문서 2가 정본(이 문서는 상속 전제로 참조), 층 등록은 문서 3(3.7), 추출 단계는 문서 4. **킷·스켈레톤·검수뷰 스키마의 실물은 자산 파일이 정본이다**(kit/ — 복제하지 않는다).

## 6.1 지위와 경계

파서는 사내 실행 프로그램이고, 시스템과는 JSON으로만 만난다(문서 2의 계약 3종이 전부). **파서 내부 구현은 에이전트 호환성과 무관하다** — 이 문서가 내부를 규격화하는 이유는 호환이 아니라 **사내에서 파서를 재현·유지보수 가능하게** 하기 위함이다.

**운영 중 파서의 LLM은 세 지점뿐이다**: 이미지 요약(코어 소유) · 좌표 태깅(닫힌 목록 선택 또는 null) · **구조 지도 산출(구조 가변 prose 한정 — 지도는 데이터, 분할은 결정적 코드).** 어느 경우에도 LLM이 청크를 직접 나누지 않는다. 판단이 안 서면 추측으로 규칙을 만들지 않고 "판정 불가"로 검수 화면에 올린다. 폴백: **문서 계층 ≠ 그래프 계층** — 평면으로 읽고 좌표만 태깅해도 그래프는 성립한다(계층은 골격이 이미 보유).

## 6.2 내부 구조 — 3단 + 어댑터

```
[reader]     원본 → 원시 추출   : 포맷별(xlsx/pptx/…) — 공용, 어댑터 아님
[preflight]  실행 전 정합 검사   : 문서 지문 ↔ ADAPTER.expects 결정적 대조 — 공용
[struct-map] 구조 지도 패스      : 구조 가변 prose 한정. LLM 지도 산출(코어 소유)
                                  → 타당성 검사(결정적) → 결정적 분할기. 지도는 산출물과 함께 보존 — 공용
[adapter]    원시 → 정규 조각    : doc_type별 — LLM 생성 대상 또는 코어 기본 어댑터
[normalizer] 자기완결 보정       : 상동 해소·병합 전개·복수값/nested 분리 — 공용
[tagger]     정규 → 계약 JSON    : 공정좌표 태깅(닫힌 목록 = 골격 전 노드 스냅샷) + 봉투 + context
                                  + 이미지 placeholder의 요약 완성 — 공용
[validator]  계약 self-check     : 3층 구조·좌표 존재·자기완결·payload_kind 정합 — 공용
```

1. **포맷 의존은 reader에만, doc_type 의존은 adapter에만 격리한다.** 새 doc_type = 어댑터 하나 추가. reader·preflight·normalizer·tagger·validator는 공용 코어로 사람이 1회 작성·유지한다 — **LLM이 생성하는 것은 어댑터뿐이고, 그마저 분할 자명 계열은 기본 어댑터로 대체된다.** 공용 코어까지 생성 대상으로 넓히면 검수가 "코드 리뷰"가 되어 검수 수준(결과 뷰 승인 1클릭)이 깨진다.
2. 골격 닫힌 목록(canonical+alias)은 파서·에이전트 **공유 자산**이다 — 스냅샷 파일과 skeleton_version(문서 2 — 2.1 규약 4).
3. 원본 바이너리는 저장하지 않는다(source_path 참조만). 전 청크 보존, 청크 텍스트만 저장.
4. **reader는 두 모드에서 같은 코드다** — 운영의 원시 추출과 구축 모드(등록 세션)의 표본 관찰 재료 공급이 동일 코어의 재사용이다. 등록 세션 전용 reader는 없다.
5. **validator의 "좌표 존재"는 필드의 존재이지 닫힌 목록 대조가 아니다.** 좌표 계약은 "목록에서 선택 또는 null"이고, 목록 밖 이름의 판정은 인입 소관(orphan_anchor)이다. validator의 목록 대조는 판정이 아니라 **보고(coord_report)**로 낸다 — **파서가 좌표를 판정하면 orphan_anchor가 도달 불가능해진다**(실측: 목록 대조를 문서 실패로 걸자 한 행 때문에 문서 전체가 미인입됐다).

## 6.3 구조 지도 패스 — 구조 가변 prose

"규칙 고정 → 결정적 실행"이 성립하는 것은 구조가 안정적인 계열(table 전체·분할 자명 prose)이다. **구조 가변 prose** — 같은 doc_type 안에서 판본·작성자별로 heading pattern·목차가 다르게 관찰되는 계열(목차형·보고형 엑셀, RFQ류) — 는 같은 doc_type이어도 양식이 고정되지 않는 것이 기본값이며, 운영 인입마다 구조 지도 패스를 거친다:

```
reader 원시 추출
  → 구조 지도 패스 (LLM · 공용 코어 소유 — 어댑터 아님, 이미지 요약과 동형 배선)
      입력: 원시 추출물 + 어댑터 expects의 힌트(등록 시점 관찰 기록 — 프라이어, 강제 아님)
      출력: 구조 지도 = 데이터 {행/단락 → 헤딩 여부·레벨·제목}
  → 지도 타당성 검사 (결정적 코드 — 헤딩 0건·레벨 비단조·커버리지 이상 검출)
      실패 시: 평면 폴백 + 기존 큐(hierarchy_unresolved·parse_failure — 신설 없음)
  → 결정적 분할기 (지도 적용 → 청크·section 산출 — 공용 코어, doc_type 무관)
```

**지도 패스의 진입은 둘이다**: 계열(구조 가변 prose)이 기본이고, **분할 자명 계열의 「단일 거대 프레임」이 두 번째 진입**이다(§6.4-5 ②의 2차 패스 — 문서 1 C13이 I6-④의 재사용으로 둔 자리다). 근거: 진입을 계열 하나로만 적으면 임계를 넘은 PPT 슬라이드가 어느 규정으로 지도 패스를 타는지가 문서로 답해지지 않는다.

**분할 레벨 선택 — 지도가 서면 어디서 자를지는 코드가 정한다**(B43). 지도는 행마다 헤딩 여부와 레벨을 줄 뿐이고, **모든 헤딩에서 자르면 분할이 문서의 목차 세밀도에 종속된다** — 헤딩이 촘촘한 문서는 한두 줄짜리 청크가 수십 개 나와 근거로 쓸모가 없고(수집 상한 8을 잡아먹는다) 성긴 문서는 거대 청크 하나가 되어 잘림·저해상도를 낳는다. 그래서 **자를 레벨을 크기로 고른다**: 지도를 받은 뒤 레벨 1..N 각각에 대해 「그 레벨에서 자르면 청크가 몇 개이고 각각 몇 행인가」를 계산하고, **목표 구간에 가장 많이 드는 레벨**을 고른다. 목표 구간의 값은 구현 소유이며 측정 후 조정한다(P7) — 명세는 산식이 아니라 **선택이 있어야 한다는 것과 그 선택이 결정적이어야 한다는 것**을 정한다. 고른 레벨과 근거(레벨별 청크 수·행 수 분포)는 **지도에 함께 보존한다** — 보존하지 않으면 같은 지도가 다른 분할을 낳을 수 있어 「같은 지도 → 같은 분할 → 같은 chunk_id」가 깨지고, 「왜 이렇게 잘렸나」의 기록도 사라진다. 고른 레벨에서도 목표 상한을 크게 넘는 청크는 **그 아래 레벨로 한 단계만 더 쪼갠다**(재귀하지 않는다 — 깊이를 열면 세밀도 종속이 되돌아온다). **이 선택은 LLM이 하지 않는다** — 레벨별 크기 분포는 지도만 있으면 결정적으로 계산되며, 여기에 모델을 부르면 같은 문서가 인입마다 다르게 잘린다.

**두 분할 경로의 차이는 「레벨이 있느냐」가 아니라 「언제 정하느냐」다**(B45 정정). 두 경로 모두 레벨 정보를 갖는다 — 지도 경로는 지도가, 어댑터 경로는 분할 신호 상수(번호 패턴 등)가 준다. 다른 것은 **결정 시점**이다: 구조 가변 prose는 문서마다 세밀도가 달라 **인입마다 고르고**(B43), 분할 자명 prose는 양식이 고정이라 **등록 때 한 번 정한다.** 그 결정을 담는 자리는 `expects`의 **판단 상수**다(§6.4-4가 「분할 임계 등」으로 이미 그 자리를 정했다 — preflight 대조 대상이 아닌 쪽이다). **등록 때 분할 크기 분포를 보고 레벨을 골라 상수로 박고, 운영은 그 상수대로 결정적으로 자른다** — 매 문서 모델을 부르지 않으므로 「구조 안정 계열은 규칙 고정 → 결정적 실행」이 유지된다. 근거: 분포를 보지 않고 「전 헤딩에서 자른다」를 기본값으로 두면 분할이 문서의 목차 세밀도에 종속되고, 그 병은 지도 경로와 같다(실측 — 참조 어댑터 표본에서 11청크 전부가 목표 구간 미만이었다). **상수를 고치는 경로는 어댑터 개정(구축 모드 재진입)이다.**

**분할 크기 분포는 두 경로 모두 검수 뷰에 보인다**(B45) — 청크 수·행 수(최소·최대·평균)·**목표 구간 밖을 짧은 쪽과 긴 쪽으로 갈라** 보인다(처방이 다르다: 짧으면 분할 신호가 과하고 길면 모자라다). 지도 경로는 고른 레벨과 레벨별 분포를 함께 싣는다. 이 화면이 **등록 시점에 상수를 고를 판단 재료**다 — 없으면 부적절한 상수가 드러나는 자리가 없다.

**section에서 좌표를 파생한다**(B43). 산문 청크의 `section`(헤딩 경로)이 골격의 이름·alias와 일치하면 그 값을 조각의 좌표 필드로 세운다 — **일치는 좌표 태깅과 같은 정확 일치 대조이고 추론하지 않는다**(문서 7 §7.1 — 파서는 좌표를 판정하지 않는다). 경로에 여러 헤딩이 있으면 **가장 깊은(구체적인) 일치**를 쓰고, 일치가 없으면 좌표를 비운 채 둔다(인입이 orphan으로 받는다). 근거: 산문에는 좌표 열이 없어 어댑터가 채울 자리가 없고, 그 결과 산문 청크가 공정에 붙는 통로가 없다 — 문서의 목차가 곧 좌표인 계열(공정별 절로 나뉜 RFQ·기술문서)에서 이 파생이 유일한 연결이다. **section 문자열을 파싱해 좌표를 지어내지 않는다** — 대조에 실패한 것은 실패로 남긴다.

불변인 것: **어댑터는 여전히 doc_type당 1개·등록 1회**(매 문서 새로 나오는 것은 지도=데이터뿐) · **LLM이 청크를 직접 나누지 않는다**(지도는 보존된다 — 같은 지도 → 같은 분할 → 같은 chunk_id, "왜 이렇게 잘렸나"의 기록) · **내용 파악은 추출 단계**(지도가 읽는 것은 형태이지 의미가 아니다) · 검수 1회 · 운영 무인 · 어댑터 순수성(LLM 호출은 코어 소유). 힌트 프라이어 확신 매치 시 지도 패스 생략은 측정 후(P7).

**보존 자리와 재사용** — **지도는 `extract/struct_maps/{doc_id}.json`에 보존한다. 같은 doc_id의 재인입은 `source_hash`가 같으면 보존분을 그대로 재사용하고 새로 산출하지 않으며, `source_hash`가 바뀌면 추출 체크포인트와 함께 무효화·재생성한다**(문서 4 §4.8-8과 같은 손잡이). **재사용 판정에 쓰는 것은 `doc_hash`가 아니라 `source_hash`다** — `source_hash`는 **원본 파일 바이트의 해시로 파서가 계산하고 보존 파일에 함께 싣는다.** `doc_hash`(문서 2 §2.4 — 정규화된 내용의 해시)는 **에이전트 소유**여서 파싱 시점에 아직 없고(C7: 파서는 정본 id를 만들지 않는다), 진입 검증은 파서가 하지 않는다(문서 2 §2.7-①: 파서는 다른 문서의 존재를 알 필요가 없다). 두 값을 같은 이름으로 부르면 한쪽 구현이 다른 쪽 값을 쓰게 되고, 정규화 전후가 달라 재사용 판정이 어긋난다. **보존 파일의 내부 형태**: 문서당 파일 하나이고 그 안에서 프레임 키로 가른다(`{"source_hash": …, "maps": {프레임 키: 지도}}`) — 어댑터의 지도 훅은 **프레임마다** 불리므로 통째로 저장하면 프레임이 섞인다(2A P-D 실측 · D-94). **보존 자리는 클린 범위(`data/` + `extract/` — 문서 7 §7.6-4) 안이다** — 밖에 두면 클린 2회 동일 그래프가 1회차 지도를 물고 통과해, 멱등성의 전면 검증이 거짓 통과한다. USE_MOCK=1에서는 지도가 고정 파일(`mock/struct_maps/` — 문서 7 §7.1)이라 보존 없이도 멱등성이 통과하므로, mock만으로는 이 결함이 드러나지 않는다(문서 7 §7.6-B가 경계한 자리).

**이미지 요약(= 이미지 페이지 청크의 `text`)도 같은 규칙을 탄다** — 지도와 함께 보존하고 재인입 때 재사용한다. 근거: 매 인입 새로 부르면 text가 흔들려 그 문서의 chunk_id가 전량 이동한다(chunk_id 결정성 — 문서 7 §7.2).

## 6.4 어댑터 인터페이스

어댑터는 doc_type당 1모듈 — **선언 1개(ADAPTER) + 함수 1개(extract)**. 배치는 `adapters/{doc_type}.py` 경로 규약을 따른다: 실물은 각자 파일로 살고, 목록·버전의 한눈 파악은 등록부가 담당한다 — 등록 확정이 registry 등재(어댑터·매칭 스키마 활성)로 끝난다 — 근거: 실물과 별개로 목록·버전을 답하는 곳이 등록부 하나여야 하기 때문이다.

```python
ADAPTER = {
  "doc_type": "…", "adapter_version": "…",   # 개정 시 사람이 수동 증가 — 봉투에 1회
  "payload_kind": "table",                    # "table" | "prose" — 닫힌 2값
  "expects": {                                # 관찰 상수 = 이 어댑터가 기대하는 양식의 지문
    "header_row": …,
    "header_labels": […],   # 원본 헤더 문자열의 순서 배열 — preflight 표류 감지의 지문. table 필수
    "columns": {…},          # {출력 필드명: 열문자}
    # 분할 자명 prose: 분할 신호 상수 / 구조 가변 prose: 힌트(프라이어 — 강제 아님)
    # 판단 상수(분할 임계 등)도 여기 산다 — 지문과 달리 preflight 대조 대상이 아니다(규약 4)

def extract(raw, struct_map_fn=None) -> list[dict]:   # 조각마다 source_locator 포함
    ...   # struct_map_fn = 코어가 주입하는 지도 함수. 어댑터가 LLM을 직접 부르지 않는
          # 유일한 통로다(규약 2·5) — 인터페이스에 없으면 주입 자리가 구현마다 갈린다
```

1. **함수는 extract 하나다 — locate를 두지 않는다.** 위치는 추출 순회 중에만 자명하고, "조각→위치" 역산은 같은 내용이 2회 출현하는 순간 모호해진다. 전처리 훅도 두지 않는다 — 시트 선택·헤더 정리는 extract 내부 사유이며, 인터페이스에 올리면 LLM 생성·검수 표면적만 는다.
2. **어댑터는 순수 함수다**: 파일 밖 상태·네트워크·**LLM 호출 금지.** 같은 입력 → 같은 출력이어야 운영이 결정적이고 리허설이 성립한다.
3. **이미지는 placeholder 조각으로 낸다**(`{source_locator, image_ref, section?}`) — 요약 LLM 호출은 공용 코어(tagger 단) 소유. 어댑터 안에 LLM 호출이 있으면 순수성이 깨지고 검수가 "코드가 맞나"에서 "호출이 잘 되나"로 번진다.
4. **관찰 상수는 expects에 데이터로 분리한다.** 용도 셋: ①검수 뷰가 코드 전문 대신 이것을 보여준다 ②preflight의 대조 기준 ③LLM 생성 시 채울 빈칸(스켈레톤). **expects는 두 종류를 담는다 — preflight 대조 대상인 「양식 지문」(header_row·header_labels·분할 신호 상수 등)과 대조 대상이 아닌 「판단 상수」(분할 임계 등 — 규약 5).** 근거: 구분이 없으면 preflight가 expects 전체를 지문으로 읽어, 임계값 하나 조정한 어댑터가 멀쩡한 문서를 adapter_mismatch로 중단시킨다.
5. **기본 어댑터 — 분할 자명은 조건부다.** 분할이 자명한 계열(PPT 등)은 코어 제공 고정 기본 어댑터를 등록 시 그대로 붙인다 — LLM 생성은 관찰이 실제로 필요한 양식에만. 단 **"PPT = 슬라이드 1장 = 청크 1개"는 임계 이하에서만 참이다**: 슬라이드 텍스트량이 임계(**코어 기본 어댑터 `ADAPTER.expects`의 판단 상수** — 측정 후 조정 P7)를 넘으면 ①1차 shape 단위 분할(결정적) ②단일 거대 프레임이면 2차 구조 지도 패스 ③폴백 통청크+큐. 근거: 통청크는 출처 입도를 잃고 추출 품질을 떨어뜨린다. **이 임계를 층 config 키로 두지 않는다** — 문서 3 §3.1의 층 config 키 일람(19종) 밖이고, 판단 상수의 자리는 문서 7 §7.1이 `ADAPTER.expects`로 정하며, PPT 스키마가 두 층에 걸쳐 있어 층 config에 두면 같은 기본 어댑터가 층마다 다른 임계로 돈다. 코어 제공 기본 어댑터의 값이므로 **조정은 그 어댑터 1곳의 개정이고 doc_type별로 갈리지 않는다.** **실행 주체 — 임계 판정과 ①shape 단위 분할은 어댑터 extract 안의 결정적 연산이고, ②2차 구조 지도 패스는 코어가 주입한 지도 함수(`struct_map_fn`)를 통해서만 부른다** — 어댑터가 스스로 LLM을 부르지 않으므로 규약 2의 순수성이 유지된다: 주체가 적히지 않으면 기본 어댑터가 직접 지도 LLM을 부르는 구현이 문면상 위반이 아니게 된다. 기본 어댑터를 써도 **등록 절차(층 지정·검수·승인 1회)는 생략하지 않는다.**
6. **preflight — 실행 전 정합 검사(코어 소유).** 운영 인입에서 extract 실행 전에 문서 실물 지문(정형: 헤더 행)을 expects와 **결정적으로 대조**한다. 불일치면 실행하지 않고 **문서 중단 + adapter_mismatch 큐**(차이 내역·adapter_version 제시). 이후 판단은 사람: 어댑터 개정(구축 모드 재진입) 또는 신규 doc_type 등록. **등록 여부 조회를 대체하지 않는다** — 조회가 모드를 가르고, preflight는 운영 모드 안의 **양식 표류**를 잡는다.
   **지문 추출 규약** — 정형의 지문은 `expects.header_row` 행의 셀을 **첫 시트에서** 열 순서대로 읽어 배열로 만든다: **병합을 전개하지 않고 원본 셀을 쓰고**, 값에는 `strip()`만 적용하며(대소문자·공백·기호의 추가 정규화를 하지 않는다), **빈 셀은 배열에 넣지 않는다.** 근거: 아래 투입 분류가 「완전 일치·누락 0·잉여 0」을 **가결정이 아니라 확정**으로 못박았는데 무엇을 배열로 삼는지가 없으면 같은 파일이 구현마다 다르게 판정된다 — 병합을 전개하면 라벨이 반복되어 잉여가 생기고, 빈 셀을 남기면 열 하나 비운 판본이 누락으로 잡힌다. 이 규약은 preflight와 지문 스캔이 같은 연산을 재사용하므로 **양쪽에 같이 적용된다.**
7. **실패 계약 — 문서 단위 단일.** 계약 위반 행·어댑터 예외·validator 위반이 하나라도 있으면 **그 문서는 통째로 인입하지 않는다** + parse_failure 큐(사유·해당 행 제시). 수리 후 doc_id 재인입이 유일한 수리 경로 — 커밋 단위 = 재인입 단위 = 문서로 정렬된다. **계층 미확정(비정형)은 실패가 아니다** — 평면 폴백으로 인입되고 표시+큐만 남는다. 조각 단위 완화는 중단 빈도가 실측으로 정당화될 때만(P7).
8. **구조 가변 prose에서 어댑터는 분할하지 않는다.** 어댑터의 몫은 지도 패스 기능 선언과 힌트(등록 시점 관찰 기록) 제공까지고, 분할은 코어의 결정적 분할기가 한다. 계열 선언의 물리 표지는 expects의 형태다: 분할 자명 prose는 분할 신호 상수(등록 시 고정), 구조 가변 prose는 힌트(강제 아님) — 근거: 분할까지 어댑터 몫이 되면 어댑터 순수성(LLM 호출 코어 소유)이 깨진다.
9. **prose라고 preflight를 생략하지 않는다 — prose에도 preflight가 돈다.** 구조 가변 prose는 힌트와 별개의 지문 키(title_row·max_col 등)를 expects에 두어 대조한다. 분할 자명 prose는 분할 신호 상수가 그대로 지문이다 — 근거: 힌트는 강제가 아니므로 지문이 따로 없으면 adapter_mismatch 판정이 성립하지 않는다.
10. **자기완결 연산은 파서 공용 코어를 부른다 — 어댑터가 재구현하지 않는다.** 병합 전개·상동 치환·복수값 전개·열문자 변환은 파서 내부 공용 모듈(normalizer)의 순수 함수 호출로 구현한다. 파서 내부 호출이므로 규약 2(순수성)와 충돌하지 않는다. **어댑터 몫으로 남는 것은 「이 문서의 어느 열이 무엇인가」의 매핑뿐이다** — 그것이 등록 세션의 LLM이 판단할 전부다. 근거: 참조 어댑터 3종이 같은 로직을 각자 재구현한 상태가 실측됐다 — 재구현이 허용되면 병합 처리 결함 하나가 어댑터 수만큼 곱해지고, 공용 코어는 정의만 있고 호출부 0인 함수가 된다(정의만 있고 호출부가 0인 함수는 구현이 아니다 — 문서 7 §7.6-B-2와 같은 판정).

**투입 분류 — doc_type 지정.** 지정은 사람이 기본(투입함/선택 UI — 투입 경로가 곧 지정). 미지정 **정형** 문서만 헤더를 등록 전체 어댑터의 expects와 일괄 대조(지문 스캔 — preflight와 같은 연산의 재사용, 결정적)해 후보 제안 + **사람 1클릭 확정.** **후보 판정은 `header_labels` 완전 일치다 — 누락 0·잉여 0.** 부분 일치는 후보로 올리지 않고 **차이 내역만 제시한다.** 근거: 기준이 없으면 유사 일치·부분집합 일치까지 후보로 올라가 사람이 확정할 수 있는 후보군 자체가 구현마다 달라진다 — 이 기준은 가결정이 아니라 확정이다. 비정형은 구조 신호의 변별력이 없어 지정 필수. **유일 일치 자동 라우팅은 하지 않는다** — 오배정률이 측정된 뒤 승격 검토(P7). 지정 실수의 안전망은 preflight다.

경계: **extract는 내용을 해석하지 않는다** — 내용 파악은 추출 단계(문서 4) 소관. 어댑터가 층 어휘를 알게 되는 순간 "새 층 = config만"이 깨진다 — **층 어휘가 파서 측으로 새는 통로를 만들지 않는다.**

## 6.5 doc_type 등록 — 입력 패키지와 워크플로우

> 이 절은 **doc_type 등록**이다 — 층 등록(문서 3의 3.7)의 입력이 아니다. doc_type은 층 지정이 필수라 층 없이 존재 불가하고, 층은 doc_type 없이 존재 가능하다(seed·config만으로 성립) — 의존이 비대칭이므로 **층 등록 → doc_type 등록의 순서를 강제한다.** 신규 층과 doc_type 등록 세션이 함께 열리더라도 **확정은 층이 먼저다** — doc_type의 매칭 스키마가 층의 카테고리·config를 참조하므로 순서가 강제다. 반쪽 상태가 없다: 층만 확정되고 doc_type 등록이 실패해도 층은 유효한 산출물이다.

**입력 패키지 — 사람 4 + 시스템 5**

| 사람 | 내용 |
|---|---|
| 표본 문서 (필수) | **2부 이상 권장, 1부 허용** — 1부면 검수 뷰에 "표본 1부 · 변형 미관찰 · 선언된 관계는 근거 1건일 수 있음" 경고 필수 표시. 1부의 위험은 preflight가 사후 안전망 |
| doc_type 이름 (필수) | 기존과 중복이면 거부 — 운영 모드로 가야 한다 |
| 층 지정 (필수) | **존재하는 층만** |
| 관찰 힌트 (선택) | 자유 텍스트 — 구조화하지 않는다(Rule of Three: 반복 유형이 쌓이면 그때 항목화). **관찰 범위 규칙("몇 줄 볼 것")은 힌트가 아니라 시스템 소유** — 프롬프트 템플릿에 고정 |

| 시스템 | 내용 |
|---|---|
| reader 원시 추출 | 표본의 head N줄 — 운영 파서와 동일한 공용 reader의 재사용. LLM은 바이너리를 직접 못 읽으므로 이 공급이 관찰의 전제 |
| 골격 닫힌 목록 | 좌표 태깅·anchor 대상 스냅샷 |
| 층 어휘 | 지정 층의 카테고리 정의문·관계 목록 — **층 등록의 산출물을 doc_type 등록이 소비하는 관계**. **여기에 존재하는 층의 목록도 함께 제시한다** — 걸침 필드의 `target_layer`(문서 2 §2.5 규약 2) 판정의 전제다: 지정 층의 어휘만 주면 다른 층을 가리켜야 하는 필드에서 어떤 층이 존재하는지 제시받지 못해 판정이 막히고(실측), 걸침 필드가 무조건 스키마 헤더 layer로 폴백된다 |
| 공용 블록 | 좌표 블록 등 — 재발명 방지 |
| 어댑터 스켈레톤 | ADAPTER 선언(expects 빈칸)+extract 뼈대 — LLM은 빈칸을 채운다. **패키지에 실리는 것은 파일 본문이다 — 경로 문자열이 아니다**(B29): 경로만 실으면 생성 세션은 뼈대를 받은 적이 없어 채울 빈칸이 없고, extract 본문을 매번 새로 작문한다(실측 — 산출 구조가 등록마다 달랐다) |

**절차 (3단 워크플로우)**: **생성**(표본 관찰 → 어댑터+매칭 스키마 초안 연쇄 산출. 분할 자명 계열이면 기본 어댑터 적용 제안) → **검수**(실행 하네스 통과 → 검수 뷰 → 재생성 루프) → **확정**(승인 1회 → 등록부 등재 + 승인 기록). **확정 시 어댑터·매칭 스키마는 검수 산출 자리에서 정본 자리로 옮겨 간다 — 어댑터는 `adapters/{doc_type}.py`, 매칭 스키마는 `schemas/{doc_type}.json`이며(6.4 경로 규약) 등록부 등재가 그 활성화다.** `review/{doc_type}/`에 남는 것은 입력 패키지·뷰 데이터·정적 HTML·승인 기록이지 정본 실물이 아니다. — 이행이 적혀 있지 않으면 확정본이 검수 산출 디렉터리에 남고, 그 디렉터리는 버전 추적 대상이 아니라 재생성 시 확정된 어댑터가 함께 사라진다. 표본 크기: 정형 head 10~20줄(다단 헤더·병합 변형의 관찰이 필요하면 상단 — B34) / 비정형 10~30줄, 목차형은 계층 패턴이 2~3회 반복해 나타날 때까지 확장. 관찰 범위를 늘리면 전송이 커진다 — B30의 크기 표시가 그 감시다. **판정이 안 서면 LLM이 추측하지 않는다** — "판정 불가"로 검수 화면에 올리고 사람이 기준을 정한다.

**전송 프롬프트의 크기 — 상한은 게이트웨이 몫, 관측과 손잡이는 시스템 몫**(B30). 생성 세션의 전송량(지시문+패키지)은 주입이 늘수록 커진다(실측 — 스켈레톤 본문·전시물 주입으로 지시문 +32%). 상한 값은 명세가 정하지 않는다 — 게이트웨이·모델의 [사내 확인] 계열이다. 시스템이 지는 의무는 둘이다: ①**조립 후 전송 전에 크기를 화면에 표시한다** — 입력 초과는 응답 잘림 경고(§7.8)가 잡지 못하는 축이라(그것은 응답 쪽이다), 크기가 화면에 없으면 초과가 조용한 거부로 나타난다 ②**전시물(few-shot) 주입은 끌 수 있다** — 컨텍스트가 작은 게이트웨이에서 등록 자체가 막히는 것보다 전시물 없는 생성이 낫다. 끈 채 생성한 사실은 산출 기록에 남긴다(같은 등록의 재현 조건이다).

**열 프로파일 — 관찰은 표본이 아니라 전 행에서 센다**(B39). 등록 세션의 관찰 재료(`reader_head`)에는 앞 N줄의 원문과 함께 **전 행을 스캔해 계산한 열별 통계**가 실린다: 비지 않은 행 수 · 고유값 수 · 빈 셀 비율 · 대표값 몇 개 · 값 형태(수치+단위 비율·길이) · **좌표 열 기준 변동성**(같은 좌표 그룹 안에서 값이 변하는가). 계산은 결정적이고 LLM을 부르지 않으며, 앞 N줄이라는 창으로는 보이지 않는 사실을 공짜로 준다(실측: 30행 표본에서 규격 열 고유 29 — 행마다 고유 · 설비 열 고유 9 — 반복 · 적용모델 열 2행뿐 — 희소). **시스템 키를 늘리지 않는다** — 관찰 재료 그릇 안의 항목이다(B36과 같은 원리).

**판정의 근거는 셋뿐이다**(B39): ①열 프로파일 ②층 어휘 정의문 ③사람의 힌트·문답. **이 셋으로 뒷받침되지 않는 판정은 내지 말고 「판정 불가」로 올린다** — 자유 서술 근거를 허용하면 근거를 지어내고, 지어낸 근거 위의 배정은 검수자가 검증할 방법이 없다(문자열을 구현으로 세지 않는다와 같은 결의 규율).

**role 배정은 3단 깔때기다**(B39). ①**기계 제안**(무LLM) — 프로파일에서 명백한 것을 분류해 제안한다: 고유값 1(전 행 동일) = 문서의 속성이지 노드의 속성이 아니다 → meta · 값이 거의 없다 → 판정 보류 · 연번·페이지 계열 패턴 → UNMAPPABLE. ②**LLM 판정** — 제안을 받아 배정하되 **뒤집으려면 위 세 근거 중 하나를 인용**해야 한다(기계 제안이 판정을 대체하지 않는다 — 제안은 재료다). attribute 후보는 **중요도순으로 정렬해 내고, 확신하는 경계선을 스스로 긋는다** — 그 아래는 「판정 불가」다. **고정 개수 상한을 두지 않는다**: 문서마다 정당한 수가 다르고, 상한은 억지로 자르거나 채우는 왜곡을 만든다(추출률 임계의 실패와 같은 유형). 경계선이 그 역할을 하고 사람이 위아래로 옮긴다. ③**사람 검수** — 검수 뷰는 **기계 제안과 LLM 판정이 갈린 열**과 **경계선 부근**을 먼저 보인다. 근거: 사람이 볼 것을 줄이는 것이 이 절차의 목적이고, 전 열을 평평하게 보이면 그 목적이 달성되지 않는다(실측 — 50열 문서에서 attribute 25개가 평평하게 올라왔다).

**생성 전 문답 — 선택 단계, 종료는 사람.** 표본만으로 열 구조 판정이 서지 않는 문서(다단 헤더·열 간 상위 구조 등)는 생성 앞에 문답 라운드를 둘 수 있다. 매 라운드 LLM은 **이해 요약**(열별로 어떻게 읽겠다)과 **질문**을 내고, 사람이 답하거나 교정한다. **문답의 종료는 사람의 명시 입력만이 정한다 — LLM은 「충분히 이해했다」를 판단하지 않는다**(조항 I4: 제어 흐름은 코드와 사람 소유). 문답 전문은 관찰 힌트에 구조화되어 입력 패키지에 실린다 — 산출물의 근거가 이력으로 남는다. **관찰 힌트 그릇이 곧 「재현 조건」의 자리다**(B36): 같은 등록을 재현하는 데 필요한 생성 입력의 선택 — 문답 전문·전시물 주입 차단 여부 등 — 은 전부 이 그릇에 구조화되어 실린다. **사람 4키·시스템 5키는 불변이다** — 키를 늘리면 회귀가 세는 명세가 흔들리므로, 새 재현 조건은 키가 아니라 힌트 그릇 안의 항목으로 는다. 검수의 재생성 루프(§6.6-2)와 같은 규율이다: 상한 없음 · 중단은 사람 판단. 문답은 검수 루프를 대체하지 않는다 — 문답은 생성 전 이해 정렬이고 검수는 산출 후 확인이다. **문답 세션은 생성 지시문의 판정 어휘 구획(role 어휘·role 배정 대상이 아닌 필드·층 어휘)을 함께 받는다**(B32) — 문답의 목적이 「생성이 내릴 판정」의 사전 정렬인데 판정의 어휘를 문답이 모르면, 질문이 스키마 판정(어느 열이 anchor·entity·attribute인가)에 겨눠지지 못하고 일반 관찰에 머문다(실측 — 문답 지시문에 role 어휘 언급 0건인 채 운용됐다). 어휘의 정본은 생성 지시문 하나이고 문답은 그 구획을 **조립 시 재사용**한다 — 두 지시문에 같은 어휘를 따로 적지 않는다(미러 실패의 구조). 근거: 사후 교정만 있으면 사람은 틀린 산출을 보고서야 기준을 말하게 된다 — 판정 기준이 열 구조에 있는 문서는 그 기준을 생성 전에 물을 자리가 필요하다(실측 — 힌트 자유 텍스트만으로는 무엇을 적어야 하는지 사람이 모른다).

**검수 리허설의 범위와 비용 관문.** 검수의 리허설 파싱은 **기본이 부분이다** — 표본의 앞 N행만 파싱하고(기본값은 구현 소유), 검수 뷰에 **「부분 리허설 — 전 M행 중 앞 N행」을 필수 표시한다**(§6.6의 이상 신호와 같은 지위 — 승인 근거 화면에서 부분임이 숨겨지면 안 된다). 전량 리허설은 명시 선택이다. **리허설 중 실호출을 유발하는 보조(좌표 미스의 LLM 선택 등)는 켜기 전에 무LLM으로 발생 건수를 세어 제시하고, 사람의 동의 없이 켜지 않는다 — 기본은 끔이다**(미스를 그대로 두는 것은 오류가 아니다 — 인입의 orphan_anchor 큐로 가는 정상 경로가 있다). 근거: 좌표 보조는 미스 행마다 호출된다 — 수천 행 표본이면 동의 관문 없이 수천 회 실호출이고, 실측에서 그 대기가 「멈춤」으로 읽혔다. 이 관문은 사람↔시스템 경계다: 비용을 쓰는 결정이 화면에 오르지 않으면 사람이 결정할 것이 화면에서 증발한다.

**doc_type의 구조 — 스키마 1 + 어댑터 N(양식 변형별)**(B37·B38). doc_type이 같다는 것은 그 문서에서 파악할 내용 — 살릴 노드 정보 — 이 같다는 뜻이고, 그 동일성을 물리적으로 지는 것이 **매칭 스키마 하나**다(fields·attr_name·role이 그래프 병합 키). 어댑터는 양식→스키마 변환기이므로 **양식 변형마다 하나씩 누적 관리한다** — 개정판이 구판을 대체하는 모델이 아니다: 구양식과 신양식 문서는 동시에 존재하고(라인별 서식·과거 문서 재인입), 대체하면 남은 쪽 양식이 preflight에 다시 걸린다. 규격 넷:

1. **스키마가 정체성이다** — 전 변형 어댑터가 같은 스키마를 공유하고, 변형 등록의 하네스 ④(스키마 정합)가 그 호환을 기계로 검증한다. **fields 키·attr_name 변경은 변형 추가가 아니라 doc_type의 변경이다** — 기존 인입분과 병합 키가 갈라지므로 「판정 불가」로 사람에게 올린다.
2. **변형 어댑터의 생성은 백지가 아니라 차분이다**(B37) — 기존 변형 중 가장 가까운 것의 전문을 생성 입력에 싣고 「관찰된 차이만 고쳐라」. 검수·승인 1회는 변형마다다(검수 없는 산출물이 flow에 들어가는 일은 없다).
3. **투입 시 변형 선택은 preflight 지문이 한다** — 지문 스캔(등록 전체 어댑터의 expects 일괄 대조)이 이미 있는 메커니즘이고, 같은 doc_type의 변형들 사이에서도 같은 대조로 고른다. 완전 일치가 없거나 둘 이상이면 사람 판단(adapter_mismatch 큐).
4. 물리 배선(변형의 경로 규약 — `adapters/{doc_type}.py` 단수 규약의 확장 — 과 등록부 표현)은 구현이 정하고 보고한다. 단 **묻는 곳이 어디든 답하는 곳은 등록부 하나**라는 기존 원칙은 그대로다.

같은 양식 안에서의 교정(오타·열 위치 수정)은 변형 추가가 아니라 그 변형의 adapter_version 증가다 — 변형은 양식이 가르고, 판은 교정이 가른다.

**부트스트랩**: 기본 내장 층은 공정정보층 1개 — seed·config로 내장하며 층 등록 세션을 거치지 않는다(층 0개 상태에서 층 생성부터 하는 것을 시스템 기능으로 만들면 시작부터 꼬인다). 층 등록 기능은 신규 층 전용이다. 층 등록 도구가 미완성이어도 수동 config 작성 경로로 절차 검증은 성립한다 — 검증 대상은 도구가 아니라 config-only 구조다.

**등록부**: doc_type 등록부는 층 등록부와 **다른 장부**다(목적이 다르면 장부도 다르다). 출처는 둘이다: **내장(builtin)** = 레포가 싣고 나온 스키마 실물 · **등록(registered)** = 등록 파이프라인이 확정해 등재한 것. **같은 이름이면 등록분이 이긴다.** 이름 중복은 내장과의 충돌까지 거부한다. 묻는 곳이 셋(인입 조회[모드 판별]·preflight[지문 대조 대상]·플랫폼 노출)이어도 **답하는 곳은 하나다** — 조회처가 각자 파일 시스템을 뒤지지 않는다: 각자 뒤지면 등록된 doc_type을 인입이 모르는 상태가 생긴다. 장부가 둘이 되면 안 된다.

## 6.6 검수 뷰 규격

전제(재론 불가): 사람은 코드가 아니라 결과 뷰를 보고, 통과 = 승인 1회(클릭 수준·분 단위), 기록은 명시적, "무수정 = 자동 통과" 금지.

**3구획**: ①**파싱 결과** — 표본을 생성 어댑터로 실제 파싱한 결과 ②**배정표** — 필드→role 매핑(필드별 role·근거 한 줄 병기, 6지선다: role 5종+UNMAPPABLE. 구조 필드는 올리지 않는다) ③**어댑터 요약** — expects와 adapter_version, 코드 전문은 접힘(펼쳐볼 수는 있게).

**UNMAPPABLE 열의 복원 산식**: UNMAPPABLE 열은 어댑터가 스스로 밝힌 미매핑분에서 파생한다 — expects.header_labels(원본 헤더 전량)에서 expects.columns가 가리키지 않는 열의 **차집합**. 스키마가 unmappable을 명시하면 그쪽이 이긴다(명시는 판정이고 차집합은 복원이다). 복원분은 배정표에 UNMAPPABLE로 뜨고 이상 신호에 질문 형태로 오른다 — 이 복원을 생략하지 않는다: 생략하면 그 열은 어디에도 이름이 남지 않아 사람이 판정할 것이 판정 화면에서 증발한다.

1. **3층 표시 — 전 포맷 공통**: ①요약 통계(조각 수·필드별 채움율·실패/경고 건수) ②**이상 신호는 전량 필수 표시** — 실패 조각·"판정 불가" 질문·경고. 발췌로 숨겨지면 안 되는 것들 ③정상 조각은 발췌 기본 + 전량 접힘(table은 head N행 레코드 표, prose는 계층 트리 전체 + 청크 경계 표시). payload_kind별로 렌더만 다르고 3층 구조는 같다 — 이 화면의 목적은 "모든 행이 맞는가"가 아니라 **"규칙이 맞는가"의 확인**이다.
2. **재생성 루프 — 상한 없음.** 수정 지시 → 재생성 → 재파싱 → 재검수. **매회 수정 지시가 승인 기록에 이력으로 남고, 중단은 사람 판단이다.** 화면에는 강제 없는 안내만 둘 수 있다.
3. **물리 형태 — 데이터와 표현의 분리.** 표본 파싱이 **검수 뷰 데이터 JSON**을 먼저 내고, 렌더러가 정적 HTML로 변환한다. 플랫폼 화면은 나중에 이 JSON을 직접 읽는다 — **렌더러만 교체되고 데이터 계약은 불변.** 뷰 데이터 스키마의 실물은 킷 자산(`검수뷰_데이터스키마.json`)이 정본이다 — 산출자(등록 파이프라인)와 렌더러의 경계 계약. **렌더러는 계산하지 않는다** — 채움율·이상 신호 판정은 전부 산출자가 뷰 데이터 JSON에 채워 넣고 렌더러는 있는 값을 그린다. **렌더러가 원시 JSON에서 재계산하지 않는다.** 근거: 렌더러가 재계산하면 계약이 렌더러에 종속되고, 플랫폼이 같은 JSON을 읽을 때 화면마다 수치·판정이 갈린다.
4. **승인 기록**: `{doc_type, adapter_version, 승인자, 시점, 수정 지시 이력}` — 승인자 없이는 등재하지 않는다.
5. **"판정 불가"는 질문 형태로 표시한다**(예: "들여쓰기 2와 4가 혼재 — 어느 쪽이 하위입니까?") — 이상 신호로서 전량 표시 대상.
6. **사람이 읽는 산출 JSON(매칭 스키마·뷰 데이터)의 표기 — 잎은 한 줄로.** 더 내려갈 구조가 없는 잎 dict·list는 한 줄로 내고, 들여쓰기는 구조 계층에만 쓴다. 로드 결과는 표기와 무관해야 한다(json.load 동일). 이것은 관측 편의 규격이다 — 다르게 정해도 위계 1·2는 깨지지 않는다. 근거: 잎마다 줄을 쪼개면 스키마 파일이 3배로 늘어(실측 66줄→22줄) 검수·diff에서 구조가 잡음에 묻힌다.

이 화면은 어댑터 성능 평가가 아니다 — 등록 승인의 근거 확인이다. 정확도 측정은 골든셋·계기판(문서 5) 소관. 재생성 루프는 운영 파싱과 무관하다 — 구축 모드 안에서 표본에 대해서만 돈다.

## 6.7 전달물 경계 — 무엇을 외부가 짜서 주고, 사내는 무엇만 하는가

**반출 불가 제약이 막는 것은 "실물 문서를 보는 것"이지 "코드를 짜는 것"이 아니다.** 실물 없이 만들 수 있는 전부는 외부에서 완성해 전달하고, 사내에 남기는 것은 실물이 필요한 최소 — 어댑터 생성 실행과 검수 — 뿐이다.

| 구분 | 사내 | 외부 (전달물) |
|---|---|---|
| 실행 | 파서 전체 실행 · 어댑터 생성 세션(사내 LLM) · 검수 승인 | — |
| 코드 | **어댑터만**(사내 LLM 생성 — 분할 자명 계열은 기본 어댑터라 생성조차 불요) | **공용 코어**(reader·preflight·struct-map·normalizer·tagger·validator + 기본 어댑터) + **생성 하네스**(구축 3단의 배선 — CLI+파일) |
| 자료 | 실물 문서 표본 | **어댑터 생성 킷 6종** (아래) |

**어댑터 생성 킷 6종** (실물 정본 = kit/ 자산 — 복제하지 않는다):

| # | 구성물 | 요지 |
|---|---|---|
| 1 | 생성 프롬프트 템플릿 | 사람이 확정·버전 관리하는 자산. payload_kind 분기(prose는 fields `{}`)·header_labels 필수(table 한정)·UNMAPPABLE 출력 제외·구조 필드는 6지선다 대상 아님·**층 어휘(층 이름·존재하는 층 목록·카테고리 정의문·관계 패턴표·공용 블록 목록)와 골격 닫힌 목록은 템플릿 본문에 적지 않고 주입한다** — 층 어휘의 원천은 입력 패키지의 `layer_vocabulary`(= 지정 층의 config)이고, 골격 닫힌 목록은 **스냅샷(`skeleton_closed_list.json`)의 지정 층 몫**에서 렌더해 주입(**손표기하지 않는다** — 손표기 목록이 실물과 어긋난 사고가 근거. **층 어휘도 같다**: 코드가 `layer_vocabulary`를 이미 싣는데 템플릿이 한 층의 어휘를 본문에 적으면 **같은 사실이 두 곳에 살고 하나가 고정**이 되어, 다른 층 등록에서 템플릿과 패키지가 서로 다른 어휘를 말한다(실측: v0.4가 공정층 어휘를 본문에 담아 품질층 등록이 갈렸다). **규칙이 문면에 없으면 다음 판이 다시 적어도 검사가 못 잡는다.** **킷 유지 규칙 주석은 LLM에 보내지 않는다** — 조립 시 제거한다: 그 주석은 킷을 고치는 사람이 읽는 것이고, 보내면 제외하려던 어휘를 주석이 다시 실어 나른다. **층 자산 `layers/{층}/skeleton.json`을 읽지 않는다** — 그 파일은 `skeleton` 선언이 `source`를 쓰는 층에만 있고[문서 3 §3.1·§3.5], 골격을 선언 안에 인라인으로 둔 층에서는 가리킬 파일이 없어 렌더가 죽는다. 스냅샷은 전 층 단일이며 auto alias까지 실은 파서 공유 자산이다[문서 2 §2.1 규약 4])·context는 딕셔너리 지시·UNMAPPABLE 회피 경고·**`mirrors`는 매칭 스키마 edges에 선언하지 않는다** — build 저장 직전의 자동 규칙(config.mirrors) 소관이므로, 골격 소유 관계의 edges 선언 허용(문서 4 §4.4)은 여기까지 미치지 않는다: 금지 문면이 없으면 근거 1쌍만 관찰한 판정자가 mirrors 엣지를 선언해도 하네스 ④도 6지선다도 그것을 거를 규범이 없다(실측)·**표본이 1부면 보수적으로 선언한다 — 변형을 관찰하지 못했으므로 근거가 1건뿐인 관계는 edges에 선언하지 말고 "판정 불가"로 올린다** — 1부 경고 표시(6.5)는 사후 표시라, 사전 억제가 없으면 근거 1건짜리 엣지를 걸러내는 부담이 전부 검수자에게 남는다(preflight는 양식 표류를 잡지 근거 부족 엣지를 잡지 않는다) |
| 2 | 어댑터 스켈레톤 | ADAPTER 선언(expects 빈칸)+extract 뼈대 — LLM은 빈칸을 채운다(자유 작문보다 검수가 쉽다). 입력 패키지에 **본문으로** 실린다(§6.5 — B29) |
| 3 | 표적 출력 정의 주입 | 계약 ①(3층 구조)은 전 층 하나로 고정이므로 신규 doc_type이라도 항상 주입 가능 — 표본이 빈약해도 출력 계약이 어댑터의 형태를 고정한다. **정본은 문서 2 — 발췌+참조, 어긋나면 문서 2가 이긴다** |
| 4 | 참조 어댑터 예시 | few-shot 3종(table 2·prose 1) — **모범 전시물이다: 현행 어댑터 규약을 따르는 판을 싣고, 파일 머리에 원본(실산출 스냅샷 또는 정본 어댑터) 경로를 표기한다.** 실산출 스냅샷의 보관은 fixture 몫이며 무손질(A11)이다 — **전시물과 스냅샷은 같은 파일이 아니다**: 규약이 개정되면 전시물은 따라 바뀌고 스냅샷은 남는다. 전시물의 산출 동등은 봉인 대조로 증명한다. **전시물은 생성 프롬프트에 주입된다 — 표본의 payload_kind에 맞는 1종을 few-shot으로 싣는다**(B29): 주입 경로가 없으면 전시물을 볼 유일한 관객(생성 세션)이 관람하지 못해 few-shot이라는 이름만 남는다(실측 — 주입 코드 0건인 채 운용됐다). 근거: 한 파일이 「무손질 보관」과 「모범 전시」를 겸하면 규약 개정 때 두 역할이 배타가 된다(실측 — 판정필요-13: 규약 10 전환이 바이트 동일 어서션과 충돌) |
| 5 | 검수 뷰 렌더러 | 뷰 데이터 JSON → 정적 HTML. 사람이 코드를 읽지 않게 하는 장치이므로 킷에 포함된다. core·파서를 import하지 않는다 |
| 6 | 실행 하네스 | 생성 산출물(어댑터·스키마)을 검수 뷰 **이전에 기계가 거르는 관문** — 4단 검사: ①로드(문법·선언 형식·순수성[금지 import]) ②preflight ③extract 실행+계약 self-check ④스키마 정합(use_blocks 전개 포함)+role 루프 드라이런. **①로드 단은 규약 10도 판정한다**(B31) — 자기완결 연산의 자기 재구현(병합 전개·상동 치환·복수값 전개·열문자 변환의 자체 정의)이 있으면 거른다: 생성 산출의 규약 준수를 사람이 검수 뷰에서 눈으로 잡게 두면 기계 관문(§6.6 전제 — 사람은 코드가 아니라 결과 뷰를 본다)이 성립하지 않는다. **하네스 판정은 늘 수 있다 — 봉인이 보증하는 것은 기존 판정의 보존(사라진 판정 0 · FAIL 0)이지 판정 수의 고정이 아니다**(B31): 수를 고정하면 관문을 강화할 때마다 봉인을 다시 쓰게 되어, 봉인이 검증 장치가 아니라 개선의 비용이 된다. **호출 규격 — 진입점 `run_adapter`, 인자 순서 `<adapter.py> <schema.json> <문서…>`**: 진입점 이름과 인자 순서를 명세가 정하지 않으면 외부 구현자가 임의 진입점을 만들어, 사내가 반입받은 하네스를 무엇으로 부르는지가 문서로 답해지지 않는다(mock 자산의 자리를 경로 규약으로 못 박는 것과 같은 이유 — 문서 7 §7.5) |

1. **외부 구현 범위에 공용 코어와 킷이 포함되며, 창작 표본으로 전 과정(표본 투입→생성→검수 뷰→등록→파싱 실행)을 리허설 통과한 상태로 반입한다.**
2. **사내 작업의 정의**: "파서 구현"이 아니라 **"파서 반입 + doc_type별 어댑터 생성 세션 실행 + 검수"**다 — 코딩이 아니라 실행·승인이다. **사내에서 파서 관련 코딩을 하지 않는다.**
   그 앞에 **role 배정 실험**이 선다 — **사내 첫 작업은 코딩이 아니라 이 실험이다.** 실물 문서 2~3종(PFMEA·Control Plan 우선)의 **열 이름 전체**에 role 배정을 시도하고, 막히는 필드는 L3/L4로 판정한다 — 설계 가정 검증이자 스키마 등록 재료다. **이 실험 없이 등록 세션에 들어가지 않는다** — 배정을 미리 시험하지 않으면 L3(새 role 필요)·L4 판정이 등록 검수 화면에서 처음 터지고, 재생성 루프로는 풀리지 않는 문제가 검수 단계에서 발견되어 등록이 멈춘다.
3. 메타데이터 스키마가 "무엇을 뽑아야 하는가"를 정의하므로 **양식을 정확히 몰라도 LLM 지시가 성립한다.**
4. [사내 확인] 사내 LLM 게이트웨이의 모델·컨텍스트 제약 · 외부 코드의 반입 절차·보안 검토 · doc_type 실물 목록 · 골격 주입 경로 · context 축 실태 · 극성 표기 실태 · 이미지 요약 게이트웨이 수준 · 기존 자산의 reader 흡수 · **role 배정 실험(2항)에서 막히는 필드의 L3/L4 판정** — 확인 목록에 없으면 착수 체크리스트에서 빠져 실험 자체가 건너뛰어진다.
5. **reader 등 공용 코드의 사내 수정은 사내 포맷 불일치 시에만** 하며, **버전 기록과 외부 통보 없이 하지 않는다** — 어댑터와 달리 공용 자산이기 때문이다.
