# 정제 명세 — README (문서 지도와 사용법)

> **이 묶음은 무엇인가**: 제조 문서 → 지식 그래프 → RAG 질의 시스템의 **재구성 가능한 명세 전량**이다. 목적 시험 한 문장 — *"이 문서들만 읽고 시스템을 다시 만들 수 있는가."*
> **정본 지위**: 이 묶음이 유일한 정본이다. 정제 전 원천(챕터 13종)은 `원천_국면1/`과 레포 태그가 보존하며, **두 벌을 함께 개정하지 않는다** — 개정은 이 묶음에만 한다.

## 문서 지도 — 읽는 순서가 곧 만드는 순서다

| # | 문서 | 답하는 질문 | 분량 감각 |
|---|---|---|---|
| 0 | **기반과 원칙** | 무엇을 왜 만들고, 사람·코드·LLM은 각각 무엇을 하나 | 짧다 — 전부 읽는다 |
| 1 | **금지와 불변** (검사기) | 무엇을 절대 하지 않고, 무엇이 항상 참이어야 하나 | 조항 표 — 대조용 |
| 2 | **계약** | 파서와 에이전트는 무슨 약속으로 만나나 (출력 3종·role·스키마·L1~L4·인입 검증) | 본체 |
| 3 | **구조 — 층과 골격** | 층은 무엇이고 골격·극성·층간 연결은 어떤 규칙인가 (+층 등록 절차) | 본체 |
| 4 | **쓰기 절차** | 문서가 그래프가 되는 전 절차 (판정·게이트·큐 20종·I축·재인입) | 가장 두껍다 |
| 5 | **읽기 절차** | 질문이 근거 있는 답이 되는 절차 (+계기판·골든셋) | 본체 |
| 6 | **파서와 구축 모드** | 파서 내부·어댑터·등록 워크플로우·검수 뷰·전달물 경계 | 본체 |
| 7 | **구현 규격과 검증** | 코드 배치·id 산식·구현 단위·시나리오 15종·완료판정·산출물 표 | 본체 |
| 부록 | **용어** | 모든 용어의 단일 정의처 | 사전 — 찾아 읽는다 |

**위계 (충돌 시)**: 문서 1(금지와 불변) > 본문 문서 0·2~7 > 부록. 같은 사실은 한 문서에만 살고 나머지는 참조한다 — 두 문서가 다르게 말하면 그 자체가 결함 신호이며, 소유 문서를 고치고 참조를 맞춘다.

**실물 자산 (이 묶음이 가리키기만 하는 것 — 복제 금지)**: 골격 seed·층 config(`layers/`) · 매칭 스키마·공용 블록(`schemas/`) · 어댑터 생성 킷(`kit/` — 킷 6종: 생성 프롬프트 템플릿·어댑터 스켈레톤·표적 출력 정의 주입·참조 어댑터 예시·검수 뷰 렌더러·실행 하네스. 봉인 정답표는 킷 구성물이 아니라 kit/에 동거하는 채점 자산 — 소유는 원천 보존본의 raw_mock 대장) · mock 제작 지침(원천 보존본의 raw_mock 대장).

## 서술 규격 (전 문서 공통)

- **태그**: 본문 규칙은 전부 확정이다. `[사내 확인]` = 실물·실명칭이 필요해 비워 둔 슬롯(사내 이식 국면이 채운다). `미결 R#` = 의도된 이연 — 트리거가 오기 전에 풀지 않는다(문서 0의 등록부).
- **부정형 문면**: 금지 규칙은 "X하지 않는다" 꼴로 통일한다 — `않는다`로 grep하면 금지 전수가 나온다(감사 가능성).
- **근거 1줄 원칙**: 규칙마다 왜가 한 줄 붙는다. 이유 없는 규칙은 다음 사람이 지운다 — 근거가 사라진 채 규칙만 남아 있으면 그것도 결함 신호다.
- **역참조**: 각 문서 말미의 「이 문서가 지키는 불변·금지」가 문서 1의 해당 그룹을 가리킨다 — 문서를 고치기 전에 그 목록을 먼저 연다.
- **용어**: 부록 등재어만 무설명 사용. 새 단어는 부록 등록이 먼저다.

## 재구성 절차 (요약 — 상세는 문서 7)

1. 문서 0→1을 읽고, 2~7을 순서대로 읽는다.
2. mock을 먼저 만든다(제작 지침은 원천 보존본의 raw_mock 대장·시나리오 정의는 문서 7) — **새로 만든 mock의 수치(큐 기준선 등)는 이전 구현과 달라진다. 기준선을 다시 세우는 것이 정상이다.**
3. 골격 seed·config(실물 자산)를 그대로 심는다 — Tier1은 창작 대상이 아니다.
4. 구현 단위 10종(문서 7)을 순서 원칙 5에 따라 만들고, 단위마다 배정 시나리오로 판정한다.
5. **완료판정**: 시나리오 15종 전부 + 기존 단위의 완료판정 전부 유효 + config-only 확증 + 클린 2회 동일 그래프(문서 7). **이 판정은 mock 위에서 메커니즘이 도는 것까지다** — 실 연결(문서 7 §7.6-B)은 판정 밖이므로 따로 확인한다.
6. 판단이 갈리는 지점은 결정 장부(DECISIONS)에서 같은 지점의 과거 판정을 먼저 찾는다 — 장부는 원천 보존본에 있다.

## 개정 규칙

- 개정은 판정 후 소유 문서 1곳에만 반영하고, 참조 문서는 참조만 맞춘다.
- 문서 1의 조항을 깨는 개정은 조항의 개정을 먼저 판정한다 — 본문이 조항을 조용히 우회하지 않는다.
- 국면·일정·진행 상태는 이 묶음에 쓰지 않는다 — 운영 기록(장부·진행 문서)의 몫이다.
- **모든 개정은 개정 대장에 [복원]·[개정]·[정정] 중 하나로 근거와 함께 등재한다** — [복원]은 원천 좌표, [개정]은 결정 장부 번호를 근거로 단다: 근거 없는 변경이 쌓이면 "정제본이 원천과 다른 이유"를 되짚을 수 없게 되어 원천 보존이 무의미해진다.
- **개정은 회귀 스위트(조항 대조·판정 재현·문면 기계 점검)를 통과해야 확정된다** — 사람이 "괜찮아 보인다"고 판단하는 자리를 두지 않는다: 읽기로만 검증된 개정이 쌓이면 이 묶음이 조용히 망가진다.
- **패치가 아니라 재작성이 필요한 때를 기준으로 정한다**: ①한 문서의 개정이 그 문서의 절 구조를 바꿔야 할 때 ②같은 절에 성격이 다른 규범이 세 겹 이상 쌓여 소유 경계가 흐려질 때 ③개정 대장의 [정정]이 [복원]을 넘어설 때 — 셋 중 하나면 그 문서를 다시 쓰고, 아니면 패치로 간다. 기준이 없으면 매번 감으로 판단하게 되고, 재작성은 대규모 옮기기라 **옮기면 샌다**(실측된 실패 유형).
- **정본을 다른 문서군으로 옮길 때는 승계 대조표 없이 옮기지 않는다** — 옛 정본의 규범을 전수 추출해 새 정본에서 하나씩 찾아 승계 여부를 판정한 표가 있어야 한다: 대조 없이 옮기면 옛 정본에만 있던 규범이 조용히 사라지고, 그 손실은 구현이 한참 진행된 뒤에야 드러난다(실측된 실패 유형 — 이 규칙이 없어서 실 연결 규격이 통째로 유실됐다).
