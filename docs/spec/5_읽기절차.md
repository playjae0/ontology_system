# 정제본 5 · 읽기 절차 — 질의(RAG), 계기판, 골든셋

> **소유**: 질의 4단 파이프라인, 이원 근거 채널과 답변 3단, 질문 유형표, 이연 항목과 벡터 대비, 계기판 8종과 골든셋.
> **경계**: 질의는 읽기 전용이다(P6). LLM은 마지막 답변 생성 한 곳에만 있다. 순서 파생·골격 규칙의 정본은 문서 3이다.

---

## 5.1 질의 4단 파이프라인

```
질문 → ①링킹 → ②확장 → ③수집 → ④답변(LLM)
```

시스템(코드)이 그래프 연결성으로 근거를 고르고, LLM은 받은 근거를 읽고 문장으로 답한다. **LLM은 그래프를 직접 읽지 않는다.**

1. **①링킹**: 질문 속 표기 → 그래프 노드. **사전 스캔 우선**(무LLM·긴 표면형 우선 매칭) → 미스 시 LLM 폴백 → 3단은 임베딩 검색 훅(이연 — 5.4). 단일 진입점 라우터가 전역 링킹 후 층별 질의를 호출한다.
2. **질의는 읽기 전용이다(P6).** 질문에 나온 표기를 사전에 배우지 않는다 — 사용자 입력은 비검증이라 사전을 오염시킬 수 있다.
3. **극성 링킹은 넓게**: 극성 제거 표면형이 양 극성 노드를 가리키면 읽기는 양쪽 다 링킹한다(쓰기는 좁게 — 문서 4와 대칭). 극성 무관 표면형은 개념 노드에 링킹되고 part_of 하향이 인스턴스를 포함한다.
4. **②확장**: config의 query_traverse 스펙대로만 뻗는다. 공정층: part_of 하향 재귀·상향 1홉, has_property 양방향 1홉. 품질층: causes·affects 양방향 1홉. cross(occurs_in·controlled_by): **1홉·비재귀·양방향 브리지.** `precedes`는 확장에서 제외한다(순서는 그래프 사실 채널과 flow 특례가 담당). `mirrors`는 기본 확장에 없다(비대칭 조회 시에만 명시 확장 — 훅). **스펙의 형식은 관계별 `{direction: "out|in|both", recursive: bool}` dict다** — core의 `neighbors(ids, traverse_spec)`가 이 dict를 **인자로** 받고 내용은 config가 소유한다(B) — 형식이 명세에 없으면 config 키 구조를 구현자가 발명하게 되고, 자산으로 인계된 층 config와 core 순회기의 형식이 어긋나면 명시적 실패가 부팅부터 상시 발동한다.
5. **확장은 프론티어 전파다**: 새로 발견된 노드에도 관계 규칙이 적용된다. `recursive: false`는 "같은 관계를 연달아 재추적하지 않음"일 뿐, 다른 관계로 도달한 노드에의 적용은 막지 않는다 — 공정→(part_of 하향)→설비→(has_property)→인자 2홉이 성립하는 근거. 방문 집합으로 순환을 방지한다. **확장 범위는 홉 수 상한이 아니다** — 범위는 관계별 규칙(재귀 여부·방향)의 조합으로 정해지며, part_of 하향은 재귀이므로 3홉 이상도 정상이다. **전역 홉 상한으로 확장을 자르지 않는다** — 홉으로 자르면 깊은 트리의 하위 노드가 근거에서 통째로 빠지고, 그 손실은 수집 상한이 아니라 확장에서 사라지므로 잘림률 계기판에도 잡히지 않는다.
6. **③수집**: 2-tier(직접 링킹 노드의 근거 > 확장 노드의 근거), **상한 8**, 최신순. 초과분은 바깥부터 잘리고 **잘림은 로그로 남긴다**(계기판 재료).
7. **④답변**: 이원 근거 채널(5.2)을 받아 생성. **근거에 없는 것은 모른다고 답한다.**
8. **순서 파생**: 순서 질문에서 링킹 노드에 precedes 선언이 없으면 부모로 올라가 대표 흐름을 찾고, 후속 노드에 동일 polarity 인스턴스가 있으면 하강해 답한다(없으면 개념 노드 — 공유 스텝 합류 자동). 조상까지 선언이 없으면 **"순서 정보 없음"으로 답한다 — 추측하지 않는다.** **파생 답은 해상도를 표기한다**(예: "(탭용접 기준) 다음 공정은 패키징" — 인스턴스 질문에 개념 해상도로 답하는 경우의 오해 방지). 결정적 연산이며 traverse 스펙(config 소유)의 일부다. 규칙 정본은 문서 3(3.9-⑸).

경계: **넓은 질의는 층별 요약으로 받는다** — "노칭 관련 전부"류는 전부 긁지 않고 층별 건수 요약을 제시해 좁히게 한다(허브 폭증의 질의 측 방어). **확장 규칙은 전부 config 소유다** — 층이 늘어도 질의 코드는 불변. **precedes가 답하는 것은 대표 흐름이다** — 공장·세대별 실제 라우팅은 그래프에 없다(R13 이연).

## 5.2 이원 근거 채널과 답변 3단

1. **채널 1 — [그래프 사실]**: 링킹·확장 노드의 엣지와 값을 config의 fact_templates로 문장화한다. 예: "노칭 다음 공정은 스태킹이다", "노칭::노칭 정밀도의 규격: ±0.1mm (출처: CP01)". 맥락형 값은 context 그룹별 한 줄. cross 브리지 엣지는 가리키는 층의 템플릿을 쓴다. **fact_templates의 키 규약**: 관계 문장화는 관계 이름을 키로 쓰고(part_of·precedes·has_property·mirrors), 값(attribute) 문장화는 `attr:{attr_name}`을 키로 쓰며, 값 템플릿은 출처 자리 `{prov}`를 포함한다 — 예: `"attr:spec": "{node}의 규격: {value} (출처: {prov})"`. 값의 문장화 키 규약이 없으면 Q4(값 조회형)의 렌더를 관계 템플릿 표에 둘지 별도 표에 둘지가 구현자마다 갈리고, 출처 자리 규약이 없으면 규격 문장이 출처 없이 구현된다(템플릿 문안 자체는 층 config가 소유한다). **[그래프 사실] 채널은 답변 LLM이 질문 관련성으로 필터한다** — 노이즈는 채널 분리로 통제한다: 그래프 사실은 관련성 필터, 청크는 tier2 잘림(5.1-6). 필터가 없으면 브리지로 딸려온 cross 사실과 part_of 하향 재귀로 모인 노드의 엣지·값이 전부 문장화되어 프롬프트에 실리므로 허브 노드 질의에서 답변 컨텍스트가 무제한으로 부풀고, 청크 쪽만 상한 8로 막혀 있어 잘림률 계기판에도 잡히지 않는다. **순서·규격 정보는 이 채널에만 있다** — 청크 단채널이면 "노칭 다음은?"에 답하지 못한다.
2. **채널 2 — [문서 근거]**: 수집된 청크 원문(청크 id·문서·섹션 표기). 서술형 질문의 답. **이 채널이 노드에서 원본으로 돌아가는 길이다** — provenance가 청크를 가리키고, 청크는 원문 무손실 + source_locator를 갖는다. 답변에는 출처가 표기된다. 원본 바이너리는 저장하지 않으며(source_path 참조) 근거 제공 단위는 청크다.
3. **답변 3단**: 근거 있음 → 근거 기반 답 + 출처, 근거 밖 내용은 "모른다" / 근거 없음 → "사내 문서에서 근거를 찾지 못했다"를 먼저 밝히고 **[일반지식 — 사내 검증 필요]** 표시와 함께 일반지식 답 + **등록 개체 안내**(그래프에 등록된 인접 개체를 함께 제시해 재질문을 유도) / 링킹 미스 → 로그 축적(하이브리드 도입 판정 데이터). 안내가 없으면 근거 없음 답변이 막다른 골목이 된다 — 사용자가 무엇을 물어야 걸리는지 모른 채 같은 미스를 반복하고, 링킹 미스율(계기판 5)이 실제 어휘 부재가 아니라 사용자 표현 미숙으로 오염되어 하이브리드 도입 판정을 흐린다.
4. **flow 특례**: "전체 공정 흐름"류는 골격 트리+precedes 체인을 통째로 근거에 공급한다(얇은 골격이라 저비용). 공급 단위는 **개념 노드 레벨 대표 흐름**이다.
5. **답변 프롬프트는 두 채널을 구분해 쓰게 한다**: [그래프 사실]은 시스템이 보증하는 구조 정보, [문서 근거]는 서술 정보다 — 한 덩어리 컨텍스트로 붙이면 답변 LLM이 둘을 동급으로 섞어, 구조·값 질문에서 청크의 옛 서술이 그래프 사실을 덮어쓴 답이 나오고 출처 등급이 뭉개진다.

## 5.3 질문 유형 대응표

질문이 요구하는 정보의 소재지는 네 곳뿐이다(엣지 / 노드 필드 / 청크 / 그래프 밖) — 아래 표는 그 기준의 **전수 열거**이며, 유형표의 완전성 근거가 여기에 있다. 예시 목록으로 읽히면 새 유형이 임의로 덧붙고 Q6·Q7의 범위 밖 판정이 재론되며, 골든셋 구성(유형당 15문항)의 완전성 근거도 함께 사라진다.

| # | 유형 | 예 | 답의 소재 | 지원 |
|---|---|---|---|---|
| Q1 | 개체 서술형 | "노칭 프레스 금형 관리 어떻게?" | 청크 | 지원 |
| Q2 | 구조 조회형 | "노칭 다음은?" | 엣지 | 지원 |
| Q3 | 전역 구조형 | "전체 공정 흐름" | 엣지 전체 (flow 특례) | 지원 |
| Q4 | 값 조회형 | "노칭 정밀도 규격?" | 노드 필드 | 지원 |
| Q5 | 역방향/필터형 | "클리어런스 관리하는 설비는?" | 역방향 엣지·cross 브리지 | 지원 — 양방향 확장 + **답변 LLM 필터**(규모가 커지면 코드 필터) |
| Q6 | 개체 없는 열린 질문 | "수율 올리려면 뭘 봐야?" | 청크 (개체 경유 불가) | **훅만** — 링킹 미스율이 정당화하면 하이브리드 도입 |
| Q7 | 집계/분석형 | "관리인자 최다 공정은?" | 그래프 연산 | **범위 밖** — 플랫폼 대시보드 소관, 사내 빈출 시 승격 검토 |
| Q8 | 그래프 밖 지식 | "노칭이 영어로?" | 없음 | 지원 — [일반지식] 표시로 |

이 표가 골든셋 설계의 뼈대다. **PoC 질의 범위 = Q1~Q5·Q8.** **질의 스모크의 채점 필드 `expected_path`(닫힌 4값 — 문서 7 §7.6)는 이 「답의 소재」 열의 축약이다**: 청크(Q1) → `chunk` · 엣지·노드 필드(Q2~Q5) → `graph_fact` · 두 채널이 함께 근거가 되는 문항 → `both` · 그래프 밖(Q8) → `general_knowledge`. 대응이 적혀 있지 않으면 문항 작성자가 소재 열과 채점 값을 별개 축으로 해석해 같은 유형의 문항이 서로 다른 채널로 채점된다. Q5의 후보 좁히기 주체를 못 박아 두는 이유: 주체가 미정이면 확장 결과 전량이 답변으로 넘어가 수집 상한 8에서 잘리거나(오답), 코드 필터를 임의 구현해 config 밖 층 어휘가 코드에 들어간다.

## 5.4 이연 항목과 벡터 대비

**이연은 "훅 + 트리거 + 준비물"의 세트다(P7).** 훅 없이 이연하면 도입 때 구조를 뜯고, 트리거 없이 이연하면 영원히 미루거나 감으로 도입한다.

| 기능 | 현재 | 도입 트리거 | 준비된 것 |
|---|---|---|---|
| 하이브리드 서치 (링킹 실패 시 청크 임베딩 검색) | 링킹 3단 훅만 | 링킹 미스율 | 전 청크 보존(계약) · 물리 사다리: numpy → faiss → 전용 벡터DB |
| 랭킹 고도화 | 최신순뿐 | 청크 잘림률 | 2-tier 수집 구조 |
| 그래프 사실 채널의 상한·우선순위 | 미규정 (채널 분리 필터만 — 5.2-1) | 사실 문장 길이 · 잘림률 | 채널 분리 |
| 판정 에이전트화 (어려운 판정에 읽기 전용 도구) | 단발 판정 | 판정 보류율 · **판정 정확도** (효과는 "수정 큐로 가는 건수 감소"로 측정) | 범위가 판정 1지점+읽기 전용이라 오염 불가 — **판정 에이전트에 읽기 전용 외의 권한을 주지 않는다** |
| Q7 집계 | 플랫폼 소관 | 사내 빈출 | 질의 이연 목록 |
| 맥락 크로스 필터 ("M2 라인만") | 노드별 맥락 값 표시는 됨 | 질의 수요 | 저장이 이미 맥락형 |
| 라우팅 표현 (공장·세대별 실제 순서 — R13) | 대표 흐름만 | 공장별 흐름 질의 실수요 | 골격 id 불변·전 청크 보존으로 이연 안전 |
| 저장 계층 전환 (R10) | GraphStore 경계만 | 계기판 7·8번 알람선(200MB/30초) | 경계 뒤 교체라 파이프라인 무수정 |

두 칸의 근거. **그래프 사실 채널의 상한·우선순위는 미규정이며 계기판(잘림률·사실 문장 길이) 관찰 후 조정한다(P7)** — 수집 상한 8과 잘림률(계기판 4)은 청크 전용이라, 이 채널을 이연으로 등록해 두지 않으면 상한을 감으로 도입하거나 영원히 미룬다(이 절 첫 문단이 경고한 상태 그대로다). **판정 에이전트화의 도입은 보류율·판정 정확도를 측정한 뒤 한다(P7)** — 보류율 단일 지표로만 판정하면, 보류율이 낮아도 오판정(틀린 매칭이 조용히 통과)이 많은 상태가 계기판에 잡히지 않아 구현자가 정확도를 재는 장치를 아예 만들지 않는다.

**벡터 대비 — 되돌릴 수 없는 것만 고정.** 임베딩 인덱스는 진실에서 재생성 가능한 파생물이다(P5) — 모델·리트리버·융합·랭킹은 되돌릴 수 있으므로 측정 후 정한다(미결 R6). 지금 고정된 것은 넷뿐:

1. **청크 id 안정성** — 결정적 id(산식은 문서 7). 재적재마다 id가 바뀌면 인덱스 전량 무효.
2. **전 청크 보존** — 링킹 0건 청크도 보존. 인덱싱할 원본이 없으면 하이브리드를 켤 수 없다.
3. **원문 무손실 보존** — 정규화·요약본은 별도 필드, 원문을 덮지 않는다.
4. **어댑터 버전 기록** — 분할 규칙 변경은 이후 문서에만 적용, 기존 문서 재파싱 없음.

판정용 임베딩(노드)은 비저장, 청크 인덱스는 재생성 캐시 — 임베딩 2종을 구분한다.

**질의 이연 목록 — 저장은 하되 질의 대상 승격은 명세 확정 후 별도 논의.** 목록을 실물로 두는 이유: 두 곳(문서 1 F16 · 위 표 Q7 행)이 이 목록을 참조한다 — 목록이 없으면 참조가 갈 곳이 없고, 승격 후보를 일괄 검토할 때 후보를 처음부터 다시 모아야 한다.

- **is_cc 등 구조체 내부 값** — 저장 전용(문서 1 F16 · 문서 4).
- **RPN 인자(발생도·검출도 등)** — "심각도 N 이상" 류 필터 질의. 등재해 두지 않으면 이 질의가 왜 지금 안 되는지가 Q7 범위 밖 판정과 연결되지 않은 채 되풀이 질문으로 돌아온다.
- **자재** — 별도 층 후보(미결 R5 — 문서 0).
- **Q7 집계·분석** — 플랫폼 대시보드 소관, 사내 빈출 시 승격 검토(5.3).
- **맥락 크로스 노드 필터** — 위 표 참조(노드별 맥락 값 표시는 이연이 아니다 — 지금 된다).

## 5.5 계기판과 골든셋

**계기판 8종 (P7의 실행 장치 — 각 지표가 이연 기능의 도입 여부를 판정한다)**

| # | 지표 | 무엇을 말하나 | 연결된 결정 |
|---|---|---|---|
| 1 | 링킹 recall (골든셋 기반) | 질문이 노드에 잘 걸리는가 | 품질 기준선 |
| 2 | plateau (문서별 신규 개체율 수렴) | 층 구축이 끝났는가 | 층 완료 선언·다음 층 착수 |
| 3 | 판정 보류율 (큐 유입률) | 판정이 얼마나 막히는가 | 판정 에이전트화 도입 |
| 4 | 청크 잘림률 | 근거가 상한에서 얼마나 잘리는가 | 랭킹 고도화 도입 |
| 5 | 링킹 미스율 | 질문이 그래프 밖으로 얼마나 나가는가 | 하이브리드 도입 |
| 6 | 허브 노드 차수 | 공정 허브에 유형이 얼마나 몰리는가 | 경유 규칙 점검·층 설계 |
| 7 | graph 저장 크기 (층별 최대 파일) | 저장 계층의 한계 접근 | **알람선 200MB → 저장 전환(R10) 판정 개시** |
| 8 | build 소요 시간 | 쓰기 비용의 직접 관측 | **알람선 30초 → 동상** |

7·8은 질의 품질이 아니라 저장 계층의 운영 지표다 — 계기판에 두는 이유는 "지표가 도입을 판정한다"는 정의에 부합하기 때문이다.

**산식과 측정 규율**

1. **recall류의 분모 — 골든셋이 서기 전까지**: 골든셋이 서기 전에는 recall류(링킹 성공률·미스율·잘림률)를 mock 스모크 12문항 분모로 계산한다 — 골든셋은 실물 문항의 장치라 그 전에는 recall의 데이터 기준이 없다. 골든셋이 서면 recall류 분모를 골든셋으로 교체한다. **mock 계기판은 메커니즘 검증이지 품질 측정이 아니다.**
2. **plateau 산식**: 문서별 신규 개체율 — provenance 첫 locator 기준, seed 제외.
3. **보류율 산식**: 큐 건수 ÷ 그래프·청크에 발자국을 남긴 조각 수. **분모의 한계를 산식에 명시해 둔다** — 어디에도 발자국이 없는 조각은 계수 밖이다.
4. **측정 중에는 운영 로그(link_miss)를 적재하지 않는다(끈다)** — 측정이 재료 로그를 오염시키면 다음 측정이 자기 흔적을 센다.
5. **계기판을 build·query 경로에 심지 않는다** — 별도 호출로만 계산한다(측정이 자기 자신을 오염시키지 않게).

**골든셋**

1. 질문 유형표(5.3)가 뼈대다. 실데이터 문항은 사내 진입 후. [사내 확인] 실물 문항 제작.
2. **기준 구성**: 지원 유형(Q1~Q5·Q8) 유형당 15문항(=90 — recall 차이 ~7%p를 변별하는 최소 수준) + 무답 문항 10(환각 검증 — "사내 근거 없음" 선언) + 멀티홉 10(프론티어 전파·cross 브리지) + 범위 밖 확인 10(링킹 미스율 재료) = **기준 120, 허용 100~150.** 실물 문항을 만들며 조정한다 — 골든셋·계기판은 파이프라인 밖의 측정 장치라 이 절만 수정해도 다른 곳이 흔들리지 않는다.
3. **BM-25 상시 대조군**: 같은 골든셋을 BM-25(키워드 검색 — 전 청크 인덱스, 그래프·임베딩 없음)로 병행 채점한다. 근거: ①모든 도입 판정이 "무엇 대비"를 요구한다 — **대조군 없는 점수는 인상이지 측정이 아니다** ②"일반 검색으로 되지 않느냐"는 사내 질문에 대한 데이터 답변(Q2~Q5 구조·값 조회의 격차가 이 시스템의 존재 증명) ③비용 사실상 0 — 전 청크 보존이 이미 계약이라 인덱스 재료가 준비돼 있다.

경계: **골든셋은 파이프라인이 아니다** — 없어도 인입·질의는 돌고, 규모·구성 수정은 이 절 하나의 개정으로 끝난다. **BM-25 대조군 ≠ 하이브리드 서치** — 대조군은 시스템 밖의 비교 기준, 하이브리드는 시스템 안의 확장 기능이다.

**플랫폼 노출(관측)**: 플랫폼 노출 목록에는 ops_log 열람(I축 연산 이력 — 5요소 표시)과 툼스톤 계수(층별 merged_into·obsolete 건수)가 포함된다 — 툼스톤은 그래프 안에 남는 산출물이라 계수가 없으면 수정 이력의 규모를 화면에서 볼 수 없다. 읽기 전용 관측이며 **그래프·큐에 쓰지 않는다.**
