## 7.1 코드 배치

```
ontology/
├── core/       처리 코드 — 전 층 공용, 층 어휘 0 (A)
├── layers/     층별 폴더 — {층}/config.json + {층}/skeleton.json(seed) — 코드 0 (B)
├── schemas/    doc_type별 매칭 스키마 + 공용 블록(blocks.json)
├── parser/     파서 공용 코어 6종 + 기본 어댑터
├── kit/        어댑터 생성 킷 6종 — 외부 전달물
├── cli/        플랫폼·질의·I축·스캔 CLI
├── tests/      회귀 스위트 (시나리오의 기계 번역)
├── mock/       mock 자산 — adapters/·fixtures/·extract_hints/·struct_maps/·
│               parsed/·queries.json (경로 규약은 7.5)
├── router.py   층 폴더 자동 발견 (등록 배선 없음)
├── run.py      파이프라인 진입점 — init[--fresh]/build/query/test/status/all
└── data/       진실 (생성물 — 버전 추적하지 않는다: 의미 축 id가 실행마다 달라
                추적하면 diff 잡음이 실제 변경을 덮는다. 미추적의 사유는 재생성
                가능이 아니다 — 사전·큐의 사람 판단 기록·승인 기록은 재생성되지 않는다)
```

**관리 자산의 원칙**: 판단·성능에 영향을 주는 자산은 **코드 안에 박지 않고 자산별 지정 파일**로 둔다 — 층 어휘는 `layers/{층}/config.json`, 매칭 스키마는 `schemas/`, 프롬프트는 프롬프트 파일(사람 확정 관리 자산·prompt_version), 어댑터 판단 상수는 `ADAPTER.expects`, USE_MOCK 문형 규칙 표는 층 config의 `extract_patterns`(관계 이름은 층 어휘다 — 코드는 정규식이 구문이라는 것만 안다). 목록·버전의 한눈 파악은 등록부가 담당한다.

- **공유 자원은 전 층 단일이다**: 동의어 사전, 청크 저장소, 수정 큐. 층 간 표면형 충돌은 사전이 허용하고 호출자가 카테고리·층으로 선별한다.
- **USE_MOCK=1(기본)에서 외부 의존(LLM·임베딩) 없이 전체가 동작해야 한다.** 에이전트 코어는 외부 패키지 필수 의존 0(orjson은 표준 json 폴백으로 원칙 보존) — 문서 포맷 패키지(openpyxl·python-pptx 등)는 파서 패키지에만 허용한다. **선택 의존(문서 포맷 패키지·모델 클라이언트)은 지연 import로 격리하고, USE_MOCK=1 경로에서 그 패키지를 import하지 않는다 — 검증 가능한 조건으로 둔다** — "요구하지 않는다"까지만 두면 모듈 최상단 import가 문면상 위반이 아니게 되어, 패키지 미설치 환경에서 USE_MOCK=1 전체 실행이 ImportError로 죽고 "외부 의존 없이 전체가 동작한다"가 실측으로 깨진다(7.6-B가 경계하는 실 연결 비대칭의 거울상이다).

  USE_MOCK=1(기본)에서 외부 의존 지점은 다음으로 대체된다 — **결정성이 우선이다**(mock 목적은 메커니즘 검증 한정 — 7.5):

  | 외부 의존 지점 | USE_MOCK 대체 |
  |---|---|
  | 개체 판정 | 문자열 정규화 규칙 — 공백 제거 후 동일/포함이면 match(점수 0.95), 그 외 신규 |
  | 임베딩 | sha256 해시 → 정규화 벡터 |
  | 추출 | `mock/extract_hints/{doc_id}.json` 힌트 파일 우선 + 문형 규칙(`extract_patterns` 정규식) 폴백 |
  | 등록 생성(어댑터·매칭 스키마의 LLM 생성) | fixture 반환 — fixture는 외부 LLM 실산출의 스냅샷이며 사람이 작성·손질하지 않는다; 재생성 지시 시 `_rev1` 대안본으로 루프 배선을 검증한다 |
  | 이미지 요약 | 고정 문자열 `MOCK 요약: {image_ref}` + `meta.image_summary=true` |
  | 구조 지도 | 번호 패턴 휴리스틱(결정적). 고정 지도가 필요한 시험은 `ask=`로 직접 주입한다 — **운영 코드가 fixture 파일을 찾지 않는다**(B48: 미리 놓은 정답을 돌려주는 갈래는 배선 없이도 초록이라 결함을 가린다) |
  | 좌표 태깅 | 닫힌 목록 스냅샷(`skeleton_closed_list.json`)의 canonical·alias **정확 일치 대조**. 목록 밖이면 값을 고치지 않고 그대로 두어 인입의 orphan_anchor에 맡긴다 — 대체가 선언되지 않은 LLM 지점은 USE_MOCK=1에서 실호출로 흘러 외부 의존 0(문서 1 B12)이 깨지고, 미설치 환경에서 실행 자체가 죽는다 |
  | 답변 생성 | 두 채널을 정형 텍스트로 나열 — 문장 생성 없음 |
  | 질의 링킹의 LLM 폴백 | **폴백을 두지 않는다** — 사전 스캔 미스는 그대로 링킹 미스로 `link_miss`에 적재한다(계기판 5의 재료 — 문서 5 §5.5). 문자열 포함·유사도 같은 임의 대체를 만들지 않는다 — 임의 대체는 미스가 아닌 값을 계기판에 실어 하이브리드 도입 판정(P7)이 자기 구현에 의존하게 만들고, 12문항 스모크의 `expected_path` 채점(7.6)을 구현마다 다르게 만든다. 1단 사전 스캔은 애초에 무LLM이라 대체 대상이 아니다 |
- **저장 계층 — GraphStore 경계**: 그래프 저장 접근은 core/graph.py(GraphStore) 경유로만 — **graph.py 밖의 코드(run·cli·테스트·파생물 포함)가 graph.json을 직접 열지 않는다.** 저장은 층별 단일 JSON 유지. **저장 쓰기는 파일 락과 원자적 쓰기(tmp+rename)로 한다 — 이는 성능의 선반영(P7 — 측정 없는 구조 선반영 금지)이 아니라 정합성 요구다**: 직렬 실행(7.3-3③)이 호출부의 약속으로만 존재하고 저장 측 방어가 0이면, 호출부가 계약을 어기거나 build가 쓰기 도중 죽었을 때 graph.json이 반쯤 쓰인 채 남는다 — data/는 백업 대상이지 재생성 대상이 아니므로(7.7·7.8) 진실이 복구 불가로 유실된다. **원자성 단위는 파일 하나이며 다중 파일 트랜잭션을 두지 않는다** — 한 문서의 인입이 두 층 그래프·사전·청크·큐를 함께 바꾸지만 그 묶음의 원자성은 보증하지 않는다: 묶음 원자성을 약속하면 스테이징·저널이 얹혀 저장 아키텍처가 P3(코어 최소·안정)·P7(측정 없는 구조 선반영 금지)을 넘어 커진다. **저장 단계의 실패는 문서 6 §6.4-7의 문서 단위 실패 계약 대상이 아니다**(그쪽은 계약 위반 행·어댑터 예외·validator 위반 셋을 다룬다). 부분 저장 상태의 정본 수리 경로는 **그 doc_id 재인입**이며(문서 4 §4.8-1의 회수→재적재가 층과 공유 자원을 모두 덮는다 — 회수 범위는 층을 제한하지 않는다), 어긋남을 찾는 상시 점검은 두지 않는다 — 수리 경로가 이미 있는데 상시 대조를 얹으면 매 빌드 비용이 붙고 그 대조가 발견해도 할 일은 같은 재인입이다. **알람선 = 층별 최대 파일 200MB 또는 build 30초**(계기판 7·8번) — 도달 시 저장 전환(R10) 판정 개시. P1의 "파일"은 "DB 서버 없이 원천 복원 가능"이다.
- **런타임 전제**: Python 3.10+ · 표준 라이브러리 우선(json·hashlib·dataclasses·pathlib·argparse·logging) — "외부 패키지 필수 의존 0"이 어느 바닥 위에서 성립하는지의 기준선이 없으면 재현 환경이 임의가 되고, 표준 모듈로 되는 일에 서드파티를 쓰는 이탈을 규범으로 막지 못한다.
- **패키지화**: `core/`·`layers/`·`cli/`에 `__init__.py`를 두고, import는 절대경로, 실행은 프로젝트 루트에서 `python -m cli.{진입점} …` 형태다 — 상대 import나 sys.path 조작으로 붙이면 CLI가 실행 위치에 의존하게 되어 7.3-3①("subprocess로 호출 가능한 CLI+파일")이 호출부의 작업 디렉터리에 따라 깨진다.
- **플랫폼이 subprocess로 부르는 진입점·서브커맨드·플래그는 계약이다**: **파싱 `python -m cli.parse run <어댑터.py> <doc_id> <문서> <출력.json>`** — 출력 경로는 인자이며 운영 산출 자리는 `parsed/{doc_id}.json`이다(7.8) · **구축 `python run.py build <parsed.json …>`** — 계약 JSON 파일 경로를 인자로 받는다 · 추출 `python -m cli.extract <parsed.json>` · 지문 스캔 `python -m cli.scan <문서>` · 플랫폼 관측 `platform ops` · 등록부 조회 `platform doctypes`(둘 다 진입점 `cli.platform` + 서브커맨드이며 **형태는 위 「패키지화」의 일반형 `python -m cli.platform ops`를 따른다**) · **I축 전 연산에 `--actor` 필수**(행위자 없는 연산 거부 — 문서 4 §4.7-4 — 의 플래그 형태). **진입점 표기를 일반형 밖의 파일 경로 호출(`python cli/scan.py`)로 적지 않는다** — 문자 그대로 부르면 절대 import가 깨져 「CLI+파일」 결합(7.3-3①)이 호출부의 작업 디렉터리에 의존한다. **`build`만 `run.py` 서브커맨드인 것은 의도다** — 파이프라인 진입점은 단계 CLI가 아니라 위 코드 배치의 `run.py`(init/build/query/test/status/all)이고, 같은 이름을 `cli/`에도 두면 부르는 쪽이 두 진입점 중 하나를 고르게 되어 계약이 둘로 갈린다. 파싱·구축 두 줄이 없으면 정형이 유일하게 지나는 파서↔에이전트 경계에만 진입점 계약이 비어, 형제 경계 둘(`extract/`·`review/`)과 대칭이 깨진다. **같은 기능을 다른 이름으로 제공하지 않는다** — 플랫폼↔파이프라인 결합이 "CLI+파일"(7.3-3①)이라 명령 이름이 계약의 일부인데, 일반형(`python -m cli.{진입점}`)만 두면 기능은 있어도 외부 호출 스크립트와 호환되지 않는다.
- **골격 심기 모듈의 자리는 `core/skeleton.py`다** — 층 config의 `skeleton` 키(type·relations)를 읽어 seed의 중첩→child 관계, 자식 배열 순서→sibling 관계를 파생하는 코드가 여기 산다(파생 규칙의 규범 소유는 문서 3 §3.9-⑴/⑵이며, core는 관계 이름을 가정하지 않는다). 자리가 지정되지 않으면 파생이 loader·인입 코드에 흩어져 관계 이름을 config에서 받는 통로가 지점마다 갈리고, 층 어휘 0(A)이 조용히 깨진다.

**core 접근 경계 — 단일 진입 모듈 5종**: 자산에 파일과 의미론만 있고 관문이 없으면 호출부마다 제 규칙으로 붙는다. GraphStore와 동형으로, 아래 다섯은 각자의 모듈 경유로만 접근한다.

| 모듈 | 노출 | 규약 — 근거 |
|---|---|---|
| `core/graph.py` (GraphStore) | `for_layer(layer)` · `add_node(canonical, category, status, attrs, provenance, aliases=None, **derived) → id` · `add_edge(src, rel, dst, status, provenance)` · `neighbors(ids, traverse_spec)` · `save` · `load` | **의미 축 id(ULID, 7.2) 발급은 이 모듈이 소유한다** — 발급이 노드 생성 경로마다 흩어지면 P4(발급 후 불변)를 강제할 단일 지점이 없고, 걸침 필드가 두 층에 쓸 때 발급 관리가 호출부로 내려간다. **`add_edge`는 중복 (src,rel,dst)를 새로 쌓지 않고 무시하며(provenance는 합집합), `status="deleted_by_user"` 툼스톤인 (src,rel,dst)-by-id는 건너뛴다** — 툼스톤 검사를 재인입 경로에만 두면 다른 문서가 같은 엣지를 주장할 때 사람의 삭제 판단이 조용히 뒤집히고(문서 4), 중복 무시가 없으면 같은 엣지가 provenance만 달리해 여러 벌 쌓여 병합의 엣지 이설과 허브 차수 계기판의 전제가 깨진다. **층별 저장 경로의 조립도 이 모듈이 소유한다 — `GraphStore.for_layer(layer)`가 경로를 정하고 호출부가 경로를 만들지 않는다**: 저장 경계는 파일을 여는 코드뿐 아니라 **저장 위치를 아는 코드**까지이며, 경로 소유가 지정되지 않으면 호출부가 `GraphStore(path)`를 조립하게 되어 걸침층 저장 배선과 테스트가 호환되지 않는다. **`add_node`의 호출 계약은 `add_node(canonical, category, status, attrs, provenance, aliases=None, **derived) → id`이며 layer 인자를 받지 않는다 — 인스턴스가 이미 층을 안다**: 노출을 이름만으로 열거하면 인자 형태를 구현자가 정한다. `derived`는 코드가 파생하는 노드 최상위 필드(`polarity`·`tier` — 7.2)이며, 통로가 없으면 파생 필드를 실을 자리가 `attrs`밖에 없어 문서 3 §3.9-⑻이 막은 attrs 우회가 호출 계약 쪽에서 열린다 |
| `core/dictionary.py` | `register` · `lookup(표면형) → 후보 id 목록` | **전 층 공유 동의어 사전 접근은 이 모듈 경유로만 한다** — graph.json에는 접근 경계(문서 1 B6)가 있는데 영속 지식(P4)인 dictionary.json에 없으면, 등재 시 provenance 필수·매칭 시에만 누적·재인입의 사전 엔트리 보존(문서 4)을 강제할 관문이 없어 노드 증식 결함의 재발 경로가 코드 배치 수준에서 열린다 |
| `core/matcher.py` | `match(surface, candidates, category)` | **개체 판정은 이 함수 하나로 수렴한다** — 문서 4가 attach_to 해소·orphan 재시도·병합 후보 세 곳에서 판정 파이프라인 재사용을 요구하는데 재사용 대상의 소재가 없으면 지점마다 별도 판정 코드가 생겨, 카테고리 불일치 안전망·극성 후보 제외·생존 판정(is_live) 필터가 한 곳에만 적용된다 |
| `core/registry.py` | doc_type 등록부 조회 | **doc_type 등록부의 유일한 조회처이며 세 소비자(인입의 스키마 로드·preflight 지문 스캔·플랫폼 노출 `platform doctypes`)가 전부 이 모듈을 부른다. 층 등록부와는 다른 장부다**(장부 구분의 규범 소유는 문서 6) — 논리("묻는 곳은 셋, 답하는 곳은 하나")만 두면 소비자마다 각자 JSON을 읽거나 별도 helper를 만들어, 등록 직후 인입·preflight·플랫폼이 같은 답을 보는지가 구현에 맡겨진다 |
| `core/store.py` (수정 큐·청크 저장소·공유 대장) | `enqueue(kind, reason, doc_id, payload)` · `drop(kind, match)` · `read` · `write` | **수정 큐는 파서 공용 코어와 에이전트 두 프로세스가 함께 쓰는 유일한 공유 상태다**(문서 2 §2.7 — 파서 측이 parse_failure·adapter_mismatch·hierarchy_unresolved를 직접 착지시킨다). **접근은 이 모듈 경유로만 하고, 쓰기는 GraphStore와 동형으로 파일 락 + 원자적 쓰기(tmp+rename)로 한다** — 관문이 없으면 dedup·우선순위 정렬·회수 규칙을 두 프로세스가 각자 구현하고, 락이 없으면 동시 read-modify-write가 항목을 조용히 잃는다(G5 — 실패를 조용히 버리지 않는다). 큐 항목의 형태와 kind별 payload 구성, dedup 키는 문서 4 §4.7이 소유한다 |

## 7.2 두 축 id — 산식의 소유처

| 축 | 대상 | 방식 |
|---|---|---|
| **의미 축** (Process·Unit·Property·Failure …) | 발급 — 발급 후 불변(P4). 개명·alias가 있는 축이라 해시 불가 | **ULID** — 중앙 카운터 없이 유일·시간순 정렬·내용 무관. **id에 의미(공정·순서·유형)를 담지 않는다** — 소속·순서는 그래프가, 사람이 읽을 이름은 canonical이 담당한다 |
| **근거 축** (문서·청크·레코드) | 내용에서 계산 — "불변"이 아니라 "결정적" | 아래 산식 |

```
doc_id    = 파서 봉투 부여 (해시 아님 — 재인입 단위, 개정 구분은 revision)
chunk_id  = f"{doc_id}:{sha256(norm(text) + '\x00' + section + '\x00' + str(occ))[:12]}"
record_id = f"{doc_id}:{sha256(norm(join(field_values, '\x1f')) + '\x00' + str(occ))[:12]}"
occ       = 그 문서 내 동일 (section, norm(text)) 조합의 출현 순번 (0부터)
```

- **table의 content 필드 청크는 위 해시 산식으로 id를 발급하지 않고 `{record_id}-{필드명}`으로 파생한다**(입도 규칙과 규범 서술의 소유는 문서 2 §2.4-④·문서 1 D8) — 위 `chunk_id` 산식은 **prose 청크 전용**이고, table 청크에서는 `section`이 산식 성분으로 들어가지 않는다. 파생으로 두는 이유: 재인입에서 같은 값이 다시 나오고 어느 record의 어느 열에서 온 청크인지가 id에 남는다. 산식 소유가 이 절인데 이 예외가 여기 없으면, 문서 7만 읽고 재구성한 구현이 table 청크에도 해시를 돌려 문서 2와 다른 id를 내고 재인입 회수가 옛 청크를 찾지 못한다.
- **계산 주체는 에이전트다** — 파서가 내는 것은 doc_id와 source_locator뿐(문서 2). 멱등성의 근거를 사내 파서 구현에 위임하지 않는다.
- `norm()` = 연속 공백 정리 + 앞뒤 공백 제거까지만. **원문은 정규화 없이 그대로 저장한다** — 정규화는 해시 계산에만 쓴다.
- 구분자(`\x00`·`\x1f`) 필수. **문서 내 위치(seq)는 해시 입력에 넣지 않는다** — 앞에 한 문단만 추가돼도 뒤의 모든 id가 바뀐다. **충돌 접미(`#2`)를 쓰지 않는다** — "어느 것이 두 번째인가"를 처리 순서가 정하게 되어 병렬·재실행에서 id가 뒤바뀐다. occ는 반복 횟수만 세므로 순서 무관이다.
- **record_id의 join 순서는 매칭 스키마 fields 선언 순서다** — 순서가 산식의 일부다.
- **join 대상은 매칭 스키마가 `fields`에 선언한 필드뿐이며 `use_blocks` 전개분은 넣지 않는다**(선언 순서도 그 범위 안의 순서다) — 넣으면 `common_core`의 `source_locator`가 해시 입력이 되어 위 구분자 불릿의 "문서 내 위치는 해시 입력에 넣지 않는다"(문서 2 §2.7-②와 같은 규범)가 정면으로 깨지고, `process_coord`의 좌표가 바뀔 때마다 같은 행의 id가 갈린다.
- **레코드의 `occ`는 (section, norm(text))가 아니라 join된 값 문자열의 그 문서 내 출현 순번이다**(0부터) — 레코드에는 section도 text도 없으므로 청크용 정의가 그대로 적용되지 않는다. 값이 완전히 같은 두 행은 occ 0·1로 갈리며, occ는 반복 횟수만 세므로 처리 순서와 무관하다.
- **`section`은 헤딩 경로를 `" > "`(공백·꺾쇠·공백)로 이어 구성한다** — 표기도 산식의 일부다: `section`은 chunk_id의 해시 입력 성분인데 이음 문자가 어댑터·분할기 구현마다 갈리면 같은 문서가 다른 chunk_id를 낳아 재인입 멱등성이 깨진다.
- 절단 12자는 문서 스코프 내 유일성용. **계산된 id가 이미 존재하면 조용히 덮어쓰지 않고 결함으로 로그한다.**
- doc_hash(문서 전체 해시)는 인입 진입에서 에이전트가 계산·대조한다(청크 해시의 부산물 — 추가 비용 0).
- **판정용 임베딩은 저장하지 않는다**(재계산 파생물). 청크 인덱스는 재생성 캐시.

**저장 레코드 스키마 — graph.json·chunks.json의 형태**: 두 축 id가 실리는 그릇이다. 형태를 규정하지 않으면 아래 규범들이 코드 구조 차원에서 우회된다.

```
graph.json  = { "nodes": { "<node_id>": {노드 레코드}, … }, "edges": [ {엣지 레코드}, … ] }

노드 레코드 = { id, canonical, category, layer, status,
               polarity?, tier?,
               attrs:      { "<attr_name>": [ 값 항목, … ] },
               aliases:    [ {surface, provenance: […]}, … ],
               provenance: […],
               (툼스톤 시) merged_into·target·at / replaced_by·obsoleted_at·obsolete_reason }
엣지 레코드 = { src, rel, dst, status, provenance: […] }

chunks.json = { "chunks": { "<chunk_id>": {doc_id, text, section, source_locator,
                                           parsed_at, meta, adapter_version, linked} },
                "describes": [ {chunk_id, node_id}, … ] }

review_queue.json = [ {큐 항목}, … ]
큐 항목 = { kind, reason, doc_id, payload, created,
           resolution?: {actor, at, decision, note} }
```

- **`polarity`·`tier`는 `attrs`가 아니라 노드 최상위 파생 필드다** — `polarity`는 닫힌 4값(`cathode`|`anode`|`none`|`unbound`), `tier`는 `main`|`sub`|`detail`이며 골격 유래 노드 한정이다(둘 다 값 어휘와 파생 규칙의 소유는 문서 3 §3.9-⑺⑻, 사용 제한은 문서 1 B7). 직렬화에서 떨어지면 mirrors 자동 페어링·순서 파생·이중 결합 방지·process_group 파생이 전부 canonical 문자열 파싱으로 되돌아가 "코드는 canonical을 파싱하지 않는다"(문서 4 §4.5)와 문서 1 C10의 금지를 정면으로 깬다. `attrs` 안에 넣으면 문서 3 §3.9-⑻이 막은 attrs 우회가 저장 형태에서 열린다.
- **툼스톤 필드는 노드 레코드가 그대로 보유한다** — 삭제하지 않고 남기는 표식이므로(문서 4 §4.7 I2·I4) 자리가 형태에 없으면 구현이 별도 파일이나 `attrs`에 실어, 생존 판정(is_live)과 전이 추적이 노드 레코드 하나를 보고 끝나지 않는다.
- **위 열거는 규범이 걸린 필드의 최소 집합이며, 구현 내부 파생 필드를 금지하지 않는다** — 최소 집합임을 적지 않으면 열거 밖 필드를 규범 위반으로 읽어 캐시·인덱스용 파생 필드를 두지 못하고, 반대로 열거를 전부로 읽으면 위 규범들이 걸린 필드가 선택 사항이 된다.
- **alias는 문자열이 아니라 `{surface, provenance}` 항목이다** — 문자열 배열로 저장하면 alias별 provenance가 사라져, 자동 생성물에 provenance 예외를 두지 않는 규범(문서 1 G2)과 병합의 "canonical·alias도 provenance와 함께 alias로 이관"·재인입 회수(문서 4)가 실행 불가능해진다.
- **`attrs`는 attr_name별 값 항목의 리스트를 담는 컨테이너다** — 값 항목 자체의 형태(단순형 `{value, provenance}` · 맥락형 `{context, value, provenance}`)는 문서 2가 소유한다. 스칼라 하나로 구현하면 맥락이 다른 두 번째 값이 덮어쓰기가 되어 "덮어쓰지 않는다"(문서 4)를 코드 구조 차원에서 위반하고, 컨테이너가 없으면 병합의 "attribute는 context 그룹별 합침"이 대상을 못 찾는다.
- **엣지는 배열에 `{src, rel, dst}` 키로 담는다. 문서 유래가 아닌 엣지의 provenance도 비워 두지 않는다** — 코드가 규칙으로 만든 엣지는 `auto:{규칙명}`(예: `auto:mirror_rule`), 골격 seed 유래는 `seed`로 표기한다. 비우면 provenance가 0이 된 auto 엣지를 걷는 점검(문서 4)이 그 엣지 전량을 매 빌드 evidence_lost 큐에 적재한다.
- **describes는 그래프 엣지가 아니라 청크 저장소가 갖는 목록이다** — 엣지로 넣으면 링킹 0건 청크 보존(문서 2)과 허브 노드 차수 계기판(문서 5)이 청크 연결로 오염되고, 재인입 회수 단위("청크·describes" — 문서 4)가 두 저장소에 걸쳐 원자성을 잃는다.
- **청크 레코드는 `linked`(링킹 여부)와 `adapter_version`(어느 어댑터 판이 만든 청크인가)을 함께 갖는다** — 없으면 재인입 회수가 무엇을 걷는지가 형태 없이 남는다.
- **청크 레코드는 조각의 `source_locator`를 그대로 보유한다** — 재인입 회수 세 집합의 둘째("기존 청크의 source_locator" — 문서 4 §4.8-2①)와 [문서 근거] 채널의 원본 좌표 복귀(문서 5 §5.2)가 이 필드를 입력으로 쓴다. 빠지면 두 규범이 읽을 필드가 없어 실행 불가가 된다.
- **`parsed_at`은 봉투 값을 청크 저장 시 에이전트가 복사해 붙인다**(`adapter_version`과 동형 — 문서 2 §2.2) — 수집의 "최신순"(문서 5 §5.1-6)이 정렬할 축이 이 필드다. 시간 축이 없으면 구현이 파일 mtime·describes 삽입 순서를 발명해 상한 8이 무작위 축에서 잘린다.
- **table 유래 청크의 `section`은 그 레코드의 `source_locator`를 적고 필드명은 `meta.field`에 싣는다** — `section`은 payload 구조 필드이고 payload가 `chunks[]`인 prose에만 실리므로(문서 2 §2.2 — table payload는 `records[]`다) table 레코드에는 이 값이 없으나 청크 레코드는 이 칸을 요구한다. table 청크의 id는 section을 해시 성분으로 쓰지 않으므로(위 산식 예외) 이 값은 표시·조회용이며, 규정하지 않으면 구현마다 빈 문자열·필드명·행 번호로 갈려 열람 창구가 문서마다 다른 것을 보여준다.
- **큐 항목의 `resolution`이 있는 항목이 「사람의 판단이 기록된 항목」이며 재인입 회수에서 보존한다**(문서 4 §4.8-2③·문서 1 H6). 없으면 미확인 후보이므로 회수 후 재생성한다 — 표시 필드가 없으면 회수가 kind 화이트리스트로 대신하게 되는데, 그것은 "재검출되지 않는 상시 목록"이지 "사람이 판단한 항목"이 아니어서 사람의 판정이 조용히 지워진다. 항목의 5키 형태와 kind별 payload 구성, dedup 키는 문서 4 §4.7이 소유한다.
- **빈 상태(init 직후)의 형태**: `graph.json={"nodes":{},"edges":[]}` · `dictionary.json={}` · `chunks.json={"chunks":{},"describes":[]}` · `review_queue.json=[]` — 클린을 "파일 없음"으로 둘지 "빈 파일"로 둘지가 갈리면 클린 2회 동일 판정(7.6-4)의 대조 단위가 갈린다. **`doc_types.json`은 클린이 건드리지 않는다**(7.6-4의 예외) — 층 등록부 `registry.json`·문서 대장 `doc_registry.json`은 빈 객체 `{}`로 초기화되며, 전자는 부트스트랩이 매 실행 재생성한다.

## 7.3 파이프라인 형상 — 3단계와 두 모드

1. **운영 모드는 3단계다**: 파싱 → 추출(비정형만) → 구축. **각 단계는 CLI 진입점 + 파일 입출력**이고, 단계 산출물(계약 JSON·추출 후보 JSON)은 체크포인트다 — 구축 재실행이 추출을 다시 돌리지 않는다.

   **인입 검증 3단(①doc_hash ②근거 축 id 계산 ③필드 검증 — 정본은 문서 2 §2.7)은 파서 산출물을 처음 받는 에이전트 단계의 진입부에서 1회 돈다 — 비정형은 추출 단계, 정형은 구축 단계다.** 청크·레코드 id는 그 시점에 확정되어 청크 저장소에 착지하며, **뒤 단계는 다시 계산하지 않고 `source_locator`로 조회한다** — 산식은 7.2 한 곳에만 살고, 두 지점에서 계산하면 같은 조각이 두 id를 얻어 재인입 멱등성이 깨진다. 따라서 **파싱과 추출 사이에 별도 단계 경계 산출물을 두지 않는다**(7.8의 3종이 전부다): 추출의 CLI 입력은 계약 JSON 하나이고, 추출이 그 진입부에서 인입 검증을 돌리므로 추출 체크포인트(문서 4 §4.10)의 `chunk_id`를 채울 수 있다. 중복 문서 차단(①)과 미등록 doc_type 차단이 비싼 추출보다 먼저 도는 것도 이 배치가 보장한다(문서 2 §2.7 — 체크포인트에 아무것도 쓰지 않는다). 배치가 적히지 않으면 추출이 chunk_id를 어디서 얻는지가 문서로 답해지지 않아, 구현이 산식을 두 지점에 복제하거나 파싱↔추출 사이에 4번째 산출물을 발명한다.
2. **구축 모드는 3단 워크플로우다**: 생성(LLM) → 검수(사람) → 확정(등록). **코드 레벨에서 세 단계가 분리**되어야 화면이 붙는다.
3. **플랫폼화 인지 계약 3**: ①모든 단계는 subprocess로 호출 가능한 CLI+파일 ②**파이프라인은 그래프를 직접 수정하지 않고** 수정 재료(status·provenance·큐)를 빠짐없이 기록 ③**build는 직렬 실행** — id 발급·저장이 비원자적이므로 호출부가 한 번에 하나를 보장한다.
4. **파이프라인을 LLM이 조종하지 않는다** — 단계 순서·재시도·커밋은 전부 코드다.

재구성 시의 구현 단위(코어·인입·질의·층 config-only·재인입·플랫폼·수정 도구의 기본 단위 위에 얹는 10종). 각 단위는 "빼면 어느 확정 사항이 구현되지 않는가"의 필요성 시험을 통과해야 한다.

|---|---|---|

| n2 | doc_hash 중복 차단 (인입 진입) | 문서 2 |
| n3 | 추출 단계 분리 + 추출 후보 JSON 체크포인트 | 문서 4 |
| n4 | 커밋 게이트 + direction_unverifiable | 문서 4 |
| n5 | I축 도구 4연산 (+canonical 선택·순환 방어) | 문서 4 |
| n6 | 구축 모드 등록 파이프라인 — 입력 패키지→생성→검수 뷰→승인·등록 | 문서 6 |
| n7 | 파서 공용 코어 6종 + 생성 하네스 — **외부 전달물** | 문서 6 |

**순서 원칙 5** (구체 배열은 구현 계획 문서 몫 — 원칙은 여기가 정본): ①**주소 체계 먼저** — n1·n2·n3은 다른 단위가 읽고 쓰는 id·체크포인트의 전제 ②**파서 측(n7·n8)과 에이전트 측(n1~n6)은 병렬** — 계약 JSON으로만 결합되므로(P1) 에이전트 측은 mock 계약 JSON으로 파서 없이 진행 가능 ③**n6은 n7 이후** — 배선할 코어가 먼저 있어야 한다 ④**n10은 인입보다 먼저** — 골격 없이 anchor 해소가 성립하지 않는다 ⑤**플랫폼보다 파이프라인이 먼저다**(플랫폼 직행 배제) — 진실이 먼저 서야 플랫폼이 보여줄 것이 생기고, 핵심 검증은 CLI+mock이 최속이며, P1(계약은 파일) 덕에 선파이프라인이 재작업을 만들지 않는다. 화면부터 세우면 data/ JSON이 서기 전에 화면 계약이 굳어 P1이 화면 요구에 끌려간다.

**완료판정 원칙**: 단위 완료 = 그 단위에 배정된 mock 시나리오(7.5) 전부 통과. **품질 측정은 완료판정이 아니다.** **테스트는 완료판정의 기계 번역일 뿐이다 — 테스트가 통과해도 판정 문구와 어긋나면 판정이 이긴다.** **단위 완료를 선언하기 전에 사람이 실물을 본다 — 그래프 JSON과 큐를 눈으로 확인하고 통과시켜야 다음 단위로 간다**(열람 창구는 7.8). 테스트 통과만으로 선언하면 테스트가 놓친 오적재가 다음 단위 위에 쌓인 뒤에야 발견된다.

**진행 규칙 (장부)**: 문서로 결정 안 되는 지점은 추측하지 않는다 — **카드·계약과 충돌하면 BLOCKERS(멈춤·3요소: 무엇이 막혔나/어느 문서 어느 절이 결정해야 하나/임시로 어떻게 두었나), 그 외 세부는 가결정 + DECISIONS 기록 + 전진.** 기록 형식: `[D-##] 지점 / 가결정 내용 / 근거 / 확정 경로`. **BLOCKERS 항목에는 3요소와 함께 판단자가 고를 선택지 2~3을 동봉한다** — 3요소는 상태 서술이라 그것만 올리면 판단자가 결정하려고 선택지를 처음부터 구성해야 하고, 멈춤 1건마다 왕복이 한 번씩 더 든다. **발번처는 DECISIONS 장부 하나다** — 보고·미러가 결정 번호를 선점하면 발번처가 둘이 된다(실사고). 구현 요청문은 전제 대조표 없이 발행하지 않는다 — 사실 전제마다 확인 방법·결과를 동봉한다. **명시적 실패(config로 표현되지 않아 core가 시끄럽게 실패하는 지점 — 문서 3)는 raise로 드러내는 데서 그치지 않고 그 지점을 장부에도 병기한다** — 런타임 예외로만 남고 장부에 쌓이지 않으면 "어느 결정점이 config로 표현되지 않았나"의 실측이 축적되지 않아, core 패턴 승격 판단을 나중에 처음부터 다시 하게 된다.

## 7.5 mock 체계와 시나리오 15종

1. **mock의 목적은 메커니즘 검증으로 한정한다.** 품질 측정은 mock으로 불가·유해 — **가짜 데이터의 점수는 가짜 확신이다.** 품질은 실데이터·골든셋 몫이고, 데모도 실데이터로 한다.
2. **모든 mock 항목은 검증할 메커니즘을 최소 하나 짊어진다**(행별 주석 명시). 메커니즘 없는 채움용 항목을 두지 않는다.
3. **사내 유래 정보는 모양만**(공정 단계명·열 이름 — 업계 일반 수준), **내용물은 전량 창작.**
4. **fixture(외부 LLM 실산출 스냅샷)는 사람이 작성·손질하지 않는다** — 손질한 fixture 위의 PASS는 어떤 LLM도 산출한 적 없는 결과물에 대한 PASS다. FAIL이면 프롬프트를 고쳐 재생성한다. mock(창작 재료·힌트)과 fixture(봉인 관측 데이터)는 지위가 다르다. **mock/adapters/는 사람이 쓴 참조 어댑터의 자리, mock/fixtures/는 외부 LLM 실산출 스냅샷 전용이다 — fixtures는 손대지 않는다**(디렉터리 경계가 지위 경계다). **재스냅샷은 손질이 아니다 — 규범이 개정되어 fixture가 새 관문에 걸리게 되면 「고쳐 재생성한다」의 그 경로다**(B35 — 판정필요-14). 절차 넷이 조건이다: ①**실호출 재생성** — 새 산출도 실산출이어야 fixture 자격이 있다(입력은 레포 창작 표본이므로 사내 유래 정보가 산출에 들어갈 재료가 없다 — 반출입 경계 유지) ②**하네스·봉인 대조 재실행 통과** — 새 스냅샷이 곧 새 봉인이다 ③**옛 스냅샷 보존** — 파일을 지우지 않고 archive 자리로 옮긴다: 옛 판은 「그 시점의 LLM이 그 프롬프트로 이렇게 냈다」는 실측 기록이고, 기록을 지우면 규약 개정의 전후 비교가 사라진다 ④**장부 기록** — 재스냅샷 사유·회차를 DECISIONS에 남긴다. 재스냅샷 전까지는 **관문이 옛 fixture의 확정을 막는 것이 옳은 동작**이며, 그동안 잃는 커버리지(해당 경로가 mock에서 끝까지 돌지 않음)는 숨기지 않고 어서션으로 표시한다.
5. **정답 기대값을 raw에서 자동 생성하지 않는다** — 동어반복이 된다. 진실은 수기 기대값이고 사슬은 단방향이다.
6. **시나리오 — 닫힌 15종.** 단위의 시험지이며 완료판정이 이것으로 내려진다.

S13이 부정 경로를 함께 지는 이유: 성공 경로만 시험하면 미해소 attach_to에 임시 노드를 만들거나 표면형을 그대로 엣지 끝점에 채우는 구현이 회귀 스위트를 통과한다 — 임시 노드 금지(문서 3)와 선언된 4경로 밖 엣지 금지(문서 1 I12)가 완료판정에서 걸러지지 않는다.

7. **회귀 실행 규약**: 회귀 판정 기준은 **클린 상태 단독 실행**이다 — 스위트 연속 실행 결과를 판정 규격으로 삼지 않는다(테스트 간 실행 산출물 공유로 순서 의존이 생길 수 있다).

**S14의 대조 산식 — 비교 제외 필드**: 역산 정합의 대조에서 **실행 시점 값(`parsed_at`·`source_path`·`parser_version`·`adapter_version`)과 `process_no`는 비교에서 제외한다.** 앞의 넷은 매 실행·환경·개정마다 달라지므로 "파서 산출 = 수기 parsed JSON"을 문자 그대로 구현하면 S14가 첫 실행부터 구조적으로 통과 불가능하고, 제외 목록이 명세에 없으면 어느 필드를 눈감아 줄지가 구현마다 달라져 S14의 엄밀도 자체가 규정되지 않는다. `process_no`를 제외하는 사유는 따로다 — parsed 계약의 검증 대상이 아니므로, 자산 쪽에서 번호 체계가 재정렬되어도 자산 쪽 번호 재정렬을 파서 결함으로 잡지 않는다 — 역산 정합은 파서 산출의 정합만 판정한다.

**창작 표본의 최소 규모**: 등록 리허설에 쓰는 창작 표본은 **정형 24행 이상 · 비정형 31행 이상 · PPT 8슬라이드 이상**으로 만든다 — 관찰 창(정형 head ~10줄 / 비정형 10~30줄 — 문서 6 §6.5)이 시험되려면 문서가 head보다 커야 하기 때문이다. **하한은 관찰 창의 상한을 넘어야 한다** — 상한 이하로 잡으면 규격을 지킨 표본이 head = 문서 전체가 되어 이 조항이 막겠다고 한 상태가 그대로 성립한다(비정형 상한 30줄이므로 31행이다). 목차형은 문서 6 §6.5가 계층 패턴 2~3회 반복까지 창을 넓히므로 그 계열은 반복이 3회 이상 담기는 규모로 만든다. 하한이 없으면 head = 문서 전체인 표본이 허용되어, 관찰 창 규칙과 preflight 지문 대조가 한 번도 시험되지 않은 채 S15와 n8(킷 완료 = mock 전 과정 리허설 통과)의 판정이 통과한다. 실물의 행 구성은 자산이 정본이되(아래 경로 규약) 규모 하한은 이 절이 갖는다.

**mock 자산의 자리 — 경로 규약**: `mock/adapters/`(사람이 쓴 참조 어댑터) · `mock/fixtures/`(외부 LLM 실산출 스냅샷 — 위 4) · `mock/extract_hints/{doc_id}.json` · `mock/struct_maps/{doc_id}.json`(7.1) · **`mock/parsed/{doc_id}.json`** — 수기 계약 JSON, S14(역산 정합)가 파서 산출과 대조하는 검체의 자리 · **`mock/queries.json`** — 질의 스모크 세트의 자리(12문항, 유형 배분은 문서 5의 지원 유형 Q1~Q5·Q8). 자리를 명세가 정하지 않으면 재구성자가 임의 경로를 만들어 S14의 대조 검체가 배선되지 않고, recall류 계기판(문서 5)의 분모 세트가 구현마다 달라진다. 각 파일의 실물과 행 구성은 mock 제작 지침(자산)이 정본이다.

**실호출로만 검증되는 항목의 표시**: USE_MOCK 규칙으로는 판정할 수 없는 항목(표기 변형 판정 등)은 **mock 항목의 데이터 필드로 표시하고, 주석으로 표시하지 않는다**(주석은 실행되지 않는다 — 7.6-B-2). 표시된 항목은 mock에서 실패하는 것이 정상이며 실호출 경로에서 검증된다 — 표시가 없으면 원래 실패해야 정상인 항목과 진짜 결함이 구분되지 않아, mock을 통과시키려고 **mock의 개체 판정 규칙**(공백 제거 후 동일/포함이면 점수 0.95 — 7.1 표)을 느슨하게 하거나 그 항목을 mock에서 빼 실호출 경로에 미검증 구멍을 남긴다.

## 7.6 구현 국면의 완료판정

mock 구현 국면의 완료는 네 조건이 전부 성립할 때 선언한다:

1. **시나리오 15종 전부 통과** (각 시나리오가 배정 단위의 회귀로 잠겨 있을 것).
2. **기존 단위의 완료판정 전부 유효** — 구현 국면 전체 완료 = 시나리오 15종 전부 + 기존 단위의 완료판정 전부 유효 + config-only 확증 + 클린 2회 동일 그래프. 질의 영역은 S1~S15 밖의 기존 단위 판정 — 2홉 도달·causes 사슬·orphan·회귀 무오염·재인입 중복 0 — 이 완료판정이다. 질의 mock 스모크는 12문항이 현행 세트다.
3. **config-only 확증** — 둘째 층이 코어 무수정으로 선다: `git diff core/` 공백. (층 등록 커밋 단독 규칙이 이 판정을 커밋 1회로 만든다 — 문서 3.) **판정이 깨진 것으로 나오면 그대로 보고한다 — 숨기거나 기준점을 옮겨 맞추지 않는다.** 판정이 커밋 1회로 잠겨 있어 경계를 옮기는 것 말고는 결과를 바꿀 방법이 없으므로, 이 금지가 없으면 층 추가가 코어를 건드렸다는 실측이 통과 보고 뒤로 사라진다.
4. **클린 2회 동일 그래프** — 깨끗한 상태에서 전체 빌드를 2회 실행해 큐·그래프가 동일(멱등성의 전면 검증). **그래프는 바이트 동일, 큐는 집합 동일로 판정한다** — 큐 항목의 적재 순서는 회수·재적재의 처리 순서가 낳는 것이고 소비 측이 kind별 조회라 순서에 의존하지 않는다: 순서까지 요구하면 멱등한 구현이 실패로 잡히고, 판정 단위를 적지 않으면 구현자가 스스로 정하게 된다. **집합 동일의 동일성 단위는 enqueue의 쌍 키 `(kind, doc_id, payload)`다**(문서 4 §4.7-3①) — 적재 시각(`created`)까지 비교하면 멱등한 두 실행이 항상 불일치로 잡힌다. **클린 상태는 `run.py init --fresh`가 만든다** — 빈 상태의 형태는 7.2다. **클린의 범위는 `data/` 전체(예외: `doc_types.json` — 등록 파이프라인이 승인 1회로 등재한 것이라 재생성되지 않으며 `review/{doc_type}/approval.json`과 한 쌍이다. 지우면 사람 쪽과 시스템 쪽이 등록 여부를 다르게 알게 되고, 다음 인입이 그 문서를 "미등록 → 구축 모드"로 되돌린다)와 `parsed/`·`extract/` 전체이며, `review/`는 지우지 않는다** — `parsed/`·`extract/`는 체크포인트라 파일이 남으면 다음 실행이 앞 단계(파싱·추출)를 건너뛰어 회귀 규약(7.5-7)이 막으려는 순서 의존이 그대로 생기고, `review/{doc_type}/approval.json`은 재생성되지 않는 사람 판단 기록이라(7.8) 지우면 승인 이력이 소실된다. `export/`는 파생물이라 어느 쪽이든 무해하다. 수동 삭제로 대신하면 "클린"의 정의가 실행마다 달라져 이 판정과 회귀 규약(7.5-7)이 서로 다른 바닥 위에서 내려진다.

**기존 단위의 완료판정 — 위 2번이 가리키는 대상**: 대상이 문면으로 있어야 2번이 공전하지 않는다. 없으면 재구성자가 단위별 합격선을 스스로 정하게 되고, "판정이 테스트를 이긴다"(7.4)는 규율이 자기가 쓴 테스트를 자기가 승인하는 구조로 무력화된다.

| 단위 | 완료판정 |
|---|---|
| 코어(저장) | 노드 2개를 add → 저장 → 로드했을 때 **id가 전역 유일하고 복원 결과가 동일하다** — 왕복 복원이 어느 판정에도 걸려 있지 않으면 GraphStore 직렬화 결함이 단위 수준에서 드러나지 않고 위 4번(전체 빌드)에서야 잡힌다 |
| 골격 심기 | seed 심기 후 Process 골격이 선다. 확인 항목은 **극성 인스턴스 간 precedes를 만들지 않을 것**과 **극성 인스턴스를 깊이 계수에서 제외할 것**(둘 다 문서 3)이다 — 노드·엣지 수는 seed 자산 종속이라 자산과 함께 재수립한다: 판정이 소유하는 것은 대조 수치가 아니라 확인 항목이다 |
| 정형 인입 | 인입 후 **Unit·Property·has_property 엣지 존재** · 스펙 충돌 행은 **spec_conflict 큐** · 맥락이 다른 값 항목은 충돌 없이 **병렬 항목**으로 남음 · 극성 결합 행은 **canonical 2노드 + mirrors 엣지 + mirror_asymmetry 큐**. **spec_conflict는 mock 표본에서 발생이 지정된 행에서만 난다** — 기준선이 없으면 우발 충돌이 결함인지 mock 설계상 의도인지 판별할 수 없다 |
| 비정형 인입 | **링킹 0건 청크가 `linked=false`로 보존** · 신규 표면형은 **status=auto + auto_node 큐** · **describes 연결** · USE_MOCK=1 전 과정 무에러 |
| 부착 두 규칙 | 신규 Property의 **auto 생성**(문서 4)과 **부착 폴백(규칙 B — 부착 대상이 없거나 미해소면 행/청크의 공정좌표에 부착)**이 실제로 동작한다 — 어느 시나리오·판정에도 배정되지 않으면 폴백을 구현하지 않아도 시나리오 15종이 전부 통과한다 |
| 질의 | 위 2번이 열거한 5항목에 더해 — 스모크 12문항이 **문항별 `expected_path`대로** 응답 · **flow 질의는 골격 전체 공급** · **링킹 미스는 로그로 기록**. 채널 일치가 빠지면 판정이 "에러 없이 응답이 나왔다"로 떨어진다 |
| cross 질의 | occurs_in·affects의 역방향이 **직접 결과**로 나오고, 수집된 노드 사이의 causes 엣지는 그래프 사실로 문장화된다. **2홉 연쇄 전체는 스모크의 요구가 아니다** — 합격선의 상한이 열려 있으면 1홉·비재귀 브리지(문서 5)와 충돌하는 재귀 확장을 시도하게 된다 |
| orphan 재시도 | 위 2번의 orphan 항목이 확인하는 것은 **재시도 성공 시 재부착 (a) 갈아끼움이 실제로 수행되고 저해상도 엣지의 provenance가 회수되는가**(문서 4)다 — 회수하지 않는 구현이 통과하면 같은 지식이 두 벌로 남아 질의 근거가 중복되고, 재인입 때 회수 대상이 어긋나 멱등성이 조용히 깨진다 |

**질의 스모크의 채점 규격**: 각 문항에 **`expected_path`를 명기한다 — 닫힌 4값 `graph_fact | chunk | both | general_knowledge`**(문항 유형표는 문서 5). 채점 규격이 없으면 "응답이 나왔다"와 "옳은 근거 채널로 나왔다"를 구분할 수 없어, 이원 근거 채널(문서 5)이 실제로 갈라졌는지가 어떤 테스트로도 잠기지 않는다.

**품질 측정(골든셋·recall)은 이 판정에 포함되지 않는다** — 실데이터 국면의 몫이다.

**이 판정의 범위를 넘겨 읽지 않는다**: 여기서 "완료"는 **mock 위에서 메커니즘이 도는 것**의 판정이지 시스템이 쓸 수 있다는 판정이 아니다. **실 연결(7.6-B)은 이 판정에 포함되지 않으므로, 판정 통과와 별개로 7.6-B의 충족 여부를 따로 확인한다** — 시나리오 통과만 세면 명세가 요구한 파일이 통째로 없어도 판정이 통과한다(실측된 실패 유형).

## 7.6-B 실 연결 규격 — USE_MOCK=0의 대칭 요구

**0. 연결 확인이 지점 판정보다 먼저다.** 지점별 판정에 들어가기 전에 **게이트웨이 왕복 1회**로 ①설정 ②도달 ③인증 ④응답 형태 ⑤구조화 출력을 **단계로 끊어** 가른다 — 어디까지 갔는지가 곧 원인이다. 이 단계가 없으면 지점 판정이 전부 붉어져도 **원인이 게이트웨이인지 지점 배선인지 갈리지 않는다**(2A 실측: 실제로 그 상태였다). 판정은 게이트웨이 설정 접근이 수렴하는 자리(`core/llm.py`)가 하고 화면은 옮기기만 한다 — 호출면을 CLI가 직접 조립하면 「비호환일 때 고칠 자리는 한 곳」이 깨진다. **인증 정보는 화면에 값으로 내지 않는다** — 설정 여부와 길이까지다.


> USE_MOCK=1의 요구(외부 의존 없이 전체 동작 — 문서 1 B12)에는 **대칭이 있다**: USE_MOCK=0에서 같은 경로가 실제 모델로 돌아야 한다. 이 절이 없으면 mock만으로 완결된 시스템을 만들고 완료판정까지 통과하게 된다 — 실측된 실패 유형이다.

1. **게이트웨이 2파일이 코드 배치에 포함된다**: `core/llm.py`(모델 호출 + JSON 파싱 + 재시도 — LLM 설정 접근이 이 파일 하나로 수렴한다) · `core/embeddings.py`(`embed(text) -> vector`). 설정은 환경변수로 받으며 **기본 명칭은 `USE_MOCK`(기본 1) · `LLM_GATEWAY_URL`(게이트웨이 주소) · `LLM_API_KEY`(인증) · `CHAT_MODEL`(모델명)이다 — 사내 게이트웨이가 다른 이름을 쓰면 그때 대체하되 이름을 비워 두지 않는다** — 이름이 없으면 구현자가 임의로 만들고, 같은 배포 환경에서 한쪽만 `USE_MOCK=0` 실호출에 연결된다. **호출부가 설정을 직접 읽지 않는다** — 수렴점이 없으면 지점마다 다른 규칙으로 붙는다. **USE_MOCK의 설정 소스는 환경변수 또는 LLM 설정 파일의 같은 이름 키이며 환경변수가 이긴다**(B42 — 설정 파일 우선순위와 동형·판독은 여전히 `use_mock()` 하나). **판독의 자리는 CLI 진입점과 core다 — 파서는 모드를 판독하지 않는다**(B48): 파서의 LLM 3지점(④이미지 요약·⑦구조 지도·⑨좌표 태깅)은 호출자가 만든 함수를 주입받고, 함수가 없으면 §7.1 대체를 쓴다. 파서에는 「지금 mock인가」라는 질문 자체가 없다 — 함수가 왔는가만 본다. **파서 패키지 코드에 `USE_MOCK` 문자열이 0건임을 회귀가 검사한다.** 근거(실측): 파서가 환경변수를 직접 읽어 설정 파일 갈래(B42)를 못 봤고, 파일로만 실호출을 켠 운영에서 core는 실호출·파서는 mock으로 갈려 **화면은 「실호출」인데 청크 경계는 휴리스틱이 정했다** — 그 경계가 chunk_id를 정하므로 재인입 멱등까지 흔들린다. 기본값 mock은 그대로다 — 외부 의존 0(B12)이 검증 체계의 바닥이다. **구조화 출력 스키마는 strict 요건을 지킨다**(B44): 게이트웨이의 구조화 출력(strict)은 **`properties`가 있는 모든 object에서 그 키 전부가 `required`에 있어야 하고 `additionalProperties`가 `false`여야 한다.** 「선택 항목」이라는 개념이 없으므로, 모델이 못 채울 수 있는 필드는 required에서 빼는 것이 아니라 **타입을 null 허용으로** 표현한다. 자유 키 사전(`additionalProperties`에 타입을 준 object)도 쓰지 않는다 — 값의 키가 닫힌 목록이면 **고정 키로 선언**한다. **이 불변식은 회귀가 검사한다** — 스키마는 코드에 있고 위반은 게이트웨이가 400으로만 알려주므로, 검사가 없으면 사내 실호출에서 처음 드러난다(실측: 선택 항목으로 추가한 필드가 400을 냈고, 응답 본문을 코드가 버려 원인 판별에 여러 회차가 들었다). **HTTP 오류는 상태 코드와 응답 본문을 함께 남긴다** — 본문이 원인을 문장으로 말하는 유일한 자리다.

**LLM을 부르는 화면 명령은 실행 머리에 현재 모드를 1줄로 표시한다**(`모드: mock(기본)` / `모드: 실호출`) — 표시가 없으면 설정 파일을 만든 운영자가 mock 산출을 실호출로 읽는다(실측 — 문답의 mock 고정 문안이 실호출 오동작으로 읽혔다). **표시는 지나칠 수 있으므로 관문을 둔다**(B48): 사람이 치는 운영 명령(등록 생성·검수·확정 · 파싱 · 인입 · 구축 · 질의)은 mock 모드에서 **실행 전에 멈추고** `--allow-mock`을 명시해야 진행한다. 회귀·doctor·init·bootstrap·llm-check·skeleton-confirm은 대상이 아니다 — 구현 환경에는 게이트웨이가 없고 그 환경의 실행이 검증의 바닥이다(B12). 관문의 자리는 모드를 정하는 **CLI 진입점 한 곳**이다 — 지점마다 두면 판독처가 다시 여럿이 된다.
2. **LLM 지점 9종은 전부 mock/실호출 분기를 갖는다**: ①비정형 추출 ②개체 동일성 판정 ③임베딩 ④이미지 요약 ⑤구축 모드의 어댑터·매칭 스키마 생성 ⑥**질의 링킹의 LLM 폴백**(사전 스캔 → 미스 시 LLM 폴백. 임베딩 3단은 이연이므로 지금 구현하지 않고 훅만 둔다 — 사다리 순서의 정본은 문서 5 §5.1-1·§5.4) ⑦구조 지도 패스 ⑧**답변 생성**(질의 4단의 ④ — 문서 5. USE_MOCK 대체는 7.1 표: 두 채널을 정형 텍스트로 나열, 문장 생성 없음) ⑨**좌표 태깅**(닫힌 목록 선택 또는 null — 운영 시점 파서 LLM 3지점의 하나, 문서 6 §6.1). 답변 생성이 목록에서 빠지면 USE_MOCK=1에서 그 지점이 무엇으로 도는지가 미정이라 답변에서만 실제 모델을 호출해 외부 의존 0(문서 1 B12)을 깨거나 임의 포맷으로 나열해 12문항 스모크의 출력이 구현마다 달라지고, 실 연결 대칭 점검에서 이 지점이 세어지지 않는다. **좌표 태깅도 같은 이유로 목록과 7.1 대체 표 양쪽에 실린다** — 대체가 선언되지 않은 LLM 지점은 USE_MOCK=1에서 실호출로 흐르고, 그 상태를 되돌리는 조항이 이 목록 밖에는 없어 패키지 미설치 환경에서 실행 자체가 죽는다. **주석으로 훅을 표시하는 것을 이음매로 삼지 않는다** — 주석은 실행되지 않는다: 자동 점검이 주석을 세면 비어 있는 지점을 구현된 것으로 보고한다. **분기가 있다는 것과 배선됐다는 것은 다르다 — 실호출 갈래는 실제 호출자(cli·core)로부터 도달 가능해야 한다**(B48). 파라미터만 있고 값이 올 통로가 없으면 배선이 아니다(실측: ⑦구조 지도는 `propose(ask=)`만 있고 `apply()`에 통로가 없어 어느 설정에서도 모델을 부르지 않았으며, 9지점 탐침은 그것을 직접 호출해 「명시적 실패 준수」로 계수했다 — 미배선이 초록이었다). **회귀는 9종 전수에 대해 도달 가능성을 잰다** — 「직접 불러서 죽는가」가 아니라 「실 호출 경로를 타서 미설정 실패(`NotConfigured`)에 닿는가」다. 배선을 하나 빼면 붉어야 한다(변이 시험).
3. **분기 형태는 `if USE_MOCK: <mock> else: <실호출>`이며, 두 갈래가 같은 반환 계약을 지킨다** — 소비부는 어느 쪽인지 모른 채 동작해야 한다. 계약이 같아야 mock 회귀가 실 연결에도 유효하다.
4. **모델 미연결 상태를 조용히 통과시키지 않는다**: 실호출 경로가 비어 있으면 명시적 실패로 끝낸다. 특히 **mock 산출물이 그래프·청크에 그대로 실려서는 안 된다** — 이미지 요약 자리표시자가 청크 텍스트가 되면 답변 근거로 되돌아온다(크래시가 아니라 조용한 오염이라 더 위험하다).
5. **프롬프트 템플릿은 파일이 정본이고 코드가 그것을 읽는다** — 버전 문자열을 코드에 적어 두고 템플릿 파일을 읽지 않는 구조를 두지 않는다: 실체 없는 버전이 체크포인트의 재현성 기록에 남는다.
6. **의존 매니페스트를 둔다**(requirements 등) — 선택 의존(문서 포맷 패키지·모델 클라이언트)의 소재를 코드 밖에서 알 수 있어야 한다.

## 7.7 파생물

1. **진실은 data/의 JSON이다.** Neo4j 적재·Cypher·CSV·Mermaid·HTML 시각화·임베딩 인덱스는 전부 **읽기 전용 파생물**이며 언제든 재생성한다. **파생물에서 그래프를 수정하는 경로는 없다** — 되돌려 읽지 않는다.
2. 파생물의 그래프 읽기도 GraphStore 경유다.
3. 파생물이 늘어도 이 지위는 불변이다 — **파생물 장애는 재생성으로 복구하고, 진실 장애만이 백업 문제다**(파생물을 백업 대상으로 삼지 않는다).

## 7.8 산출물 표 — 무엇이 파일로 남고, 어떻게 보나

> 계약(형식)과 별개로, **관측 창구**를 명세에 둔다 — 이 표가 없으면 시스템을 받은 쪽이 "중간 산출물이 없다"고 오인한다(실측된 혼선). 실행 산출물 디렉토리(data/·extract/·review/·export/)는 버전 추적하지 않는다. 단, **data/는 진실(생성물 — 버전 미추적)이다. 미추적의 사유는 재생성 가능이 아니다** — 사전·큐의 사람 판단 기록·승인 기록은 재생성되지 않는다. 파생물 장애는 재생성으로 복구하고, 진실 장애만이 백업 문제다 — **data/는 백업 대상 축에 있다**(7.7).

**data/ — 진실**

| 파일 | 무엇 | 열람 창구 |
|---|---|---|
| `{층}/graph.json` | 그래프 본체 — 노드·엣지 | 골격 트리·노드 상세·엣지 열람 명령 · **엣지 삭제 도구**(사람의 삭제를 `deleted_by_user` 툼스톤으로 기록 — 문서 4 §4.7-4) |
| `chunks.json` | 청크 저장소 — 원문 전량 + describes | 청크 열람 |
| `dictionary.json` | 동의어 사전 — 영속 지식(P4). 접근은 `core/dictionary.py` 경유로만(7.1) | 노드 상세의 별칭 |
| `review_queue.json` | 수정 큐 (닫힌 20종) | kind별 큐 조회 — **참조가 많은 auto 노드를 앞에 두는 우선순위 정렬**(문서 4 §4.7-3) |
| `doc_registry.json` | 문서 대장 — doc_id → doc_hash·revision·원본 경로 | 문서 역추적 |
| `doc_types.json` | doc_type 등록부 | 등록부 조회 |
| `registry.json` | 층 등록부 | 등록부 조회 |
| `skeleton_closed_list.json` | 골격 닫힌 목록 스냅샷(+skeleton_version) — 파서 공유 자산·파생물 | 골격 트리 |
| `ops_log.json` | I축 연산 이력 (연산 발생 시 생성) | 연산 이력 조회 |
| `gate_rejects.json` | 게이트 거부 로그 — 큐가 아니라 관측 신호 | 직접 열람 |
| `defects.log` · `link_miss.log`(링킹 미스 — 계기판 5의 재료) · `chunk_truncated.log`(청크 잘림 — 계기판 4의 재료) | 조용히 버리지 않기 위한 자리 — **사건이 있어야 생긴다**(없으면 그런 일이 없었다는 뜻). **두 계기판 로그는 별도 파일로 둔다** — 문서 5 §5.5-4가 측정 중에 `link_miss` 적재만 끄라고 하므로 한 파일에 합치면 끄는 순간 잘림 재료까지 함께 죽는다 | 직접 열람 |
| `review/{doc_type}/approval.json` | 승인 기록의 물리 정본 — {doc_type, adapter_version, 승인자, 시점, 수정 지시 이력}. 사람 판단 기록이라 재생성되지 않는다 | 등록 산출 열람 |

**수정 도구 세트의 등재**: 위 두 행의 엣지 삭제 도구와 큐 우선순위 정렬은 규범을 문서 4 §4.7이 소유하되 **산출물·창구로는 이 표가 등재한다** — 도구가 표에 없으면 규칙만 남고 그것을 만드는 구현 단위가 생기지 않는다(실측된 실패 유형).

**단계 경계 산출물**: 계약 JSON `parsed/{doc_id}.json`(파서 출력 — 파서/에이전트 경계. **파일 존재 = 파싱 완료**) · `extract/{doc_id}.json`(추출 체크포인트 — **파일 존재 = 추출 완료**) · `review/{doc_type}/`(등록 산출 — 입력 패키지·뷰 데이터 JSON·정적 HTML·승인 기록 approval.json). 첫 항을 추출 체크포인트와 대칭으로 못 박는 이유: 정형 경로에는 추출 단계가 없어 이 파일이 유일한 단계 경계 산출물인데 자리와 완료 판정이 조건부로만 적혀 있으면, 파서↔에이전트 경계를 건너는 물건이 실행마다 다른 경로에 떨어져 구축 진입점(7.1)이 무엇을 받는지가 정해지지 않는다. **`mock/parsed/{doc_id}.json`은 S14 수기 검체의 자리이고(7.5) 운영 산출 자리와 구분된다** — 같은 이름을 쓰되 뿌리가 달라서, 구분을 적지 않으면 리허설이 수기 검체를 운영 산출로 덮어쓴다.

**export/ — 파생물**(Cypher·CSV·다이어그램): 필요할 때만 산출하고 **되돌려 읽지 않는다.** 그래프 수정은 I축 도구뿐이다.

**시각화 3형태**: 그래프 뷰어는 **html(브라우저에서 관계 그래프를 본다)·Cypher(내보내기)·Neo4j(적재)** 3형태를 갖추고, 셋 다 GraphStore 경유로 읽는다(문서 1 B6 — graph.json을 직접 열지 않는다). html은 진실을 대신하는 것이 아니라 **사람이 그래프의 모양을 확인하는 창구**다 — 텍스트 열람(아래 ①)이 있다고 해서 생략하지 않는다: 층·카테고리·status·tier 필드가 있으므로 전체를 한 번에 그리지 않고 걸러 그린다. **걸러 그리더라도 cross-layer 엣지는 화면에 표시한다** — occurs_in·controlled_by 브리지가 화면에 나오지 않고 층별로만 그려지면, 이 시스템의 존재 이유인 층간 연결을 사람이 눈으로 확인할 창구가 없어져 그 동작을 텍스트 열람으로만 증명하게 된다. **파생물에서 그래프를 수정하는 경로는 두지 않는다**(7.7).

**요구 규격**: ①진실의 전 파일은 시각화 없이 텍스트 창구로 열람 가능해야 한다 ②골격 트리·노드 상세(값·별칭·출처·연결·근거 청크)·문서 역추적("이 문서가 무엇을 만들었나")의 3열람은 필수다 — 골격이 틀리면 뒤가 전부 어긋나고, 역추적이 없으면 무엇이 들어갔는지 모른 채 질의만 하게 된다 ③플랫폼 노출에는 ops_log 열람(5요소 표시)과 **툼스톤 계수**(층별 merged_into·obsolete 건수)가 포함된다 — 계수가 없으면 수정 이력의 규모를 화면에서 볼 수 없다.

**로그 규격**: 로깅은 표준 로깅 모듈·레벨 INFO로 하고, **MOCK 경고·큐 적재·명시적 실패 3종은 반드시 로그로 남긴다** — 명시적 실패가 예외 메시지로만, MOCK 경고가 표준출력으로만 나가면 자동 점검이 그것을 세지 못해 "자동 점검이 비어 있는 지점을 구현된 것으로 보고한다"(7.6-B-2)가 로그 축에서 그대로 재발한다. **LLM 사용량도 관측 대상이다** — 실호출마다 지점 이름과 사용량(입력·출력·합계 토큰)을 로그로 남기고, 응답이 길이 제한으로 잘렸으면 경고를 함께 남긴다. 화면 명령은 세션 합계를 표시한다. 근거: 사용량이 보이지 않으면 비용은 조용히 쌓이고 잘림은 산출 훼손으로만 발견된다 — §6.5 비용 동의 관문의 건수 제시도 이 수치가 전제다.
