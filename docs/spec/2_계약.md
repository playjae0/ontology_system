## 2.1 파서의 위치와 경계

파서는 사내 문서(Excel·PPT·Word·PDF)를 읽어 **온톨로지 에이전트가 소비하는 JSON**으로 바꾸는 프로그램이다. 사내에서만 실행되며, 시스템의 나머지와는 **코드가 아니라 JSON 파일로만 만난다.**

```
사내 문서 → [파서: 사내 실행] → 파서 출력 JSON → [에이전트: 외부 설계] → 그래프
                                      ↑ 유일한 접점
```

파서가 사내에 있는 것은 선택이 아니라 제약이다 — 데이터가 사내 반출 불가이므로 문서를 직접 읽는 부분은 사내에서만 돈다. 파서 출력 JSON을 소비하는 에이전트·플랫폼은 실물 없이 설계 가능하므로 외부에서 만든다. **계약 언어는 role이다** — 사슬에서 파서의 종착점은 메타데이터 JSON이고, 그 다음 칸(role 번역표)부터가 에이전트다.

```
사내 문서 →[파서]→ 메타데이터 JSON →[매칭 스키마 = role 번역표]→ 그래프 쓰기 동작 → 온톨로지
```

규약:

1. **결합은 파일 계약(JSON)으로만 한다.** 함수 호출·라이브러리 공유·DB 공유가 없다. 한쪽을 고쳐도 다른 쪽 코드는 건드리지 않는다(P1).
2. **파서 내부 구현 방식은 에이전트 호환성과 무관하다.** 에이전트는 파서 출력 계약(2.2)만 의존하고 검증한다.
3. **파서에 대한 요구는 "예쁘게 파싱"이 아니라 계약 준수다** — 필드가 명확히 분리되고 각 값이 스칼라 또는 명시적 구조체이면 만족한다. 예: 규격이 `"−0.1~+0.1mm"` 한 문자열이 아니라 `{min, center, max, unit}` 구조체.
4. **골격 파일은 파서·에이전트의 공유 자산이다.** 좌표 태깅용 닫힌 목록은 시스템이 파서에 공급한다 — 코드가 아니라 데이터이므로 P1 위반이 아니다. **공급 형태는 스냅샷이다**: 그래프의 골격 전 노드(auto alias 포함 — seed에 없는 파생 표기까지. **auto alias의 생성 산식은 문서 3 §3.9 ⑹**)를 한 시점에 추출해 고정한 `skeleton_closed_list.json` + `skeleton_version`(어느 골격 판 기준의 태깅인지 추적 — orphan 원인 진단의 근거). [사내 확인] 사내 배포 경로.

파서가 하지 않는 것: **개체 판정**(표기 변형은 에이전트의 사전·판정이 흡수 — 이름 정규화도 요구하지 않는다) · **관계 생성**(필드 사이의 관계는 매칭 스키마 edges 선언 몫) · **카테고리 발명** · **그래프 id 부여**(정본 id는 에이전트가 계산 — 파서가 내는 것은 원본 내 위치 표기 `source_locator`뿐).

## 2.2 파서 출력 계약 3종

이 셋을 만족하는 JSON이면 파서 내부가 어떻게 생겼든 시스템은 받는다.

### 계약 ① — 메타데이터 양식(3층 구조)

| 층 | 필드 | 성격 |
|---|---|---|
| 문서 봉투 (doc 단위) | `doc_id`, `doc_type`, `payload_kind`, `source_path`, `revision`, `parsed_at`, `parser_version`, `adapter_version`, `classification?`, `context?` | 재인입의 단위 — doc_id가 같으면 같은 문서의 개정 |
| 조각 공통 (모든 record/chunk) | `source_locator`, `doc_type`, `process_group`, `process_ref`, `process_no?`, `electrode_type`, `context?` | 모든 조각이 달고 들어오는 위치·좌표·소속 |
| payload (doc_type별) | table → `records[]` / prose → `chunks[]` — 텍스트 청크(`text`,`section`,`meta`) 또는 이미지 placeholder(`image_ref`,`section?`) | 문서 성격별 본문 |

- **`payload_kind`는 `table`\|`prose` 닫힌 2값이다** — payload가 records인지 chunks인지 가르는 결정적 스위치. 이 값 밖은 계약 위반(문서 단위 실패)이다.
- **`adapter_version`은 봉투에 1회만** — 한 문서는 한 어댑터로 파싱된다. 청크 저장 시 에이전트가 봉투 값을 복사해 붙이므로 "이 청크가 어느 분할 규칙으로 잘렸나"는 그대로 조회된다. doc_type별로 따로 개정되므로 parser_version으로 대체할 수 없다. 어댑터 개정 시 **사람이 수동 증가**시킨다.
- **`classification`은 자리만 있는 선택 필드다**(널 허용·자유 문자열). 문서 등급의 좌석 — 지금은 아무도 채우지 않고 인입은 읽지 않는다. 권한 로직·값 어휘·검증 전부 R12 이연. 등급은 문서의 성질이므로 위치는 봉투다.
- **각 role 배정 대상 필드의 값은 role 배정 가능한 형태여야 한다** — 스칼라·의미가 한 덩어리인 구조체·배열. 여러 의미가 한 문자열에 뭉치면 계약 위반이다.
- **payload 고정 키 4종(`text`·`section`·`meta`·`image_ref`)은 payload 구조 필드다.** role 배정 대상이 아니고 매칭 스키마 fields에 넣지 않는다. `section`은 청크의 소속 표기이자 chunk_id 산식의 성분이며, 그 의미가 문서마다 다르다는 관찰은 결함이 아니라 이 지위의 증거다 — 비정형은 문서마다 목차가 다른 것이 정의다. **`section`의 값은 헤딩 경로를 `" > "`(공백·꺾쇠·공백)로 이어 만든다** — 예: `"1. 개요 > 1.1 노칭"`. 이음 문자는 어댑터 재량이 아니라 계약이다: section은 chunk_id 산식의 성분이므로(문서 7) 구현마다 이음이 갈리면 같은 문서가 다른 chunk_id를 낳아 재인입 멱등성이 깨진다.
- `context`는 소속 맥락의 **임의 딕셔너리**다(스칼라로 내면 계약 위반 — 인입이 그 필드를 버린다). 축 이름은 열린 집합 — 실물에서 관찰되는 것만 쓰고(후보: 모델·사이트·라인), 새 축은 스키마 한 줄(L1). **봉투에 있으면 전 레코드 기본값, 레코드에 있으면 그 레코드만 덮어쓴다**(상속). 값은 스칼라 또는 리스트.

**계약 ①-부속 — id의 소유: 파서는 위치를, 에이전트는 정체성을**

| 값 | 누가 | 무엇 |
|---|---|---|
| `doc_id` | **파서** | 문서 식별자 — 해시가 아니다. 재인입 단위이므로 **개정판이 같은 doc_id를 가져야 하며**(개정 구분은 revision), **같은 문서에 항상 같은 doc_id를 부여하는 것이 계약이다.** 이것이 깨지면 재인입 자체가 성립하지 않는다 |
| `source_locator` | **파서** | 조각의 원본 내 위치 표기(예: `"Sheet1!R12"`). role=meta — 그래프에 들어가지 않는다. 형식은 파서 자유, 요구는 **같은 문서 안에서 유일할 것** 하나 |
| `chunk_id`/`record_id` | **에이전트** | 인입 시점에 산식(**문서 7 §7.2**)으로 계산하는 정본 id. **파서 출력에 이 필드는 없다** |
| `doc_hash` | **에이전트** | 문서 전체 내용 해시 — 중복 문서 차단(2.8) |

계산 주체가 에이전트인 근거 셋: ①멱등성의 근거를 사내 파서 구현에 위임하지 않는다 — 파서 버전마다 산식이 갈리면 "두 번 넣으면 그래프가 같다"가 깨진다 ②산식은 재인입·저장 규칙에 종속되므로 소유가 에이전트다(계약은 데이터, 산식은 로직) ③파서 계약이 산식 개정의 영향을 받지 않는다.

### 계약 ② — 공정좌표 태깅 의무

1. 모든 조각에 공정좌표를 태깅한다: `process_group`(대공정)·`process_ref`(선택된 골격 노드). **둘 다 role은 anchor다.** `process_no`는 anchor가 아니라 meta다 — 사내 번호 체계가 비표준·가변이라 조회 키로 쓸 수 없다(변하는 값을 키로 쓰면 P4 실질 위반).
2. **닫힌 목록은 시스템이 공급한다 — 골격 전 노드(개념+극성 인스턴스)의 canonical과 alias.** 파서는 이 목록에서 고르거나 해당 없으면 `null` — **목록에 없는 이름을 지어내지 않는다.** 문서가 상위·개념 해상도로만 말하면 개념 노드를 고른다 — 오류가 아니라 저해상도 부착이다.
3. **process_group은 별도 목록 없이 선택 노드의 tier:main 조상에서 파생한다** — 따로 고르게 하면 두 좌표가 어긋날 수 있다. process_ref가 null이면 process_group도 null이다.
4. **부착의 기본 대상은 process_ref 하나다.** process_group은 해소만 하고 부착에 쓰지 않는다 — 용도는 process_ref의 골격 조상 대조(검증)이며, 어긋나면 `coord_mismatch` 큐로 표면화한다(조용히 한쪽을 택하지 않는다). record의 electrode_type과 부착 골격 노드의 polarity가 둘 다 확정인데 다를 때도 같은 큐다.
5. 좌표가 골격과 맞지 않으면 시스템이 orphan_anchor 큐로 받는다. **따라서 파서 LLM에 요구되는 것은 완벽이 아니라 일관이다** — 같은 문서의 같은 대상에 항상 같은 좌표를 붙이면, 틀렸더라도 사람이 한 번에 고칠 수 있다.

이 계약이 중요한 이유: 좌표가 붙어 있으면 **그래프 부착이 LLM의 추측이 아니라 사전 조회라는 결정적 연산**이 된다 — 파서의 좌표 태깅 품질이 그래프 정확도를 직접 좌우한다.

### 계약 ③ — 레코드 자기완결성

행 하나가 **단독으로 읽어도 의미가 성립**해야 한다. 파서가 해소하는 것 넷:

| 대상 | 해소 | 예 |
|---|---|---|
| 상동 기호(`〃`·빈칸=위와 같음) | 실제 값으로 채움 | `공정: 〃` → `공정: 노칭` |
| 병합 셀 | 값을 각 행에 복제 | 3행 병합 "노칭" → 3행 모두 |
| 복수값 셀 | 개별 값으로 행 전개 — **전개 소유는 normalizer, 구분자는 기본 닫힌 목록 `[",", "/", 개행]` + 어댑터 expects 재정의** | `설비: A, B` → 2행 |
| 중첩 구조 | 쌍으로 평탄화 | 고장모드 1 : 원인 3 → (모드,원인) 3행 |

추가 둘: **표면형에 극성을 결합하지 않는다** — 극성은 electrode_type 필드로만 전달한다. 결합은 에이전트가 조건 확인 후 수행하며(문서 4), 파서가 미리 붙이면 이중 접두가 발생한다. **원문을 무손실 보존한다** — text에는 원문 그대로, 정돈본·요약본은 별도 필드로 두고 원문을 덮지 않는다(다른 임베딩 모델이 원문을 볼 수 없게 된다 — 구축 시점에 결정되어 사후 복구 불가). 예외는 이미지 페이지 하나 — 텍스트 원문이 없으므로 LLM 요약이 곧 text이며 `meta.image_summary=true`로 표시한다. 다운스트림은 이미지 유래 청크를 예외 처리하지 않는다.

**계약 위반은 조용히 통과하지 않는다** — 스키마 밖 필드는 unknown_field 큐, 필수 값 부재는 missing_field 큐, entity 필드의 리스트는 뭉개지 않고 드롭+큐. 시스템은 계약 위반을 **오염이 아니라 신호**로 바꾼다. **전 청크 보존은 파서의 의무다** — 개체가 없는 일반 서술 청크도 버리지 않는다(하이브리드 서치의 전제·되돌릴 수 없는 결정). 저장하는 것은 텍스트 조각이고 원본 바이너리는 source_path 참조만 남긴다.

## 2.3 LLM 활용 수준 — 시점이 성격을 정한다

원리: **설계는 과감하게(1회+검수), 운영은 보수적으로(무검수+안전망).**

| 시점 | 빈도 | 검수 | 허용 수준 |
|---|---|---|---|
| 설계·등록 (구축 모드) | doc_type/층당 1회 | **있음 (생략 불가)** | **어댑터 코드 생성까지.** 표본 관찰 → 어댑터 + 매칭 스키마(+층이면 config 초안) 연쇄 산출 |
| 운영 (운영 모드) | 매 문서 | 없음 | **닫힌 3종 + 예외 1종**: ①이미지 요약 ②좌표 태깅(닫힌 목록 선택) ③고정 분할 규칙의 결정적 실행 + **구조 지도 패스**(구조 가변 prose 한정 — 문서 6) |

- **운영 중 LLM이 청크를 직접 나누지 않는다.** 분할 판단은 등록 때 1회 하고 코드로 굳힌다(table·분할 자명 계열). 구조 가변 prose는 지도 패스를 거치되 — LLM이 내는 것은 지도(데이터)이고 나누는 것은 결정적 코드다.
- 비정형의 "내용 파악"은 파서가 아니라 **독립된 추출 단계**의 일이다: `[파싱] → 계약 JSON → [추출] → 후보 JSON(체크포인트) → [구축] → 그래프`. 근거: 추출은 비싸고 구축은 싸다 — 재빌드 때 추출을 다시 돌리지 않으려면 산출물이 독립 체크포인트여야 하고, "파서는 형태만 다룬다"가 지켜지며, 플랫폼에서 단계별 상태로 보인다.

**수준과 무관한 금지선 3**: ①개체 동일성 판정은 구축 단계의 판정 파이프라인만 수행한다 ②그래프에 쓰이는 관계는 커밋 게이트를 통과한 것뿐 — 파서·추출의 출력이 직접 엣지가 되는 일은 없다 ③운영 중 카테고리는 닫힌 목록 선택만. 근거는 권한 분리다: **파서·추출은 "후보"를 만들고, 구축이 "사실"을 만든다** — 후보 생산이 과감해져도 사실 확정의 관문(판정·게이트·검수)이 코드와 사람에게 있는 한 그래프는 오염되지 않는다.

**산출물 형태의 비대칭은 정당하다**: 에이전트 측 산출물은 데이터(매칭 스키마·config — 범용 실행기가 있으므로), 파서 측 산출물은 코드(어댑터 — 포맷별 실행이 필요하므로).

## 2.4 role 어휘 — 필드 role 5종 + edges 선언

**role은 그 필드의 값으로 에이전트가 그래프에 수행하는 쓰기 동작이다.** 에이전트는 필드의 이름이 아니라 role만 보고 동작한다. 한 문장: *anchor로 기존 골격에 닻을 내리고, entity로 노드 후보를 데려오고, edges로 그들 사이에 선을 긋고, attribute로 노드에 값을 붙이고, content는 청크로 보존해 연결하고, meta는 출처 장부에만 적는다.*

**왜 이 목록이 충분한가 — 봉쇄의 근거.** role 목록은 예상이 아니라 그래프 데이터 모델이 허용하는 **쓰기 동작의 전수 열거**에서 도출했다: ①기존 노드를 찾아 부착점으로 쓴다(anchor) ②노드를 만든다(entity) ③노드 필드에 값을 쓴다(attribute) ④두 대상 사이에 엣지를 만든다(edges) ⑤청크를 노드에 연결한다(content) ⑥그래프에 쓰지 않고 이력만 남긴다(meta). **제7의 쓰기 동작은 그래프 모델상 존재하지 않는다** — 커버리지가 경험이 아니라 구조로 보장되며, 이 보장이 깨지는 유일한 경우(property graph가 못 담는 정보)는 L4로 분리된다. edges는 필드에 붙는 것이 아니라 스키마 레벨 선언이며 전용 핸들러가 없다 — 표기는 "필드 role 5종 + edges 선언"으로 통일한다.

**① anchor — 닻.** 값이 **이미 존재하는 골격 노드를 가리킨다.** **동작은 "해소"이지 "부착"이 아니다** — 골격 노드를 찾아내는 것까지가 role의 일이고, 해소된 노드를 무엇에 쓰는지는 스키마가 정한다(edges의 `@좌표필드` 참조 / 폴백 대상 / 다른 anchor의 검증 기준). 대상 골격의 형태는 무관하다(트리든 평면 목록이든) — 조건은 "사람이 보증한 Tier1 노드"인 것 하나다. 처리: **사전 조회(정확 일치·alias) → 해소, 미스면 곧바로 orphan_anchor 큐.** **anchor 해소에는 후보검색·유사도·LLM 판정을 쓰지 않는다** — 골격은 사람이 고정한 유형이고(P2), 추론으로 끌어당기면 사람의 보증을 코드가 뒤집는다. 좌표 태깅이 닫힌 목록의 **정확 일치 대조**인 것과 같은 성질이다(문서 7 §7.1). 실측: 포함 매칭을 열면 `레이저노칭`이 `노칭`(seed)에 0.95로 걸려 **다른 공정의 결함이 엉뚱한 공정에 붙고**, `노칭`이 Tier1이라 아래 「Tier1 한정」 방어도 걸리지 않는다(2A P-B 실측 — 큐 69→68로 줄지만 그래프가 틀린다). 표기 변형은 사전의 alias가 흡수하고, 사전에 없으면 큐에서 사람이 판단한다. **미해소는 레코드 전체를 보류하지 않고 해당 엣지만 생략한다** — 좌표만 못 붙은 행의 entity·attribute·content까지 함께 사라지면 큐에는 orphan_anchor 1건만 남아, 조용히 버린 사실이 큐 화면에 드러나지 않는다. **생략된 엣지의 출발 노드는 orphan_anchor 큐 항목이 payload로 보유한다**(예: occurs_in이 생략된 행의 Failure) — 큐 항목이 재시도 배치의 손잡이이므로, 보유하지 않으면 골격이 나중에 자라도 그 노드는 영영 공정에 붙지 않는다. 따라서 **「Failure는 반드시 공정에 붙는다」는 서술은 정상 경로 한정이다**(미해소의 연쇄와 재시도의 정본은 문서 4). **entity 생성으로 폴백하지 않는다** — 골격은 유형이고 유형은 사람이 고정한다(P2). **Tier1 한정**: 조회 결과가 auto 노드뿐이면 anchor로 쓰지 않고 큐로 넘긴다 — 산문에서 스쳐 언급된 auto 노드가 골격 행세하는 우회로 차단. **이때 큐 항목에는 조회된 auto 노드 후보 id를 싣는다** — 후보를 동봉하지 않으면 사람이 큐 화면에서 후보를 다시 검색해야 판단할 수 있다. 선택 속성 `target_category`(조회 대상 골격 지정 — 생략 시 공정 골격).

**② entity — 개체.** 이름을 갖고 구별되어 **노드가 될 자격이 있는 것.** 처리: 사전 조회 → 후보 검색 → LLM 동일성 판정 → 3분기(매칭/신규/불확실 — 문서 4). 필수 속성 `category`(닫힌 목록 지정). 선택 속성 `attach_to_field`·`target_layer`(걸침 필드 — 생략 시 스키마 헤더 layer). **부착 폴백(규칙 B)**: attach 대상이 없거나 미해소면 행의 공정좌표에 부착 — 오류가 아니라 저해상도이며 후속 문서가 보강한다. **리스트 값은 계약 위반** — 뭉개지 않고 드롭+missing_field 큐(핸들러는 단일 값만 본다는 전제를 코드가 방어). 존재 자체가 맥락별로 다른 개체는 context 태그로 표현하지 않는다 — 노드 분화 문제로 실물 관찰 후 별도 판단. canonical 스코프(층 config의 `canonical_scope.bind_categories` 지정 카테고리는 canonical이 `{세부공정}::{표면형}`으로 유일화 — 대상은 config 값이며 코드는 모른다)의 규칙·근거는 문서 4 소유.

**③ attribute — 속성값.** 어떤 것**에 붙어 있는** 성질/값 — 노드를 만들지 않고 필드에 저장한다. 값 타입은 스칼라뿐 아니라 **구조체·배열도 통째로 하나의 값**으로 저장·비교한다(예: `spec: {min,center,max,unit,…}` — 사람이 스펙을 세트로 파악하는 단위와 일치하고, 개정 충돌이 실체대로 1건으로 집계된다). 구조체 내부 필드는 고정하지 않는다 — 스키마 파일 몫(L1). **값 항목은 provenance 필수** — 단순형 `{value, provenance}`, 맥락형 `{context, value, provenance}`. 재인입이 doc_id로 회수·교체하는 근거다. 부착 대상은 entity뿐 아니라 anchor로 해소된 골격 노드도 된다(예: severity → effect_category). **부착 대상 자체가 미해소면 그 attribute는 저장을 보류한다**(예: effect orphan·process orphan 행의 severity) — 처분이 정해져 있지 않으면 구현자가 임시 노드 생성·조용한 폐기·좌표 없는 노드 부착 중 하나를 임의로 고르는데, 세 갈래가 전부 명세 위반이다. **보류된 값은 그 미해소가 만든 큐 항목의 payload에 `pending_attrs`로 동봉해 보존한다** — anchor 미해소면 `orphan_anchor`, attach 미해소면 `orphan_attach` 항목이 `pending_attrs: [{attr_name, value, context?, provenance}]`를 함께 보유하고, orphan 재시도 배치(문서 4 §4.7-5)가 그 좌표를 해소하면 그때 보유한 값을 해소된 노드에 저장한다. **이 처분을 위해 새 큐 kind를 만들지 않는다** — 큐는 닫힌 20종이고(정본 = 문서 4 §4.7-3 표) 착지할 kind가 이미 둘 다 있다. 근거: 착지점을 적지 않으면 "보류"가 구현에서 조용한 폐기가 되어 G그룹(아무것도 조용히 버리지 않는다)이 문면 위반으로 잡히지 않은 채 깨지고, 큐 항목이 재시도의 유일한 손잡이이므로 값이 항목 밖에 있으면 좌표가 나중에 해소돼도 그 값은 영영 노드에 붙지 않는다. **판별 테스트: "이것에 대해 더 말할 게 생기는가?"** — 노칭 프레스는 더 말할 게 있다(entity), 규격 ±0.1mm는 없다(attribute). **그래프 입장 시험 — attribute는 전량 수록이 아니라 선별이다**(B33). 열을 attribute로 올리는 것은 두 시험이 모두 예일 때다: ⓐ**질문 시험** — 이 값을 단독으로 묻는 질문이 성립하는가(「노칭의 규격은?」은 성립한다 · 측정 포인트 개수 같은 서식 통계는 대개 성립하지 않는다) ⓑ**충돌 시험** — 두 문서가 이 값을 다르게 말할 때 사람이 그 충돌을 판정할 가치가 있는가(attribute는 spec_conflict의 대상이다 — 충돌이 잡음인 값을 올리면 개정 재인입마다 큐가 잡음으로 차 사람의 판정 시간을 먹는다). 하나라도 아니오면 **meta로 내린다** — 레코드 이력에는 남되 그래프·질의에 오르지 않는다. 지식이 아니면(서식 번호·서명란·개정 표기) UNMAPPABLE이다. **의심스러우면 내린다.** 방향의 비대칭이 근거다 — 잘못 내린 열은 원본 참조(source_locator → 문서 대장의 원본 경로)로 답할 수 있고 나중에 스키마 한 줄(L1)+재인입으로 올릴 수 있지만, 잘못 올린 열은 올라가 있는 동안 충돌 큐·답변 근거의 잡음으로 사람 시간을 이미 쓴다. 그래프는 문서의 보관소가 아니라 **질의가 찾는 층**이다 — 전량 보존은 원본 파일과 청크의 몫이고, 이 시험이 「기억할 가치」의 doc_type 단위 판정이다.

**④ content — 서술.** 자유 서술 텍스트. prose: 청크 보존 → 언급 추출 → 해소 노드에 describes 연결(미해소는 orphan_chunk_link 큐). table: 행 문맥이 명확하므로 **추출 없이 attach_to_field로 대상 직접 지정.** table의 청크 입도: 한 record에 content 필드가 여럿이면 **필드별 별도 청크**(id `{record_id}-{필드명}`) — 합치면 검색에 노이즈가 딸려온다. 링킹 0건 청크도 원문 그대로 보존한다. **판별 기준은 "자유 서술"만이 아니다 — 필드 단위 규칙 처리가 불가능하고, 값이 아니라 문장으로 읽히며, 청크로 보존해 노드에 연결할 것이면 content다. 짧아도 조치·설명·대응 계열이면 content다**(길이는 기준이 아니다). 근거: 길이를 기준으로 삼으면 짧은 정형 문구(부적합 조치·대응계획 계열 열)가 attribute로 배정되어, 같은 성격의 열이 문서마다 다른 role로 갈린다(실측 — 판정이 갈린 열).

**⑤ meta — 관리 정보.** 내용물이 아니라 내용물의 신상정보 — 저장만, 그래프 무기록. "내용 바깥의 관리 정보"라는 뜻이지 "가공 전 원료"가 아니다.

**⑥ edges 선언 (스키마 레벨).** 관계는 필드 하나의 성질이 아니라 필드 **사이**의 성질이다. 형식 `{from, relation, to, optional?}` — from/to는 필드명 또는 `@좌표필드`. 처리 시점: 모든 필드 해소 **후** 루프 후처리. **`optional: true`의 의미**: from/to가 빈 행에서 **해당 엣지만 조용히 생략** — 레코드 전체를 보류하지 않는다. **`mirrors`는 edges에 선언하지 않는다** — 극성 대칭은 필드 사이의 관계가 아니라 build 저장 직전에 자동 규칙(config.mirrors)이 polarity 필드 비교로 산출하는 관계다(자동 규칙 경로는 문서 4). 근거: 선언을 허용하면 근거 1쌍만 관찰한 표본의 특이점이 그 doc_type의 규칙으로 굳는데(실측), edges 참조 무결 검사도 검수 6지선다도 이것을 걸러내지 못한다.

**리스트 값의 role별 처리 (전수 — 별도 cardinality 규칙은 두지 않는다)**: entity=파서가 전개(미전개는 드롭+큐) / attribute=통째 저장(배열도 하나의 값) / content=무영향 / anchor=**허용 안 함** — 둘 이상이면 가리키는 노드가 미정이므로 스칼라가 아닌 값은 그 필드만 버리고 **missing_field**로 보낸다(§2.7 「리스트 값 방어」와 같은 자리다) / meta=무영향. **anchor의 리스트 값을 orphan_anchor로 보내지 않는다** — orphan_anchor는 "골격에 없는 좌표"이고 그래프가 자라면 해소되는 항목이라 orphan 재시도 배치(문서 4 §4.7-5)가 무는데, 리스트는 골격이 아무리 자라도 해소되지 않아 영구 재시도로 남고 사람은 골격 결손 목록에서 계약 위반 행을 보게 된다.

경계: 같은 글자라도 role에 따라 동작이 다르다("노칭"이 anchor면 찾아라, entity면 데려와라). role은 의미 분류가 아니라 **쓰기 동작의 분류**다. role 어휘를 미래까지 완벽하게 지금 완성하는 것은 목표가 아니다 — 목표는 부족했을 때 확장이 국소적이도록(L3=함수 1개) 구조를 잡는 것이다. **table 문서에는 추출 LLM이 필요 없다** — role 선언이 추출을 대체하고, LLM은 개체 판정에만 남는다.

## 2.5 매칭 스키마 — 필드 인벤토리와 role 번역표를 겸하는 한 파일

매칭 스키마는 한 doc_type의 필드에 role을 배정하고 엣지를 선언하는 파일(`schemas/{doc_type}.json`)이다. 등록 시점 1회 작성, 런타임에는 doc_type 문자열로 조회만.

**메타데이터 스키마("무엇이 나와야 하는가"의 선언)를 별도 파일로 두지 않는다 — 매칭 스키마의 fields가 겸한다.** 어댑터 코드에만 둘 수 없는 근거 셋: ①어댑터는 사내, 스키마는 외부 — JSON으로만 만나므로 필드 목록이 코드 안에만 있으면 에이전트가 알 수 없다 ②검증할 근거가 없어진다 — 어댑터 코드는 "무엇을 만드는가"이지 "무엇이어야 하는가"가 아니다 ③어댑터는 자주 손보고 계약은 안정적이어야 한다. 그러면서 **세 번째 파일을 만들지 않는 이유는 하나: 같은 필드 목록이 두 파일에 살면 반드시 어긋난다.**

```
어댑터 코드 (파서)        : 어떻게 뽑는가          — 자주 손봄
매칭 스키마 (공유 계약)    : 무엇이 나와야 하고 그것이 무슨 role인가 — 안정적
        └─ 둘은 "필드명"으로 만난다 (얇은 약속)
```

**규약 1 — 파일은 헤더 + fields + edges.** 헤더: `doc_type`(조회 키) · `schema_version` · `layer`(기본 기록 층 — entity의 target_layer 생략 시 이 값) · `use_blocks`. schema_version은 파서의 adapter_version과 짝을 이뤄 "어느 규칙으로 읽었나"를 추적한다 — 짝은 공동 증가 의무가 아니라 두 산출물(어댑터=어떻게 뽑았나 / 스키마=무슨 role인가)의 버전 병기다.

**규약 2 — 필드 spec 속성 일람이 문법의 전부다.** 표 밖의 속성은 존재하지 않으며, 필요해지면 L1/L3 판정 신호다: `role`(필수) · `category`(entity 필수) · `target_category`(anchor) · `attach_to_field`(entity·attribute·content) · `attr_name`(attribute — **저장 키 이름, 생략 시 필드명**) · `target_layer`(entity 걸침) · `contextual`(attribute 맥락형) · `optional`(전체). edges 문법: `from`/`to`/`relation`/`optional`.

**`attr_name`이 attribute의 저장 키를 고정한다** — 값은 attach_to_field가 가리키는 노드의 필드로 저장되며 그 키가 attr_name이다. 지정이 없어 항상 필드명으로 저장되면 doc_type마다 열 이름이 다른 같은 개념이 서로 다른 키로 쌓여, 같은 노드 위의 값 병합·spec_conflict 판정·재인입 교체가 대상 키를 찾지 못한다.

**규약 3 — fields에 나열하는 것은 payload 필드와 "role 배정이 필요한 조각 공통 필드"뿐.** 후자는 첫날부터 블록으로 조립한다: `common_core`(source_locator: meta) · `process_coord`(process_group: anchor · process_ref: anchor · process_no: meta/optional). **나머지 계약 필드는 구조 필드다** — role 핸들러를 타지 않고 시스템이 직접 읽는다:

| 구조 필드 | 왜 role이 없나 |
|---|---|
| 봉투 전체 | 문서 단위 처리 정보 — 재인입 단위·스키마 조회·payload 분기·진입 검증에 쓰이며 그래프 쓰기 동작이 아니다 |
| 조각 공통 `doc_type` | 스키마 조회 키(봉투 값의 반복) |
| 조각 공통 `context` | 맥락 상속 처리의 입력 — attribute 저장 시 소비 |
| 조각 공통 `electrode_type` | entity 해소 코드가 직독해 극성 결합을 판정하고 polarity 파생 필드를 기록한다(문서 4) — 스키마가 이 필드의 처리를 바꿀 수 없다 |
| payload 고정 키 4종 (prose) | 청크의 몸체·주소·부속 — 소비자는 시스템 코드(청크 저장·chunk_id 산식·이미지 요약 경로) |

구조 필드의 판정 3조건: ①계약이 고정 ②소비자가 role 핸들러 아님 ③그래프 쓰기 6동작 미유발 — 전부 만족해야 한다. 구조 필드는 검수 6지선다에 올리지 않는다 — UNMAPPABLE(미해결)과 달리 **정상·완결 범주**다.

**규약 4 — 블록 승격은 관찰 후에**(스키마 레벨의 Rule of Three) — 2~3개 스키마에서 같은 묶음이 실제로 관찰될 때 올린다. 블록도 값이라 코드 리스크 0. **겹침 규칙**: 같은 필드 이름이 스키마 선언과 공용 블록에 함께 있으면 스키마 선언이 이긴다. fields 유무의 판정(prose는 빈 목록)은 스키마 선언분으로 한다 — 블록은 스키마가 쓴 것이 아니라 참조한 것이라, 블록 전개가 prose 판정을 흔들지 않는다.

**규약 5 — prose의 fields는 빈 목록 `{}`이다.** payload가 고정형인데 그 고정 키는 전부 구조 필드이므로, **층 배정(layer)과 블록 선언(use_blocks)이 계약의 전부다.** 개체·관계는 등록 시점의 role 배정표가 아니라 인입 시점의 추출 후보가 낸다. 등록 비용은 "표준양식 종수 × 1회"다. — 구판의 "payload가 고정형이라 fields가 같다"는 문면은 "고정 키가 fields에 들어간다"로도 읽혔고, 그 이중 독해가 생성 킷의 prose 오배정 사고(section을 role 배정하려다 만족 불가능한 지시가 됨)의 명세 측 뿌리였다. **정의는 이중 독해가 안 되는 문면으로 쓴다.**

**규약 6 — role이 메타데이터 확정의 상류 제약이다.** 필드는 role(닫힌 5종)에 매핑 가능한 것만 스키마에 확정하며, 매핑 불가 필드는 **UNMAPPABLE로 사람이 판정**한다(L3/L4로 넘김 — 스키마에 넣지 않고 어댑터 출력에서도 제외). 근거: role 밖 필드는 매칭 불가 → 그래프 진입 불가 → 파싱해도 무효다. 적용 대상은 role 배정 대상 필드(table의 열)다.

파일 실례(PFMEA — 걸침·anchor·부착의 전형). **실례의 정본은 자산 `schemas/pfmea.json`이고, 아래는 읽는 법을 위한 발췌다 — 필드 전량과 선언 순서는 자산이 갖는다.** 본문에 스키마 전문을 복제하지 않는다(복제 금지 자산 — README): **선언 순서가 record_id의 join 순서이므로**(산식은 문서 7 §7.2) 본문 사본을 보고 만든 스키마는 같은 행에 자산과 다른 record_id를 낸다 — 순서 차이는 장식이 아니라 근거 축 id를 가른다. **같은 필드 목록이 두 파일에 살면 반드시 어긋난다**는 이 절 머리말의 근거는 본문 복제에도 그대로 적용된다(실측: 이 자리의 구판 사본이 실물보다 두 필드 좁고 순서도 달랐다).

헤더: `doc_type: pfmea` · `schema_version: 1` · `layer: quality` · `use_blocks: ["common_core", "process_coord"]`.

fields 발췌 — **자산의 선언 순서 그대로**이며 각 필드는 role과 핵심 spec만 보인다:

| # | 필드 | role | 핵심 spec |
|---|---|---|---|
| 1 | `failure_mode` | entity | `category: Failure` |
| 2 | `cause` | entity | `category: Failure` |
| 3 | `severity` | attribute | `attach_to_field: effect_category` |
| 4 | `effect_category` | anchor | `target_category: FailureEffect` |
| 5 | `effect_detail` | content | `attach_to_field: effect_category` |
| 6 | `control_item_for_fm` | entity | `category: Property` · `target_layer: process`(걸침) |
| 7 | `control_item_for_cause` | entity | `category: Property` · `target_layer: process`(걸침) |
| 8 | `prevention_control` | content | `attach_to_field: cause` |
| 9 | `detection_control` | content | `attach_to_field: failure_mode` |

3·5~9는 `optional: true`다. **선언 순서를 처리 순서로 읽지 않는다** — 3이 아직 선언되지 않은 4를 attach_to_field로 가리키는 것이 정상인 이유는 부착이 전 필드 해소 후의 2-pass이기 때문이다(문서 4 §4.2).

edges 발췌(형식은 `{from, relation, to, optional?}`): `cause ─causes→ failure_mode` · `failure_mode ─affects→ effect_category` · `failure_mode ─occurs_in→ @process_ref` · `failure_mode ─controlled_by→ control_item_for_fm`(optional) · `cause ─controlled_by→ control_item_for_cause`(optional).

읽는 법: ①layer가 quality이므로 걸침 필드(control_item_*)만 target_layer를 명시 — 한 번의 인입이 두 층에 기록된다 ②effect_category가 anchor인 것은 FailureEffect가 닫힌 Tier1 골격이라 auto 생성 금지이기 때문 ③severity가 effect_category에 붙는 것은 표준 FMEA에서 S가 영향 기준값이기 때문이며, 이로써 병합 노드의 우발 spec_conflict가 구조적으로 소멸한다 ④`controlled_by` 2줄은 **cross 엣지도 정형 edges 선언으로 만든다**는 실례다(도착점은 골격이 아니라 Tier2 노드인 Property) — 별도의 층간 연결 프로그램이 없고 table 문서에는 추출 LLM도 없으므로(2.4), 이 선언이 빠지면 control_item 열이 Property 노드는 만들되 controlled_by 엣지는 한 건도 생기지 않는다.

**CP 계열 배정 예**(정형 — 걸침 없이 has_property + attribute 사슬):

| 열 | role 배정 |
|---|---|
| 설비/지그 | entity(Unit) |
| 관리항목 | entity(Property) |
| 규격/공차 | attribute → 관리항목에 부착, `attr_name: spec` |
| 측정방법/주기/샘플 | attribute → 관리항목 |

edges: `설비 ─has_property→ 관리항목` — 정형 스키마 실례가 PFMEA(걸침·anchor 중심) 하나뿐이면 CP 계열을 처음 등록하는 사람이 참조할 배정 예가 없다. 규격의 저장 키를 `spec`으로 고정하는 것은, doc_type마다 열 이름이 달라도 같은 Property 노드 위에서 값이 한 키로 병합되게 하기 위해서다.

경계: **파서 출력 양식(2.2)과 매칭 스키마는 두 개의 스키마가 아니다** — 같은 필드 목록의 파서 측 시각과 에이전트 측 시각이다(3층 구조의 원천 서술은 2.2에 일원화). 매칭 스키마는 데이터이지 코드가 아니다. fields 밖 필드가 레코드에 있으면 unknown_field 큐(구조 필드는 예외 — fields 밖이 정상). 맥락 축을 미리 발명하지 않는다.

## 2.6 변경 등급 L1~L4

무엇이 바뀌면 무엇을 고쳐야 하는지의 4등급 — **이 표가 "범용성"의 조작적 정의다.**

| 등급 | 사건 | 고치는 것 | 코드 변경 |
|---|---|---|---|
| L1 | 필드명 변경·필드 추가/삭제 | 스키마 파일 한 줄 | 0 |
| L2 | 새 doc_type (기존 role로 표현 가능) | 스키마 파일 1개 추가 | 0 |
| L3 | 기존 role로 표현 불가한 필드 성격 | role 1종 + 핸들러 함수 1개 | 함수 1개 — **기존 핸들러 무수정** |
| L4 | 그래프 모델 자체가 못 담는 정보 | 설계 재검토 | 구조 변경 |

- 범용성의 정의: L1~L2가 사건의 대부분이 되게 하고, L3의 비용을 함수 1개로 봉쇄하는 것.
- **L4는 어떤 설계로도 예방 불가한 영역임을 정직하게 기록한다** — 예방하는 척하지 않는다.
- **카테고리 추가는 제안까지만 허용하고 L3/L4로 판정한다 — 파급이 크다(role 봉쇄 훼손).** 카테고리는 발명 금지 3종의 하나이자 role 봉쇄의 전제라, 제안이 저비용 경로로 곧장 반영되면 닫힌 목록 봉쇄가 사실상 무력해진다.
- **L1이 "쉽다"는 뜻이지 "안전하다"는 뜻은 아니다** — 예: canonical_scope 대상 변경은 스키마 한 줄이지만 걸침 필드 병합 규칙을 선행 마감하지 않으면 층 간 키가 갈라진다. "L1 한 줄이 지뢰"가 될 수 있는 지점은 해당 규칙 절에 경고로 명시한다(문서 4).
- 이 표는 스키마 축만 다룬다 — 인스턴스 축의 변경(개명·병합·분리·폐기)은 **직교 축 I축**이며 문서 4가 소유한다.

## 2.7 핸들러 루프와 인입 검증

role이 정해지면 처리는 단순한 루프다 — **코드에는 필드명이 등장하지 않고 role만이 분기 스위치다.** core는 스키마를 순회할 뿐이다("모든 문서를 수용하는 똑똑한 실행기"가 아니라 "가정을 안 하는 단순한 순회기").

```python
for field, spec in schema["fields"].items():
    resolved[field] = HANDLERS[spec["role"]](record.get(field), spec, ctx)
for e in schema.get("edges", []):        # edges는 HANDLERS에 없다 — 루프 후처리
    graph.add_edge(resolved[e["from"]], e["relation"], resolved[e["to"]])
```

- **핸들러 공통 시그니처는 `handle(value, spec, ctx) → resolved_id|value|None`이다.** `ctx`는 여섯으로 구성한다 — 층별 graph 묶음 · 사전(dic) · **문서 해소 버퍼(buffer)** · 큐(queue) · record · schema. 버퍼를 열거에서 빼지 않는다 — 이 열거가 닫힌 목록으로 읽히는데 버퍼가 없으면 핸들러가 attach_to의 해소 범위(문서 4 §4.10-6 — 문서 해소 버퍼 전체 + 사전)에 손이 닿지 않아 그 조항이 구현 불가가 된다. 버퍼의 형태·수명·층 스코프의 정본은 문서 4 §4.2 Pass 1이며, 레코드 단위 `resolved`(필드명 키)와는 다른 그릇이다. **반환 3형태를 비워 두지 않는다** — 반환 3형태가 정해져 있지 않으면 edges 후처리가 "미해소"를 무엇으로 판별할지 미정이 되어, optional 엣지의 조용한 생략과 진짜 미해소(orphan_anchor·orphan_attach)의 구분이 구현자 재량으로 내려가고 미해소가 큐 없이 사라지는 경로가 열린다.
- **모든 role 핸들러는 3단 구조를 따른다: 규칙 → LLM 폴백(훅) → 수정 큐.** anchor·entity는 본래 이 구조이고, attribute·content·edges는 훅의 자리만 확정하고 채움은 실물 갭 관찰 후로 미룬다(P7). **관찰 대상 갭 4종**: 빈 셀 부착(부착 대상 부재) · 상동/병합 셀 · 복수값 셀 · entity 칸의 혼입 산문. 단 상동/병합/복수값의 1차 방어선은 파서의 자기완결 레코드 계약(2.2 계약 ③)이다 — 무엇을 관찰할지가 없으면 훅은 영영 안 채워지거나 근거 없이 채워진다.
- 실제 인입은 2-pass다(해소 → 부착) — 절차는 문서 4.
- **핸들러가 예외를 삼키지 않는다.** 처리 못 한 값은 반드시 큐로 간다 — 조용한 실패는 커버리지를 과대평가하게 만든다. 알 수 없는 role 값은 크래시 대신 invalid_role 결함 로그로 방어한다.

**인입 검증의 전체 배열**:

```
투입 분류(사람 + 지문 스캔) → [파서] preflight → (struct-map — 구조 가변 prose 한정)
→ extract → normalizer → tagger → validator → [에이전트] ①doc_hash → ①′회수(기존 doc_id면) → ②id 계산 → ③필드 검증
```

파서 측 = **문서 단위 실패**(parse_failure·adapter_mismatch — 정본은 문서 6), 에이전트 측 = **큐 착지** — 역할이 겹치지 않고 이어진다. **파서의 실패 보고는 별도 파일 형식을 계약하지 않는다** — 파서 공용 코어가 전 층 공유 단일 큐(review_queue)에 parse_failure·adapter_mismatch·hierarchy_unresolved 항목을 직접 착지시킨다(같은 data/ 위에서 실행되므로 에이전트가 대신 적재하는 단계가 없다). 항목 내용은 사유·해당 행 동봉 규칙을 따른다. 에이전트 3단(+재인입이면 ①′ 회수 칸이 ①과 ② 사이에 든다):

**① 진입 검증 — 중복 문서 차단.** doc_hash를 계산해 대조 — **같은 doc_hash가 다른 doc_id로 이미 존재하면 인입을 보류하고 사람 확인을 요청한다**(두 문서의 파일명·크기·시점·기존 doc_id를 함께 제시). **파일명·크기를 판정 기준으로 쓰지 않는다** — 화면 참고 표시만, 판정은 내용 해시로. 같은 doc_id 재도착은 중복이 아니라 재인입(정상 경로)이다. doc_hash는 청크 해시 계산의 부산물이라 추가 비용이 없다. 진입 검증은 파서가 하지 않는다 — 파서는 다른 문서의 존재를 알 필요가 없다. **보류 해제는 사람의 2택이며 그 판단은 `duplicate_doc_hold` 항목에 기록된다**: **㉠같은 문서로 인정** → 이번 인입을 폐기하고 항목을 종결한다(같은 파일을 다시 넣어도 같은 판정이 반복되므로 재투입으로는 흐름에 돌아오지 못한다) · **㉡다른 문서로 인정** → `--allow-duplicate`로 그 doc_id를 인입하고 doc_registry에 그 doc_hash의 예외를 등재해 이후 인입이 다시 걸리지 않게 한다. 어느 쪽이든 사람의 판단이 기록된 항목이므로 재인입 회수 대상이 아니다(문서 4 §4.4-7 — 판단이 기록된 큐 항목은 보존). 해제 경로를 적지 않으면 보류된 문서가 큐에만 남고 그래프로 들어갈 길이 없는데, 그 상태는 「조용한 소실 금지」를 표시만으로 만족한 것처럼 보여 결손이 계기판에 잡히지 않는다.

**①′ 회수 — 재인입 한정.** 같은 doc_id가 이미 있으면 그 문서 몫을 걷어낸 뒤 새 판을 적재한다(회수 3분류와 보존 대상의 정본은 문서 4 §4.8-2). **회수는 ①doc_hash 차단 뒤·재적재 앞에서만 돈다** — ① 앞에 두면 보류돼야 할 중복 문서가 남의 옛 판을 걷어내고, 재적재 뒤에 두면 방금 쓴 새 판을 지운다. **회수 후 새 판에 결손이 있어도 롤백하지 않는다** — 결손은 ③의 missing_field 큐로 가고 새 판이 정본이다: 롤백하려면 걷어낸 옛 판을 되살릴 스테이징이 필요한데 그 장치를 두지 않으므로, 롤백을 규정하면 지킬 수 없는 조항이 된다.

**② 근거 축 id 계산.** 각 조각의 내용에서 chunk_id/record_id를 계산한다. source_locator는 계산 입력이 아니다 — 위치를 해시에 넣으면 앞에 한 문단만 추가되어도 뒤의 모든 id가 바뀐다. 계산된 id가 이미 존재하면 **조용히 덮어쓰지 않고 결함으로 로그**한다. 산식은 문서 7 소유.

**③ 필드 검증.** 스키마 밖 필드 등장 → 값을 동봉해 unknown_field 큐(파서가 앞서갔다는 신호 → 스키마 갱신. 구조 필드는 예외). 스키마에 있는데 없음 → optional 검사, 미선언이면 missing_field 큐 — 큐로 갈 뿐 문서를 죽이지 않는다. optional:true면 통과 + 관여 edges만 조용히 생략.

- **payload_kind 닫힌 2값 위반과 미등록 doc_type은 폴백이 아니라 문서 단위 미인입 + parse_failure** — 그래프·청크·체크포인트에 아무것도 쓰지 않는다(구축 모드 배선과 별개로, 여기서는 명시적 실패까지다).
- **발명 카테고리**: 어느 층도 선언하지 않은 카테고리는 invalid_category + 노드를 생성하지 않는다.
- **리스트 값 방어**: entity·anchor 값이 스칼라가 아니면 missing_field + 그 필드만 버리고 전진 — 파서의 복수값 전개(정상 경로)와 층위가 다르다: 이것은 파서가 거르지 못한 값이 에이전트에 도달했을 때의 방어선이다. **attribute는 이 방어의 대상이 아니다 — 2.4대로 구조체·배열을 통째로 하나의 값으로 저장한다.** — 이 방어가 막는 것은 리스트가 표면형 정규화(문자열 강제 변환·포함 규칙)를 타고 기존 노드에 흡수되는 사전 오염인데(실측: 사전에 리스트 문자열 키), attribute 값은 사전을 타지 않는다.
- **invalid_role은 큐 kind가 아니다** — 결함 로그만 남긴다(닫힌 20종 밖 kind를 만들지 않는다).

**정합성 감시는 양방향이다** — 어긋남이 조용한 오염 대신 큐에 시끄럽게 나타난다.

> **플랫폼 훅**: 큐는 처리 대상 목록이자 화면이다 — kind별 조회·처리·재시도가 API 형태로 노출 가능해야 한다. 진입 보류(①)는 "사람 확인 대기" 상태를 갖는 첫 화면 지점이다.
