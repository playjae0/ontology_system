## 2-a. 구축 계획 — 층 설계 (2026-09-28 사용자 논의)

**순서(사용자)**: 설비층으로 뼈대 → 공정 정보 붙이기 → 불량정보층 → 화성으로 확장 → PPT 대량 투입(지금 가진 자료는 대부분 PPT).

**정한 것(사용자)**
- **골격 노드는 공정명의 Process 노드다** — 「노칭 설비」 노드를 두지 않는다. 설비 정보와 공정 정보는 성격이 달라 **층을 나누고, 둘 다 같은 Process 노드에 와서 붙는다**: 설비층(좌표 층 — 공정명 Process 노드 + 설비 구성 Unit·Component) · 공정층(공정 정보 — **Property(파라미터·관리특성)는 여기** · `Process`를 선언하지 않는다) · 불량층. 그래야 공정 정보든 불량이든 한 노드에서 넓어진다. **Property를 설비층에 두지 않는다**(사용자 확정 2026-09-28 — 설비와 공정은 성격이 다르다).
- **「노칭 설비」가 「노칭」으로 붙는 자리 — 로직이 해 주는 것과 안 해 주는 것**(실물 확인 2026-09-28):
  - 해 주는 것: 좌표(anchor)는 골격 **조회 전용**이다 — 새 노드를 만들지 않고, 못 찾으면 `orphan_anchor` 큐(`core/build/build.resolve_anchor` · 유사도·LLM 0). 그래서 좌표 자리에서 「노칭 설비」 노드는 생기지 않는다.
  - **안 해 주는 것**: 「설비」「equipment」「기」를 떼는 변환은 **없다**. 조회는 공백 정리만 하는 **정확 일치**이고(`ids.norm` — 대소문자도 구분: `notching` ≠ `Notching`), 「노칭 설비」가 「노칭」에 붙는 것은 그 표기가 골격 `ALIASES`에 있을 때뿐이다. 없으면 큐로 간다.
  - 추출 통로: 산문에서 LLM이 「노칭 설비」를 **개체(Unit 등)로** 뽑으면 로직이 막지 않는다 — 정의문(config)이 안내할 뿐이고 판정 결과에 따라 별도 노드(auto)로 설 수 있다.
  - 그래서 지금은 **data 몫**이다 — `ALIASES`에 설비 표기를 표기마다(영문 대소문자 변형 포함) · Process·Unit 정의문에 「설비 이름이 아니라 공정 이름」. **로직으로 보장하려면** 층 config가 선언한 접미 목록(예: 「설비」「equipment」「기」)을 조회 때 떼는 규칙이 필요하다(어휘는 config · 코어는 규칙만) — 과하게 뗄 위험(「공급기」 ≠ 「공급」?)이 있어 사내 큐에서 접미 변형 건수를 본 뒤 정한다(§2-b 2의 겸·자기 좌표 규칙이 먼저 — 그 뒤에도 남는 변형만).
- **뼈대층(설비·공정)의 골격 개념**(사용자 확정 2026-10-01 — 파악에 꼭 필요한 내용이라 남긴다): 골격은 **공정 두 단**이다 — **상위 공정**(예: notching — 설비 단위 · equip)과 그 아래 **하위 공정**(예: cutting unit — unit 단위). 둘 다 골격 노드다. **구분은 그 아래부터** — `Component`(설비층 — 구성 기계·부품)와 `Property`(공정층 — 파라미터·관리특성)가 골격 노드에 갈라 붙는다. 그 위(골격)는 구분이 필요 없다.
  - 두 단을 카테고리로 나눌지: 사용자 원칙 「**다른 엣지가 붙어야 하면 다른 노드로 관리한다**」 · 「지금은 두 단에 다른 관계가 필요 없다」 → 지금은 나누지 않는다(허브: 두 문장에서 따라 나온다) — 두 단 모두 `Process` 골격 + 겸 `Unit`(`common.json` `"Process": {"also": {"Unit": [상위 단, 하위 단]}}` — 대공정이 1단이면 `["sub", "detail"]`) · 단별 설비 표기(「notching 설비」·「cutting unit」 류)는 그 노드의 골격 `ALIASES`(정확 일치 — 변형마다). 두 단에 다른 관계가 필요해지면 그때 카테고리를 나눈다.
  - 겸을 켜는 것은 데이터 셋이다 — `also` · 골격 `ALIASES` · 정의문. 자기 좌표 규칙(B90)은 `also`와 `ALIASES`가 **둘 다** 있을 때만 돈다(접미를 떼는 코드는 없다 — 아래 접미 규칙은 이연). 꺼져 있어도 지금은 화면이 말하지 않는다 → B93.
  - **통용 규칙이 아니다** — 뼈대층(설비·공정층)을 **처음 세울 때**(config·골격 초안) **만** 주는 정보다. 자리는 가이드의 한정된 절 + 사내 LLM에 config·골격 초안을 맡길 때 주는 요청문 틀이다 — 런타임 `prompts/`가 아니다(거기 넣으면 모든 층 추출에 들어간다) → B93.
  - 기존 가이드와 부딪치는 곳: 골격작성 §3 「노칭 프레스·노칭 커터(스테이션 아래 구성 기계) — 골격에 두지 않는다 · 인입이 Unit으로」 · config작성 Process 정의문 예시 「스테이션 아래 구성 기계(프레스·커터·로봇)는 Unit」 → 하위 공정(unit)은 골격 · 그 아래 구성 기계·부품이 `Component` (B93).
  - 남는 것: 골격에 없는 unit 표기는 지금처럼 인입이 새 Unit으로 만든다 — 뼈대를 닫힌 목록으로 볼지(못 찾으면 큐)는 사내 실측 뒤.
- **층 사이 호환과 공통 config**(사용자 확정 2026-10-01 — B93 뒤 논의):
  - **골격은 사람이 만든다** — LLM 초안은 되지만 확정은 사람(`skeleton-confirm`). 골격은 층마다 독립된 섬이고(골격 안의 연결은 seed 중첩 — LLM 0), 다른 층과는 문서에서 뽑힌 엣지로만 이어진다.
  - **같은 이름이면 층이 달라도 노드 하나** — 골격이 아니어도 그렇다(예: 불량층과 이슈이력층이 함께 `Failure`). 조건은 같은 카테고리 이름을 쓰는 것 하나 · 같은 노드인지는 매칭이 판정 · 유형/사례는 관계로(`instance_of`). 공통 config에는 그 카테고리의 **집 한 줄**만 있으면 된다 — `also`는 이름이 다른데 같은 것(골격 특수 케이스)에만 쓴다.
  - **공통 config에 쓰는 층 목록**(`used_by`)을 둔다 — 공통 config 하나로 전체를 안다(누가 무엇을 쓰고 어디에 사는가). `bootstrap`이 층 config에서 자동으로 적는다(사람이 관리하지 않는다 — 새 층이 생겨도) → **B94로 닫힘**(개정대장 §CF — 결과 기록 · 판정은 읽지 않는다).
  - **새 층에 주는 것은 금지 목록이 아니라 재사용 목록**이다 — 「같은 뜻이면 기존 이름 · 새 이름은 뜻이 다를 때만」 + 공통 config 첨부. 같은 뜻을 다른 이름(`DefectHistory`)으로 만들면 호환이 끊기는데 B92 자동 추가 뒤로는 사람이 볼 자리가 화면 한 줄뿐이다 → 새 카테고리 경고 **B94로 닫힘**(가이드 config작성 §0-a 재사용 규칙 · 초안 첨부에 `common.json`).
  - **다른 층은 골격 카테고리(`Process`·`Unit`)를 선언하지 않는다** — 골격 이름은 선언 없이 붙는다(추출의 부착·부모 후보가 좌표 층 골격에서 온다 — 문서의 층과 무관 · mock 품질층이 `Process` 없이 `Failure occurs_in Process`로 돈다). 선언하면 산문에서 골격 밖 `Process` 노드가 생길 수 있다. 공정층 config는 `Property`(+ 부품을 말하면 `Component`)만. 골격에 없는 노드(Component·골격 밖 Unit)를 다른 층 문서에서 이름으로 뽑으려면 그 층이 카테고리를 선언한다(선언 = 뽑아도 된다는 허가 + 정의문 — 노드를 따로 만들지 않는다 · 해소는 집 그래프에서).
  - **골격 카테고리 개체는 조회 전용** — 산문에서 골격 카테고리로 뽑힌 이름이 골격에 없으면 노드를 만들지 않는다→ **B94로 닫힘**(문서 4 §4.3 예외 — 골격 밖 표기는 노드 0 · `orphan_anchor` · 재시도가 거두는 것은 큐 항목이고 언급은 재인입이 붙인다).
  - 열린 것: 다른 카테고리인데 **seed 때부터 공정에 매달려야 하는 나무**(예: 공정별 불량 유형 트리) — 지금 장치 없음(문서 엣지로만) · 불량층 설계 때 본다(P7 — 미리 짓지 않는다).
- **불량: 유형과 사례를 관계로 가른다** — 유형 → 공정 `occurs_in`(발생할 수 있다) · 사례 → 유형 `instance_of` · 사례 → 공정은 별개 관계(실제 발생) · 사례 속성에 공장·일정 · 답변 문장 틀도 관계마다. 사례는 문서에 서술된 것만 — 발생 건수·로트(T3)는 밖.
- **조립 끝 → 화성 시작은 `precedes`로 잇는다** — 지금 `precedes`는 같은 부모 아래 형제끼리만 파생된다(루트끼리 `조립 → 화성`은 생기고 `패키징 → 화성 첫 스테이션`은 안 생긴다 — `core/state/skeleton.py`). 방법은 화성 때: ㉠ 자동 경계 규칙(루트 A → B면 A의 마지막 흐름 스테이션 → B의 첫 흐름 스테이션) ㉡ seed에 명시(구문 마커 밖 — 명세 개정) ㉢ 질의 쪽에서만.
- **이름 겹침(화성의 커터 등)**: Unit·Component는 스테이션 접두 키라 충돌하지 않는다(`노칭::커터`). 화성 스테이션(2단) 이름은 조립과 달라야 한다(충돌 검사가 막는다) · ALIASES에 공정 붙인 표기 · 정의문에 구분 기준 — 화성 때.
- **PPT 투입 전 기본 확인**: `llm-check` ⑦(그림 입력) · `soffice`(쪽 렌더 · WMF 변환) · doc_type은 목적별(한 doc_type = 한 층 — §2-b 3에서 기본값으로 남는다) · 몇 부 먼저 실측(문서당 호출·큐·잡음 슬라이드 비율) 뒤 확대 · doc_type마다 골든 질문 몇 개. 슬라이드 관문은 잡음이 실측되면(P7).
